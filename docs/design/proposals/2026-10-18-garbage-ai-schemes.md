# 垃圾图像识别：AI 方案选型与可直接实施设计（供队长决策）

- 日期：2026-10-18；性质：技术方案（尚未改动任何工程代码）
- 对应赛题：紫光同创 FPGA 赛道**选题一**「基于紫光同创 RISC-V 指令集 CPU 设计」的**高阶任务 3：AI 加速**
- 应用方向：垃圾图像识别；**不做机械分拣**，以「语义识别」完成高阶任务原文的三种功能之一
- 依据：赛题 PDF 第 10–11 页（印刷页 8–9）；当前工程只读核查（2026-10-18）；模型资料来自公开仓库/模型卡（见 §9）

**结论先行（推荐顺序）：**

| 排序 | 方案 | 一句话 | 适用条件 |
|---|---|---|---|
| ★推荐 | **方案 B：轻量 YOLO 检测（YOLO-Fastest 1.1，160×128，全片上 BRAM）** | 能塞进 PG2L100H 片内、且真正叫“YOLO”的最大成熟模型；不依赖 DDR3 | 摄像头/引脚资料可拿到、有一次 GPU 微调条件、≥12 周 |

## 0. 先回答三个关键问题

**Q1：用现成训练好的 YOLO 是否合规？**
合规。赛题原文写“**移植** YOLO 或轻量版大模型”（PDF 第 10 页高阶任务 3），并未要求从零训练；原文也没有模型来源、精度阈值的硬性规定。但要注意：①这是高阶任务，不是基础任务必需；②必须是“基于设计的 RISC-V 处理器”的**板上**边缘 AI 加速单元——电脑跑模型、板子只显示结果不算；③模型/权重的来源与许可证必须记录，不能用“完全自研”表述（CPU 复用开源代码的参赛资格边界也仍待主办方书面答复）。

**Q2：只做整张图片分类够不够？**
官方要求“完成图形的加速或**语义识别**或机械控制等功能”（三选一），按字面整图分类可算“语义识别”，原文没有强制输出检测框/位置。但高阶任务原文点名“移植 YOLO 或轻量版大模型”，如果只做分类 CNN，①可能被评委认为未完成“YOLO 移植”；②本队计划书也写明“若最终只做 CNN 分类，需先向主办方确认”。因此：**分类只能作为保底/过渡，不能默认等于完成高阶任务**。既然方向是“垃圾图像识别”且原文点名 YOLO，建议以检测（类别+位置）为主，检测框也更便于演示与量化识别率。

**Q3：哪些必须在板上算？CPU 与加速器怎么分工？**
板上必须完成：图像采集 → 预处理 → 模型推理 → 结果输出全链路（至少推理必须在板上）。官方未规定 CPU/加速器切分，以下是团队设计：
- **CPU（自研 RISC-V 核）**：系统控制、摄像头配置（SCCB）、AI 加速器配置与启动、结果后处理（反量化/框解码/NMS/阈值）、串口与 LED 输出、计时与性能统计；
- **FPGA AI 加速器**：卷积/深度卷积/池化/上采样/残差/拼接等重计算的逐层执行与片上存储调度；
- **内存**：全部权重与特征图放 FPGA 片内 BRAM（本方案的关键决策，见 §1.2/§4.3），不使用、也不假设 DDR3 可用。

| 技术实现与文档 | 代码规范；性能分析文档；ILA 抓取的波形分析 | AI 部分要有逐层/端到端 ILA 波形与性能分析；不能只交跑分 |

### 1.3 现有工程接口（只读核查结论）

- **CPU/SoC**：RV32IM、三级 IF/ID/EX+解耦取指、两路组相联 I/D Cache、BTB 预测、原生 AXI4；程序 RAM 16 KiB@0x0、数据 RAM 16 KiB@0x1000_0000；UART/GPIO/Timer/SPI/IRQ；M 模式 CSR/异常/中断。交付源码三宏默认关闭、交付位流全开（重建需绑定宏配置）。
- **缺口**：**没有** DDR3 控制器/约束、摄像头 DVP、HDMI/显示、DMA、AI/NPU 任何 RTL 或软件；`firmware/code` 内无 OV5640/HDMI 例程与引脚。计划书引用的 `HDMI_DDR3_OV5640_100H` 采集例程**不在仓库内**。
- **可利用的已有机制**：
  - BRAM 权重初始化：工程已有 `$readmemh` + `INIT_FILE` 的 RAM 初始化机制（`rtl/perips/axi_ram.v:117-119`，`build.tcl:97-105` 已处理初始化文件路径），模型权重可用同法在综合时写进 BRAM，**无需运行时从外部加载权重**。
  - AXI 地址空间：0x0 程序、0x1000_0000 数据、0x2000_0000 timer、0x3000_0000 UART、0x4000_0000 GPIO、0x5000_0000 SPI、0x6000_2000 perf、0x6000_3000 irq；**0x7000_0000 起空闲**，可挂 AI 控制/缓冲窗口。
  - ILA 观测网已内建在板级顶层（`rtl/soc/pangoriscv_top.v:59-87`），可直接用厂商 ILA 采集 AI 波形。

### 1.4 必须先落实的前置条件（任一不满足都会改变方案选择）

1. **摄像头硬件**：是否有官方 OV5640 双目 DVP 模块 + 盘古 676 的 FMC/40pin 转接板？仓库无任何摄像头实物/引脚证据。若没有，需先采购并拿到板卡原理图/引脚表。
2. **厂商 DVP 例程**：计划书写的 `HDMI_DDR3_OV5640_100H` 采集例程（或等价 DVP 配置/引脚资料）是否可获取？拿不到就要自己从 OV5640 寄存器序列开始调，风险显著增加。
3. **训练条件**：是否有一块 CUDA GPU（或可用的云 GPU）做一次 YOLO 微调 + INT8 量化？方案 B 需要；方案 C 可零训练但需要 DDR3。
4. **时间/人力**：距离提交还有多少周、能投入几名 FPGA/软件同学？这直接决定 A/B/C 的选择（见 §7 决策树）。
5. **显示**：官方只要求“传感器**或**显示设备”，摄像头作为传感器即满足；HDMI 叠加显示属于加分演示项，不是必需（加 HDMI 约 +4–6 人周，且引脚/例程未知）。

## 2. 候选模型筛选

### 2.1 筛选标准（按优先级）

1. **能否全片上**：INT8 权重 + 特征图 + 输入帧 ≤ 约 679 KiB（151 块 DRM）；
2. **是否 YOLO 家族**（直接满足高阶任务原文）；
3. **公开预训练权重/垃圾数据可得性与许可证**；
4. **RTL 算子复杂度**：优先 1×1/3×3/5×5 卷积、深度卷积、maxpool、add、concat、nearest 上采样、LeakyReLU；避免 SiLU/Swish、Focus、复杂 SE、可变形卷积等；
5. **算力**：64 MAC@27 MHz（1.73 GMAC/s）下，单帧 MAC ≤ ~60 M 可做到实时级（≤50 ms）；
6. 数据集/精度可验证（有标注、有公开测试集）。

### 2.2 候选模型与筛选结果

| 模型 | 任务/输入 | 参数量 | 计算量 | INT8 权重 | 本方案特征图+输入后总占用 | 151 块内？ | 垃圾预训练权重 | RTL 复杂度 | 结论 |

### 2.3 筛选结论

- **片上 BRAM 的硬上限决定了模型规模**：能装进 679 KiB 的 YOLO 家族里，**YOLO-Fastest 1.1 是最大且成熟的候选**（0.319 M 参数、0.251 GFLOPs、320 输入 COCO mAP@0.5=24.4%）。
- 所有**带现成垃圾检测权重**的模型（YOLOv5n 起步）都 ≥1.87 M 参数，必须依赖 DDR3/外部存储；而本工程目前**没有**任何 DDR3 打通证据，因此不能作为第一阶段方案。
- 若坚持“完全不训练”，可选方案只有：①用 YOLOv5n-garbage + DDR3（方案 C）；②用 COCO 预训练的 YOLO-Fastest 直接推（只能识别 COCO 类别，对“垃圾”类别基本无效）——后者不可取。
- 因此**方案 B 需要一次面向垃圾数据的微调**（这是“移植 YOLO”的正常环节，不算从零训练），训练量很小（0.25 GFLOPs 模型、1 万张图，单卡数小时）。

## 3. 方案 A：整图分类（保底 / 第 0 里程碑）

**定位**：用最小风险先把“摄像头 → 预处理 → FPGA 加速推理 → CPU 输出”全链路跑通，同时作为方案 B 无法按期完成时的保底。它的加速器/视频前端与方案 B 共用大部分模块。

### 3.1 模型与数据
- 模型：**MobileNetV2（宽度系数 α=0.35，ImageNet 预训练）** 改 6 类输出；输入 160×160 RGB（由摄像头 4:3 画面 letterbox 得到）。
- 数据：**TrashNet**（6 类：glass/paper/cardboard/plastic/metal/trash，2,527 张，分类标签；原论文测试精度约 75%，后续迁移学习工作普遍 90%+）。仅用分类标签，不需要目标框。
- 训练/量化：ImageNet 权重上微调（CPU 也可在数小时内完成小模型）；INT8 PTQ（校准 500 张）；导出每层 golden。
- 目标精度（自定验收线）：测试集 top-1 ≥ 85%（TrashNet 同分布）；现场受控场景 ≥ 80%。

### 3.2 加速器与资源
- 复用方案 B 的 64-MAC 引擎，只需子集算子：conv 1×1/3×3、depthwise 3×3、add（残差）、全局平均池化（CPU 或 RTL 小模块）、FC（CPU 也可）；无 NMS。
- 权重 ~420 KiB + 激活 ~50 KiB + 输入 75 KiB + 摄像头帧 38 KiB ≈ **约 129 块 DRM（83%）**，APM 64（27%），LUT 约 +8k。
- 算力：约 19 MMAC@160 → 11 ms 理想 @64 MAC/27 MHz，端到端预计 25–40 ms → 25–35 fps 上限，实际演示 ≥10 fps。

### 3.3 软件与输出
- CPU：SCCB 配置摄像头 → 抓帧 → 预处理 → 启动分类 → 读 6 类分数 → argmax → UART 输出“类别 + 置信度 + 帧号 + 延迟”；LED 指示类别。
- 无 NMS/框解码，CPU 负担极低。

### 3.4 官方匹配与风险
- 官方“语义识别”字面可覆盖；但原文高阶任务点名 YOLO/LLM，**只做分类是否被认可需主办方确认**（团队判断，非官方明文）。因此方案 A 仅作为里程碑/保底，对外表述不得写成“已完成 YOLO 移植”。
- 风险低：无目标框标注、训练快、资源宽裕；但演示效果（只有类别、没有位置）弱于检测。

### 3.5 工作量
约 **8–10 人周**（视频前端 3 + 加速器 4 + 集成/验证 2），其中视频前端与 B 共用。

## 4. 方案 B：轻量 YOLO 检测（推荐）

### 4.1 模型冻结

**YOLO-Fastest 1.1**（Darknet 模型；公开仓库 `dog-qiuqiu/Yolo-Fastest` / 镜像 `tianzhen97/Yolo-Fastest`），改造为垃圾 6 类：

| 项目 | 冻结值 |
|---|---|
| 网络 | YOLO-Fastest 1.1（ShuffleNetV2 风格 backbone + SPP + 2 个检测头，stride 32/16） |
| 输入 | **160×128 RGB**（宽×高，均为 32 的倍数；训练与硬件一致）；相机 320×240 → 2:1 抽取到 160×120 → letterbox 上下各补 4 行到 160×128 |
| 类别 | 6 类：可降解垃圾/纸板/玻璃/金属/纸张/塑料（与公开垃圾检测数据集一致） |
| 参数/权重 | 0.319 M 参数；INT8 权重 **311.5 KiB**（BN 已折叠；`$readmemh` 初始化进 BRAM） |
| 计算量 | 25.1 MMAC/帧；@64 MAC×27 MHz 理想 14.5 ms |
| 检测头 | 2 个：5×4 与 10×8 网格 × 3 anchors ×（4 框 + 1 目标 + 6 类）= 33 通道 |
| 量化 | W8A8：权重 per-channel 对称 INT8；激活 per-tensor 非对称 INT8；bias INT32；LeakyReLU(0.1)、maxpool、add、concat、nearest 上采样均 INT8 定点 |
| 后处理 | CPU 做 sigmoid/框解码/NMS；RTL 可选做 objectness 预筛（把候选 anchor 数从 300 降到 ≤32） |

**为什么不是 320 或 256 输入**：按 §2.2 实测预算，320 需要约 1.36 MiB、256×192 需要约 815 KiB，均超过 679 KiB；160×128（521.5 KiB 核心 + 视频前端后约 129 块）可留出余量。若后期实现层融合把激活峰值再降 30–40%，可升级到 160×160 或 192×160（精度提升，但 DRM 逼近 100%，属二阶段优化）。

### 4.2 数据与训练/量化

- 数据（公开、带框、6 类）：HuggingFace `keremberke/garbage-object-detection`（Roboflow GARBAGE CLASSIFICATION 3 导出，**10,464 张**，COCO 框标注，6 类，CC BY 4.0）。可叠加 TACO（约 1,500 张、60 类，COCO 格式，用于困难场景补充）与自采受控场景照片。
- 划分：使用数据集自带 train/valid/test（或按源图 80/10/10 重划）；注意 Roboflow 曾做翻转/旋转增强，必须去重防跨集泄漏。
- 训练：以 YOLO-Fastest 1.1 的 COCO 权重初始化，替换检测头为 33 通道，输入 160×128，batch 32–64，约 100–200 epoch（0.25 GFLOPs 模型 + 1 万图，单卡 RTX 3060 级约数小时）；锁定随机种子与权重 SHA。
- 量化：先 PTQ（校准 500–1,000 张），mAP 掉点 ≤2 个点则接受，否则做 QAT；导出：
  1. 每层 INT8 权重 + per-channel scale（打包成 `.hex`，按 BRAM 位宽分 bank）；
  2. 每层输入/输出 golden（测试图片），用于 RTL 逐层比对；
  3. 锚点、步长、激活量化参数表（C 头文件 + RTL 参数文件，由同一脚本生成，禁止手抄）。
- 验收线（自定）：测试集 mAP@0.5 ≥ 0.50、6 类每类 AP ≥ 0.35；板端与 PC INT8 结果的类别一致率 ≥95%，框 IoU ≥0.9（同图对比）。

### 4.3 硬件架构（AI 子系统，新增文件，不改 CPU 核）

```
OV5640(DVP) ──> dvp_capture (pclk域) ──> async_fifo ──> frame_decimate(2:1) ──> 160x120 RGB565 frame BRAM
                                                                  │
                                                    preprocess(RGB565→INT8, 归一化+letterbox)
                                                                  ▼
CPU ──AXI slave(0x7000_xxxx)──> ai_ctrl(寄存器/状态/中断) 
                                      │
                                      ▼
                               layer_fsm(逐层描述符) ──> conv_engine(64 INT8 MAC) ──> activation/quant
                                      │                        ▲
                                      │                  weight BRAM (311.5 KiB, $readmemh 初始化)
                                      ▼
                          input/activation BRAM (ping-pong) ──> 检测头输出 buffer
                                                                  │
CPU <──AXI 读结果───────────────────────────────────────────────────┘
```

**模块清单（新增，建议放 `rtl/ai/`、`rtl/video/`）**

| 模块 | 作用 | 关键参数 |
|---|---|---|
| `rtl/video/ov5640_sccb.v` | SCCB(I2C) 主机，配置 OV5640 | 100–400 kHz，寄存器序列 ROM 由 CPU 写入或固化 |
| `rtl/video/dvp_capture.v` | DVP 8-bit 采集，RGB565 组装、VSYNC/HSYNC 状态机、帧完整性校验 | pclk 域；错误帧丢弃计数 |
| `rtl/video/frame_decimate.v` | 2:1 行列抽取（2×2 平均或取一），320×240→160×120 | 2 行 line buffer，1.3 KiB |
| `rtl/video/preprocess.v` | RGB565→RGB888→INT8（每通道 scale/zero-point）、letterbox 边界填充 | 3 个 8×8 乘法或 LUT；参数寄存器可配 |
| `rtl/ai/ai_top.v` | AI 子系统顶层：BRAM 阵列 + 引擎 + 控制 | — |
| `rtl/ai/ai_ctrl.v` | AXI4-Lite 从机：控制/状态/描述符地址/结果窗口 | 见 §4.6 寄存器表 |
| `rtl/ai/layer_fsm.v` | 读取层描述符，按序调度各算子；完成中断/错误码 | 描述符表 ≤256 项 |
| `rtl/ai/conv_engine.v` | 1×1/3×3/5×5 卷积、depthwise、maxpool、add、concat、nearest×2 | 64 MAC/cycle，3 行 line buffer |
| `rtl/ai/mac_array.v` | 8×8 INT8 乘加阵列 + INT32 累加 + 饱和 | 64 APM（18×18） |
| `rtl/ai/quant.v` / `requant.v` | 激活量化/反量化、LeakyReLU、per-channel 权重缩放 | 定点乘+移位，DSP/APM 复用 |
| `rtl/ai/weight_bank.v` | 权重 BRAM 初始化与分 bank 读取 | `.hex` 由模型脚本生成；`$readmemh` |
| `rtl/ai/result_buf.v` | 检测头输出缓存，可选 objectness 预筛 | 33×(5×4+10×8) B ≈ 3.3 KiB |
| `rtl/soc/ai_axi_slave.v` | AI 窗口的 AXI 从机（CPU 访问 AI BRAM/寄存器） | 单拍/≤8 拍 INCR，4 KiB 边界 |

**MAC 阵列工作方式**：8 输出通道 × 8 像素/周期；3×3 卷积每 kernel tap 循环，9 拍累加；depthwise 重配置为 8 通道 × 8 像素 × 1 tap；1×1 卷积 1 拍。输入按通道流式读 line buffer（3 行×160 B/通道），输出片内 int32 累加 → requant → 8 位写回。这样 25.1 MMAC @64 MAC ≈ 39.2 万拍（14.5 ms @27 MHz）为理想值，按 60–75% 效率预计 20–25 ms 纯计算。

**内存预算（160×128，单位 KiB）**

| 用途 | 容量 | DRM 块数（4.5 KiB/块） |
|---|---|---|
| 权重（INT8，含 per-channel scale） | 311.5 | 约 70 |
| 激活 ping-pong（峰值，120→含早期大张量） | 150.0 | 约 34 |
| 输入张量 160×128×3 | 60.0 | 约 14 |
| 摄像头 160×120 RGB565 帧 | 38.4 | 约 9 |
| line buffer/描述符/头输出/结果 | 约 25 | 约 6 |
| **合计** | **约 585 KiB** | **约 133 块（余 18 块）** |

（若升级 160×160：激活 187.5、输入 75 → 合计约 649 KiB / 约 145 块，余量 6 块，需先做层融合优化。）

**时钟/复位**：AI 子系统全部 27 MHz（与 CPU/AXI 同域，避免 PLL 与额外 CDC）；仅 DVP 采集用摄像头 pclk（异步 FIFO 跨域，FIFO 满丢整帧并计数）。若后续算力不够，再加 PDS PLL 生成 54/81 MHz 给引擎（需重新时序收敛与 CDC，不作为首版）。

### 4.4 视频前端（摄像头）

- **配置**：CPU 通过 SCCB 写 OV5640 寄存器：输出 **320×240 RGB565、30 fps**；DVP 8-bit；XCLK 由 FPGA 输出 27 MHz（OV5640 允许 6–27 MHz，需实测；若不稳再由 PDS PLL 分频出 24 MHz）。
- **采集**：`dvp_capture` 按 VSYNC/HSYNC/PCLK 组装 16-bit RGB565，写入 320×240 帧缓冲（可先全帧缓存 150 KiB 做调试，量产后改为 2:1 抽取直写 160×120 的 38.4 KiB 缓冲）。
- **2:1 抽取**：2 行 line buffer（约 1.3 KiB），2×2 平均或抽点，输出 160×120；抽点/平均方式必须与训练时 resize 规则一致。
- **预处理**：RGB565→RGB888→INT8（`y = clamp((x - zero_point) × scale)` 每通道可配），写入 160×128 输入张量；上下各补 4 行 letterbox 填充（填充值 = 训练时 letterbox 值，通常为 0 或灰度）。
- **无摄像头时的开发路径**：先做内部彩条/棋盘测试图发生器替代 DVP 输入，可把采集/预处理/加速器/软件全部调通，最后只替换输入源——这是降低“摄像头卡壳”风险的关键安排。

### 4.5 CPU 软件与后处理（裸机）

新增应用（建议 `tests/example/ai_trash/`），不改动 CoreMark/现有测试：
1. 初始化 UART、GPIO、AI 窗口（uncached）；SCCB 配置摄像头；
2. 循环：等帧就绪（或软件轮询）→ 写 AI 控制寄存器（输入/权重/描述符地址）→ 启动 → 等 done/中断；
3. 读检测头输出（INT8 + scale），CPU 做：
   - 反量化 → 目标置信度 sigmoid → 类别分数；
   - 按 anchors/stride 解码框（cx,cy,w,h → x1,y1,x2,y2，限制在图像内）；
   - 置信度阈值（如 0.3）+ NMS（IoU 0.45，最多 20 个框）；
   - UART 输出：`frame, latency_ms, class, score, x1,y1,x2,y2`（没有检测则输出 `none`）；
4. 计时：`mcycle` 记录采集→结果总周期，串口打印，作为“端到端延迟”证据。

CPU 负载估算：300 个 anchor × 33 通道 ≈ 1 万次 INT8 读取 + 300 次解码 + 少量 NMS，27 MHz 下约 5–15 ms；若 RTL 做 objectness 预筛（阈值以下 anchor 直接丢），CPU 只处理 ≤32 个候选，可降到 2–4 ms。

### 4.6 与现有 SoC 的集成（地址/寄存器/接口）

**地址窗口（建议）**

| 地址 | 内容 | 大小 | 访问 |
|---|---|---|---|
| 0x7000_0000 | AI 控制/状态寄存器（AXI4-Lite 风格从机） | 4 KiB | CPU 读写 |
| 0x7001_0000 | AI 输入张量（160×128×3 INT8） | 60 KiB | CPU 写（测试注入）/加速器读 |
| 0x7002_0000 | 摄像头帧缓冲（160×120 RGB565） | 38.4 KiB | 视频前端写/预处理读 |
| 0x7003_0000 | 检测头输出 + 结果表 | 16 KiB | 加速器写/CPU 读 |
| 0x7004_0000 | 权重/层描述符只读窗口（调试用） | 4 KiB | CPU 读 |

**寄存器表（`ai_ctrl`，沿用计划书 T12 语义）**

| 偏移 | 名称 | 说明 |
|---|---|---|
| 0x00 | CTRL | bit0 START；bit1 软复位；BUSY 时重复启动置错误 |
| 0x04 | STATUS | bit0 BUSY，bit1 DONE，bit2 ERROR；DONE/ERROR 写 1 清 |
| 0x08 | DESC_ADDR | 层描述符表首地址（启动时锁存） |
| 0x0C | INPUT_ADDR | 输入张量地址 |
| 0x10 | OUTPUT_ADDR | 检测头输出地址 |
| 0x14 | FRAME_CNT | 已完成帧计数 |
| 0x18 | CYCLE_CNT | 本次推理周期数（27 MHz 计时） |
| 0x1C | ERROR_CODE | 总线/描述符/尺寸错误码 |
| 0x20 | IRQ_EN | 完成中断使能（可选接 irq_ctrl） |
| 0x24 | VERSION | RTL/模型版本号（权重 SHA 前 32 位） |

**总线**：AI 只作为 **AXI4 从机**接入互连（新增一个从端口），**不新增 AI 主设备/DMA**：摄像头直接写 AI 私有 BRAM，CPU 通过从机窗口读写；这样避免改主设备仲裁、Cache 一致性和 DMA 描述符的复杂度。代价是 CPU 搬图较慢（仅测试注入路径需要），量产路径不经过 CPU 搬图。此决策与计划书 T12 的“AI 数据主接口”不同，需在实施记录中说明原因（降低首版风险）。

**Cache/一致性**：AI 窗口地址不进入 D-Cache 可缓存范围（现有 D-Cache 已对 MMIO 旁路，需在地址译码中显式排除 0x7000_0000 段）；CPU 启动前执行 `fence iorw,iorw`，完成后再执行内存屏障。

### 4.7 验证方案（交付证据链）

1. **模型侧**：PyTorch FP32 → INT8 模拟器；在测试集上给出 mAP@0.5、每类 AP；导出每层 golden（输入/输出 INT8 + scale/zero-point）。
2. **RTL 逐层**：`tb/ai/tb_ai_layer.sv` 用 `$readmemh` 载入 golden，逐层比对（目标：逐元素完全一致；若因舍入差，允许 ≤1 LSB 且需记录）。
3. **整模型**：10–20 张测试图（经 AXI 注入）跑完整模型，与 Python INT8 结果比对：类别一致、框 IoU ≥0.9、分数差 ≤1 LSB，通过率 ≥95%。
4. **视频链路**：彩条测试图 → 采集/抽取/预处理校验和；再接真摄像头，串口输出抽样像素/校验和，确认无错行/错帧。
5. **板端整机**：受控场景 20–30 组（每类垃圾、不同距离/光照/背景），记录识别结果、误检/漏检；统计端到端延迟（mcycle）与帧率。
6. **ILA**：抓 CoreMark 关键算法区间（官方要求，属基础任务交付）与 AI 加速器关键区间（层启动/完成、MAC 阵列占用、AXI 握手、帧起止），分析流水线效率。
7. **回归**：现有 13 套仿真、PDS 时序、CoreMark 板测不得退化（AI 未使能时资源/时序应与交付版一致；AI 使能后单独报告资源）。

**验收线（自定）**：逐层比对 100% 通过；整模型 ≥95% 图一致；测试集 mAP@0.5 ≥0.50；板端端到端 ≥5 fps、单帧延迟 ≤200 ms；连续运行 30 分钟无死锁/丢帧错误。

## 5. 方案 C：现成预训练 YOLOv5n-garbage + 外部存储（高配/高风险，暂缓）

**模型（零训练路径）**：HuggingFace `keremberke/yolov5n-garbage`——YOLOv5n（1.87 M 参数）在该 6 类垃圾检测数据集上的公开权重，模型卡标 mAP@0.5 ≈ 0.3199（config input 640）。另有 `turhancan97/yolov5-detect-trash-classification`（YOLOv5s，7.2 M，MIT，TrashNet+TACO+COCO 训练），规模更大。

**为什么暂缓**：
- INT8 权重约 1.87 MiB + 特征图（320 输入时 >1 MiB），**远超 679 KiB 片内 BRAM**；必须依赖 DDR3（板载 2×DDR3 32bit@533MHz，但工程无控制器/IP/引脚约束）或外部 Flash 流式加载。
- 本工程无 DDR3 任何打通证据；计划书把 DDR 列为 T11 硬关卡（未完成）。做 DDR3 控制器 + AXI 前端 + 新主设备仲裁，预计 **+8–12 人周**，且需厂商 IP/例程/板级资料，风险高。
- YOLOv5 算子（Focus、SiLU、CSP、Concat）比 YOLO-Fastest 复杂，引擎更大（建议 ≥128 MAC），调试周期长。
- 许可证：Ultralytics YOLOv5 为 AGPL-3.0，若直接复用其代码/权重需评估参赛与再分发合规（本项目 RTL 自研，但仍需记录）。

**何时考虑**：DDR3 已由本队打通并有板测证据、且时间 ≥24 周、目标是更高精度演示时；否则不作第一阶段。

## 6. 方案 D：轻量版大模型（LLM）——不推荐

- 官方允许“轻量版大模型”，但本板可用存储 679 KiB、无 DDR3 路径；即使 0.5B 参数 INT4 量化也需约 250 MB 权重，差 300 倍以上。
- 27 MHz + 240 APM 的算力与 LLM 自回归解码需求差数个数量级；无实用路径。
- 结论：**直接排除**，用 YOLO 满足“移植 YOLO 或轻量版大模型”的“或”。

## 7. 对比与推荐

| 维度 | 方案 A 分类 | 方案 B 轻量 YOLO | 方案 C YOLOv5n+外存 |
|---|---|---|---|
| 官方高阶任务匹配 | 弱（非 YOLO/LLM，需主办方确认） | **强**（YOLO + 传感器 + 语义识别） | 强（现成垃圾权重，零训练） |
| 片上资源 | 宽裕（~129 块） | 紧但可行（~133 块/155） | 不可行（需 DDR3/外存） |
| 精度 | TrashNet 高（受控场景），无位置 | 6 类检测，mAP 取决于微调（目标 ≥0.50@0.5） | 现成 mAP@0.5≈0.32（640 输入，降到 320 会再降） |
| 训练需求 | TrashNet 微调（短） | 垃圾检测数据微调（数小时 GPU） | 零训练 |
| RTL 工作量 | 8–10 人周 | 15–20 人周 | 28–36 人周（含 DDR3） |
| 风险 | 官方认可风险 | 摄像头/内存/训练风险，整体可控 | 最高（DDR3 从零） |
| 演示效果 | 只有类别 | 类别+框，贴合“垃圾识别” | 类别+框，精度上限更高 |
| 建议 | 作为 B 的 M0/保底 | **推荐第一阶段目标** | 二阶段（DDR3 打通后） |

**决策树（按团队实际条件）**
- 摄像头/引脚资料、GPU、≥12 周 → **选方案 B**（先做 160×128 首版）；
- 摄像头未到位但可先用测试图 → 先并行做方案 A 的加速器/视频链路，同时催硬件；
- 时间 <8 周 或 无人做加速器 → 只做方案 A 并准备向主办方确认“分类是否满足高阶任务”；
- 已有 DDR3 打通 + ≥24 周 → 可评估方案 C；
- LLM 任何情况都不选。

**与现有收口工作的关系**：方案 B 全部为新增文件/新分支，不修改 `firmware/code/rtl/core` 现有 CPU 代码；在另一 AI 完成基础收口（候选合并、ILA、600 迭代正式成绩）前不合并 AI 改动。AI 应用可以并行设计与小原型验证（M0/M2 的测试图链路不需要摄像头），但正式集成放在基础收口之后。

### 9.2 计算口径
- 算力：本表用 **MAC 数**（乘加一次算 1 MAC）；GFLOPs 为 2×MAC 的近似，仅用于与公开资料对齐。
- 权重：INT8 下 1 参数 = 1 字节；表中为 BN 折叠后实际卷积权重（不含读入时临时 scale 表，约 <1%）。
- 片内 BRAM：155 块 DRM36K ≈ 155×36 Kb = 5,580 Kb = 697.5 KiB；扣除 CPU 程序 RAM 4 块，AI 可用约 151 块（679 KiB）。表内“块数”按 4.5 KiB/块向上取整。
- 激活峰值：用“每层输出张量 + 生命周期（liveness）”估算（全张量存储，较保守；实际可用 line buffer/层融合再降）。
- 延迟：理想值 = MAC 数 ÷（64 MAC × 27 MHz）；实际按 60–75% 效率估；最终以板端 mcycle 实测为准。
