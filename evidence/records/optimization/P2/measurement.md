# P2 · D-Cache 扩容实验结果（2026-10-17）

> 结论：**D-Cache 容量不是瓶颈。** 容量 ×4（2 KB → 8 KB）只换来 **0.53%** 的周期下降，
> 缺失次数只降 2.2%，而面积代价是 LUTRAM 线性增长。→ 放弃扩容方向，转向 store 路径。
> 证据等级：仿真实测（20 迭代，同一镜像，只改 RTL 参数）。

---

## 1. 为什么要先做一步"参数化"

`dcache_axi.v` 的 `SETS` 虽然是 parameter，但地址切分是**硬编码**的：

```verilog
wire [21:0] req_tag  = req_addr[31:10];   // 22 位，对应 32 组
wire [4:0]  req_set  = req_addr[9:5];     // 5 位
```

直接改 `SETS` 只会让 tag 宽度和实际索引对不上。所以先把切分改成从 `SETS` 推导：

```verilog
localparam integer IDXW = $clog2(SETS);        // 32 组 -> 5
localparam integer TAGW = 32 - 5 - IDXW;       // 32 组 -> 22
wire [TAGW-1:0] req_tag  = req_addr[31:5+IDXW];
wire [IDXW-1:0] req_set  = req_addr[5+IDXW-1:5];
```

同时把 `tag_q`、`tag_mem`、`set_q`、`set_wr_q` 的位宽改成 `TAGW` / `IDXW`。

**验收标准与结果**：`SETS=32` 时行为必须逐位不变。

| 指标 | 基线 | 参数化后 SETS=32 |
|---|---|---|
| Total ticks | 15,316,450 | **15,316,450**（完全一致） |
| cycles | 17,256,182 | 17,256,182 |
| retires | 6,418,312 | 6,418,312 |
| axi_d_ar | 194,298 | 194,298 |
| axi_d_aw | 287,914 | 287,914 |

→ **参数化本身零行为改变，可以保留。**

## 2. 容量扫描结果

| SETS | 容量 | cycles | axi_d_ar（load 缺失） | 相对基线 |
|---|---|---|---|---|
| **32（基线）** | 2 KB | 17,256,182 | 194,298 | — |
| 64 | 4 KB | 17,188,970 | 191,547 | cycles **−0.39%**，缺失 **−1.4%** |
| 128 | 8 KB | 17,163,895 | 190,070 | cycles **−0.53%**，缺失 **−2.2%** |

load 总数 1,288,696（20 迭代），缺失率始终在 **14.8%~15.1%** 之间，几乎不随容量变化。

**判读**：缺失不是容量冲突缺失，而是**强制性/流式缺失**——CoreMark 的链表遍历和矩阵访问
在一个迭代内对同一数据行的复用很低，缓存再大也接不住。所以"扩 Cache"这条路被实测否掉。

### 代价（为什么连试都不值得）

`data_mem` 是**分布式 LUTRAM**（组合读命中路径，见 P1 记录 §4.1）：

| SETS | data_mem 容量 | 预计 LUTRAM 占用 |
|---|---|---|
| 32 | 2 KB | 2,685 LUT |
| 64 | 4 KB | ~5,370 LUT |
| 128 | 8 KB | ~10,740 LUT |

即：**用 +2,685 LUT（总 LUT 从 12,572 涨到约 15,257，+21%）换 0.39% 的周期**。
按三项评分口径这是明显亏本的交易。

## 3. 过程中踩的两个坑（都写进排错手册）

### 坑 1：`set_q` / `set_wr_q` 还是 `[4:0]`

第一次跑 `SETS=64` 结果**变差**：缺失率从 15% 涨到 47%，25 M 周期还没跑完。

原因：`set_q`、`set_wr_q` 声明是 `reg [4:0]`，64 组需要 6 位，set 索引被截断，
访问全部挤到 32 个索引上，冲突暴增。

**教训**：改 `SETS` 时必须把所有"与组数相关"的位宽一起扫一遍：
`tag_mem`/`tag_q`（TAGW）、`set_q`/`set_wr_q`（IDXW）、`req_tag`/`req_set`、以及它们的复位常量
（`22'd0` → `{TAGW{1'b0}}`，`5'd0` → `{IDXW{1'b0}}`）。

### 坑 2：用脚本做源码替换把文件写空了

用 `-replace` + `[IO.File]::WriteAllText` 批量改源码时，PowerShell 把替换串里的逗号
当成参数分隔符，`-replace` 抛异常，后续写入变成空内容，`dcache_axi.v` 被清成 0 字节。

**教训**：源码修改一律走 edit 工具（精确字面匹配），不用脚本正则；
每次写完必须核对文件大小/行数。本次靠 `git checkout` 恢复，未造成损失。

### 坑 3（第三次复现）：编译时忘记打开开关

`soc_config.vh` 的三个开关仓库默认是**关**的。编译前忘记打开，就会得到一个
**无 Cache、无预测器**的设计：它能跑，但 IPC 从 0.372 掉到 0.10，所有访存直连 AXI
（`axi_d_ar = ld 条数`）。这一个坑浪费了两轮排查。

**对策**：编译必须走固定流程——打开 → 验证"3 个开关" → vlog → **无条件还原**。

## 4. 结论与下一步

| 项 | 决定 |
|---|---|
| D-Cache 扩容 | **否决**（4× 面积换 0.53%） |
| 地址切分参数化 | **保留**（零行为改变，为将来任何容量实验铺路） |
| SETS | 保持 32 |

**下一个目标是 store 路径**，理由是它占的份额最大：

- 287,914 次 store，`axi_d_aw = 287,914` → **每一次 store 都走完整 AXI 写（AW→W→B）才退休**
- 即使写命中也要等 B（`dcache_axi.v` 注释：write-through: applies after a good B）
- 粗算 store 侧占用 2.3~2.9 M 拍，占 20 迭代总周期的 13~17%

具体改法见路线图 P2'，需要先解决"store fault 精确性"这个正确性边界。
