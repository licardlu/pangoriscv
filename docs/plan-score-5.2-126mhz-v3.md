# 5.2 CoreMark/MHz + 126 MHz 计划（v3：先把基线定准，再谈优化）

日期：2026-10-22　前置：`docs/plan-score-5.2-120mhz-v2.md`（其 §19 的分数结论建立在错误的基线上，见 §1）

所以这一版不先谈优化，先把"我在优化谁""分数怎么算""路径长什么样"三件事钉死。

## 1. 基线复核：交付成绩属于另一个核

| 事实 | 证据 |
|---|---|
| 板测 **3.8557**（1152 迭代 / 298,780,717 ticks / 11.066 s / 27 MHz）来自 **旧核 `pangoriscv`** | `build/perf_p37b/compile/*.log` 里 **`rv32_top` 出现 0 次**，层次名是 `cpu/u_if_id`、`cpu/u_id_ex`、`cpu/u_ex`（`pangoriscv.v` 的子模块） |
| 当前工作树编译的是 **新核 `rv32_top`** | `build/p5_126` 之后每个构建的 compile 日志里 `rv32_top` 出现 14 次；`pangoriscv_axi_top.v` 在 `CORE_RV32` 下实例化 `rv32_top cpu(...)`，而 `soc_config.vh` 默认定义 `CORE_RV32` |

⇒ **"相对交付基线 3.8557"的每一次比较都不成立**。v2 的 §19.4（IPC 1.79 不可达）、
§19.5（只需砍 48%）都是把新核的仿真周期除以旧核的板上周期得来的。

新核从未上板。本轮所有数字一律重新定标，标注是"板测"还是"仿真边际"。

## 2. 分数怎么算（三个口径错误，每个都能让结论偏 20% 以上）

### 2.1 20 迭代仿真的绝对周期里有 ~1.89 M 的固定启动开销

两点定标（同镜像 `sim20_o2`、同 TB）：20 迭代 **7,168,871**、40 迭代 **12,451,519**
⇒ 边际 **264,132 周期/迭代**、**288,292 指令/迭代**、边际 IPC **1.09**。

板测是 1152 迭代，启动开销摊销到 1,901 周期/迭代，可忽略；20 迭代仿真里它占 **26%**。
所以：**A/B 看总周期可以做，反推分数/ IPC 必须用边际**。

### 2.2 板测镜像是 `-O2`，不是 `-O3`

`score1152` / `board126` 的 `manifest.json` 里 `flags` 是 `-O2`。
拿 `sim20_o3` 做 A/B 会改掉指令构成（20 迭代 6,791,889 vs O2 的 6,960,622，−2.4%）。
⇒ **A/B 一律用 `sim20_o2`**；O3 只能用来验证"换编译选项能白拿 2.4%"，不能混进 RTL 对比。

### 2.3 `Iterations/Sec` 不能用（会虚高 6.4%）

分数只能由 `Total ticks` 算，这条 v2 已写进 mistakes-log，此处只做提醒。

**当前真实位置**（新核 `rv32_top`、`sim20_o2`、20 迭代、含 P6 的预测目标配对）：

| 口径 | 值 | 折算 |
|---|---:|---:|
| 仿真总周期（含启动） | 6,960,622 | —— |
| **CoreMark `Total ticks`（计分窗口）** | **5,073,274** | 253,664 周期/迭代 ⇒ **3.942 CM/MHz** |
| 两点定标边际 | (6,960,622−1,886,231)/20 = 253,719 | 与窗口值差 **0.02%** |
| 板测（旧核，1152 迭代，O2） | 298,780,717 ticks | 259,358 ⇒ 3.8557 |

两个独立口径（窗口 / 边际斜率）对到 0.02%，说明**20 迭代的计分窗口可以直接当分数用**，
前提是只取 `Total ticks`、不取总周期。

```
5.2 需要 192,307 周期/迭代 ⇒ 从 253,664 还要 −24.2%
边际 IPC 1.09 → 需要 1.50（+37% 吞吐）；2 发射的结构上限是 2.00
```

**顺带一个白拿的 3.2%**：板测镜像一直是 `-O2`，而 `-O3` 镜像的五项 CRC 与它完全相同
（`0xe9f5 / 0xe714 / 0x1fd7 / 0x8e3a / 0x4983`），计分窗口 5,073,274 → **4,915,158**
⇒ **4.069 CM/MHz**。这是编译器选项，不是改 CoreMark，面积与 RTL 都不动；
采纳它只需要重出一次位流（未做：需要烧板复测）。

## 3. 关键路径长什么样（本轮唯一的实证来源）

`build/perf_p37b/report_timing/pangoriscv_top.rtr`：38 级、35.86 ns、0 失败端点（27 MHz 约束）。

```
ID/EX 控制位 →（CSR 读 mux）→ 乘法 4 级 DSP 级联 [13.7 ns 含布线]
  → ALU 结果 mux → lane1 比较 / jump_flag
  → BTB 目标查表 → pred_miss 32 位比较 → redirect_valid（fanout 159）
  → ID/EX 有效位 → IF/ID take2（fanout 57）→ IF/ID **时钟使能**
```

三件事挤在同一拍：**乘法（13.7 ns）、分支结清（含预测校验）、前端 CE 与冲刷**。
这把 v2 §19.5 的"寄存器读 → 双 ALU → 比较"结论否掉了——那条链在这一版里只占 ~5 ns。

新核的对应数字（126 MHz，`device_map`）：综合 Setup WNS **−13.490 ns**（路径 21.4 ns）；
同流程整实现（`p7_impl126`）给出布线后的真实值，见 §5。

## 4. 执行顺序（一次只改一个模块，每步都有验收）

排序依据：**每周期能省多少 > 每 ns 能省多少**。因为分数是第一指标，而当前 24% 的差距
全在周期上；频率那 2.6× 的差距不是靠"再调一拍"能到的。

| 步 | 模块 | 改动 | 预期 | 代价 | 验收 |
|---|---|---|---|---|---|
| **S1** | `rv32_top` | load-use 互锁只在 **miss** 时阻塞（命中当拍已回数据） | **−15~22% 周期**（`load_use` 占 22.7%） | 控制路径变长（`done_valid`→stall） | ISA 21 例 + 五项 CRC |
| S2 | `rv32_top` | 乘法移出 EX 拍（RR/M1 边界寄存操作数） | −3.3 ns | −4.6% 周期（`pkt_lduse`/`load_use` 各 +19 万） | 仅在 S1 收益兑现后才考虑 |
| S3 | `rv32_top` | 分支结清寄存一拍（`br_go_q`） | −1.75 ns | +0.76% 周期（53,270 次误预测） | 同上 |
| F1 | `ifu_axi` | 前端 CE/配对判定从 EX 状态解耦 | 未知，需先有真实路径 | — | 综合 WNS |
| F2 | `rv32_top` | 7 级（EX 拆 ALU / 结清两拍） | 需 −62% 才能到 8.33 ns | 大改 | — |

**S1 优先的理由**：它是唯一一条"收益量级 ≈ 目标差距"的改动。`STALLDBG` 的桶是互斥的，
`load_use=1,630,819`（22.7%）里绝大部分属于"命中却仍停一拍"；
`DC_DBG hit=982,886 / miss=110,382` 说明命中占 90%。
把命中那部分放行，理论上限就是 −20%，正好把 253,719 打到 200,000 以下。

**S2/S3 的顺序被 S1 的结果决定**：如果 S1 兑现，分数靠近 5.0，那么频率的 2.6× 差距就
变成"另一个课题"，不该再用分数去换 ns（v2 已经证明过一次这笔交易是亏的）。

## 5. 频率：新核布线后 26.65 ns（37.5 MHz），路径已经拆开来看

### 5.1 怎么测的（126 MHz 约束根本跑不完）

126 MHz 约束（7.937 ns）对一条 21~26 ns 的路径：`pnr` 跑 30 分钟后仍有 **10,638 条
未布线网络**，继续跑下去得到的时序报告没有意义。所以改用**满足式测量**：
`platform/pango_native/pango_native_40mhz.fdc` 保持 PPLL 14/3 不变、只把参考时钟放慢，
核心时钟落到 **25.0 ns**。这一版布通了，`report_timing` 直接给出真实路径。

| 构建 | 约束 | 综合 WNS | 布线后 `Estimated Period` | 等效频率 | 面积 |
|---|---|---:|---:|---:|---|
| `p7_impl126b` | 126 MHz | −13.490 ns（21.4 ns） | 未收敛（10,638 条未布线） | — | 18,723 / 9,478 |
| `p7_path40b` | 40 MHz（25 ns） | +2.163 ns（22.84 ns） | **26.647 ns（−1.647）** | **37.5 MHz** | 18,583 / 9,478 |
| 旧核 `perf_p37b`（交付 3.8557） | 27 MHz | — | 32.553 ns | 30.7 MHz | — |

⇒ **新核比交付的旧核快 22%**（37.5 vs 30.7 MHz），且面积更小（LUT 18,583 vs 18,829 同口径）。
**但要 126 MHz 需要 −70%**（25.9 ns 逻辑+布线 → 7.2 ns 预算）。

### 5.2 这 25.9 ns 花在哪（`p7_path40b/report_timing/*.rtr`，39 级）

```
w_rd_h[4]（WB 旁路寄存器）
  ├─ 操作数选择网络（N190/N296/u_regs/u_div 共 7 级）            ≈ 9.4 ns   ← 最大一块
  ├─ u_mul 4 级 DSP 级联（13.87 → 19.96）                       ≈ 6.1 ns
  ├─ u_alu_h 比较链 → br_taken_h                                 ≈ 1.5 ns
  ├─ ex_next_h 目标加法器 → N665 预测校验比较                     ≈ 3.1 ns
  └─ N226_3 → perf_inst/cnt[*] 的 CE 级联（16 个 CECO）          ≈ 4.6 ns
```

四条结论，每条都能单独动手：

1. **操作数选择网络 9.4 ns 是最大单块**，不是 ALU。它是"4 读口 + 双写穿透 + 4 级旁路"
   串起来喂给乘法/除法，v2 §19 想用"提前采样操作数"消掉它，方向是对的；
   当时失败是因为同时加了 `lane0_raw_pair`（见 mistakes-log §26），**没有单独验证过**。
2. **乘法又回到路径上了**（6.1 ns）。上一轮把它移到 M1 换到 4.08 ns，代价 −4.6% 分数；
   在这一版路径里它是 `alu_a_h` 的来源，说明存在"乘 → lane1 比较"的同拍串联。
3. **`perf_inst` 的 CE 级联占 4.6 ns**，而 skill §9.7 要求交付位流默认关 `PERF_ENABLE`。
   交付构建如果关掉它，这 4.6 ns 与那 594 LUT 一起消失（本轮只做了综合验证：
   关掉后综合 WNS 从 +2.163 变 +1.251，说明这条 CE 是**末端**而非起点，
   真正的最长路径会换到别处——所以不能据此宣称频率提升）。
4. **预测校验（N665.eq）与目标加法器在 EX 同拍**：这一段的 3.1 ns + 前面的 1.5 ns
   只能靠"分支结清单开一拍"来切，代价是每次误预测 +1 拍（53,270 次 / 20 迭代 = 0.76%）。

### 5.3 结论

- **120 MHz 不是"再调一拍"**：要 7.2 ns 的逻辑+布线预算，等于把上面四块里至少三块
  各砍一半，同时把剩下那块拆到两个周期。这是 7~8 级流水 + 操作数预采样 + 乘法独立级的
  工程量，不是本轮的能量级。
- 本轮能给的确定收益：**新核 37.5 MHz（旧核 30.7 MHz）、3.942 CM/MHz（旧核 3.8557）、
  LUT 更小**。三个指标同向，只是都还没到目标线。

## 6. 面积纪律（沿用 skill §9，不放松）

1. 一次提交只改一个模块，提交信息写 `module: <名> ΔLUT/ΔFF/ΔLUTRAM`。
2. `Δ(LUT+FF+LUTRAM) ≤ 0`；S1 不加任何存储，预期 LUT 变动在 ±50 以内。
3. 收尾跑 `tools/check_area_budget.py --from-used`，非零退出必须在文档里写清原因
   （v2 §19.3 的 FF +3 是打包噪声，这条判据继续有效）。
4. 门禁红灯不许用"删功能逻辑"去凑绿。

## 7. S1 实测：放行 load-use 是错的（已回退）

| 版本 | 改法 | ISA 21 例 |
|---|---|---|
| 基线（HEAD `3da4bae`） | — | 20/21（case 21 是探针口径问题） |
| S1-a | `load_use = load_dep && !mem_rsp` | **16/21**（fail 2, 5, 14, 18） |
| S1-b | `load_use = load_dep && !(mem_accept && done_valid)` | **17/21**（fail 2, 5, 18） |

**结论**：`load_use` 在这个核里不是"等数据"的互锁，而是"让 load 在 `ex` 级多留一拍、
把缓存响应落进 `m_value`"的**时序结构**（`m_value` 的捕获式要求 `ex_load` 仍在那一拍成立）。
按命中率放行会让消费者读到上一拍的 `m_value`。要省这一拍只有两条正路：
把数据在 `ex` 拍内组合旁路进 ALU（路径会毁掉频率），或把 load 拆成独立 M 级（改流水结构）。

细节与判据见 `docs/lessons/mistakes-log.md` §33。**这也是本轮最大的方法论收获**：
"停顿占比最大的那一项"不等于"最容易消掉的那一项"——先看它是否同时承担了别的职责。
