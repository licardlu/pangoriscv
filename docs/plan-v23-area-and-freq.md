## 0. 先把目标拆成三项独立指标

赛题口径（`docs/contest/`、skill `pango-riscv-contest` §3）：

| # | 指标 | 公式 | 当前交付 | 备注 |
|---|---|---|---|---|
| 1 | 执行效率 | `CoreMark/MHz = 1e6 / (ticks per iteration)` | **5.2484**（190,535 拍/迭代） | 与频率**无关**：提频不涨这一项 |
| 2 | 最高时钟 | 在各自时序约束下 `report_timing` 通过 | **50 MHz**（20.000 ns，布线 19.355） | 独立一项 |
| 3 | 资源效率 | `CoreMark / LUT` | **0.3056 /kLUT**（5.2484 / 17,174） | 面积越小越高 |

## 1. 结论先行：这两项在本微架构上互斥（四条独立证据，均为实测/定标）

1. **静态 ILP 上界**（`tools/ilp_bound.py`，用实测 IPC 1.7525 校准，k=1.097）：

   ```
   width memports  model IPC  calibrated  ticks/iter   score
       2        1      1.598       1.752      191534   5.221   <- 今天的实机是 5.2484
       3        2      2.060       2.259      154523   6.472
       4        2      2.212       2.427      145703   6.863
       4        4      2.283       2.504      142002   7.042   <- 天花板
   ```

   CoreMark 指令流的 ILP 上限是 **IPC 2.504**（4 发射 + 4 访存端口，零流水线代价）。
   ⇒ 每迭代最少 **142,002 拍**（7.04 CoreMark/MHz），这是天花板。
   （2026-10-24 13:2x 用 `sim20_O2/firmware.dump` 现场复算，与历史记录一致。）
2. **每加一级访存流水线的真实代价 = 34,757 拍/迭代**（探针实测 `load_use_1` = 695,148/20 迭代）。
   ⇒ 142,033 + 34,757 = 176,790（5.656，勉强还在 5.2 以上）；
   再加一级 = 211,547（**4.727，破线**）。
3. **120 MHz 需要几级**：本设计布线后 19.355 ns，其中 **Logic 3.685 ns / Route 16.470 ns**；
   120 MHz 预算是 8.333 ns ⇒ 需要 `S = 20.1 / 8.333 = 2.41` 级。
   ⇒ 至少 2 级。与第 2 条相乘，**即使做到 4 发射 + 4 访存端口，分数也只剩 4.73**。
4. **摆放地板实测**：`--freq 120 --place-only` 摆放后最差路径 **14.07 ns（slack −5.77）**，
   即这条网表的"摆放地板"≈ 70 MHz。60 MHz 约束摆 15.50、50 MHz 摆 18.32。
   ⇒ 120 MHz 不是"再调调参数"的事，必须动结构（切 2 级），而切级要花拍数，见第 2 条。

**所以"5.2 且 120 MHz"不是本轮能不能做到的问题，是被 ILP 上界和切级代价联合关死的问题。**
本文件不再重复论证，只做两件事：

* **A 线（守 5.2，抬指标 2 与指标 3）**：在不花一拍的前提下抬频率、压面积。
* **B 线（120 MHz 的真实路径）**：写成可执行的工程清单，标注工量与前置条件，不假装本轮能交付。

## 2. A 线的可动杠杆（按"每拍收益 / 风险"排序）

| │ ├ `u_csr` | 442 | 289 | 0 | 0 | 0 |

**两条新结论**（都推翻了旧记录）：

1. **16 KiB 数据 RAM 早就进 BRAM 了**（`data_ram` 4 DRM / 188 LUT）。
   `area-budget.csv` 里 M2 "blocked，2,048 LUTRAM"的条目已过时——
   所以"把 data_ram 搬进 BRAM 省 2,048 LUT"这条路**不存在**，别再走。
2. **2,274 LUTRAM 全部是两级 Cache 的阵列**（I$ 1,172 + D$ 1,102），
   而且**是被复制过的**：DRM 只有一个读口，而 RTL 每 bank 要 2 个异步读口，
   映射器只能把阵列复制一份（M5/M6 已记录）。
   ⇒ 这 2,274 LUT（占 13%）与"双 lane 同拍访存"是绑死的，
   换成 BRAM 就等于砍掉一个读口 = 加一级访存流水 = 18% 拍数（见 §1-2）。**不能动。**

⇒ 面积真正可动的是 `cpu` 的 7,330 LUT（其中 `u_bp` 1,089 + `u_regs` 1,137 = 2,226 是可讨论的），
和 `fabric` 729 + 外设 1,189。但它们都不是"免费的"：动 `u_bp` 会掉拍数，动外设会掉功能。

## 4. B 线：120 MHz 的真实工程清单（本轮不交付，写清前置与工量）

按 §1，唯一能同时满足"120 MHz 且 ≥5.2"的结构是：

```
4 发射 + 16 B/拍取指 + 4 个独立访存端口 + 2 级访存流水
⇒ 142,033 + 1×34,757 = 176,790 拍/迭代 = 5.656（1 级）
⇒ 142,033 + 2×34,757 = 211,547 拍/迭代 = 4.727（2 级，破线）
```

即：**2 级访存流水时，只有把"零级代价"的每迭代拍数压到 150,000 以下
（= IPC 3.0 以上）才可能守住 5.2，而 CoreMark 的 ILP 上限只有 2.504。**
所以 B 线在数学上就不存在，除非换基准或换算法（不允许）。

可以交付的中间形态（按指标 2 优先，放弃指标 1）：

| 形态 | 频率 | 分数 | 需要的结构 |
|---|---|---|---|
| 现交付 | 50 MHz | 5.25 | — |
| 1 级访存流水 | ~70 MHz（摆放地板） | ~4.7 | D$ 输出寄存 + 地址在 ID 算好 |
| 2 级访存流水 | ~100–120 MHz | ~4.4 | 再加一级；访存端口要真并发 |

工量估计：1 级 ≈ 3~5 天（含 ISA 21 项回归 + 上板），2 级再加 3~5 天。
**这不是一次会话能完成的事，也不该被说成"再试试就行"。**

## 5. 本轮不做什么（避免重复踩坑）

| 不做 | 原因（已实测） |
|---|---|
| 换 `pnr -seed` | 静默 no-op，seed 3 与 seed 7 摆放逐位相同 |
| 重跑同一棵网表 | 同一网表的摆放是确定性的，重跑结果相同 |
| 加 `-place_worst_slack` | 要 +8 ns 反而让摆放从 16.93 退到 17.18 |
| 两步流程（紧约束摆放 + 松约束布线） | 摆出来是拥塞布局：60 MHz 摆 15.45，布线吃 4.7 ns 到 20.204 |
| floorplan / 区域约束 | 横带/竖带/紧凑方块三种形状全部负优化 |
| 把 Cache 阵列搬 BRAM | 复制是为了第二个读口；砍读口 = 加一级访存 = 18% 拍数 |
| `lane0-load → lane1` 旁路 | 仿真 +0.66% 分，但两棵不同网表都吃 3.9~4.8 ns 摆放 |
| `ls/sl/ss` store buffer | 配对 100% 成功，ticks 只动 20 拍（store 仍占同一端口） |

## 7. 本轮的确定性结论（2026-10-24 15:30）

### 7.1 52 MHz 的下限是 19.426 ns，五种配方一模一样

在**同一棵 cut-2 网表**上换了五种布线配方，结果**逐位相同**（摆放 slack +1894 ps、
布线 186 轮收敛、最差路径 19.426 ns、Logic 7.938 / Route 10.960、
WNS −0.195、失败端点 12、LUT 17,027）：

| 配方 | 结果 |
|---|---|
| 四选项（dc_dup + slack_prior + recluster + recovery） | 19.426 |
| 三选项（去掉 recovery） | 19.426（逐位相同） |
| 四选项 + `-plc_decongestion 1 -share_router_control_signal TRUE` | 19.426（逐位相同） |
| 四选项 + `-enable_route_constraint_iterate` | 该选项失效（lesson 99），空转 |
| 默认配方 | 20.222 |

⇒ **这条网表的布线是确定性的**（lesson 9 的第五次确认）：**重跑同一个网表、换任何
不影响逻辑/摆放的选项，都不会产生新抽样**。想换抽样只有一条路——**扰动网表**。
而目前唯一现成的扰动（P57）会让它变差 0.83 ns。

### 7.2 为什么"只有 0.195 ns"还是过不去

缺口不在布线（10.96 ns 已经是全族最干净的），在**逻辑 7.938 ns / 13 级**。
这 13 级里的主体是 `RF 读 mux → 操作数选择 → ALU 4 级 → 转发 mux → 4×APM 乘法级联`。
要压掉它只能：
* 删掉 ALU→乘法这条链（P57）→ 实测把最差路径换成 24 级/16.47 ns 布线，**更差**；
* 或者加一级流水 → **每级 +34,757 拍/迭代（18%）**，5.2 立刻变 4.44。

这就是 §1 那条边界在具体路径上的样子：**5.2 分买下的"单拍 ALU + 单拍 D$"，
正好是 50 MHz 这个频点。再往上 0.195 ns 都要用拍数换，而拍数已经没有余量。**

### 7.3 因此本轮的交付是

| 指标 | 值 | 说明 |
|---|---|---|
| CoreMark/MHz | **5.2484**（190,535 拍/迭代） | 仿真 `Total ticks 3,810,700`，五项 CRC 全对 |
| 最高时钟 | **50 MHz** | 交付位流约束 20.000 ns，布线 19.355 ns，WNS +0.645 |
| CoreMark/LUT | **0.3056 /kLUT**（17,174 LUT） | 若换成 cut-2 树的 50 MHz 实现则 0.3082（见 §7.4） |

### 7.4 仍然可做的（下一个人接手时按这个顺序）

1. **把 cut-2 树落到 50 MHz**：同一套四选项、`--freq 50`。若通过，
   面积 17,174 → 17,027（指标 3 +0.85%），拍数与分数不变。
2. **上板实测**：唯一未完成的验收项。`board_verify.ps1` 已就绪（本机缺下载线）。
3. **120 MHz**：见 §4，不是调参问题。

### 7.5 最后一步：主干 RTL 回退到**交付树**（cut-2 是净亏）

`p64r50`（cut-2 树 + 三选项 + 50 MHz）布线后 **21.717 ns / WNS −1.717 / 147 端点 / hold −0.060**，
与历史上的 `p50cut2`（cut-2 + 默认选项 + 50 MHz，21.532 / −1.717）**逐位相同**
⇒ 三项布线选项在 50 MHz 上同样是空转，问题在树本身。

| 树 | 50 MHz 布线后 | LUT |
|---|---:|---:|
| **交付树（`232dfa3`，无 cut-2、无 P57）** | **19.355 ✓** | 17,174 |
| cut-2（`37129f8`） | 21.532 / 21.717 ✗ | 17,021 |
| cut-2 + P57 | 20.252（52 MHz 约束）✗ | 17,152 |

cut-2 省了 153 LUT，但把 `Logic` 从 3.685 ns 顶到 7.938 ns（综合把 ALU 锥合并得更深），
净效果差 **2.2 ns**。⇒ **"面积更小、综合 WNS 更好"的树，交付频点上更差**（lesson 97）。

因此 **主干 `main` 的 RTL 已回退到交付树**（与位流 `pangoriscv_board50_i2800_5p248.sbit` 的源码
**逐字节相同**），否则"三项指标出自同一份实现、可由命名的分支复现"这条就断了。
cut-2 与 P57 的代码留在 `docs/patches/cut2-csr-read-split.patch`、`docs/patches/cut2-and-p57.patch`，
等将来真能换到更高频率时再捡回来。

## 8. 第二轮（16:00–16:40）：综合侧的新杠杆，也是死路

结论先写：**综合侧也不能动**。`help synthesize` 暴露的 `-retiming` 是本轮唯一的"新"杠杆，
它把综合 WNS 做好了 1.485 ns，把布线后做坏了 4.32 ns。详见
`evidence/records/optimization/p66r52ret/measurement.md` 与 lesson 100。

| 建 | 树 | 综合 | 约束 | pnr | 布线后 | WNS |
|---|---|---|---|---:|---|---:|
| p65r52 | **交付树** | std | 19.231 | 三选项 | 布线拥塞（>80 min 未收敛，终止） | — |
| p66r52ret | cut-2 | **retiming** | 19.231 | 三选项 | **23.750** | **−4.519** |

两条附带结论：

1. **交付树在 52 MHz 上比 cut-2 更难布**：摆放 slack 只有 +1,136 ps（cut-2 是 +1,894），
   且布线到第 27 轮还有 7,960 根未通、每轮 31 s。它在 50 MHz 的 19.355 ns 是一次好抽样，
   不是"这棵树天生更快"。
2. **综合 WNS 与布线后结果的相关性为零**（本族 n=10）：`p50cut2` 综合 +1.117 布出 21.532；
   `p66r52ret` 综合 +1.577 布出 23.750；`p58r52` 综合 +0.092 布出 19.426。
   ⇒ 任何"综合报得更好"的改动都不构成改善证据。

## 9. 收口：52 MHz 的最终判定

**8 次满流程、5 种布线配方、2 种网表变体、1 个更松的约束，最好的一次是 19.426 ns（差 0.195 ns），
而且同一棵网表的 3 种配方逐位相同。52 MHz 在这套微架构上不可达。**

要过 52 MHz 只有两条路，代价都已量化：

| 路 | 代价 | 结果 |
|---|---|---|
| 加一级访存流水 | +34,757 拍/迭代（实测 `load_use_1`） | 5.2484 → **4.44**，指标 1 破线 |
| 加宽到 3 发射 + 6R3W + 一级流水 | ILP 定标 186,811 拍 | **5.353 分**，但那是数周的重写（v18/v20 有设计） |

所以：**盯 5.2 分这一档，50 MHz 就是天花板；想要更高频率，必须先接受指标 1 掉到 4.4~5.4，
而那需要重写发射宽度，不是调参。**

## 10. 交付版最关键路径的逐段账（2026-10-24 16:45，第一次做成表格）

来源 `build/p48r50e/report_timing/pangoriscv_top.rtr`（50 MHz 约束，WNS +0.437/+0.645，
12 条路径里最差的那条，24 级）。路径本身是**写**方向，不是读：

| # | 段 | 累计 ns | 这一段花了多少 | 说明 |
|---|---|---:|---:|---|
| 1 | `w_valid` FF → `cpu/N639[1]` | 3.423 | 0.577 | fanout 18 |
| 2 | `N639[1]` → `u_csr/read_data_*` 三级 | 6.419 | 2.996 | **CSR 读 mux 三级**，其中一根线 0.763（fanout 86）、一根 1.010 |
| 3 | CSR → `alu_a[24]` → `u_alu` 四级 | 11.446 | 5.027 | `alu_a` fanout 16（0.599）、ALU 内部一根 **1.426** |
| 4 | `alu_y[4]` → `fwd1_h[4]` | 12.638 | 1.192 | **fanout 5 的一根线就 1.118 ns** |
| 5 | `fwd1_h` → `mem_addr_h[8]` | 13.316 | 0.678 | 地址加法器尾巴 |
| 6 | → `ls_req_addr[8]` | 14.611 | 1.295 | **fanout 144**，1.221 ns |
| 7 | → `data_cache/N30_47 muxf8` | 14.851 | 0.240 | 用了 L8 mux |
| 8 | → `_N20169` | 16.060 | 1.209 | 一根线 1.209 |
| 9 | → `hit_any` | 17.304 | 1.244 | tag 比较、set 选择 |
| 10 | → `state_q_fsm` → `N1542` → `_N80029` → `_N80054` | 19.502 | 2.198 | **FSM 组合链 5 级** |
| 11 | → `N4032_10[8]` → **`N4033[0]`** | 22.076 | **2.574** | **fanout=256，单根线 2.500 ns**，直连 1,024 个 `ram64x1d/WADDR` |

### 10.1 结论：最贵的一段是"写地址被命中检测门控"

第 9–11 段合计 **4.77 ns（占 22.1 ns 的 22%）**，全部只为一个目的：
**在命中时把 `w_data` 合并进 D\$ 阵列**，而写地址 `didx(hit_way, req_set, req_word)` 必须等
`hit_any`（第 9 段）和 FSM（第 10 段）算完才有值，最后再扇出到 1,024 个阵列原语（第 11 段，2.5 ns）。

**这三段是"纯写"路径，读路径不需要它**（读的是第 1–9 段，到 `accept_word` 就结束了）。
所以它是最理想的切割对象：把写地址**打一拍**，让这 4.77 ns 从关键路径上消失，
而拍数成本理论上为 0（store 本来就经由 store queue 延迟落地）。

### 10.2 为什么上一轮没做成（lesson 90）

`docs/patches/cut6-*.patch` 那一版功能全对（ticks/CRC/ISA 全过），
但 **PDS 综合从 3 分钟变成 40 分钟不结束**。原因本次看清了：那个写法在 FSM 的 `case` 里
新增了一条写路径，与已有的三条"延迟写"路径（`ST_WR_REQ`/`ST_WR_RESP`/`ST_WR_HOLD`，
都用已寄存的 `hit_way_q/set_wr_q/word_q`）并列，综合器要为同一个阵列做**四选一的写地址 mux**，
而每个选项又是 1,024 位宽。

**正确的做法不是"再加一条"，而是"只留一条"**：把 `ST_IDLE` 里那条即时写（line 604）
改成锁存 `{idx, data, strb}` 的延迟写，同时**删掉** `ST_WR_*` 里的三条重复写
（它们写的是同一份数据、同一个地址，是历史遗留的多余路径）。

唯一的正确性风险：store 被接受后的**下一拍**若有一条 load 命中同一 index，会读到旧数据。
处置有两条路，任选其一：
* **加一拍互锁**：`req_ready` 在"上一拍刚接受过 store 且未落地"时拉低。代价是
  store→load 紧邻时的 1 拍，CoreMark 里这种组合很少（store 占比 ~4%，紧随同址 load 更少）；
* **加一条 store→load 旁路**：用 11 位比较器 + 字节合并 mux 补在 `accept_word` 上。
  代价是把逻辑加到**读**路径（本来就已经 4.89 ns 的那段）上，**不推荐**。

⇒ 下一轮应该做的是：单写口延迟化 + 删三条重复路径 + 一拍互锁，然后**先用小仿真量互锁代价**，
再跑满流程。这一步的收益上限是 **4.77 ns（19.355 → 约 14.6 ns，折合 68 MHz）**，
是本项目目前唯一一个"量级正确"的杠杆。

## 12. 第三轮（18:50 起）：把 cut 6 做成"工具能吃下"的形状

### 12.1 目标与边界（先把账算清，避免自我欺骗）

cut 6 摘掉的是交付版关键路径第 9–11 段共 **4.77 ns**（22.076 → 约 17.3 ns）。
17.3 ns ⇒ **约 57.8 MHz**。**这不是 120 MHz，也不可能是**——120 MHz 要 8.333 ns，
需要 2.41 级流水，而每级访存流水 +34,757 拍（5.2 直接掉到 4.44），这条边界在 §1/§9 已封。

所以本轮的目标是**明确且可达的那一档**：在不损失任何拍数（分数仍 5.2484）的前提下，
把频率从 50 MHz 推到 **56 MHz（17.857 ns）**，若布线给面子再试 58 MHz（17.241 ns）。

**收益**：指标 2 从 50 → 56/58 MHz（+12%~+16%），指标 1 与指标 3 不变。这是当前唯一
"零拍成本"的真实提升。

### 12.2 上一轮失败的三条原因（已定位，分别对症）

| 变体 | 失败方式 | 根因 |
|---|---|---|
| A | 流水线 stall | `req_ready` 在 `ST_IDLE` 外拉低 = **丢请求**，不是停顿（lesson 102） |
| B | tech-mapping 12 min+ | 阵列**写源 5 个**，综合要做 1,024 位宽的多路写地址 mux |
| C | LUT 64,270 / LUTRAM 1,250 | 写地址是**组合 wire** ⇒ 映射器放弃 LUTRAM 推断（lesson 104） |
| D | 仿真跑飞 | 脚本化打补丁时把三处接受点的锁存改坏（`dwr_idx` 只补了两处 + 寄存器/分量混用） |

### 12.3 变体 E 的设计（三条约束同时满足）

1. **写地址必须是寄存器**：`dwr_idx` 用 `reg`，在三处接受点与 `dwr_data/dwr_strb`
   一起锁存（不再寄存 `way/set/word` 分量，避免两套索引）。
2. **读路径只能有一个地址表达式**：把接受沿的读地址抽成命名 wire
   `rd_idx_acc = didx(hit_way, req_set, req_addr[4:2])`，
   `accept_word_raw = dread(rd_idx_acc)`、旁路判断 `rd_idx_acc == dwr_idx`，
   **共用**同一个表达式（变体 C 的两个独立 `didx(...)` 才是 LUTRAM 丢失的直接原因）。
3. **保留 `ST_WR_REQ/RESP/HOLD` 三处重写**：它们用的是**已寄存**地址
   （`hit_way_q/set_wr_q/word_q`），不在关键路径上，而且它们防的是
   "store 接受后、B 回来之前，该行被换出又填回"的竞态 —— 变体 C 删掉它是有正确性缺口的，
   本轮**不删**。写源数 4（延迟写 + 三个重写里的两个 + fill），可接受。

### 12.4 判据（缺一不可）

1. CoreMark 20 迭代 `Total ticks == 3,810,700`（逐位）+ 五项 CRC 全对 + `cycles` 相同
2. ISA **17/18/19/20 全 PASS**（case 21 覆盖率探针恒 0，见 lesson 98）
3. 综合后 **LUTRAM == 2,274**（这一条一眼判定阵列有没有丢推断）、LUT ≤ 18,000
4. 满流程 `report_timing`：56 MHz（17.857 ns）WNS ≥ 0 且失败端点 0
5. 上板：`board_verify.ps1` 退出码 0
