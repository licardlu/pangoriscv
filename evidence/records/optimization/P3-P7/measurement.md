# P3/P7 · 取指吞吐与 store 路径的实测结论（2026-10-17）

> 本轮结论：**取指通路的 0.5 IPC 天花板是结构性的（IFU 与 I-Cache 各需 2 拍），
> 不是靠局部调参能打开；一次合并改动验证时死锁，已回退。** store 路径的改造需要
> AXI 写引擎支持多笔未完成事务，属于架构改造。
> 证据等级：仿真实测 + 一次失败实验（回退后基线已复核）。

---

## 1. 结构性上限的确诊

| 模块 | 代码事实 | 后果 |
|---|---|---|
| `ifu_axi.v` | `eng_req_valid` 仅 `state==S_IDLE` 允许；发一次请求后进入 `S_WAIT` | 每 **2 拍**才发一次 |
| `icache_axi.v` | `req_ready = state==IC_IDLE`；命中在受理沿给出响应，但要停在 `IC_RESP` 一拍 | 每 **2 拍**才受理一次 |

两者锁步 → 取指供给上限 = **1 条 / 2 拍 = 0.5 IPC**。
实测 IPC 0.372，取指饥饿 18.1%，与该上限一致。

---

## 2. 两个实验与结果

### 实验 A：只改 IFU，让它能在收到响应的同一拍继续发下一次请求

改动（1 行条件）：

```verilog
assign eng_req_valid = ... && ((state==S_IDLE)||((state==S_WAIT)&&eng_rsp_valid)) && ...
```

**结果：与基线逐位相同。**

```
Total ticks 15,316,450 / cycles 17,256,182 / retires 6,418,312
axi_d_ar 194,298 / axi_d_aw 287,914   ← 全部与基线一致
```

**解释**：I-Cache 在 `IC_RESP` 里不接受新请求，`eng_req_ready` 无法连续为高，
所以 IFU 拿不到"背靠背"的机会。这反过来证明：**限速点是 I-Cache，不是 IFU。**

### 实验 B：IFU + I-Cache 同时改成背靠背

改动：`req_ready` 增加 `(state==IC_RESP && rsp_valid && rsp_ready)` 条件，并把
`IC_IDLE` 与 `IC_RESP` 合并到同一个受理分支。

**结果：死锁。**

```
STALL_DETECT cycles=219023 last_retire_cycle=19022 retires=19
TEST_FAIL T_COREMARK_STALLED no retirement for 200000 cycles
```

只退休了 19 条指令（`retire_pc=0x34`），说明在极早期（UART 初始化前后）就卡住。
推断原因：在 `IC_RESP` 受理新请求时，响应寄存器与 `addr_q/id_q/way_q` 被同拍覆盖，
而命中路径又依赖"上一拍登记的地址"来做 `rsp_data` 的组合选择，出现了响应与登记
不同步；此外 `rsp_valid` 的置位/保持路径在合并分支后不再互斥。

**处理：整组改动已 `git checkout` 回退，未进入任何提交。**
回退后基线复核：`Total ticks 15,316,450`、`cycles 17,256,182`、
`retires 6,418,312`、`axi_d_ar 194,298`、`axi_d_aw 287,914`，与基线完全一致。

## 3. 为什么不能"再试一次就完了"

要把取指做到 1 条/拍，需要同时满足：

1. I-Cache 受理与响应在**同一个流水级**完成（响应寄存器与请求登记必须分离成两级），
2. IFU 需要能同时持有 **2 笔未完成请求**（当前 `state` 只有 1 位、`req_pc_q` 只有一份，
   响应归属靠"唯一未完成请求"推断），
3. 重定向时按请求身份丢弃（现在靠 `stale_q` 单标志）。

这三点合起来等于**重写取指前端**，不是调参。按路线图 §1 的铁律（接口合同冻结、
一次一个变量），它应当作为一个独立的架构任务立项，并且先在 `tb_ifu_axi` 单元级
验证背靠背 / 重定向同拍 / 队列满等场景，再进整机。

## 4. store 路径同理

`axi_d_aw = 287,914` = store 条数，证明每次 store 都走完整 AXI 写。
但"让 store 不等 B"在现有结构里**换不来收益**：`axi_data_engine` 是单笔未完成的，
下一笔 AW 必须等上一笔 B 被消费；把等待从 D-Cache 挪到引擎只是换了个地方等。

真正的解法是写引擎支持 ≥1 笔未完成写（或 D-Cache 写回 + dirty 位），
同样属于架构改造。
