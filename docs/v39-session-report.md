# v31–v40 阶段报告：把三条 ~20 ns 路径量清楚，只留下一条证明无害的改动

日期：2026-10-27
基线：交付位流 `pangoriscv_board50_i2800_5p248.sbit`
`Total ticks = 533,875,894`（2800 迭代）⇒ **5.2447 CoreMark/MHz @ 50 MHz**，五项 CRC
`e9f5 / e714 / 1fd7 / 8e3a / bd59`。本报告所有对比都以这条为基准。

---

## 0. 首先要记住的一件事：镜像的编译器版本决定了 4.6% 的分数

本机只有 xpack **GCC 13.2.0** 与 pango openisa **GCC 7.1.1**；交付位流里的 CoreMark 是
**GCC 15.2.0** 编译的。用本机工具链重建同一份源码，500 MHz 都一样、CRC 都一样，
但 `Total ticks` 从 533,875,894 变成 558,585,077（**+4.6%**）。

交付位流在同一块板子上重测：`533,875,894`，**一位不差**。所以：

* 板子、串口、测量链路是**完全确定性**的，逐位对比有效；
* 但**用 GCC13 重建的镜像永远到不了 5.2447**，这 4.6% 与 RTL 无关。

本轮已把 **GCC 15.2.0** 装到 `toolchain/xpack-riscv-none-elf-gcc-15.2.0-1`，
并按 `--extra-flag=-march=rv32im_zicsr` 重建参考镜像，
上板得到 **`Total ticks = 533,875,894`、`CoreMark/MHz = 5.2447`、五项 CRC 逐位相同**
⇒ 参考镜像**已逐位复现**。以后凡是压分数字的对比都必须用这个工具链。

（两个传参坑：`--opt=-O3`/`--extra-flag=...` 必须用等号；`--prefix riscv-none-elf-`
必须带尾部连字符，否则工具去找 `riscv-none-elfgcc.exe`。）

## 1. 三条 ~20 ns 路径，逐个量清楚

50 MHz 下这个设计有三条长度几乎相同的路径，谁排第一取决于布线运气。拆掉一条只会露出下一条
——这就是"改了半年还是在 50 MHz"的原因。

| # | 路径 | 实测 | 结构成因 |
|---|---|---|---|
| A | `w_csr → u_csr 读 mux（5 级 40 选 1）→ csr_rdata → wb_value → 寄存器写穿透 → 32:1 读 → alu_a → ALU` | 交付版 19.355 ns / v32 综合 19.666 ns | CSR 在 **ID 和 WB 各读了一次**；WB 那次顺着写穿透穿进 EX 的 ALU 操作数 |
| B | `m_valid → 旁路 → u_alu(lane 0) → fwd2_h → u_alu_h(lane 1)` | v31 布线 23.438 ns 到达 | **两条 32 位 ALU 链 + 一级旁路挤在一个周期** |
| C | `rr_inst → u_alu(lane 0) → fwd1_h → u_mul_h（4 个 APM 串联 6.14 ns）` | v36 布线 22.081 ns 到达 | lane 1 的乘法器被 lane 0 的 ALU 结果同拍喂进去 |

共同特征：**80~86% 的延迟是布线**（A: 82.9%，B: 86.2%，C: 80.5%），逻辑只有 2.9~4.1 ns。

## 2. 三次时间攻击，两次被数据否掉

### 2.1 乘法器两级化（rev 2.0）—— 回滚

50 MHz 满流程 `build/v31_50mul`，布线真收敛（0 unrouted @ 564 迭代），

| | 交付版 | v31 |
|---|---|---|
| WNS / 周期 | +0.645 / 19.355 ns | **−1.160 / 21.160 ns** |
| LUT / APM | 17,174 / 8 | **17,784 / 16** |
| 失败端点 | 0 | 559 |

根因：截断 `mul` 确实让低积变成 3 个无级联 APM，但高位通路要拼 66 位加树，**+610 LUT**。
86% 延迟是布线时，面积涨就是延迟涨。已回滚（教训 111）。

### 2.2 截断乘法器（P34）—— 回滚

想给 `mul` 低字加一条独立的截断 32×32，绕开 6.14 ns 的 APM 级联。
位精确性已验证（40,000 组向量 0 失配）。结果综合 **18.861 → 20.852 ns（更差 2 ns）**。

根因：`CPO→CPI` 级联是器件内部布线，单级 1.36~1.8 ns；三级并联 APM 之后要用 **LUT 进位链**
把三个 32 位部分积加起来，比被它替换掉的级联还慢。已回滚（教训 117）。
**乘法器保持交付版 rev 1.2 不动。**

### 2.3 删掉"包内同拍旁路"（P32）—— 回滚，代价被实测钉死

`fwd1_h/fwd2_h` 首级 `lane0_raw ? alu_y :` 是路径 B 和 C 的共同源头。把它从 RTL 删掉
（而不是只在译码级拒绝配对——`pair_ok` 对综合不可见，路径照样在），再强制拆包保证正确性。

综合确实变好：19.666 → 18.420 ns（P32+P33）。**但上板：**

```
Total ticks : 590,274,834     (参考 533,875,894)
CoreMark/MHz: 4.7436          (参考 5.2447)      → −5.7%（相对同镜像）
五项 CRC 逐位相同              → 语义正确
```

用 **10.6% 的周期** 换 2% 的频率是坏交易。已回滚（教训 115）。
顺带否掉了"包内 RAW 很少见"的旧判断——CoreMark 里约 10% 的包有包内依赖。

## 3. P33：唯一留下的改动（零 IPC 代价，已上板证明）

`wb_value = w_csr ? csr_rdata : w_value` 在 WB 拍**第二次读 CSR**，而：

1. `rr_csr_old`（ID 预读）已经把同一个值流水到 `w_csr_old`；
2. **`csr_new`（写给 CSR 的值）一直用的是 `w_csr_old`**，从来没第二次读；
3. `id_bypass` 表达式里本来就排除 `dec_csr`，CSR 一定在 ID 寄存器停一拍，预读必被采到；
4. `rv32_top.v` 自己的注释写的就是"CSR 从 ID 级读"，`.addr(w_valid && w_csr ? w_csr_addr : id_csr_addr)`
   反而**违背了自己的文档**。

改动：`wb_value` 用 `w_csr_old`；`.addr` 固定 `id_csr_addr`；删掉死寄存器 `w_csr_addr`。

| 指标 | 交付版 | P33 |
|---|---|---|
| LUT | 17,174 | **17,020（−154）** |
| FF | — | 8,645 |
| APM | 8 | 10 |
| 综合周期 @50 MHz | — | **18.861 ns（WNS +1.139）** |
| 布线后 | 19.355 ns | 19.801 ns（WNS +0.199，布线波动范围内） |
| **`Total ticks`** | 533,875,894 | **533,875,894（完全相同）** |
| **五项 CRC** | — | **逐位相同** |

**这是本轮唯一可以声称的改进：路径 A 被从结构上删掉、面积少 154 LUT、综合时序好 1.1 ns，
而分数与功能逐位不变。** 布线后那 0.45 ns 的差是布线波动（同一 RTL 两次布局都给出
+2.541 ns，布线分别落到 19.801 ns）。

## 4. 物理手段：紧凑 floorplan 是负结果

`pango_native_floorplan_compact.fdc`（把 `i:soc.core` 绑进 x10..106 / y15..161）：

| 阶段 | 无 floorplan | 有 floorplan |
|---|---|---|
| 布局后 slack | +2.541 ns | **+2.466 ns** |
| 布线后 | **19.801 ns（+0.199）** | **21.156 ns（−1.156）** |
| 布线迭代 | 340 | 320 |

布局器算出更短线长，布线器却因为区域内太挤必须绕出去，**一进一出净亏 3.6 ns**。
结论：只看"布局后 slack"会得出完全相反的结论；必须以布线后 `report_timing` 为准（教训 116）。

## 5. `-O3`：小幅但可复现的提分（+0.29%）

参考镜像是 `-O2`。同一份源码换 `-O3`（GCC15.2.0，4000 迭代，保证 ≥10 s）：

| 镜像 | ticks/迭代 | CoreMark/MHz |
|---|---|---|
| `-O2`，2800 迭代（参考） | 190,670.0 | 5.2447 |
| `-O3`，4000 迭代 | **190,118.5** | **5.2599** |

`seedcrc/crclist/crcmatrix/crcstate` 四项（与迭代数无关）**逐位相同**，`Correct operation
validated`；`crcfinal` 不同仅因为跑的是 4000 迭代而不是 2800。

结论：CoreMark 在 `-O2` 下已经压得很紧，`-O3` 只有 0.29% 的余量——不是"编译器没优化好"，
而是这条路本来就是平的。**不要指望编译器旗帜能救频率。**

两个位流已归档到 `pangoriscv-verify/bitstreams/`：

* `pangoriscv_v39_p33_o2_2800_5p245.sbit` —— 与交付版**逐位同分**（533,875,894）的等价网表
* `pangoriscv_v40_o3_4000_5p26.sbit` —— **5.2599**，当前最高分

## 6. 现在的状态与下一步

**留下的树内改动**：只有 P33（`rtl/core/rv32/rv32_top.v`）。
P32/P34/rev2.0 全部回滚，补丁与数据分别归档在 `docs/patches/` 与 `docs/lessons/mistakes-log.md`
（111、115、116、117、118）。

**墙在哪里**：路径 B（双 ALU 链）与 C（ALU→乘法器级联）仍然存在，且都要 8~10 ns 的
lane0→lane1 同拍依赖。要抬频率必须同时拆掉 B 和 C，而拆掉它们的唯一手段（P32）要付 10.6%
的 IPC——**在本架构上这两者的乘积是负的**。

**功能等价性（最强判据）**：同一个自检镜像分别烧进交付版网表与 P33 网表，串口输出
**逐字符相同**（含既有失败项 `FAIL mask=512`、`delta=5000063`）。该 `FAIL_CSR` 是
`test_timer_csr()` 里三条针对旧版 `init.c` 的断言过时所致，两个网表一致，与 P33 无关。

**因此真正的出路只有两条，都不是"调参"：**
1. **取消 lane1 与 lane0 的同拍依赖**，但不牺牲配对率：需要 lane 1 的操作数来自寄存器
   （例如给被拒的包加一级"lane1 单独重放"而**不是**拆包），这样既不丢发射槽，又能删掉
   `lane0_raw` 分支。代价是重放控制（复杂度高，但 IPC 损失应为 0）。
2. **缩短 lane1 的乘法器**：6.14 ns 的 4-APM 级联只服务 `mulh*` 的高半部分和 `mul` 的低半部分。
   已证明"截断 + LUT 加法树"更慢；剩下的是"lane 1 不支持 mulh"（把 mulh 配到 lane 0），
   这需要重测配对率，但可能比 P32 便宜。

分支预测/IPC 方向（`CoreMark/MHz` 的另一半）本轮没动，仍是 5.2447 的水平。
