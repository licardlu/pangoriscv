# YOLO120 / 008 时序收敛修复计划

日期：2026-11-03  
状态：方案阶段；未修改 RTL、时序约束或构建结果。

## 1. 目标与约束

本计划要解决的是 YOLO120 集成版 008 在目标频率下未通过最终静态时序分析（STA）的问题，同时保住 CPU 约 120 MHz 的运行频率和现有 CoreMark 跑分水平。AI 加速器的性能可以作为独立折衷项评估，但不能通过降低 CPU 时钟来换取表面上的时序通过。

验收目标：

- CPU 主时钟保持约 120 MHz，最终实现中的时钟约束和 PLL 配置均有报告证据。
- 最终布局布线后的慢角、快角 setup/hold、recovery/removal、最小脉宽均无失败端点，WNS 为正，TNS 为 0。
- DDR、摄像头/视频、CPU 与加速器之间的时钟域交互经过功能验证；不以 false path 隐藏真实数据通路。
- 最终镜像、固件和 RTL/约束快照与验收报告对应；随后再单独做上板验证。

## 2. 已知事实与边界

### 2.1 集成版 008 的失败

008 的最终时序报告将 `ai_clk` 约束为 8.300 ns，等效约 120.48 MHz。慢角 setup 为 WNS −1.540 ns、TNS −668.634 ns、共 1,533 个失败端点（其中 `ai_clk` 1,530 个、DDR 3 个）；快角 setup 通过。慢角 DDR `phy_dq_sysclk_1 -> ddrphy_sysclk` 3 个失败端点，最差 −0.088 ns。快慢角 hold 汇总通过。对应验收记录标记为 `timing_pass: false`、`board_verified: false`；`routed` 在 008 的 `acceptance.json` 中为 `true`，在 006 中为 `false`。

最差 CPU 路径从 `execute_ctrl2_up_integer_RS1_lane0[13]` 出发，经过移位与写回/寄存器堆选择网络，到达运算单元 `N8470/gopapm/X[13]`。路径 11 个逻辑级，逻辑延迟 1.642 ns、布线 7.544 ns（布线占 82.1%）；布线占主导。此路径表明问题不只是 AI MAC 运算速度。

### 2.2 当前时钟连接

YOLO120 顶层用 `ai_perf_pll` 产生 `ai_clk`，并将它接到 `yolo_ai_client.clk_sys`。该客户端内部 CPU 和当前 AI 加速器的寄存器/计算模块均以 `clk_sys` 为时钟。因此直接降低这个时钟会同时降低 CPU，违背本计划目标。DDR native 接口工作在 `core_clk`，客户端已有 DDR 请求/响应 CDC；这不代表 CPU 到 AI 寄存器接口、视频寄存器接口也可以直接异步连接。

### 2.3 最新 CPU ZIP 的证据

`D:\FPGA_Project\CPU_120MHz_latest.zip` 内的 `provenance/SELECTED_IMPLEMENTATION.json` 记录了独立 CPU 候选 `board021_gshare10_route20` 在 120.467 MHz 下通过多角时序：慢角 setup +0.148 ns、快角 setup +3.159 ns，setup 失败端点为 0；其余 hold、recovery、removal、最小脉宽检查也记录为正裕量、0 失败端点。这说明该候选 CPU 实现有约 120 MHz 通过 P&R STA 的证据，但不能单凭它证明 YOLO 集成版也会收敛，因为 ZIP 没有包含完整 `.rtr` 报告，而且集成后的外设、布线拥塞、资源映射和布局都可能改变关键路径。

## 3. 修复策略概览

按风险从低到高推进：

1. **复现并固化 008 基线**：确认输入源、约束、工具版本和报告对应关系，抽取关键路径及全部失败路径类别。
2. **优先集成最新已收敛 CPU RTL**：以 ZIP 的受控快照作为 CPU 源码候选，保持 CPU PLL 频率和当前功能不变，在 YOLO120 工程中重新实现。先验证它是否能直接带来集成版收敛。
3. **如果集成后仍失败，先处理布局/布线主因**：关键路径布线占比高，检查 CPU 关键逻辑的实际映射、扇出、拥塞和物理距离；只添加工具确实执行且报告能证明生效的物理约束。
4. **若需要，再做局部 CPU 逻辑优化**：针对报告中的 late shifter/写回路径做小步、可回归的 RTL 变化；每个候选单独完整 P&R 和 STA。
5. **AI 单独降频作为独立可选项**：只有在 AI 模块与 CPU 总线/视频接口有明确 CDC 设计后才拆时钟。该项不能替代 CPU 关键路径优化，因为 008 的主失败路径位于 CPU。

不允许通过修改时序周期数字、漏约束时钟、把真实同步路径设为 false path、只看综合结果或中间 P&R 快照来宣称收敛。采用时钟使能降低 AI 运算活动率也不会自动放宽同一时钟域的 STA 周期；除非路径被严格证明为合法多周期路径且功能握手与约束一致，否则不得以此作为时序修复。

## 4. 分阶段执行计划

### 阶段 A：基线复核与可追溯性

1. 只读归档 008 的 `acceptance.json`、最终 `.rtr`、源文件清单、约束文件、固件哈希和 PDS 版本。
2. 确认最终报告时钟表中的 CPU/AI、DDR、像素和摄像头时钟均存在且频率匹配 RTL；检查各快慢角汇总中的端点数非零。
3. 从完整报告导出最差 20–50 条 CPU setup 路径，按起点/终点、逻辑级数、逻辑延迟、布线延迟、扇出/拥塞归类；另单独列出 DDR 三条失败路径。
4. 记录基线资源利用率、拥塞/布线摘要、关键时钟周期和 CPU 跑分基准，供候选对比。

**阶段门 A：**如果时钟约束缺失、端点数为零、输入快照与报告不匹配，先修正证据链或约束建模并重新实现；不进入优化结论。

### 阶段 B：用最新版 CPU 替换集成工程中的 CPU 实现

1. 将 `CPU_120MHz_latest.zip` 解压到独立的只读输入快照/候选目录，不覆盖当前 CPU 源码和 008 构建目录；记录 ZIP 与解压文件哈希。
2. 比对 YOLO 工程目前生成的 CPU、Vexii 集成壳、执行阶段 include、PLL 与约束，确认 ZIP 中 CPU 版本可被工程生成脚本直接使用；避免只替换 `pango_vexii_top.sv` 而遗漏依赖文件或配置。
3. 对比候选与当前 008 CPU 关键源文件，特别检查 `project/pds_native_120/rtl/core/execute/replica_late1_shifter.v`（ZIP 内路径为 `execute/replica_late1_shifter.v`）、相关 pipeline sections、CPU 参数/插件配置和 PLL 源。输出差异清单，确认变更与 `board021_gshare10_route20` 的来源一致。
4. 建立新的构建名，不覆盖 `yolo120-008`。CPU 时钟仍保持现有约 120.461538 MHz PLL，保持相同模型、固件、摄像头、视频和 DDR 接口配置。
5. 运行完整 PDS compile、布局布线、最终多角 STA 和工程检查；synthesis-only 或预布局报告只用于早期筛错，不作为通过依据。
6. 通过后比较新集成版与独立 CPU 包的关键路径：CPU 最差路径是否仍是 late shifter/写回，WNS 裕量是否保留，资源和拥塞是否变化；同时验证固件及 CoreMark 功能结果。

**阶段门 B：**如果全角 setup/hold 等检查通过且 CPU 时钟仍约 120 MHz，则主修复路径成立，转阶段 E 做功能和上板确认。如果仍失败，记录失败路径后转阶段 C；不得因独立 ZIP 的 STA 汇总通过就跳过集成验证。

### 阶段 C：优先改善关键路径物理实现

因为 008 最差 CPU 路径约 82% 延迟来自布线，先判断物理问题是否可通过布局改善解决，再改 CPU 功能逻辑：

1. 查看 CPU 寄存器、late shifter、写回网络和 APM/DSP 端点的映射实例，确认是否跨越较远区域、被拥塞绕行，或存在高扇出控制/数据网。
2. 对照 PDS 的拥塞、线长、扇出和关键路径布线视图，确定 CPU 逻辑组的实际叶单元名。不要依赖已被综合优化掉的层级通配符。
3. 如果证据指向可局部聚类的 CPU 关键单元，在单独候选上添加最小范围的区域/布局约束；按项目 lessons 经验，验证约束在 `dev_map` 后仍存在、PNR 命令确实执行、目标实例实际匹配，并确认日志无 `E:` 错误。
4. 每个布局候选至少做一次完整 P&R；如果布局随机性明显，使用多个 seeds/候选评估稳定性，不能只选一个偶然正 slack 结果。
5. 比较 WNS/TNS、失败端点、关键网布线延迟、拥塞、资源和 CPU 分数。若物理约束改善一条路径但恶化其他路径或 DDR/视频，则回退该候选。

**阶段门 C：**若关键路径布线延迟稳定下降且多角 STA 有正裕量，可进入阶段 E；若改善不足或关键路径逻辑占比变高，进入阶段 D。

### 阶段 D：局部 CPU 逻辑优化（最后手段）

1. 以阶段 B 的最新 CPU 候选为基线，一次只改一个关键逻辑点。首先分析 late barrel shifter 输出到整数写回/寄存器读取端点之间是否存在可合并/减少的选择级或高扇出网络。
2. 优先选择保持 ISA 与流水线语义不变的结构整理或组合扇出优化；如果需要对执行级做流水线调整，必须先评估停顿、旁路、异常/中断、分支和写回协议影响，并扩大仿真范围。
3. 对移位指令覆盖 RV32I 算术右移、逻辑右移、左移、移位量 0/1/31、符号位和旁路/停顿交错；运行 CPU 现有回归、诊断固件和 CoreMark。
4. 每个 RTL 候选以新构建快照完整综合、布局布线及多角 STA；保留源文件哈希与失败结果。若延迟路径转移到别的逻辑，按新的真实关键路径继续，不固守旧路径假设。
5. 如果可行候选通过，但 CoreMark 或模型推理结果改变，先定位功能差异，不将性能变化归因于频率或 P&R。

**阶段门 D：**功能回归全部通过，最终 P&R 多角 STA 正裕量、失败端点为零，且 CPU 仍约 120 MHz，才接受 RTL 优化。

### 阶段 E：独立 AI 降频（可选，不阻塞 CPU 收敛修复）

只有在 CPU 120 MHz 主路径先被证明可收敛后，才决定是否需要让 AI 加速器运行得更慢。执行步骤：

1. 拆分“CPU 控制/AXI-Lite 寄存器接口”和“AI MAC/卷积运算数据通路”，明确哪些模块归 CPU 时钟域、哪些模块归 AI 时钟域。不要把整个 `clk_sys` 直接换成慢时钟。
2. 设计并检查 CPU→AI 命令/参数与 AI→CPU 状态/中断握手。多位命令数据要用握手保持稳定或异步 FIFO；不能逐位打两拍后当作总线 CDC。
3. 检查视频快照前端、AI 寄存器接口及 DDR DMA 数据的跨域。已有 DDR CDC 可以复用经验证的边界，但必须确认它接收的请求/响应源时钟与复位域仍正确。
4. 配置 PLL 的第二路输出或可行的独立时钟源时，保持 CPU 输出的 120 MHz 不变；对 AI 输出创建正确 generated clock、相位和异步时钟组约束，检查时钟树和复位同步。
5. 在仿真/形式或 CDC 检查中验证复位先后、命令 backpressure、连续事务、异常响应、DMA burst、视频读写以及复位中途取消事务。
6. 完整 P&R 和多角 STA，确认 CPU 主时钟约束端点与频率没有变化，CPU setup/hold 全部通过，AI 时钟本身也在其目标周期下通过，跨域接口无未处理路径。
7. 重新测端到端推理时间和帧刷新率。较低 AI 频率可能降低吞吐，即使功能正确也可能不满足项目实时目标。

**阶段门 E：**CPU 时钟保持 120 MHz 且全路径时序通过，CDC 验证通过，AI 的端到端性能仍满足目标，方接受双时钟方案。若 AI 性能不达标，保留 CPU-only 收敛修复，重新评估 AI 时钟或计算结构。

## 5. DDR 三个轻微失败端点的处理

008 中 DDR 另有 3 个慢角 setup 端点，WNS −0.088 ns。虽然裕量很小，也必须在最终实现里单独解决并通过：

1. 从 008 及新候选 `.rtr` 中定位这三条路径的确切 startpoint/endpoint、时钟关系、输入/输出延迟和数据/时钟布线。
2. 判断它们属于 DDR PHY 内部合法同步路径、跨 PHY/系统时钟路径，还是时序约束/生成时钟建模问题。
3. 若为真实同步路径，依据 PHY 与 PDS 报告调整实现或适用的 DDR 时钟/相位配置；若为约束模型问题，修正生成时钟/时钟组并检查目标端点确实被分析。
4. 不将 DDR 路径整体设为 false path。只有经过设计结构证明的异步 CDC 数据路径可以按规范切断 setup 分析，并须有同步器/异步 FIFO 结构及 CDC 验证支撑。

## 6. 最终验证清单与放行标准

### 静态时序与构建

- 新 build ID，输入源和工具版本可追溯，且最终 `.rtr` 来自同一轮完整布局布线。
- CPU 约束频率不低于项目 120 MHz 目标；报告中的目标时钟有实际端点。
- 快角、慢角 setup、hold、recovery、removal、minimum pulse width 全部满足门禁：slack > 0、TNS = 0、失败端点 = 0。
- DDR 那 3 个旧失败端点全部消失或经路径级分析证明其报告分类正确；无新未分析的关键时钟域。
- 无工具约束加载失败、路径被意外忽略或约束目标为空的日志；有效 PCF/区域约束与命令执行证据齐全。
- 位流哈希、固件 ELF/RAM 镜像哈希与本次通过 STA 的 build 绑定。

### 功能和性能

- CPU 诊断固件、基本 ISA/异常测试和 CoreMark 均通过；确认跑分测试配置和原 5.346252494 CoreMark/MHz 基准（7,000 次、1,309,328,358 ticks @ 120.461538 MHz）一致。
- YOLO 固件、模型、85 个算子和视频数据路径通过现有回归；对比输出检测结果/CRC，确保未发生功能回归。
- 若启用双时钟 AI，额外验证 CDC、复位、背压和异常场景；实测推理时间及帧率。
- 最终板级验收必须下载与已通过 STA 的位流完全匹配的实现，并单独记录 `board_verified`。静态时序通过不等于板上验证完成。

## 7. 可能问题、识别方法与应对

| 可能问题 | 识别信号 | 应对 |
|---|---|---|
| 独立 CPU 通过，集成后仍失败 | 新集成版 CPU 路径仍有负 WNS；布线延迟/拥塞显著上升 | 先对比映射与布局、资源拥塞及时钟扇出，再做局部物理优化；不能把独立 CPU 报告当作集成验收 |
| ZIP 缺少原始时序报告 | 汇总 JSON 有结果和 hash，但 `.rtr` 不在包内 | 要求/从归档恢复同 hash 报告；当前结论标为“包内记录通过，报告未独立复核” |
| 替换 CPU 时漏文件或配置不一致 | 生成文件哈希与来源 manifest 不一致、综合层级/参数变化 | 固化来源 manifest 与依赖清单，以脚本化映射替换，重新做源快照和哈希校验 |
| AI 降频后 CPU 也变慢 | CPU 与 AI 仍共用 `ai_clk` 或 `clk_sys` | 不动该共享时钟；先建立独立 AI 时钟域及 CDC，再测频率和 STA |
| AI 时钟拆分出现间歇性错误 | 事务丢失/重复、总线数据撕裂、复位后卡死 | 使用握手/FIFO CDC，加入随机背压与复位仿真、CDC 检查和板级长时间测试 |
| 用时钟使能但 STA 没改善 | 关键路径仍按完整 CPU 时钟周期分析 | 明确 CE 仅控制更新频率；不把 CE 等同较慢时钟。真实多周期路径须同时满足功能和约束条件 |
| 布局区域约束没有生效 | 报告路径位置未变、日志约束未执行或匹配数为 0 | 按本仓 lessons 在映射后检查活动 PCF、叶单元名和执行日志；新实现后重验 |
| 单次 P&R 正裕量、重跑又失败 | WNS 接近 0，seed/拥塞变化导致关键路径变化 | 保留安全裕量，比较多个 seed；以可复现、稳定的候选为准，不接受偶然通过 |
| CPU 时序通过但 DDR 仍失败 | CPU WNS 正，DDR setup 仍负 | 独立按 DDR 端点分析和修复；整体验收仍判失败 |
| AI 降频造成实时性能不达标 | 每帧推理时间增加、队列/显示延迟上升 | 先测量吞吐目标；调节 AI 频率或优化算子流水/并行度，不回退 CPU 时钟 |
| 时序“通过”来自漏约束 | 报告时钟端点为 0、路径类别消失、约束工具有 warning/error | 以最终 clock summary、端点数和约束日志复核；恢复真实时钟关系再验收 |

## 8. 推荐决策顺序

1. 先以最新 CPU ZIP 候选重建 YOLO 集成版，CPU 频率不变，完整跑 P&R 与 STA。这是最能直接验证用户最新版 CPU 是否解决集成版主路径的步骤。
2. 如果失败，先做关键路径布局/拥塞分析与小范围物理优化，因为 008 关键路径主要由布线延迟构成。
3. 物理优化不足时，才对 CPU late shifter/写回路径做定点 RTL 优化，并完整验证功能。
4. 最后再考虑 AI 单独降频；它是 AI 吞吐与资源/功耗的折衷，不是 008 CPU 关键路径失败的直接修复。
5. 只有 CPU 120 MHz 全角 STA、DDR STA、CDC 与功能回归都通过后，才进入上板验证和发布。

## 9. 当前决定与未执行事项

当前决定是保留 CPU 约 120 MHz，首先把最新版独立 CPU 集成到 YOLO120 并取得新的最终 STA 证据。尚未开始解压/替换、未改 RTL 或时序约束、未创建新 P&R 实现，也未做板级测试。具体 AI 降频数值应在 CPU 主路径收敛后，依据独立时钟可行性和端到端推理性能决定。
