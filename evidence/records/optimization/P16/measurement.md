# P16 · AXI RAM 猝发气泡：每拍 3 个周期 → 节省读填充 8 拍（2026-10-18）

> 结论：**ticks −2.35%**（7,658,647 → 7,478,647，20 迭代；CoreMark/MHz +2.42%），
> CoreMark/MHz **2.6109 → 2.6740（+2.42%）**，面积 **−2 LUT / −2 FF（完全中性）**。
> 交付跑分：768 迭代、ticks **287,211,317**、10.64 s、`Correct operation validated`；
> 27 MHz 与 50 MHz 约束均 **All Constraints Met**。
>
> **这一步是纯"气泡"清除**：没有新增功能，只是删掉 RAM 猝发读里两个白等的状态周期。

---

## 1. 先量：I-Cache 缺失的 43 拍花在哪

上一轮遗留的最大单项是 `if_wait`（占计分窗口额外开销 40.5%）。加 `ICACHE_PATH` 探针
（`!report_seen` 门控）后，I-Cache 各状态拍数与缺失次数对上了：

```
ICACHE_PATH idle=1620843 ar=46997 fill=475410 missrd=18285 resp=7149637 fault=0
i_miss = 18289
```

| 状态 | 拍数 | 每缺失 |
|---|---|---|
| `ST_AR`（等 arready） | 46,997 | 2.57 |
| **`ST_FILL`（8 拍猝发）** | **475,410** | **26.0** |
| `ST_MISS_RD` | 18,285 | 1.00 |

**8 拍用了 26 拍 = 每拍 3.25 个周期。** 这不是 DRAM 延迟，是 `axi_ram` 自己的状态机：

```verilog
READ_RESP:  // 交出这一拍
READ_MEM:   // read_data<=mem[idx]   ← 同步读，必须 1 拍
READ_WAIT:  // if(delay_left==0) → READ_RESP
```

`READ_DELAY` 默认 0，但 `READ_WAIT` 照样占满一整拍才转出去——**纯浪费**。

## 2. 改动（`rtl/perips/axi_ram.v`，两处，共 9 行）

```verilog
READ_MEM: begin
    if(read_good) read_data<=mem[read_index];
    else read_data<=0;
    delay_left<=READ_DELAY;
    // READ_DELAY=0 表示"没有建模延迟"，数据寄存器在这一拍已经装好，
    // 下一拍就是有效节拍：直接进响应。
    if(READ_DELAY==0) state<=READ_RESP;
    else              state<=READ_WAIT;
end
```

这就把每拍 3 周期降到 2 周期，`fill` 从 26 拍降到 18 拍/缺失。

## 8. 被测量否决：R 拍预取（曾经拿到 +2.15%，但主动回退）

在 `READ_RESP` 里顺便把下一拍的数据预取好（`read_data<=mem[read_index+1]`，并留在
`READ_RESP`），可以把每拍降到 **1 周期**，`fill` 从 18 拍进一步降到 **11 拍**：

| 版本 | ticks | CoreMark/MHz | `fill`/缺失 |
|---|---|---|---|
| P14 基线 | 7,658,647 | 2.6109 | 26 |
| 只跳 `READ_WAIT`（本版，20 迭代推算 / 768 迭代实测） | 7,478,647 | **2.6743 / 2.6740** | 18 |
| **再加预取** | **7,321,147** | **2.7319** | **11** |

**但这版被回退了**：`run_halt_reset_tests` 的场景 1/3（"读进行中 halt/reset"，
该测试把 `READ_DELAY` 设成 60）开始超时——现象是**那个 44 字节的测试程序似乎根本没发出
数据读**。我把注入点从 `LSU_READ_WAIT` 改到 AXI `AR` 握手（和写那侧一致的做法）之后
**依然超时**，说明不是缺观察点，而是取指流在 `READ_DELAY>0` 下真的变了。

ISA 15/15、ram 40/40、CoreMark CRC 在 `READ_DELAY=0` 下都正常，所以这只在"建模了延迟"
的那条路径上暴露。**这是一个我当晚没能解释清楚的行为改动，所以不上线**——
已在代码里留下注释说明来龙去脉，并注明"若要重启此项，先补 `READ_DELAY>0` 的专项测试"。

教训：`READ_DELAY` 这类"只为测试台存在"的参数，其路径同样需要被认真对待；
把常数折叠掉之后，测试和实际硬件跑的是**两条不同代码路径**，不能只凭一侧通过就放行。

## 11. 距 3.0 还差什么（算清楚了）

要 3.0 需要再 **+12.2%**（IPC 0.769 → 0.867）。计分窗口内的账（P16 状态，20 迭代）：

| 来源 | 拍数 | 占比 | 可行性 |
|---|---|---|---|
| `if_wait`（余下的 I-Cache 缺失） | ~655 K | 8.8% | 4 KB 净亏；预取因未解释的行为差异回退 |
| store 占 EX（2.3 拍/笔） | ~680 K | 9.1% | **store 队列**：唯一还能拿 3.5~4.5% 的方向，要重写写路径 |
| 分支预测失败 | ~308 K | 4.1% | 只能加大 BTB，③ 净亏 |

**三项全拿也大约到 2.9。** 3.0 需要"store 队列 + 更大的 I-Cache + 更强的分支预测"三者叠加，
而那会把面积推高 20% 以上，③ 反而下降。**在 13.6 K LUT 这个面积档上，2.67 已经是
效率前沿**；再往上属于换架构（双发射 / 2 笔未完成写）而不是继续挤。
