# 可复用的排错经验

## PDS 区域约束文件已加载，但布局没有执行区域命令

现象：`add_constraint` 成功，映射日志却有 `Pcf file ... has been covered`；
PNR 日志中没有 `def_region` / `def_inst_region` 执行记录。

查什么：比较准备时物理约束哈希与映射后的 PCF 内容，检查 PNR 是否实际执行命令。

原因：`dev_map` 会向已注册的 PCF 导出物理引脚约束，覆盖先前写入的区域命令。

怎么办：保留独立的区域输入，在 `dev_map` 后追加到活动 PCF，再启动 PNR。
门禁同时检查只读输入哈希、活动 PCF 内容和每条命令执行成功；加载文件不算约束生效。

映射还会展开层级：报告路径含 CPU 前缀，不代表前缀本身仍是可约束实例。
`def_inst_region` 不匹配通配符，也不递归约束已消失的层级。应从同次映射 DB
导出实际叶单元名后逐个绑定。PDS 即使报 `PhysicalConstraintEditor-0023` 仍可能
打印该命令 `successfully`，因此必须同时拒绝 `E:` 错误行。

## PDS 显示约束通过，但有时钟域根本没有分析

现象：最终摘要可能显示已约束路径通过，compile/STA 日志却有
`Clock pin ... has no clock`、`Clock source ... need a clock constraint`，
或 `Nothing implicitly matched` / clock group 被忽略。

查什么：最终报告 Clock Summary 以及快慢角 Setup/Hold 的实际端点；
比对 RTL 中所有分频寄存器用作时钟的逻辑。不能仅看最后一行成功摘要。

原因：PLL 自动推导不一定覆盖普通寄存器产生的分频时钟；约束使用信号名时，
该名字也未必是工具中的时钟名。例如摄像头 SCCB 的 `clock_20k` 是 /2500 寄存器分频。

怎么办：根据 RTL 的真实分频比添加 generated clock，并确认目标实际匹配；
同一 PLL 的输出要保留正确相位/占空比。发布检查必须要求关键时钟有非零约束端点。
完整重新实现后用最终多角报告验收，中间 `after_hold_fix` 快照不作最终依据。

PDS 2022.2-SP6.1 还会拒绝周期 ≥100000 ns 的时钟。若真实慢速分频超过该范围，
可用更短的整数分频作保守分析模型，并明确区分物理分频和分析分频；必须确认
没有依赖不同慢钟精确相位的数据路径，不能把分析分频改小后声称 RTL 时钟也改变了。

## Windows 原生 GCC 退出却没有错误输出

现象：Python 能启动 `gcc.exe`，编译返回非零但 stdout/stderr 均为空；
或加入 PATH 后链接器称找不到实际存在的 CRT/库文件。

查什么：子进程退出码、GCC bin 目录是否在子进程 PATH；安装路径是否包含中文。

原因：编译器子程序缺少 DLL 搜索目录时可能无法输出诊断；部分 MinGW 工具在中文
安装路径下会出现路径编码不一致，导致链接器无法定位自己的 CRT/库。

怎么办：只给编译子进程的 PATH 前置显式编译器 bin 目录，始终保存日志和退出码；
路径编码问题改用已经安装在纯英文路径下的编译器。不要把编译失败当成用例跳过。
