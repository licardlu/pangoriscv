# 比赛收口裁决与队长执行提示词

## 一、明确裁决

批准开展收口，但不照搬评审答复中的全部结论。
本轮目标是“可重复构建、可正确运行、可有效计分、可解释、可交付”的比赛版本。
不是无限优化 CoreMark，也不是在测试未收口前扩展处理器架构。

1. 以 T4 + LSU 候选为拟交付版本，先在隔离目录完成验收，不立即覆盖生产树。
2. 正式跑分采用 600 次迭代；若任一要求计分的运行不足 10 秒，则统一升级迭代数并重新构建对应 A/B。
3. case 7 优先修测试，不预先批准 CSR 旁路、气泡或计数器 RTL 改动；必须补独立证据。
4. 内部写通路先采用受限契约方案，不新增写缓冲；若合法输入也会被丢弃，则必须做最小 RTL 修复。
5. ILA 是本轮比赛交付的必做项，可在有效成绩后执行，但不得留作无限期的可选任务。
6. 先形成重建脚本、修测试与接口验收，再进行昂贵的最终 PDS/板测，避免反复构建。
7. 收口后才决定下一项性能优化；高阶任务缺口和下一步建议只在同一份状态记录中简要更新。
8. 不批准外部 Flash 擦写、驱动更换或电气配置调整；本轮仅使用已验证的易失性 JTAG 配置流程。
9. 优先修改代码、执行验证和上板；只记录必要的结果与原始证据，不反复撰写评审、答复、总结或同内容的多份报告。

## 二、队长答复必须先更正的内容

- 板测 T4→LSU 吞吐提升 = 279957350/226427447-1 = 23.6411%。
  板测 B0→LSU 提升 = 320725708/226427447-1 = 41.6461% 左右。
  两者不同是因为参照版本不同，不是因为前者属于仿真。
  仿真数据应另列，不能以该理由否认板测增量收益。
- “轮询版 PASS”支持原测试有不合理的即时进位假设，但单独不能证明计数器所有语义正确。
  不以“计数器时序都实现定义”为理由免除顺序 CSR、写入和退休计数检查。
- 受限内部 W 契约可以约束生产者不得先发数据，但现有 WR_IDLE 会真实给 ready。
  因而负向测试应该明确报告契约违例，不能声称不改 RTL 已实现“早到数据不被握手消费”。
  同拍合法请求不能被错误断言拦截。
- 跟踪了完整改后文件并不因父提交无同路径就无法恢复。
  应核实可取得的 T4 基础提交、覆盖文件与构建脚本，精确定义缺的是哪一项依赖；patch 是手段而非唯一形式。
- 不使用 iterations/(seconds×27e6) 的结果直接标注 CoreMark/MHz；那是按 Hz 归一化的数值。
  使用本文下面的统一公式与单位。
- 不要求所有板测 UART 字节永远一致；时间戳、计数或元数据可变化，工作量、校验和及结果语义必须一致。
- 增加迭代次数不必然增加运行缓冲大小；重新检查 ELF/镜像容量即可，不能未经测量宣称 800 次需要更大 RAM。
- “没有修改 RTL”不等于测试、固件、脚本修改零风险。
- 完整长时间 RTL 仿真按资源安排，不重复执行没有新增证据价值的所有长程组合；不得因此删掉最终候选的端到端正确性验证。

## 三、可直接发送的执行提示词

你负责我们紫光同创 RISC-V CPU 比赛工程的最终收口实施。以下是已批准的执行任务，不要重复询问 600/800、是否补 ILA、是否开始收口。本轮目标是完成有完整证据的比赛候选交付，而非无边界追分。

**执行优先级：代码与测试 > 实验执行 > 必要记录。不要花大量时间写报告。**
只维护下面“最小记录要求”规定的内容；已有文件能用就原地更新，不新建重复文档。不为每一步单独写方案、评审答复和总结，不重新整理全部历史报告。记录尽量由脚本产生，失败先定位解决，不停下来写长篇分析。

### 1. 工作范围与安全

- 工作区：`E:\file\pango\project`。先读赛题 `docs/contest/contest-pages-10-11.txt`、权威设计计划和现有评审结论，只提取当前执行所需约束；无需再写阅读报告或逐条评审答复。
- 查实际生产路径，当前应为 `firmware/code`；实验在 `evidence/records/bottleneck_audit`。不得沿用不存在的旧路径。
- 修改前备份源码、测试、构建脚本、约束和镜像，生成 SHA256；保存当前 git 状态、HEAD、工具版本。保留旧 B0/T4/LSU 位流和原始日志。
- 在独立目录修改和构建，不删除未跟踪物，不覆盖原始证据，不全局清理进程，不擅自 force-push。
- 可以自行仿真、PDS、用既有已验证 JTAG 易失配置流程下载及抓串口。烧录前核对器件、位流 SHA、串口、供电前提；先开串口再下载。无法核对电气条件时停止板级动作并报告，不猜测。
- 若下载工具导致异常、驱动崩溃或蓝屏，立即停止反复下载，保存证据；不自动换驱动或改系统安全设置。
- 未验证项标记 NOT RUN；不得用仿真代替板测，也不得把工具估算频率标成实测。

### 2. 先建立可重建的候选

- 选择明确的一个 T4 基础 commit，不得写成“80e39ce 或 f01c6ff”。查证哪个提交包含所需源码。
- 用基础提交加 3 个 LSU RTL 覆盖文件/补丁、配置和构建入口重建候选；纳入必要 TB 与脚本。差异清单直接使用 git diff，不另写改动报告。
- 所有后续改动先落在可跟踪的候选中，再做干净重建；不要最后才补 patch。
- 修 `sim/run_pipeline_tests.py` 源清单，使生产宏配置能直接使用正式 runner 通过。优先使用已有权威源清单或项目一致的依赖管理方式，不再只给替代命令。

### 3. case 7：修时序依赖，不靠改硬件迁就判据

- 先保留原失败用例及日志；复核 EX CSR 接线，在统一状态记录中简短更正“ID 级 CSR RAW 冒险”的错误归因并链接原记录，不重写多份历史报告。
- 把回绕检查改成有界轮询，设置合理循环上限和 TB 周期超时，超时必须 FAIL，不能无限等待或吞掉失败。
- 明确高半初值、写入低半与期望进位，必要时先写 mcycleh=0；新增初始化的语义也必须被验证。
- 独立保留无间隔 mscratch 背靠背读写、CSR 三种读改写、只读别名与非法写异常检查。
- 增加逐拍计数器检查：显式写覆盖、自然递增、回绕、minstret 退休增加与异常不退休；不要把轮询成功当全部计数器语义通过。
- 不为测试通过加入无依据 NOP、CSR 气泡/旁路或修改计数器读值。若发现真实 RTL 缺陷，先记录最小反例与规范依据，再做局部修复并重跑。
- 修 runner 判据和必要注释，最终要求最终宏配置与全关配置 ISA E2E 均通过，独立重建树同样通过。

### 4. 内部写握手：采用受限契约，但必须真实验证

- 本轮不新增写缓冲，不支持提前 store 退休，保持单笔在途及成功 B 后完成语义。
- 先核实每个生产者是否保证 W 与内部写请求同拍或之后；写清合法输入时序、数据保持、背压、错误和复位规则。
- 断言必须允许“同拍请求被接受且 W 同拍接受”的合法情形，不能只按前一拍 req_pending 判断。
- 若契约规定禁止 W 先到，负向测试必须预期准确的契约违例；不能把被禁止输入默默丢弃又判 PASS，更不能说现有 ready 已经阻止握手。
- 若任一合法输入下发生假握手、丢失、重复、死锁或错误完成，批准局部 RTL 修复；保持同拍快路径，不扩大成独立写缓冲。相应测试、仿真、PDS 全部更新。
- 测 req/W 同拍、req 先到、延迟 W、W 单拍脉冲、独立 AW/W 背压、B 延迟/背压、SLVERR/DECERR、字节掩码、MMIO、halt/reset 排空。外部 AXI AW/W 独立，不得把内部受限契约强加到外部总线。

### 5. 完整回归门槛

- 对实际申报宏配置运行全部相关单元、引擎、Cache、预测器、流水线、ISA E2E、halt/reset；再测全关配置，按配置列出结果。
- 无论既有问题还是新问题，最终配置有真实 FAIL 就不冻结；测试被证明有误才能修测试，不可删检查、改阈值掩盖。
- 使用独立 work 库、明确源清单；一项机制只保留一份最终修改，避免实验树漂移。

### 6. 正式 CoreMark：600 次，两套种子

- 固定真实 27 MHz、GCC 与优化参数、2000 字节数据、宏及链接条件。
- 构建 performance 种子 0,0,0x66 与 validation 种子 0x3415,0x3415,0x66，均 600 次。
- 最少为 B0/最终候选 × 两套种子构建四个独立配置的位流；同一模式两版使用逐字节相同的 program.hex/data.hex。如增加 T4 正式结果，再单独构建，不能套旧 400 次成绩。
- 位流内嵌镜像，换固件必须重新执行本工程支持的完整构建流程；不能只改串口显示或软件宏。
- PDS 进程 CWD 必须是对应独立流程目录，不能依赖已知无效的 -work_dir；PANGO_NATIVE_BOARD_DIR 指向实际含 native_sources.tcl/FDC/PCF 的 platform/pango_native 目录。
- 核对内存加载日志、镜像路径和非空初始化，保存输入镜像 SHA。两条加载提示是辅助证据，不是唯一充分条件。
- 必须 All Constraints Met；记录慢/快角 Setup/Hold、资源、约束和 seed。不得通过降约束或忽略端点掩盖失败。
- 两套种子做端到端仿真与板测；长程 RTL 仿真先评估预算，短程机制验证不能冒充完整 600 次板测。
- 每个正式板测配置至少两次完整串口采集，运行实际不少于 10 秒、完整校验成功，无错误提示；同模式 A/B 校验相同。
- 若不足 10 秒，统一增加迭代数、重建对应对照镜像/位流并重测，不采用预测时长充当证据。
- crcfinal 随迭代数可能变化；跨迭代不强求相同，按该模式/参数的参考结果核对。
- 正式指标统一：
  `CoreMark/MHz = iterations × 1000000 / ticks`；
  `CoreMark = iterations × actual_clock_hz / ticks`；
  `CoreMark/LUT = CoreMark / 同版成绩位流 LUT`。
- 分开列 B0→候选累计提升、T4→候选增量提升；不得混淆参照版本或 MHz/Hz 单位。

### 7. 本轮完成 ILA 比赛分析

- 基于冻结候选生成独立带 ILA 的调试版，选 PC/retire、分支重定向、队列、Cache、LSU 与 AXI 握手等实际存在的探针。
- 用算法入口或明确执行标记触发，采集 CoreMark 关键算法区间，不以启动、流水灯或 UART 输出波形代替。
- 调试版重新 PDS、上板确认功能，保存原始采集或可复查导出、必要截图、触发条件；在统一状态记录中用一小段解释观察到的停顿，不单独写长报告。资源/时序与无 ILA 成绩版分列。
- 分别解释取指、访存和分支停顿，说明采样深度和区间，不能用短窗口声称覆盖全部 10 秒。

### 8. 交付、合并与下一阶段

- 无真实失败、正式成绩有效、重建成功后，授权将验收通过的候选合并到唯一生产树；此前先备份并保留独立回退版本。
- 提交源代码、测试、构建入口、配置、约束、固件和源清单；证据保存 SHA 与输入关联。大文件可外部归档，但必要输入不可仅留绝对本机路径。
- 干净目录执行重建，核对源码/固件的预期身份；PDS 如不保证逐位确定性，说明工具、seed 与非确定因素，不伪造“必须 bitstream 完全一致”。
- 不删除历史错误记录，在统一状态记录追加简短更正；大产物保留或校验归档，不为目录整理拖延开发，不以“清理”为名删除。
- 在统一状态记录放一张简短赛题对账表：基础、两路 I/D Cache/突发、动态预测、异常/中断、ILA、AI/传感显示应用。每项只写状态与证据路径，不另建 `CONTEST_FINAL_ACCEPTANCE.md` 或长篇验收报告。
- 收口后用最新候选重测瓶颈；下一阶段优先补赛题未闭环的高阶能力和真实应用，再选择一个性能机制实验。不能只优化 CoreMark 代替 AI 任务。
- 若有多个应用方向，只提出一个与现有资源、接口、期限匹配的建议方案，给出 CPU/加速单元分工、模型/传感或显示、延迟/准确率/资源验收，不擅自开启大规模应用重构。
- 文献只服务于已测瓶颈；引用官方仓库/论文原文，核实标题、作者、年份与许可，不承诺“顶刊方法必提升”。

### 9. 最小记录要求

沿用现有证据目录和文件；以下是逻辑分类，不要求为已有文件改名或复制。已有同类文件就继续使用，不能创建第二套重复记录。

1. **一份状态记录**：当前 commit/宏配置、改动目的、尚未解决的问题、赛题状态表、下一步。每个问题只写“现象/原因/处理/验证”各一句并链接日志。追加本轮变化，不重复历史全文。ILA 用必要截图和一小段分析满足赛题要求，正式参赛材料到提交时再从这些记录整理。
2. **一张实验结果表（CSV 或现有表格）**：运行编号、版本、宏/镜像/种子/迭代数/频率、回归 PASS/FAIL、CoreMark ticks/CRC/时长/分数、LUT/FF/存储资源、Setup/Hold 和原始日志路径。不同实验类型填适用列即可，不手填重复数据。
3. **一份重建入口**：尽量是可执行脚本，配最短 REBUILD 说明；包含工具版本、基础提交、配置、构建/仿真/PDS/下载命令、工作目录和必要路径。已存在脚本只补缺项，不把全部命令再抄进状态报告。
4. **机器生成的身份清单**：源码提交和未提交差异、固件/镜像/位流 SHA256、对应输入及运行编号；不对临时 work 库和不断增长的日志做反复全量哈希。
5. **原始证据与必要产物**：原始回归日志、PDS 时序/资源结果与构建日志、完整 UART、关键 ILA 采集、失败最小用例、可重建输入和最终位流。保留失败到修复的关键记录，不复制多套相同产物，不默认长期保留巨量全程 VCD 或临时库。

不可省略的是可复查数据、正确性验证、有效跑分和赛题必需 ILA；可以省略的是重复叙述、漂亮排版、长篇评审和多份同义总结。不得为了精简记录删除原始证据或降低验证门槛。

### 10. 最终答复格式

聊天汇报只给：通过/阻塞、改了什么、关键验证与板测数字、生产树/提交状态、剩余比赛任务和证据入口。以一张表加几句话为主，不输出长篇报告。时间估计只在有必要时说明，不为汇报中断正常执行。

能自主完成的既定工作不再逐项请示；只有电气/驱动安全、不可用设备资料或范围必须显著扩展时报告阻塞。没有证据就明确未完成。
