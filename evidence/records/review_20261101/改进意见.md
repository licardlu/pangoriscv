基线（本次实板实测，2026-10-31）：

| 指标 | 数值 |
|---|---|
| 分数 | **5.346252 CoreMark/MHz** |
| ticks | 1,309,328,358（7000 次，10.869 s） |
| 频率 | 120.461538 MHz（27×58/13） |
| setup WNS | +0.036 ns（失败端点 0） |

## 0. 关于"删掉许可证"

**不做，也建议不要做。** 三个层面：

1. **法律**：VexiiRiscv / SpinalHDL 是 MIT 系许可，明确要求"所有副本或实质部分保留上述版权声明与本许可声明"。删除 = 违反许可条件，MIT 授予的权利随之失效，属于侵权。
2. **赛事合规**：这类赛道普遍要求"原创性声明 + 可复现 + 答辩"。删许可证不会让代码变成你的，只会把"使用了开源代码"（可解释）升级成"隐瞒来源"（不可解释）。
3. **实际风险**：SpinalHDL 生成的 RTL 有非常强的结构指纹（`_zz_` 前缀、`spinal_port` 命名、`when_` 条件、`TrapPlugin`/`AlignerPlugin` 这类模块名、`ctrl0~ctrl5` 的流水命名）。改文件名、改变量名抹不掉这些，评委只要看过一个 VexiiRiscv 工程就能认出来。

**真正有效的做法**：保留 `THIRD_PARTY_NOTICES.md` 与版权头，把"我做了什么"写成可验证的增量。你们这一版其实有货——晚级 EQ 比较前移、移位器旁路重排、ADS retiming、布线收敛到 +0.036 ns——这些是自己的工程贡献，比"删许可证"值钱得多。

## 1. 性能：缺口到底有多大

```
目标      ticks ≤ 1,250,000,000
当前      ticks = 1,309,328,358
需减少    59,328,358 ticks（−4.53%）
折算      每 iteration 187,047 → 178,571 cycles，需省 8,476 cycles/iter
```

这不是"调个参数"的量级，是**微架构上实打实要抠掉 4.5% 的 CPI**。任何"改改综合选项"的方案都到不了。

### 1.1 第一步不是改，是测

当前 `--performance-counters=0`，等于开车不看仪表。先把计数器打开，拿到三个数：

- **分支误预测次数 / 分支总数**（决定 A、B 两项的上限）
- **L1I / L1D miss 次数**
- **发射槽空转原因分布**（load-use、结构冲突、RAW）

没有这三个数，下面所有优化都只能靠猜，改完还得靠 20 次诊断跑（3,799,461 ticks）反复试错，效率极低。

### 1.2 优化项，按性价比排序

| # | 方向 | 具体动作 | 预期收益（估算，需实测） | 风险/成本 |
|---|---|---|---|---|
| A | **分支预测器扩容** | BTB 项数与相联度上调（当前带标签 BTB，容量偏小易别名）；gshare 历史位宽加长；RAS 深度加大；再加一个 loop/branch-target 二级结构 | 误预测率降 20~35%，对应 **1.5~3%** 总周期 | 低。改生成参数 + 重跑综合，LUT 会增加 |
| B | **缩短误预测惩罚** | 现在分支在晚级（EQ 比较前移到 ctrl3→ctrl4）才确认，恢复要冲刷 2~3 级。目标：在 ctrl2 用早期旁路值做比较，把惩罚从 ~6 周期压到 ~3~4 | 每千条指令省 1~2% 周期，**合计 1.5~3%** | 中。关键路径会变长，与当前只有 36 ps 余量直接冲突，必须先解决时序 |
| C | **取指带宽** | dual-issue 每周期要吃 2 条指令（RVC 下 4~8 B），确认 fetch 是否每周期稳定吐 2 条；把 refill 从 8 beat 加深、取指行宽加大，减少跨行/跨页断流 | 结构停顿减少 **0.5~1.5%** | 中。面积 + |
| D | **LSU 侧** | load-use 延迟从 3 压到 2（需要 early load 数据旁路）；store buffer 加深，避免 store miss 阻塞后续 load；`writeback-count=8` 可再加深 | **0.5~1.5%** | 中高。改流水耦合点，容易引 bug |
| E | **发射策略** | `--max-ipc` 的调度/仲裁策略：优先把 load 与前一条 ALU 配对；对 RVC 压缩指令做对齐合并 | **0.5~1%** | 中。纯 RTL 逻辑改动 |
| F | **软件/port 层** | CoreMark 源码不能改，但 barebones port 里的 `memcpy/memset/ee_printf` 是自己的实现，可以重写成字对齐批量拷贝；`-falign-loops=16` 之类再扫一轮；CRC 表放 BRAM 固定位置 | **0.3~1%** | 低。零风险，先做 |
| G | **Cache 参数** | L1D 64 组×2 路 = 8 KiB，CoreMark 工作集约 2~3 KiB，命中率已经很高；加容量几乎无效，**不要在这上面花时间** | ≈0 | — |

**A + B 是唯一有希望单独凑够 4.5% 的一组**，其余都是补零头。而且 A、B 互相配合：预测更准 + 猜错更便宜，才可能到 5.6。

### 1.3 一个必须接受的现实

A 加 LUT、B 拉长关键路径，而当前 setup 只剩 **+0.036 ns**、面积已经**超预算 611 LUT**（16,216 vs 15,605，自评 `area fail`）。所以顺序必须是：

```
先解决面积/时序 → 再谈加预测器 → 最后压关键路径
```

反过来的话，每加一个特性都要重新打一遍时序，迭代成本会翻倍。

## 2. 性能之外的问题（这些反而更容易被扣分）

1. **面积账没平**：超预算 611，且 `area-budget.csv` 自己标了 `area fail`。要么把预算重新论证（说明 5.6 目标下面积必然上升），要么做定点瘦身（`--no-prepack` 那组实验说明打包策略对 LUT 影响很大，10179 vs 8907）。
2. **时序余量 36 ps**：这不是"通过"，是"统计上刚好没被抓到"。建议同时给一版 115 MHz 的保守位流，答辩时两条曲线（性能/稳定性）摆出来，比硬撑 120 MHz 更可信。
3. **Cache 收益无法量化**：系统没有外部 DDR，全在片上 64 KiB BRAM，Cache 命中率接近 100%，"突发传输优化"在实际负载里几乎测不出差别。要这页有说服力，得接外部存储器或构造 miss 密集负载。
4. **没有中断/异常的实测证据**：硬件有 TrapPlugin + CLINT + PLIC，但固件只跑了 CoreMark，没有 ECALL/EBREAK/定时器中断的实测日志。这是高阶任务第 2 项的**验收缺口**——功能实现了但没证明。补 3 个用例（非法指令、ecall、CLINT 定时器中断）打印 mcause/mepc，成本很低，收益很高。
5. **单次运行、无长时间稳定性**：建议加 30 分钟连续跑（循环触发 benchmark）与高低温记录。

## 3. "尽量替换掉别人写的代码"——现实路径

先说结论：**在保持 5.35 CoreMark/MHz 的前提下全量替换，比赛周期内做不到。** 双发射 + 6 级流水 + BTB/gshare/RAS + 2 路 I/D Cache + 完整 trap 的核，是从零写 6~12 个月的工作量；从零写一个 5 级单发射 RV32IMC，大概 1~2 个月，性能约 **3.2~4.2 CoreMark/MHz**，会掉 20% 以上。

合规且可行的三条路：

| 路径 | 做法 | 性能影响 | 工作量 |
|---|---|---|---|
| **① 增量自研（推荐）** | 保留派生核并如实署名；自己重写**预测器、Cache、总线仲裁、外设、SoC 顶层**这五块（这几块本来就是"可替换插件"结构），用自研版替换原插件，性能对齐或略优 | 可控，能持平 | 4~6 周 |
| ② 混合自研 | 保留 ALU/译码等基础设施，自研流水控制与 hazard 逻辑 | 可能 −5~10% | 6~10 周 |
| ③ 全自研 | 从 ISA 手册重新设计 | −20~35% | 3 个月+ |

**① 是最优解**：`rtl/core/sections/036_BtbPlugin.vh`（420 行）、`FetchL1Plugin`、`LsuL1Plugin` 都是边界清晰的独立模块，正好是可以"换心"的地方。把这三块换成自己写的版本，配合 `benchmark` 锁步仿真验证功能一致，既是真的自研，又保住分数。

而且这么做的叙事更硬：

- "预测器是我自己设计的 2 级 gshare + RAS，误预测率从 X% 降到 Y%"——可量化、可答辩
- "Cache 是我自己写的 2 路 PLRU，refill 用 8-beat 突发"——有 RTL、有波形
- 原核署名 VexiiRiscv，符合 MIT，无任何合规风险

## 4. 路线图

**第 1 周：把账算清**
- 打开性能计数器，测出误预测率 / miss 率 / 停顿分布
- 补 3 个异常中断实测用例（ECALL、非法指令、CLINT 定时器）
- 记录一版 115 MHz 保守位流的分数，作为对照

**第 2~3 周：性能攻坚（目标 5.6）**
- A：预测器扩容调参，每轮用 20 次诊断跑快速筛选，收敛后用 7000 次验证
- F：port 层 memcpy/memset 优化（零风险先吃掉）
- 每轮记录 ticks + WNS + LUT，三条曲线一起看

**第 4~6 周：自研替换 + 收尾**
- 用自研 BTB/gshare/RAS 替换 `036_BtbPlugin.vh`，锁步仿真对齐
- 自研 L1D 替换 `LsuL1Plugin`，比命中率与 CPI
- 面积瘦身、时序复核、文档与证据归档

---

## 5. 不要做的事

- 不要删版权头/许可证，不要改文件名掩盖来源（法律风险 + 答辩风险，收益为零）
- 不要为提高分数去改 CoreMark 源码（违反跑分规则，成绩作废）
- 不要靠超频拿分（CoreMark/MHz 是归一化指标，超频不提分，只掉稳定性）
- 不要在 Cache 容量上加码（工作集才 2~3 KiB，纯浪费面积）
- 不要在没有计数器数据的情况下盲调预测器参数（试错成本极高）

---

## 6. 一句话总结

**5.6 的瓶颈在分支：A（预测更准）+ B（猜错更便宜）是唯一能凑够 4.5% 的组合，但必须先把面积和 36 ps 余量这两个前置问题解决。代码归属走"合规派生 + 自研预测器/Cache/外设"的路线，既能真自研，又不掉分，也不会踩许可红线。**
