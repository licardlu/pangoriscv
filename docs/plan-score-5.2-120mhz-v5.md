## 2. 为什么这一轮必须动结构，而不是再调互锁

`docs/lessons/mistakes-log.md` §36 已经用三个失败版本（20/21、16/21、17/21）证明：
**只要"读寄存器"和"执行"在同一拍，load-use 就是结构性的**。
三种写法改变的是出错方式，不是那一拍本身。

病根在访存的位置：

```
现在：RD/EX 拍算地址 → M1 拍发请求、命中当拍回数据 → M2 拍数据才进 m_value
消费者在 EX 拍就要用 → 永远差一拍 → load_use
```

改法只有一个：**把访存请求挪到算地址的同一拍（EX）**，让 load 的数据和 ALU 结果
在**同一个时钟沿**落地。这时 load 与普通 ALU 结果没有区别，
距离 1 的旁路（`ex_value`）就能覆盖它，`load_use` 整块消失。

## 3. 模块清单（一次提交只动 `rv32_top` 的一处结构，每处独立验收）

| 序 | 模块 | 改动 | 目标 | 预计收益 | 面积 |
|---|---|---|---|---|---|
| **R5** | `rv32_top` | 访存请求从 M1 挪到 EX：`issue_mem`/LSU 端口/`mem_rsp`/`mem_wait` 全部改挂 `rr_*`；load 数据在 EX→M1 沿落进 `ex_value`；`fwd1` 放开 `!ex_load` 限制 | **分数** | −1.71 M 周期 ⇒ ≈5.95 | FF **−128**（`ex_addr/ex_sdata/ex_addr_h/ex_sdata_h` 变成死链，删掉） |
| **R6** | `rv32_top` | 寄存器堆读搬到 RD 级：`raddr*_i` 改接 `id_*`，新增 `rr_o1/rr_o2/rr_o1_h/rr_o2_h` 四个操作数寄存器，`fwd*` 的底层输入由 `rf_d*` 换成 `rr_o*` | 频率 | 把 rf 读 + 4 级 32:1 mux（§35 实测 4.4 ns）移出 EX | +128 FF |
| **R7** | `rv32_top` | 分支误预测比较寄存一拍：EX 只算 `next/taken`，比较与重定向在 M1 生效 | 频率 | 砍掉 cmp→redirect→IFU 段 | +~40 FF，误预测 +1 拍 |
| **R8** | `rv32_top` | lane1 的 ALU 挪到 M1（skip 机制），破掉 lane0→lane1 双加法器串联链 | 频率 | 砍掉第二条 ALU 链（≈2.5 ns） | +~96 FF |

顺序是硬性的：**先分数（R5），再频率（R6→R7→R8）**。
理由 = 教训 §27：目标函数是分数时 ns 一文不值；R5 单独会让 WNS 变差，
但它买到的是 5.95 分，这是这一轮唯一必须拿到的东西。

R7/R8 是**候选**，按 WNS 实测决定做不做：
R6 之后若 WNS ≥ −1 ns（即 ≥ 110 MHz），R7、R8 都不做；
否则按 R7 → R8 顺序一条一条上，每上一条复测分数，分数掉出 5.2 就回退。

## 4. 面积纪律

- 起点 17,323 / 7,680 / 3,684，预算上限 20,400 / 9,900 / 3,628
  （`docs/architecture/area-budget.csv` 的 `budget __max__`）。
- R5 净减 128 FF，R6 净加 128 FF，**合计应为 0**。
- R7/R8 允许上浮，但 LUT+FF+LUTRAM 合计不得越过 20,400/9,900 这条线。
- 每次提交信息写 `module: rv32_top ΔLUT/ΔFF/ΔLUTRAM`。

## 5. 验收顺序（每步都跑，不许跳）

1. `run_isa_e2e.py` 全 21 例 —— 基线 20/21，任何新红都回退。
2. `run_coremark_sim.py --image sim20_o2 --define RV32_DEBUG` —— 取
   `Total ticks` 折算分数，核对五项 CRC（必须仍是 `0xe9f5 / 0xe714 / 0x1fd7 / 0x8e3a / 0x4983`），
   并打印 `STALLDBG` 证明 `load_use` 真的降到 0 而不是换了名字（§33 判据）。
3. `run_pds_flow.py --freq 126 --mode synth` —— 综合 WNS + 面积。
4. 频率判收敛用 `--mode full`，且必须看 `Logic/Route` 占比（§37）：
   `Route > 70% 且 WNS > 0` 不算数。
5. 结论写 `evidence/records/optimization/<阶段>/measurement.md`，一个实现一个目录。
6. 错误经验回写 `docs/lessons/mistakes-log.md`，只收可复用的判据。

## 6. 不做什么（明确排除）

- **不**拒绝"一切包内 RAW"（§26，ISA 18/21）。
- **不**按 hit/miss 放行 load-use（§33 两次失败）。
- **不**把乘法挪出 EX 拍（§27，−5% 分数）。
- **不**用满足式宽约束测上限（§37）。
- **不**为了 ns 牺牲 `packet_load_use` 之外的配对能力。

## 7. 执行结果（2026-10-22，R5 已落地）

| 项 | 起点 P8 | R5 落地 `p9i` | 计划预计 |
|---|---:|---:|---|
| `Total ticks` | 5,073,264 | **4,518,354** | 3,352,000 |
| CoreMark/MHz | 3.942 | **4.427** | 5.95 |
| `load_use` | 1,714,576 | **0** ✔ | 0 |
| `mem_wait` | 233,091 | 1,268,139 | 未估 |
| **两笔合计** | **1,947,667** | **1,268,139** | — |
| LUT / FF / LUTRAM | 17,323 / 7,680 / 3,684 | 17,369 / 7,576 / 3,684 | 17,323 / 7,552 / 3,684 |
| 面积合计（三维相加） | 28,687 | **28,629（−58）** | ≤ 0 ✔ |

**估算为什么错了**：计划把 −1.71 M 全算成收益，隐含假设"load_use 消失 =
这 1.71 M 变成可用周期"。实际上 load 的数据本来就要等 AXI 回来，
那段时间**本来就要付**。互锁真正的浪费是

```
浪费 = 互锁停拍 − 那一刻硬件真的忙的时间 = 1,947,667 − 1,025,847 = 921,820
```

R5 把这 0.92 M 的浪费压到 0（新 `mem_wait` 1.27 M ≈ 新的 LSU 忙时间 1.27 M，
`MEMDBG presented == accepted` 证明没有重复发射），剩下的差额（−0.25 M 的净增长）
是因为从 EX 发请求会把"cache 不空闲"的等待也暴露出来，而 M1 发请求时它能被流水盖住。
最终结算 −0.56 M 周期。

**可复用判据**：**互锁计数器的读数不是它的代价**，代价是
（互锁停拍 − 该资源的真实忙时间）。估收益前先把 `LSU_PATH`/`DCACHE_PATH` 的
忙时间对一遍，否则会把"本来就要等的时间"重复计入收益，估出 5.95 这种数。

**到 5.2 还差什么（已量化，见 `evidence/records/optimization/p9-ex-mem/measurement.md` §4）**：
`mem_wait` 1.27 M = refill 自己 0.58 M + 被写通 store 队列挡住的 0.69 M。
后者是 `dcache_axi` 读写共用 `state_q` 的后果（`ST_WR_DRAIN` 占全程序 32%）。
要拿到 5.2 需要 R6 = 读写状态机解耦（预估 −0.5 M ⇒ 4.8）
加真正的非阻塞 D$（MSHR，再 −0.4 M ⇒ 5.2 以上）。本轮没有做完，不虚报。

**频率**：`run_pds_flow.py --mode synth` 在 PDS 2022.2-SP6.1 下**拿不到时序**
（`report_timing` 只接受 PnR 之后的数据库，`Flow-0044: Place & Route hasn't been run`，
脚本因此返回 exit 1）。面积是有效的；WNS 必须用 `--mode full` 才有，
而 §37 已经说明 126 MHz 约束跑不完布线。R5 对时序的影响方向：
LSU 地址端口从寄存器驱动变成 ALU 加法器直驱（变长），
`issue_mem` 多了一个 `ctrl_miss_now` 输入（复用已有的 `br_miss` 逻辑，只多一级与门）。
