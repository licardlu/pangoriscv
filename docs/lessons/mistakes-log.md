# 可复用的错误经验（现象 → 查什么 → 怎么办）

> **收录标准：只有"下次遇到同样现象能直接用上"的才写这里。**
> 一次性事实（某一轮超时了、某个编号忘了改、某文件编码坏了）**不写这里**，
> 它们属于 `docs/verification.md` 的 §2 问题台账，或 §4/§5 交接记录。
>
> **遇到问题先翻这一页**，按现象找对应小节；找到了就照"怎么办"做，别从头再踩一遍。
> 新踩的坑先问自己"这条能被复用吗"，能，才加一条。

---

## 1. 数字类：分数 / 余量 / 资源被算大或算错

### 1.1 用被截断的字段反推分数 → 虚高 6.4%

- **现象**：算出的分数比另一处算法高好几个百分点，或"和预期对不上"。
- **查什么**：固件打印的 `Total time (secs)` 与 `Iterations/Sec` 是否**整数截断**
  （CoreMark portme 里 `HAS_FLOAT 0` 时必然截断）。
- **怎么办**：分数**只用 `Total ticks`**：`iterations / ticks × 1e6`。
  截断字段只可原样展示，不得参与换算。
  实例：P16 用 `Iterations/Sec=76` 算得 2.8444，真值 2.6740，**高 6.4%**。
- **为什么可复用**：任何"下位机打印整数、上位机想看小数"的场合都会重演。

### 1.2 引了"中间报告"当最终值

- **现象**：你写的 slack 与工具摘要、或别人重跑的结果差 0.1~1 ns，两边都"通过"。
- **查什么**：`place_route/*_timing_summary_after_hold_fix.txt` 是**中间快照**；
  收尾还会有一轮优化，通常是"用 setup 换 hold"（setup 降、hold 升）。
- **怎么办**：**slack 只从 `multiseed_summary.csv` 的 `single` 行取**，并把文件名写进文档。
  实例：27 MHz 中间 15.404/0.025、收尾 15.267/0.030。

### 1.3 LUT 报数不写阶段

- **现象**：同一份实现，你报的 LUT 和别人差 100~200，双方都说"取自资源报告"。
- **查什么**：三个阶段三个数 —— synthesis（Mapping Summary）、**device_map**、后布线。
- **怎么办**：**报 LUT 必须写阶段**，且分数换算用同一个数。默认用 device_map
  （可在 `multiseed_summary.csv` 的 `Used` 行核对）。

### 1.4 百分比标错对象

- **现象**："ticks −2.43%"，实际 ticks 只降 2.35%，2.43% 是另一个量的增幅。
- **怎么办**：写成 **"A 从 x 变成 y，±z%"**，把"哪个量"写死。
  `ticks` 降幅与 `CoreMark/MHz` 增幅**不是同一个数**（互为倒数）。

### 1.5 把自算的数写进标着"原始输出"的代码块

- **现象**：读者按代码块复现，发现和工具输出不一致。
- **怎么办**：标了"原始输出"的块，**每行都必须是工具/固件一次产出的原文**；
  推导值放正文并注明"由 X 计算"。这条比看起来重要：它决定别人信不信你的数据。

## 2. 证据类：事后无法自证

### 2.1 同一个构建目录跑两次实现 → 证据被覆盖

- **现象**：交付位流存在，但它对应的时序/资源/日志目录里是**另一次**实现的产物。
- **怎么办**：**一个实现 = 一个独立目录**，跑之前先建；先跑非交付频率、最后跑交付频率，
  让交付频率的产物留在目录里。目录内容：位流+SHA、`multiseed_summary.csv`、
  `report_timing.rtr`、各阶段 log、镜像 manifest。

### 2.2 `.gitignore` 把证据文件误伤

- **现象**：本地有这份证据，仓库里没有，别人 clone 下来无法自证。
- **查什么**：`*.rtr`、`*.sbit`、`*.log`、`build/` 这类通配规则会连带证据目录。
- **怎么办**：用**退出码**判断，别看输出：`git check-ignore -q <路径>`
  → **0 = 被忽略，1 = 会入库**。（`check-ignore -v` 对**否定**规则也会回显 `!模式`，
  别把"有输出"当成被忽略。）要找回就加否定规则，如 `!evidence/**/*.rtr`。

### 2.3 证据只留在 `build/` 里

- **现象**：清理构建目录后，某个数字再也找不到出处。
- **怎么办**：关键数字**先抄进证据文件，再清理**。顺序永远是"先归档、后删除"。

## 3. 测试类：绿灯可能是假的（最危险）

### 3.1 runner 用"黑名单"判据 → FAIL 永远匹配不到

- **现象**：测试台明明打印了 `FAIL`，runner 仍报 `PASS`。
- **查什么**：日志行是否带前缀（本项目是 `# `），而判据是 `line.startswith('FAIL')`
  —— 前缀一加就永远匹配不到。
- **怎么办**：判据改成**白名单**：必须看到显式成功标记（`TEST_PASS <名字>`）；
  失败行先去前缀再匹配。本项目已抽出 `sim/tb_verdict.py` 统一处理。
- **为什么可复用**：任何"抓日志判结论"的脚本都有这个陷阱，**黑名单判据天生不可靠**。

### 3.2 "全绿"必须先证明判据能变红

- **现象**：改完代码测试全过，其实是测试根本没在检查。
- **怎么办**：挑一处改动**临时改回旧版本**，确认测试**真的会失败**，再相信绿灯。
  本项目正是靠这一步发现"新用例在旧代码下也 PASS"，进而挖出判据 bug。

### 3.3 用例的"次数"会掩盖边界缺陷

- **现象**：2-bit 饱和计数器用例全过，实机却多出 10% 预测失败。
- **查什么**：用例训了几次？**偶数次**恰好停在饱和值，**奇数次**才暴露"饱和被降级"。
- **怎么办**：验证饱和/溢出/往返计数时，**奇偶两种次数都试**。

### 3.4 测试台不等 `ready` 就撤 `valid`

- **现象**：单元测试台偶发超时；换成真实总线却正常。
- **原因**：DUT 当时 `ready=0`，请求被静默丢弃，测试台以为已受理，于是死等响应。
- **怎么办**：驱动任何带反压的接口，都要 `while(!ready) @(posedge clk);` 之后再撤 `valid`。

## 4. RTL 类：快捷路径的四个坑

> 这一类最值钱：四个坑里三个都是"为了省一拍而引入的正确性问题"。

### 4.1 同拍应答忘了读写分流 → 死锁

- **现象**：基准跑到某个 PC 后完全停摆，退休数不再增长。
- **原因**：给"读命中当拍应答"开的快捷路径没排除写；一次**缓存写命中**被当成读应答，
  CPU 以为完成就退休，而缓存还在等它的写确认 → 双方互等。
- **怎么办**：任何"同拍/提前完成"的快捷路径，**第一步先确认它对读和写都成立**；
  把 writer 排除掉再谈优化。

### 4.2 绕过某个状态 → 该状态里的副作用全丢

- **现象**：功能正常、CRC 不变、测试全绿，但**质量指标变差**（如缺失率上升）。
- **原因**：把响应路径从"停在某状态"改成"直接回空闲"，而 LRU/计数器更新写在被跳过的状态里。
- **怎么办**：绕过某状态时，**逐个检查该状态里的所有副作用**（替换策略、计数器、
  握手标志、错误码记录）。这类回归只有查质量指标才看得见。

### 4.3 提前应答的地址范围按"总线窗口"定 → 吞掉错误响应

- **现象**：访问不存在的外设地址不报 fault，程序静默跑偏。
- **原因**：乐观完成的范围用了 256 MB 总线窗口上界，而非从站**真实可服务**的 16 KiB
  物理范围；空洞里的写拿到错误响应时已退休，无法再报异常。
- **怎么办**：**乐观完成/提前应答的范围按从站物理可服务范围定**，并写成显式参数
  （如 `DATA_RAM_LIMIT`），不要复用窗口常量。

### 4.4 一个信号服务两条语义不同的路径

- **现象**：整字访问正常，byte/halfword 访问偶尔变成总线错误。
- **原因**：`ARSIZE` 被硬写成"永远整字"—— 对缓存行填充成立、对 MMIO 单拍读不成立；
  且读路径没锁存 size，用的是**上一次**的值。
- **怎么办**：一个信号服务两条路径时先问"**两条路径的要求一样吗**"；不一样就用选择器
  分开，并确认每条路径都**锁存了自己需要的字段**。

### 4.5 "延后发出"的 store 会破坏顺序语义（P19 实测失败）

- **想做什么**：store 等 B 响应占全部周期 5.1%，于是想把数据 RAM 的 store 改成
  **受理即回答 CPU + 进一条后台缓冲延后发 AXI**，让 `req_ready` 不再等 B。
- **现象**：改完 `ISA 13/15`（case 5 `store→load`、case 15 定时器中断失败）、
  `halt-reset 4/5`（scenario 2 写触发失败）。
- **根因**：把写延后，等于让"已经退休的 store"在内存里**尚未生效**。这会破坏两类假设：
  1. **store→load**：后续 load 若未命中该行，会从 AXI 读到**旧值**
     （只有缓存行做了写通合并，非命中路径没有转发机制）；
  2. **停机/复位前排空**：测试（以及真实的 halt 流程）假设"store 退休后写事务已在路上"，
     延后之后排空窗口被推后，触发点可能错过。
- **正确做法**（若要重做）：必须同时提供
  ① **store buffer 转发**（load 命中缓冲或内存前先查缓冲）；
  ② **明确的排空点**（halt/reset 时强制 drain，且 `req_ready` 的反压要覆盖缓冲满）；
  ③ 非命中读在缓冲非空时全序等待（本次做了，但不足以弥补 ①② 的缺失）。
- **结论**：这不是"少一拍"级别的改动，而是**访存一致性语义**的改动。
  在单发射、顺序退休、写通的核上，store 必须**在对后续访存可见前真正落地**，
  否则一定会踩上面两类假设。收益 5% 但代价是一次完整的内存模型重做。
- **纪律**：按"改不动就退回"处理——本次已完整回退，ISA/halt-reset 恢复 15/15、5/5。

### 4.6 改 Cache 行宽是"跨三个模块 + 一个联调 TB"的连带改动（P20 实测失败）

- **想做什么**：`if_wait` 占 8.6% 的周期，主要是 I-Cache 缺失成本。把几何从
  **32 组 × 2 路 × 32 B** 改成 **16 组 × 2 路 × 64 B**（容量仍是 2 KB、tag 宽度不变），
  顺序代码的缺失数应近乎减半，而面积不变。
- **实测过程（三次都失败，逐步逼近）**：
  1. 只改 `icache_axi`：`unit icache` 直接红 —— 测试台把 `ARLEN=7 / 8 拍 / 行尾 0x1C /
     最后拍 7` 全写死了。把期望改成跟随 `dut.LINE_BEATS` 后，又暴露
     **`line_addr` 还在按 32 B 清低 5 位**（`{tag,set,5'b0}`）→ 取错行。
  2. 改对 `line_addr` 为 `6'b0` 后，单元测试过了；但 **halt-reset 0/5、ISA 无结果**。
     根因是 `axi_ram.v` 的 `burst_ok` 写死 `len<=8'd7`（"最多八拍填一条 32 B 行"），
     **16 拍猝发被当成非法突发**。
  3. 把 `burst_ok` 放开到 `len<=8'd15` 后：**ISA 15/15 通过**，但
     **halt-reset 仍 3/5**（读触发场景 1、2 失败）—— 还有 8 拍/时序假设没有覆盖。
- **结论**：Cache 行宽**不是一个常量**，它同时牵动
  ① 位段（set/word/tag）与 `set_q/word_q/beat_q` 宽度、
  ② **行地址掩码**（最容易漏，且错得很隐蔽：数据字看起来是对的，只是取错了行）、
  ③ 猝发长度（`m_arlen`）**以及从机的猝发合法性检查**、
  ④ 所有把拍数/行尾写死的单元与联调测试。
  单点改动一定失败；正确做法是把它当**一次几何迁移**来做，四处同时改，
  并用 `dut.LINE_BEATS` 之类的参数把测试与实现解耦。
- **纪律**：三次都按"改不动就退回"处理，已完整回退，回归恢复
  `icache 1/1 / ISA 15/15 / halt-reset 5/5 / RAM 20/20`。
  保留的净收益：`tb_icache_axi.sv` 里把 `ARLEN/拍数/行尾/最后拍` 全部改成
  跟随 `dut.LINE_BEATS`（这次没吃到的收益，是下次的基础设施）。

### 4.7 扩 Cache 组数（8 KB 级）同样要过"联调 TB 这一关"

- **想做什么**：把 I-Cache 从 **32 组 → 64 组（2 KB → 4 KB）**，
  **只改组数、不动行宽**（这是 P20 失败后刻意收窄的风险面：不碰 `axi_ram` 猝发、
  不碰拍计数、不碰行地址掩码的位数）。
- **结果**：单元测试 T1–T6 全过（几何解耦生效），但
  **T7「猝发进行中被打断」超时**——因为它用的地址 `0x3000` 已被 T4 缓存过，
  命中后没有猝发可打断，`while(!(m_arvalid && m_arready))` 永远等不到。
  把 T7 换到新行 `0x0C00` 后，又出现 `bursts=12` 这类**累计计数**不匹配
  （T7 的 fork 遗留了未清的观测状态）。改动在"测试期望"这一层继续发散。
- **结论（比 P20 更具体）**：这类几何实验的真正瓶颈往往不是 RTL，
  而是**单元/联调测试里大量隐式的"地址—组—行—拍"耦合**：
  同一个地址被多个用例共用、跨用例的累计计数器、fork 分支的时序假设。
  正确做法是先做一次 **测试台重构**（每个用例独占地址区间 + 每次用例前清零观测），
  再动 RTL；否则每次都在追测试的尾巴。
- **纪律**：已回退 RTL，只保留**测试台的几何解耦**（`T1/T3/T6` 跟随 `dut.LINE_BEATS`、
  `T4` 用对 32/64 组都同组的地址、`T7` 换到独占新行），
  32 组几何下回归全绿：`icache 1/1 / ISA 15/15 / halt-reset 5/5`。

### 4.8 面积一涨，27 MHz 的 hold 就先破（P22 实测：+2.6% 性能但不可交付）

- **做了什么**：把 I-Cache 从 **32 组 → 64 组**（2 KB → 4 KB），只改组数、不动行宽。
  这次把 P21 的漏点补上了——`rd_index_q` 必须从 9 位加宽到 10 位，
  否则读回索引被截断、返回**另一行**的数据字（P21 的"数据不对但地址对"就是这么来的）。
  补上后：单元 1/1、ISA 15/15、halt-reset 5/5、RAM 20/20 **全绿**。
- **跑分确实变快**：768 迭代 ticks **284,997,892 → 277,725,088（−2.55%）**，
  IPC 0.7747 → **0.7949**，CoreMark/MHz **2.6948 → 2.7653（+2.6%）**，CRC 全同。
- **但综合不过**：LUT 13,503 → **14,485**（+982）、FF 8,507 → **9,836**（+1,329）。
  三个种子全部 **hold 违例**：seed 11 路由不收敛（2,700+ 未布通）、
  seed 23 hold **−0.017 ns**、seed 41 加强 hold 修复后反而 **−0.028 ns**。
  基线本来就只有 **+0.024 ns** 的 hold 余量，**面积一涨就先破 hold**。
- **结论**：赛题 ② 要求 `report_timing` 无失败端点，hold 破就意味着位流不可靠 →
  **这条优化不可交付，已回退**。① 赚 2.6%、③ 掉约 5%，还把 ② 弄破，不划算。
- **可复用**：本项目 **hold 是第一个被面积撞破的约束**（setup 还剩 12~15 ns，hold 只剩 0.024）。
  以后任何"加面积换性能"的想法，**先估 FF 增量**（这颗设计每 +1,300 FF 就会把 hold 打穿），
  要么同步做时序优化（少一级组合、少一片 LUTRAM），要么换不来。

### 4.9 BTB 索引散列不是杠杆（P23 实测，零收益）

- **想法**：预测器 32 项、索引 `PC[6:2]`、全 tag 比较。怀疑分支冲突导致 10.6% 的
  预测失败率，于是把高位异或进索引（零面积，只改连线）。
- **实测**：
  - `index = PC[6:2] ^ PC[31:27]`：**mispred 137,945，与基线一模一样**。
    原因：程序只占 `0x0000~0x3FFF`，高 5 位恒为 0，异或等于恒等。
  - `index = PC[6:2] ^ PC[12:8]`：ticks −0.07%（噪声），但 **mispred 反而升到 139,252**。
- **结论**：**CoreMark 在这个 32 项 BTB 上几乎没有冲突缺失**，
  10.6% 的失败率来自"冷启动 + 分支本身无规律"，不是容量/别名问题。
  要再降只能换算法（锦标赛/局部历史），那是**加面积**的方向——而 §4.8 已证明
  加面积会先破 hold，所以这条在 27 MHz 下也基本关死。
- **可复用**：**先确认"高地址位是否真的在变"**再设计散列；小程序镜像的高位恒 0，
  任何只用高位的散列函数都会退化成恒等。改完必须比较 `mispred`，
  只看 ticks 会被 `i_miss` 的随机波动骗过去。

### 4.10 综合前必须核对"开关"和"面积"，否则会拿一个假位流当真（P24 实测踩中）

- **现象**：4 KB I-Cache 改完后按 P22 的教训换种子扫 PnR，seed 7 报
  `All Constraints Met`、setup **+16.928** / hold **+0.239**、
  **LUT 7,774 / FF 2,932 / 端点 29,888** —— 看着是完美结果。
- **为什么这是假的**：2 KB 版本是 LUT **13,503** / FF **8,507** / 端点 **54,333**。
  **缓存变大而面积和端点腰斩**，物理上不可能 —— 真实原因是上一轮收尾跑了
  `set_switches.py off`，**三个开关关着，缓存根本没被综合进去**。
  那版"通过"的位流不是赛题配置，一旦烧进板子就是另一个设计。
- **怎么防**：
  1. **每次 PDS 前后都跑 `set_switches.py status`**，并把三个开关状态写进日志；
  2. **拿面积当断言**：LUT/FF/端点数应当与上一版同量级（缓存+2 KB 应是
     LUT 与 FF **上升**约 1,000）；**面积突变就要停下来查配置**，不要庆祝 slack；
  3. 把端点总数（`endpoint` 列）当作配置指纹，它比 slack 更能暴露"综合了别的东西"。
- **附带结论**：开关打开后重扫 seed **7 / 13**，hold 分别是 **−1 ps / −25 ps**，
  加上之前的 seed 11（路由不收敛）、23（−17 ps）、41（−28 ps）——
  **4 KB I-Cache 在本项目声明的约束下诚实收不了**（`pango_native.fdc` 明确
  "不添加人工 hold 不确定度"，所以不能靠加 guardband 把它凑过）。
  → ① 的 +2.6% 已在仿真验证，但 ② 过不了，**不可交付，已回退**。

### 4.11 改"LSU ↔ D-Cache 的 store 协议"必须同步改单元测试的引擎模型（P25）

- **想做什么**：`wdata_store` 占 3.8% 的周期，全是"为了递一个 store 数据多等一拍"。
  方案：让 LSU **在请求拍就把数据递出来**（`eng_w_valid/eng_w_data/eng_w_strb` 在 REQUEST 拍有效），
  D-Cache 在受理拍锁存并当拍回答，LSU 从此不再进入 `WRITE_DATA`。
  **注意这与 P19 不同**：P19 是延后 AXI 写事务（破坏顺序），本方案写事务照常发起。
- **实现结果**：两侧都改完（`dcache_axi.v` 加 `wpend_q`、受理拍锁存 + 当拍回答、
  引擎 W 改由内部寄存器驱动；`lsu_axi.v` 请求拍递数据 + 受理拍接受 B）。
- **失败点**：`unit 5/5 → 卡在 lsu_axi`，报 `Fatal: store lanes/backpressure`
  （`tb_lsu_axi.sv:75`）。原因：测试台的**假引擎**按旧协议断言
  "受理后 `eng_w_valid` 要连续 5 拍保持、`eng_w_data/strb` 要对"，
  新协议下 W 只在**受理拍**有效，测试台模型随即不成立。
- **结论**：这不是 RTL bug，而是**接口契约变了**——凡是"谁在什么时候递数据"的改动，
  都必须同时改 **单元测试里的对端模型**，否则会被判成功能回归。
  正确顺序：先改 TB 的引擎模型（在受理拍采样 W）+ 保留一个"W 迟到一拍"的负向用例，
  再改 RTL。
- **纪律**：本轮按"改不动就退回"处理，已完整回退，`unit 5/5 / ISA 15/15` 恢复。
  完整 diff 与验收清单保留在 `evidence/records/optimization/P18/measurement.md` §9。

---

- **补充（第二次尝试，按"先改 TB 再改 RTL"的正确顺序）**：
  先按新契约重写 `tb_lsu_axi.store_case`（在**受理拍**采样 W、受理拍给 B），
  同时改两侧 RTL。结果仍然失败，但**推进了一层**：
  - 第一层 `Fatal: store lanes/backpressure` → 已解决（模型改对了）；
  - 第二层 `Fatal: LSU side effect counts` → **测试台的副作用计数器**
    （`requests/writes/completions`，按 `eng_w_valid && eng_w_ready` 计 W 拍）
    在新协议下不再成立，因为 D-Cache 不再用 `eng_w_ready` 握手，LSU 也不等它。
- **教训升级**：协议改动要连带改**三样**，缺一不可：
  ① 对端 RTL 模型；② 单元测试的**激励**（什么时候采样）；③ 单元测试的**计分/断言**
  （握手次数、副作用计数、覆盖点）。只改前两样，会在第三样上被判失败。
- **纪律**：两次尝试都完整回退，`unit 5/5 / ISA 15/15` 恢复。
  这条拆成了三个独立可验证的小步（模型 → 激励 → 计数），下次按此顺序逐个子步提交。

### 4.12 构建开关是"被跟踪的文件"，`git add -A` 会把开关状态一起提交

- **现象**：两次"只改文档"的提交（`0f21436`、`c43ae79`）里，
  `firmware/code/rtl/core/soc_config.vh` 被一起提交，三个宏被注释掉：
  ```diff
  -`define CACHE_ENABLE
  -`define PREDICT_ENABLE
  -`define PERF_ENABLE
  +// `define CACHE_ENABLE
  ```
  也就是说 **HEAD 一度处于"缓存关闭"状态**，而位流和成绩是"全开"配置下产生的。
  若不核对，下一个人 `git clone` 出来综合，会得到一个**完全不同的设计**（LUT 7,774 vs 13,503）。
- **根因**：`tools/set_switches.py` 直接改**被跟踪文件**；收尾时若用 `set_switches.py off`
  还原"默认"，再 `git add -A`，开关状态就混进了提交。
- **怎么办**（三条，任选其一，推荐前两条同时做）：
  1. **提交前跑 `set_switches.py status`**，确认三开关 ON 与交付配置一致；
  2. **提交信息里写明配置**（"三开关 ON"），并在 PDS/跑分记录里带上 status 输出；
  3. 更彻底：把开关改成**构建参数**（`-D`/命令行传入），不再改被跟踪文件；
     或在 `.gitignore` 之外用一个未被跟踪的 `soc_config_local.vh` 覆盖。
- **可复用**：**任何"改文件来改配置"的工具，都是提交污染源。**
  交付前要核对的是"仓库里那份配置"，而不是"我这台机器当前那份"。

### 4.13 "仿真全绿 + 时序全过"仍然可能在板子上完全不跑（P25 实测）

- **背景**：P25（store 数据随请求拍递出）在仿真里表现很好：
  `unit 5/5 · ISA 15/15 · halt-reset 5/5 · RAM 20/20`，
  768 迭代 ticks `284,997,892 → 280,487,382`（**−1.58%，CoreMark/MHz 2.6948 → 2.7381**），
  五项 CRC 逐项相同；PDS 也是 `All Constraints Met`（setup +12.852、hold **+0.100**、
  LUT 13,468 还比原来小）。
- **板上结果**：烧进去 `done bit = 1`（配置成功），但 **串口一个字节都没有**（连跑 2 次、每次 120~150 s）。
- **隔离实验（关键）**：把位流换回 P18 那一版，同一块板、同一个串口、同一个程序，
  **立刻正常输出** `Total ticks : 284997892`。
  → **不是板子、不是串口、不是烧写流程的问题，是 P25 位流本身跑不起来。**
- **结论（必须记住）**：
  **仿真通过 + 时序收敛 ≠ 硬件可用。** 板子是最终裁判，
  任何 RTL 改动都必须走完"仿真回归 → 跑分 → PDS → **上板实测**"四段才算成立；
  只到 PDS 就宣布成功，会交付一个"纸面上全过、实际不工作"的位流。
- **本轮的处置**：整个 P25 提交已 `git revert`（`19f8b1d`），交付位流回到 P18 的
  `6C5D819CD6DB7DA00D4C874B543B49DB76D9F4572596DF3F2B67010AE657CAF65`，
  并已重新上板确认 `284,997,892` 正常打印。
- **下一步排查方向**（留给下一轮）：P25 改变了 store 的完成时机，
  最可能在**真实 AXI 从机时序**下出问题（仿真 TB 的 axi_ram 行为与板上不完全一致），
  建议先做 ILA 抓 `aw/w/b` 三通道，看第一笔 store 是否真的发出去了。

### 4.14 方案被否决后，必须回头清理"已经写进档案的成绩数字"

### 4.15 推测（待 ILA 验证）：P25 的 `wpend_q` 可能给旧事务多发一拍 W

- **背景**：P25 在仿真里跑通 768 迭代（CRC 全同），PDS 也 `All Constraints Met`，
  但**板上零输出**。仿真与板子的差异之一是**从机响应延迟**。
- **可疑时序（复核 P25 diff 后发现）**：
  ```verilog
  wire eng_w_valid = rst_n && wpend_q;          // 只看"欠一拍"
  if (wpend_q && i_w_ready) wpend_q <= 1'b0;    // 一拍就清
  ```
  `wpend_q` 在**受理拍**置 1。但受理那一拍，写引擎可能正被**上一笔写**占着
  （上一次的 `AW` 还没走完，引擎停在 `WR_PREP` 且 `i_w_ready` 为高）。
  于是下一拍 `eng_w_valid=1` 会被**上一笔的 AW** 当成它自己的 W 拍取走，
  等于给旧事务多发了一拍 W → 从机收到的 beat 数与 AW 的 len 不匹配 → 卡死或报错。
  - 仿真里 AXI RAM 响应快，几乎不会出现"受理时引擎还被占着"；
  - 板上真实 RAM 慢，这个窗口就打开了 —— 与"仿真过、板上挂"完全吻合。
- **正确修法**：把 W 拍的使能绑定到**本次事务已被引擎接收**，而不是"欠一拍"的计时器：
  ```verilog
  reg wsent_q;                                   // 本次 AW 已被引擎接收
  if (i_write_accept && i_req_ready) wsent_q <= 1'b1;
  if (eng_w_take)                    wsent_q <= 1'b0;
  wire eng_w_valid = rst_n && wsent_q;           // 只有本事务的 AW 在飞时才是 1
  ```
  同时补一条**定向用例**：让引擎在受理时正处于上一笔写的 `WR_PREP`，
  断言"不会出现第二拍 W"。
- **验证顺序（下一轮按此执行）**：
  1. 先在 `tb_unit_lsu_axi` / dcache 单元测试里构造"引擎被占"的场景（仿真可复现）；
  2. 修好后再跑 `ISA/halt-reset/RAM` + 768 跑分；
  3. **PDS 之后必须上板**（§4.13），板上看到 `284,997,892 → 280,487,382` 才算成立；
  4. 若仍无输出，再用 ILA 抓 `aw/w/b` 三通道对照（顺带补齐赛题 C02 的波形证据）。

### 4.16 批量改多个文件时，脚本中途退出会留下"改了一半"的树

- **现象**：用脚本按顺序改 3 个文件（`lsu_axi.v` → `dcache_axi.v` → `tb_lsu_axi.sv`），
  第 2 个文件的锚点不存在（因为上一次已回退，锚点随代码消失），脚本 `sys.exit` 退出。
  结果：**文件 1 已写入、文件 2/3 未动**。
  回归立刻给出 `ISA 0/15`、`halt-reset 4/5` —— 看起来像"改坏了 RTL"，
  其实是**半成品状态**。
- **为什么危险**：如果只看失败数字去调试，会去查一个根本不存在的"新 bug"；
  真正的错误是"只改了一半"。
- **怎么办（三条）**：
  1. **先把所有锚点在内存里全部校验通过，再统一写盘**（两阶段提交）。
     改脚本时最容易忽略这一点——边校验边写盘，前面几个文件就已经落盘了；
  2. 每个文件**独立提交**（一个文件一个 commit），失败时可精确回退；
  3. 脚本退出码非 0 时，**先 `git status` 看哪些文件被改了**，再决定继续还是还原。
- **可复用**：**回归突然大面积失败时，先确认"改动是不是完整落地"**，
  再怀疑逻辑。`git status` + `git diff --stat` 比读波形快得多。

## 5. 工具类：写文件把内容写坏

### 5.1 用 PowerShell 写文件 → BOM / 控制字符

- **怎么办**：CSV **只用 `csv` 模块**读写，不手拼逗号；写完校验"每行列数 = 表头列数"。

## 7. 上板类：工具、驱动、通道抢占

> 这一类是"代码全对、就是找不到板子"的地方。判断顺序永远是：
> **先分三件事** —— ① JTAG 用什么芯片 ② 板载串口用什么芯片 ③ 谁占了同一颗 USB 芯片的通道。
> 三者混在一起看，会一直在错误的方向上重试。

### 7.1 JTAG 工具"秒退、零输出、退出码空" = 缺 DLL，去查导入表

- **现象**：`cdt_js.exe` / `cdt_cfg.exe` 一启动就退出，stdout/stderr 都是 0 字节，
  `Process.ExitCode` 读出来是空。看起来像崩溃或驱动问题。
- **查什么**：用 `cmd /c` 包一层 `.bat` 拿到真实退出码（注意：`cmd /c "... & echo %ERRORLEVEL%"`
  里的 `%ERRORLEVEL%` 在解析时就展开了，**读到的是上一条命令的**，必须写成 `.bat` 文件才准）。
  实测 `-1073741515` = **`0xC0000135` = DLL 未找到**。
- **定位缺哪个**：解析 PE 导入表（可用 Python 读 DataDirectory[1]），并**递归检查被导入的 DLL 自己的导入**。
  本例：`cdt_js.exe → FTD2XX.dll → CH347DLLA64.DLL`（最后这个缺失）。
- **怎么办**：`CH347DLLA64.DLL` 就在 PDS 安装包自带的
  `PDS 安装包\驱动安装包\CH341PAR.ZIP` 里的 `CH341PAR/` 目录下，
  解出来放到 `PDS_2022.2-SP6.1\bin\` 即可。

### 7.2 打开串口会把 JTAG 踢掉（同一颗 USB 芯片的多通道）

- **现象**：单独扫链成功，一旦"先开串口再烧"就报
  `E: JtagServer-0306: No devices detected while scanning the JTAG chain`，
  且 `cfg_connect` 从 4 s 变成 40~60 s、`The cable List` 变成空。
- **原因**：下载线是一颗双通道 USB 器件（FTDI FT2232），
  **通道 A 走 D2XX 给 JTAG，通道 B 是虚拟串口**。把某个通道当串口打开会抢占整颗器件。
- **怎么办**：**烧写期间不要打开任何属于下载线的 COM 口**；确认办法是
  关掉全部串口后重烧一次，成功即证明。
  板子的**串口是另一颗独立芯片**（本例是 CP2102），打开它不会影响 JTAG。

### 7.3 板载串口芯片的驱动要单独装

- **现象**：`CP2102 USB to UART Bridge Controller` 在设备管理器里带黄色感叹号，
  `ProblemCode = 28`（未安装驱动），于是**一个 COM 口都没有**，
  板子明明在跑却读不到任何输出。
- **怎么办**：装厂商驱动（本例 `CP210x_Universal_Windows_Driver` 里的 `silabser.inf`）：
  ```
  pnputil /add-driver "<...>\silabser.inf" /install      # 需要管理员
  ```
  装好后会多出一个新 COM 口，那才是板子的串口。
- **判断顺序**：先看设备管理器有无感叹号，再数 COM 口数量，别直接怀疑固件。

### 7.4 工作目录带空格 → 工具参数被拆断

- **现象**：`E: Flow-0072: In command 'cdt_js', the argument 'Nebula\AppData\...' is not defined`。
- **原因**：`Start-Process -ArgumentList @('-work_dir',$path)` **不加引号**，
  路径里的空格把参数切成两段。用户名带空格的机器（如 `Twinkle Nebula`）必踩。
- **怎么办**：**把工具的工作目录放到无空格路径**（如 `D:\pangowork`），
  比自己改脚本拼引号更稳。

### 7.5 工具报 `Public-4023 ... run command clean` 时的正确理解

- **现象**：`cfg_assign_file` / `cfg_program` 前打印
  `W: Public-4023: Error has occurred, please run command clean before running again`，
  而脚本用 `catch` 吃掉错误后照样打印 "OK"，**看起来烧成功、实际 done bit 仍是 0**。
- **查什么**：`cfg_clean` / `clean` / `cfg_cmd clean` 这三个命令**都不存在**
  （`cfg_*` 命令全表可用 `cfg_help` 打印）。这条消息的真实含义是
  **"前一条命令失败过，状态已脏"**，要去修前一条命令，而不是找 clean。
- **怎么办**：判断烧写是否真的生效，**只看两样**：
  ① `configuration_tcl.log` 里有没有 `cfg_program succeed`；
  ② 重新扫链看 **`done bit`** 是否变成 1。不要相信脚本打印的 "OK"。
- 附带：`cfg_verify` 在这套工具/板组合上会报 `Configuration-0009: Operation error`，
  **属固有失败，不代表烧写失败**。

## 8. 提分天花板类：先算边界，再动手

### 8.1 单发射的 CoreMark/MHz 上限 = 1e6 / 每迭代指令数

- **怎么算**：`CM/MHz = IPC × 1e6 / 每迭代指令数`。
  本项目每迭代 289,296 条指令（222,179,042 / 768），
  所以 **IPC=1.0 时上限 = 1e6 / 289,296 = 3.457**。
- **含义**：想要 3.5 就必须 **IPC > 1**（双发射）或**把每迭代指令数降到 285,714 以下**。
  在单发射 + 现有编译器的前提下，**3.457 就是天花板**，任何"优化到 3.5"的说法都是假的。
- **以后**：接手先算这条边界，把目标定成"逼近上限"而不是"超过上限"，
  否则会一直做注定失败的尝试。

### 8.2 `-O3` 在小程序 RAM 上不可用

- **现象**：`region 'flash' overflowed by 5220 bytes`。
- **根因**：程序 RAM 只有 **16 KB**（`link.lds` 的 `flash` 区），
  `-O3` 的代码比 `-O2` 大约 5 KB，直接装不下。
- **怎么办**：**编译器口径这条路被硬件容量封死**，`-O2` 是唯一可用档位。
  想靠编译器提分，只能先扩程序 RAM（那是 BRAM 成本，会拖累 ③）。
- **可复用**：任何"换个编译档位就更快"的念头，先看 `.text` 是否还装得下；
  小容量裸机镜像上 `-O3` 经常是负收益。
