# v26 阶段报告 —— 把缓存阵列从"分布式 RAM 撒满全片"里救出来

> 本轮的两个改动都**不改功能语义**：一个把 I$ 数据阵列搬进 DRM，一个把阵列索引
> 从整数函数改成拼接。目标不是"再抠 1 ns"，而是**拆掉 54 MHz 以上布线永不收敛的物理根因**。
> 判据只有一条：上板 `Total ticks` 必须与交付位流逐位相同（533,875,894 / 2800 迭代），
> 五项 CRC 必须与交付一致（e9f5 / e714 / 1fd7 / 8e3a / bd59）。

---

## 1. 先把诊断钉死：不是逻辑深，是布线烂

`evidence/records/optimization/p48e-board50/report_timing.rtr`（交付位流自己的报告）：

```
core_clk  Requested 50.0000 MHz   Estimated 51.1169 MHz   19.5630 ns   WNS +0.437
Logic Levels: 23      Logic: 3.340 ns (17.1%)      Route: 16.139 ns (82.9%)
```

**19.563 ns 里 16.1 ns 是布线。** 逐跳看，几乎每一跳都是跨越大半片芯片的长跳：

| 网 | 扇出 | 延迟 |
|---|---:|---:|
| `soc/core/ls_req_addr[8]` | 144 | 1.221 ns |
| `data_cache/_N20169` | 1 | 1.209 ns |
| `u_alu/_N4420` | 2 | 1.426 ns |
| **`data_cache/N4033[0]`** | **256** | **2.500 ns** |
| `cpu/fwd1_h[4]` | 5 | 1.118 ns |

终点是 `soc/core/data_cache/data_mem_b0_*_*/ram64x1d/WADDR[0]` ——
**D\$ 分布式 RAM 的写地址**。`N4033[0]` 一根线 2.5 ns、256 个引脚，就是"阵列撒满全片 +
一根地址线串起来"的物证。

另一侧的证据：布局满意、布线崩。

| 构建 | 约束 | 摆放 slack | 布线 |
|---|---:|---:|---|
| `v25_d32_56`（D\$ 2 KB，I\$ 仍 LUTRAM） | 56 MHz | **+1.058 ns（有余量）** | 第 631 轮仍有 **~800 根网未布通**，在 797↔829 之间震荡 |
| 全片利用率 | — | LUT 25%、分布式 RAM 9%、DRM 8% | 只用了四分之一芯片 |

⇒ **利用率 25% 布不通，不可能是容量问题，只可能是局部"引脚/通道"被阵列挤爆**。
`-fanout_guide 32`（复制驱动器，`p67r50f32`）与 `-retiming`（`p66r52ret`）都已实测为负优化，
说明这条路只能靠**换存储介质**走通，不能靠工具旋钮。

## 2. 改动 1：I\$ 数据阵列 → DRM（同步读，对外时序不变）

`rtl/core/icache_axi.v` 重写（v2.0）。

**为什么 I\$ 可以先动、而且零代价**：I\$ 的阵列地址只由**请求地址**决定，与 tag 比较无关，
所以"地址必须先一拍寄存"这件事可以免费塞进流水线：

```
周期 N    : 接受 req_addr，锁存译码，驱动 bank 读地址
周期 N+1  : bank 数据 + tag 比较 + way 选择 → rsp_valid（组合）
```

旧实现的 `rsp_valid` 是"在 accept 沿装载的寄存器"，同样在**周期 N+1** 可见 ——
所以对外时序、1 拍 1 次命中的吞吐、以及必须保持组合的 `req_pair_ahead`
（IFU 用它决定预取指针 +4 还是 +8）全部不变。

- 数据阵列：`even_mem`/`odd_mem` 各 512×32，各 1 读口 1 写口（简单双口）。
- 新增 `IC_MISS_W` 一个等待拍：DRM "读写同址返回旧数据"，必须让最后一拍填线落到
  读口之后再取样（miss 路径本来就有十几个周期，这一拍不影响分数）。
- tag / valid / LRU / 后继行侧阵列**仍留分布式 RAM**：`req_pair_ahead` 必须在请求当拍回答。

**综合器认了这个结构**（`build/v26_ic_bram_syn/run.log:1487`）：

```
I: The 2 insts soc/core/instruction_cache/even_mem, odd_mem have been mapped
   one inst even_mem_bwe_2[GTP_DRM36K_E1] with byte-write-enable function
```

两块 512×32 被并成一块 512×64 的 DRM36K，用字节写使能区分两个 bank —— 正好是
"端口 A 读 even / 端口 B 读 odd，读写不同拍"的形状。

### 面积（同一综合流程、同一频率约束，4 KB I\$ + 4 KB D\$）

| | 交付（v25 表） | v26 | 变化 |
|---|---:|---:|---:|
| LUT | 17,306 | **15,946** | −1,360 |
| 分布式 RAM 单元 | **2,274** | **1,182** | **−1,092（−48%）** |
| `GTP_RAM64X1DP` | ~1,700 | 1,146 | −538 |
| `GTP_DRM36K` | 12 | 13 | +1 |
| FF | ~8,600 | 8,827 | +227 |

用 1 块 DRM 换掉 538 个单比特 LUTRAM 单元 + 262 个 LUT，是**面积和频率同向**的改动。

## 3. 改动 2：阵列索引从整数函数改成拼接（零语义变化）

`rtl/core/dcache_axi.v`：删掉 `widx()`/`didx()`。

```
widx(w,s)   = w*SETS + s                 ≡ {w, s}
didx(w,s,k) = (w*SETS + s)*LINE_WORDS + k ≡ {w, s, k}
```

写成整数表达式时，综合器把它做成**加法/选择锥**，再用这个锥的**一个输出**
去驱动全部 512 个数据阵列地址脚 —— 这就是 `N4033[0] fanout=256, 2.500 ns` 的来历。
改成拼接后，低位地址直接来自 `req_addr`（很早），**只有 way 那一位还挂在 tag 比较后面**，
这本来也是它唯一该挂的地方。

顺带把 `dread()` 的参数从 `integer` 改成 `[IDXW+3:0]`，避免同一个锥再被复制一次。

> 这一改动不改变任何索引取值，因此**不需要重新验证功能**：它只影响网表形状。
> 仍按纪律上板复核 ticks/CRC。

## 5. 下一步的决策矩阵（等本轮数据落定再走）

| 观察到的结果 | 下一步 |
|---|---|
| 50 MHz 收敛、ticks/CRC 与交付一致 | 直接上探 56 MHz（D\$ 仍 LUTRAM），验证"≤1,182 单元能不能布通" |
| 56 MHz 收敛 | 得 5.24 @ 56 MHz，再探 58/60，并把 2 KB D\$（188,888 拍，5.294）作为并列候选 |
| 56 MHz 仍不收敛 | D\$ 必须离开 LUTRAM。此时唯一零 CPI 的路是"把 AGU 提前到 RR 级、D\$ 用寄存读"，否则要付 +29,850 拍/迭代（=5.24→4.53），必须同时做第 3 发射槽才回得来（v25 M3） |
| ticks 变了 | I\$ 语义有 bug，回退改动 1，先修再谈频率 |

**禁止清单（已实测无效，不再重复）**：换 seed、重跑同一网表、三种 floorplan 形状、
`-retiming`、`-fanout_guide`。

## 6. 结果（实测，2026-10-27 16:24）：**两个改动都回退了**

`build/v26_ic_bram_50`（50 MHz 约束，4 KB I\$ 进 DRM + D\$ 拼接索引，2800 迭代镜像）：

```
core_clk   Requested 50.0000 MHz   Estimated 45.0897 MHz   22.1780 ns   WNS -2.178
Setups   TNS -3145.193   失败端点 7469 / 49086（15%）
Hold     WHS +0.006  0 失败
布线     0 根未布通，267 轮收敛（对比：56 MHz 的老网表在 631 轮仍有 ~800 根）
```

**判读（三条，按重要性）**

1. **可布性没有变差，但也**没有**变好——原先写的"假设成立"要收回。**
   分布式 RAM 单元 2,274 → 1,182（−48%）之后，50 MHz 全流程 267 轮收敛、0 根未布通；
   但交付网表在 50 MHz 只用 114 轮就收敛了。**50 MHz 本来就能收敛**，
   所以这一次只证明"搬进 DRM 不会破坏可布性"，**不构成"DRAM 改善可布性"的证据**。
   要证明那件事，必须在 55/56 MHz 上看它能否收敛（本轮没做到）。
2. **但最终 slack 反而差 −2.6 ns，失败端点 7,469 个。** 摆放阶段是 **+1.320 ns（有余量）**，
   布线之后掉到 −2.178——再次复现 `performance-analysis` §6.2 的"摆放乐观模型"，
   以及"50 MHz 只是布线分布的中位数"（本族 19.3~21.5 ns）。
3. **新的最差路径不再是 D\$，而是乘法器**：
   ```
   ex_valid -> alu_y[20] -> fwd1_h[20] -> u_mul_h/N17_m1 (PO->P 1.969 + net 2.850)
            -> u_mul_h/N17_m3 (PO->P 1.608) -> prod[52] -> ex_value_h[20]
   Logic 7.859 ns (36%) / Route 13.787 ns (64%)      Slack -2.178
   ```
   乘法器单独就占 **9.9 ns**（1.969+1.362+2.850+1.608+1.362+0.719）。

**动作**：两处改动全部 `git checkout` 回退。理由不是"没收益"，而是**不能用一次抽样去替换
一份已经 19.355 ns 的交付网表**（`performance-analysis` §6.2 的结论），而且第 3 条给出了
一个新的、比缓存更值钱的目标：**乘法器**。下一轮（v27）只做那一件事。

**同时记下一条工具事实**（省下一次踩坑）：综合报告 `apm_drm_lutram_utilization.log` 会直接
列出每个 APM 的 `Cascade / X Size / Y Size / P Size`，不用猜哪几块被串成了级联——
v26 里 `u_mul_h` 是 `N17_m1`(24x17, CPO>>24 → m2) + `N17_m2`(17x9) + `N17_m3`(24x16 → m4)
+ `N17_m4`(16x9)，两条级联都来自同一个 33x33 有符号乘法。
