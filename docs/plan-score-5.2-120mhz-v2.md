### 1.1 目标差多少

| 指标 | 现在 | 目标 | 差距 |
|---|---:|---:|---:|
| CoreMark/MHz | 3.8557 | ≥5.2 | 周期 −25.9%（259,358 → ≤192,307） |
| 每拍周期 | 37.037 ns | ≤8.333 ns | 路径要短 **3.9 倍** |
| IPC（指令数不变时） | 1.115 | ≥1.504 | +35% |

两项必须同一份位流同时成立：**只加频率不降周期，分数不动；只降周期不上 120 MHz，频率项不动。**

### 1.2 关键路径在读什么（决定"能不能靠改约束解决"）

39 级逻辑的真实构成（同一条路径串起来的）：

```
ID/EX 寄存器
 → EX 组合乘法（4 个 APM 串接，约 6.3 ns）
 → ALU 结果 → lane1 操作数
 → 分支判定 jump_flag（fanout 32）
 → actual_next_pc_h → 与预测目标 32 位比较（4 级）
 → pred_miss → redirect_valid（fanout 156，走线 0.82 ns）
 → id_ex 冲刷（fanout 245）
 → if_id take2（fanout 57，走线 1.28 ns）
 → if_id 写使能链（fanout 55，走线 1.41 ns，再串 7 级 CECO）
```

三个结论：

1. **组合乘法必须切**（6.3 ns 占 19%）。
2. **"重定向 → 冲刷 → 写使能"是一条 4 级高扇出链**，靠调约束、换种子都救不回来，只能改结构（epoch 标记代替全局 flush 扇出）。
3. 剩余 20 级是"取指/译码/寄存器读/ALU/访存"挤在同一拍——**这是 4 级流水的固有形态，必须加流水级**，不是"优化"能解决的。

### 1.3 GPT-6 未提交的 W 提交级实验：已判定死路

| 项 | 结果 |
|---|---|
| ISA 回归 | **21/21 PASS**（本轮实测） |
| CoreMark 20 迭代 | 7,914,282 cycles = **395,714 cycles/iter, IPC 0.865** |
| 对比基线 | 259,358 cycles/iter → **慢 52.6%** |
| 结论 | 功能正确但吞吐崩了：W 级把所有完成/写回/重定向都串行化，X1 必须等 W |
| 处置 | 归档到分支 `exp/w-boundary-gpt6`（保留证据），**不作基线、不继续** |

它唯一的价值是证明了"提交边界"这个思路必须做，但不能做成"整包等到 W"。新架构用 **epoch + 逐级 valid**，让 W 只做架构提交，不参与完成判定。

## 3. 流水线（8 级，目标 8.333 ns/级）

| 级 | 名称 | 主要工作 | 预算（组合级数） |
|---|---|---|---:|
| F | IFU 输出 | 取指队列出包（复用 `ifu_axi`），预测后继 PC | 复用 |
| S1 | ID | 两槽译码、配对判定、非法指令、依赖检查 | ≤8 |
| S2 | RR | 寄存器读（LUTRAM 同步读）、操作数选择、立即数 | ≤6 |
| S3 | EX | ALU×2（并行）、分支比较与目标、AGU、乘法输入寄存 | ≤8 |
| S4 | M1 | D-Cache tag 读、乘法第 1 级 | ≤6 |
| S5 | M2 | D-Cache 数据读 + 路选择 + 对齐、乘法结果 | ≤7 |
| S6 | WB | 写回、旁路源、异常判定（寄存） | ≤6 |
| S7 | CT | 架构提交：CSR、重定向、写寄存器、预测训练 | ≤6 |

关键设计选择（每条都对应一个已踩过的坑）：

1. **epoch 代替全局 flush**：重定向只 `epoch <= epoch+1`，各级 `valid = valid_q && (epoch_q==epoch)`。
   消除 fanout-156/245 的冲刷链（§1.2 第 2 条）。
2. **乘法两级**：输入寄存 + DSP 输出寄存；`mul` 结果从 M2 旁路，避免 6.3 ns 串在 ALU 后。
3. **分支在 S3 解决，重定向在 S4 生效**：代价是误预测惩罚 3–4 拍，但路径里不再有"比较→冲刷→取指写使能"。
4. **访存 1 端口/拍**：一包最多 1 条 load/store；地址在 S3 算、S4 tag、S5 数据。
5. **写回端口 1 个 + 1 项写队列**：两槽同拍写不同寄存器时，年轻槽入队下一拍写；旁路覆盖 RAW，不产生停顿。
6. **不允许"lane1 依赖 lane0 结果"配对**：那等于一拍串两个 ALU，直接毁掉 8.333 ns。

## 4. 存储系统（同时服务 IPC 与频率）

| 项 | 现状 | 新方案 | 目的 |
|---|---|---|---|
| I-Cache | 4 KB 2 路，分布式 RAM | **8 KB 2 路，BRAM**（32 B 行，critical-word-first） | 命中率↑、LUT↓、同步读 1 拍 |
| D-Cache | 4 KB 2 路，写通 | **8 KB 2 路，BRAM，写通 + 4 项写缓冲** | CoreMark 的 list 初始化是写密集 |
| 数据 RAM | 16 KB 被推断成 2,048 个 LUTRAM（面积账 §12.2 的历史包袱） | 改**寄存器地址 + 寄存器输出**，落 DRM | LUTRAM −2,000 站点，帮助 ③ 与 hold |
| 程序 RAM | 32 KB BRAM | 保持 | `-O3` 可装 |

面积账：4 个 DRM → 最多约 20 个 DRM（器件 100K LUT 级，DRM 充裕），
LUT 侧因为"LUTRAM → BRAM"应当**净下降**；这是三项评分里 ③ 的加分项，
不是用面积换性能。

## 5. IPC 预算（把 1.504 拆成可验证的账）

以 20 迭代窗口为准，259,358 → 192,307 cycles/iter，需要回收 **67,000 周期/迭代**。
按已知瓶颈桶分配，每项都有独立验证手段：

| 动作 | 依据 | 预期回收 | 验证 |
|---|---|---:|---|
| 双发射配对率 1.115 → 1.35 | 配对规则放宽（预测目标配对、branch+mem） | ~40,000 | `CORE_SUMMARY pair=`、cycles |
| 重定向 3.5 拍 → 2 拍 | S3 解决 + epoch + IFU 直接收 redirect PC | ~10,000 | `mispred`、cycles |
| 第二槽访存（已有雏形） | 一包内 ALU+mem / branch+mem | ~8,000 | `cycles` |
| load-use 2 拍 + 写缓冲 | 访存重叠 | ~6,000 | `cycles` |
| I/D-Cache 8 KB + 预取 | 缺失率下降 | ~3,000 | 缺失计数 |

这些数**不是承诺**，是分配；每阶段实测后重排。若某项实测 <50% 预期，立刻回退并换方向。

## 8. 度量口径（写文档时必须一致）

- 分数只用 ticks：`iterations / total_ticks × 1e6`；禁止用整数截断的 `Iterations/Sec`。
- 周期/迭代 = `total_ticks / iterations`；IPC = `retires / cycles`（同一窗口）。
- LUT 必须写阶段（synthesis / device_map / post-PnR），默认 device_map。
- 仿真数字只能报"仿真口径"，上板数字必须附位流 SHA 与串口原文。

## 9. 度量口径：20 迭代窗口含固定初始化，必须用"斜率"算每迭代成本

`tb_coremark_uart` 打印的 `cycles` 是从复位到报告打印**全程**，其中 CoreMark 的
`core_list_init` 等一次性初始化约占 **1.88 M 周期 / 6.1 万条指令**。两个数据点定标：

| 迭代数 | cycles | retires | 来源 |
|---:|---:|---:|---|
| 20 | 7,033,225 | 6,819,652 | 本轮实测（tag `score-3.8557-e2`，镜像 `indep20`） |
| 1152 | 298,780,717 | — | 板上交付 |

解 `cycles = a + b×iter`：**b = 257,727 周期/迭代**，a = 1,878,685。
指令数同样解出 **287,913 条/迭代**（与历史 289,296 一致，差 0.5%）。
→ **IPC = 287,913 / 257,727 = 1.117**，与文档口径吻合。

因此：

- 5.2 对应的**边际**周期上限是 **192,308 周期/迭代**（不是 192,308 除以某个窗口）；
- 同一个镜像的 A/B 可以直接比 `cycles`（固定开销相同），但**不同迭代数的两次跑分不能直接相除**；
- 每阶段验收都用同一条 20 迭代镜像 `indep20` 或 `sim20_O2`，只比 cycles 与 CRC。

1. 把 6 个 stage register 的 `valid`/`payload` 使能画成一张表：
   每级"谁能让它停"只能有一个来源（本级等待 / 上级停），两处都写就会丢或重。

### 11.1 分级使能已落地，剩余一个 load 死锁（下次从这里接）

流水线使能已改成"每级只有一个停因"：
`hold_ex = load_use||div_wait||mem_wait||trap_wait`（EX 与 RR 停）、
`hold_m1 = mem_wait||trap_wait`（M1 停）、`hold_wb = trap_wait`（M2/WB 停）；
被停级的下一级进气泡；提交用 `w_done_q` 保证只发生一次。

**注意**：`load_use` 不能让 M1 也停——停 M1 会让 load 的响应在 `done_ready=1` 下被 LSU 吃掉，
消费者随后永远等不到数据，形成死锁。这是本轮最大的一个结构性教训。

**当前残留**：用例 2 在 0x210（连着的第二条 load）之后停住，退休 6 条后不再前进。
下次第一件事：在同一拍打印
`op_valid / op_ready / is_store / done_valid / done_ready / mem_issued_q / ex_load / hold_m1 / hold_ex`，
判断是"请求没发出去"还是"响应回来了没被接住"。已知 `mem_issued_q` 的置位/清零优先级
改过一次（清优先），若仍卡住，优先查 `lsu_axi` 的 `fast_issue` 在 `op_valid` 只持续一拍时
是否漏掉了接受。

### 11.2 进展：test 2 只剩最后两条指令（rs2 读成 0/X）

本轮修掉两个真 bug：
1. **同拍完成**：D-Cache 命中时 `op_valid` 与 `done_valid` 可以同拍，只看 `mem_issued_q`
   会把这次响应判成"不是我的"→ 死锁。门控改成 `done_valid && (mem_issued_q || mem_accept)`。
2. **符号扩展极性反了**：`load_unsigned=1` 是**零**扩展，`lb/lh` 必须给 0、`lbu/lhu` 给 1。
   原来写反，导致 `lbu` 返回 `0xffffffcd`、`lb` 返回 `0xcd`。

结果：test 2 的 x11–x17 全对（`0x8000abcd / 0x8000abce / 0xcd / 0xffffffcd / 0x8000 /
0xffff8000 / 0x12345678`）。**只剩最后两条**：
- `add x18, x17, x13` → x18 = X
- `sub x19, x17, x11` → 得到 `0x12345678`，等价于 **rs2（x11）读成 0**

共同点：两条都是"紧跟在 load 之后的 ALU，rs2 来自更早的 load 结果"。下一步查
`rf_d1 / a1_d / rr_op2` 这条第二读口的路径（x0 强制与写穿透都用 `a1_d`，
若 `a1_d` 在 load-use 停顿时比 `q1` 晚一拍，就会把一条老指令的 rs2 当成 x0 → 读 0）。

| 新核 P1（单发射 6 级） | 8,744,325 | 6,799,260 | **0.778** |

指令数一致（差 0.7%，来自 init 循环读 mcycle 的时序差），说明**功能等价**；
周期多 18.5%，原因是 6 级流水 + **分支在 EX 解析**的冲刷代价，加上
`load_use`/访存等待的逐条停顿。预测器反而更好（mispred 124,350 vs 137,950）。

**结论（决定了 P2 的形态）**：5.2 需要 192,307 周期/迭代、约 287,913 条指令/迭代
⇒ **IPC 必须到 1.50**。单发射的物理上限是 1.0，所以：

1. **P2 双发射不是优化项，是必要条件**——没有它，5.2 在数学上不可达；
2. 单发射阶段还得先把"每条指令的停顿"压下去（P1.x），否则双发射的收益会被停顿吃掉；
3. 目标分解：双发射把 IPC 从 0.78 抬到 ~1.5，靠的是配对率 ~65% 加上把
   `load_use`/重定向代价摊薄到两个槽。

### 12.3 P2 开工前的三件事（按顺序，都有硬判据）

1. **停顿归因**：用 `tb_coremark_uart` 已有的 `PROGRESS`/统计口，把
   `hold_ex`(load_use/div/mem_wait) 与 `redirect` 各占多少周期量出来，
   先做掉占比最大的那一项（预计是 load-use，因为 CoreMark 的链式列表操作密集）。
2. **取指带宽**：单发射前端每拍只能吃 1 条（`fetch_ready2` 接 0）。双发射要求
   每拍能取到 2 条，IFU 队列必须成对弹出——这是 P2 的第一个结构改动。
3. **寄存器堆**：4 读口已经就位（`ra2/ra3` 现在接 0，P2 直接接第二个槽），
   写口 1 个 + 一个写队列（第二个槽的写延后一拍，由旁路覆盖可见性）。

### 12.4 停顿归因（实测，8,744,325 周期 / 6,799,260 条）

| 计数器 | 值 | 占周期 |
|---|---|---|
| `id_stall`（RR 级被占住但停发） | 1,367,338 | 15.6% |
| `no_retire`（该周期没有提交） | 1,944,774 | 22.2% |
| `mispred`（预测失败次数） | 124,350 | — |
| `lsu_nonidle`（LSU 忙） | 676,939 | 7.7% |
| EX 里的 load / store / 其他 | 193,172 / 4,527 / 1,317,616 | — |

按 6 级流水、每拍取 1 条的代价模型核对：
`124k 次预测失败 × ~7 拍 ≈ 0.87M` + `访存额外等待 ~0.3M` + `load-use ~0.08M`
≈ 1.25M 多余周期，与 8.74M − 6.80M = 1.94M 同量级（差额是流水线填充/排空的边界效应）。

**⇒ P2 的设计输入**（两项都必须做，缺一项都到不了 1.5）：

1. **配对取指**：前端每拍 2 条，重定向后的重填从 6 拍降到 3 拍——
   直接把 0.87M 的预测失败代价砍半，这是"改一个地方同时提升 IPC 和降惩罚"的唯一动作；
2. **配对执行**：ALU+ALU / ALU+load / ALU+store / ALU+branch 四类组合覆盖
   CoreMark 的主要指令混合（实测 ALU 类占 EX 的 87%，load 13%），
   目标配对率 ≥60%。

**暂不做**（按计划书原顺序，先保 P2 结构正确）：
BTB 加深/RAS（P3，治 124k 次失败本身）、8 KB BRAM Cache（P4，治访存等待 0.3M）。

## 13. P2a 落地：双发射（ALU + 分支/jal 进 lane1）

### 13.1 结构

| 项 | 做法 | 理由 |
|---|---|---|
| lane1 装什么 | 纯 ALU（含 lui/auipc）+ 分支/jal | 见下 |
| lane1 不装什么 | 访存、CSR/系统、mul/div、jalr、非法指令 | 一次性删掉 lane1 触发 trap 的整类问题 |
| 对齐保证 | 分支/jal 进 lane1 要求 `imm[1]==0` | 目标恒 4 字节对齐 ⇒ 不可能触发未对齐陷阱 |
| 寄存器堆 | 换成交付核的 `regs`（4 读 **2 写**） | ~70% 配对率下每拍 1.7 次寄存器写，单写口阵列吸收不了；两个写口无法用分布式 RAM 搭 |
| 旁路 | 每级比两个通道，lane1 更年轻优先；WB 那一级由 `regs` 的写穿透承担 | 距离 3 不需要单独一级，正好抵消新增比较器 |
| 取指 | `fetch_ready2 = fetch_ready && pair_ok`；成对弹出时 `pc_q <= fetch_predicted_next_pc_hi` | IFU 用 `request_pc` 校正队列头，指针必须落在 lane1 的预测后继上 |
| 提交 | lane0 走写口 1、lane1 走写口 2；lane0 trap 时 lane1 不提交 | "只提交更老的前缀"退化成一条门控 |
| 计数器 | `minstret` 每包 +1/+2；`arch_next_pc` 取包尾的后继 | 否则 CoreMark/MHz 的口径会错 |

### 13.2 实测（同一镜像 `sim20_O2`、同一 TB、同一命令）

| 版本 | 周期 | IPC | 预测失败 | CRC |
|---|---|---|---|---|
| 旧核（交付基线同族） | 7,377,786 | 0.928 | 137,950 | 0x4983 |
| 新核单发射 P1 | 8,744,325 | 0.778 | 124,350 | 0x4983 |
| 新核双发射（仅 ALU 进 lane1） | 7,633,654 | 0.891 | 108,925 | 0x4983 |
| **新核双发射（+分支/jal 进 lane1）** | **7,348,329** | **0.931** | **68,060** | **0x4983** |

配对率 33.6%（1,722,860 / 5,119,000 包）。ISA：单发射门禁 **21/21**；
默认门禁（要求双发射覆盖计数）17/21，缺的 4 例全部需要 **lane1 访存**。

### 13.3 下一步（按收益排序）

1. **lane1 访存（P2b）**：`lw;lw;add;add;bne` 这类热循环现在只能配到 2/4，
   把 load 放进 lane1 需要解决"每包最多一个访存"的端口仲裁与
   lane1 load 的写回数据通路——这是把配对率推向 60% 的唯一路径，也是默认门禁
   18/19/20 三例的必要条件。
2. **lane0 是控制转移时也允许配对**：目前 lane0 是分支/jal/jalr 就单发，
   而"分支 + 后续指令"在每 4–5 条里就有一次。
3. 预测器加深/RAS（P3）治剩余的 68k 次失败；BRAM Cache（P4）治访存等待。

## 14. P2b：lane1 承载 load/store，并量出真正的瓶颈

### 14.1 做了什么

| 项 | 做法 |
|---|---|
| 配对 | lane1 允许 load/store；**每包最多一个访存**（LSU 单端口），两通道同时访存则拆包 |
| 端口仲裁 | `mem_from_h` 决定 address/data/size/unsigned/rd/pc 全部取自哪一通道 |
| lane1 未对齐 | 在 **EX** 判掉，`issue_mem` 不置起（case 20 检查"不得发请求"） |
| lane1 总线故障 | 走 M1→M2→WB 的 `m_trap_h`，WB 合并：`mepc/mcause/mtval` 取 lane0 优先、否则 lane1；lane1 不写回、不计数 |
| 死锁修复 | `mem_issued_q` 原来只看 `m_is_mem`，lane1 的访存永远置不上"已发起" → 响应被当成无主的丢弃 → 永久等待 |

### 14.2 结果

| 版本 | 周期 | IPC | 配对率 | CRC | ISA 默认门禁 |
|---|---|---|---|---|---|
| P2a（lane1=ALU+分支） | 7,348,329 | 0.931 | 33.6% | 0x4983 | 17/21 |
| **P2b（+lane1 访存）** | **7,273,094** | **0.941** | **39.0%** | **0x4983** | **20/21** |

默认门禁只剩 **case 21**（要求"lane0 是控制转移时 lane1 仍能提交"，即分支与其后继配对）。

### 14.3 关键结论：配对率已经不是瓶颈

`PAIRGAP` 实测（P2a 时的构成）：配对 177 万 / 取指端无对 220 万 / lane1 不合法 86 万
（其中访存 76 万）/ 包内 load-use 25 万 / lane0 独立 17 万 / 完全没取指 209 万。

把 lane1 访存那一项（76 万）做掉之后，**周期只降了 7.5 万**。原因：
一个 lane1 的 load 配对成功后，这个包仍然要在 M1 等 LSU 的 ~2.8 拍，
配对省下的是取指/译码/发射的槽位，不是访存延迟。
换句话说：

1. `no_pair=220 万` 不是"错过的配对机会"，而是**取指带宽只有约 1 条/拍**——
   6.84M 条指令在 1 条/拍的前端上最快也要 6.84M 周期，而我们现在是 7.27M。
   **前端已经接近利用率上限。**
2. 真正的两个杠杆变成：
   - **IFU 每次响应供 2 个字**（8 字节对齐取指），让 `q_pair` 常为 1；
   - **LSU 命中当拍返回**，把 `mem_wait` 造成的 ~1.4M 停顿周期吃掉。

### 14.4 当前折算

用交付基线反推的初始化固定开销 2.19M 周期：
`(7,273,094 − 2,190,000)/20 = 254,155` 周期/迭代 → **约 3.94 CoreMark/MHz**
（基线 3.8557）。5.2 需要 **192,307** 周期/迭代、IPC **1.50**；现在 IPC 0.941。

⇒ 下一阶段（P2c/P4）的顺序由数据决定：先做"取指成对供给"和"LSU 命中零等待"，
这两项都在 ~1.4–2.2M 周期量级上；预测器（剩余 64k 次失败 ≈ 45 万周期）排在其后。

## 15. P2c：取指成对供给（IFU 一行改动），瓶颈彻底锁定在停顿

### 15.1 改了什么

IFU 原来的"对"定义是 `q_pair[head]`——只有当**两个字来自同一次总线响应**时才算一对。
但队列本身就是一条指令一个 entry（两字推送会把第二字单独再存一份），
所以正确的定义是"**队列下一条就是连续的 pc**"：

```verilog
wire pair_adj = (count_q > 1) && (q_pc[head+1] == head_pc + 4) &&
                (q_pred[head] == head_pc + 4) && !q_fault[head+1];
```

`q_pred[head] == head+4` 保留了架构规则（首字被预测为顺延时第二字才有效），
故障字排除在外，使共享的 fault 字段保持真实。

### 15.2 实测

| 版本 | 周期 | IPC | 配对率 | 预测失败 | CRC |
|---|---|---|---|---|---|
| P2b | 7,273,094 | 0.941 | 39.0% | 63,878 | 0x4983 |
| **P2c（成对供给）** | **7,168,871** | **0.962** | **46.1%** | **53,270** | **0x4983** |

配对次数 +13%（192 万 → 218 万），**周期只降 1.4%**。

### 15.3 结论：停顿是唯一的大头，且已经量化

`ret_cyc=3.82M`（有提交的周期）/ `no_ret=1.48M`（完全没有提交）。
4.72M 个包用了 7.17M 周期 → **每包 1.52 拍**，其中约 2.45M 周期是停顿与重填。

`lsu_nonidle=676,939` / 24.6 万次访存 = **每次访存约 2.8 拍**。
这就是全部原因：每次 load 都在 M1 挡住流水线 2–3 拍，而 CoreMark 每 28 条指令就有一次访问。

⇒ **P4（访存延迟）是唯一还剩的大杠杆**，且必须动 Cache/LSU：
命中要在"接受请求的同拍"返回数据（现在要 2–3 拍），miss 才走多拍路径。
按 2.8 拍降到 1.2 拍估算，可省 `24.6万 × 1.6 ≈ 39万` 周期，再叠加
`load_use` 因数据更早到而减少的停顿。

### 15.4 折算（初始化固定开销按基线反推 2,190,626 周期）

`(7,168,871 − 2,190,626)/20 = 248,912` 周期/迭代 ≈ **4.02 CoreMark/MHz**
（交付基线 3.8557）。126 MHz 下约 **506 CoreMark**；5.2 需要 655（= 5.2 × 126）。
差距仍在 IPC：现在 0.962，需要 1.50。

## 16. P4 诊断：访存停顿的真正原因不是容量，是"请求放大"

### 16.1 先否掉一个假设（容量）

D-Cache 是 32 组 × 2 路 × 32 B = 2 KiB，CoreMark 的工作集（`TOTAL_DATA_SIZE=2000`
的 state 缓冲 + 1 KiB 矩阵 + 链表 + 栈 ≈ 3.5–4 KiB）比它大，所以第一假设是容量抖动。
把 `SETS` 从 32 改成 128（8 KiB）实测：

| 配置 | 周期 | refills | IPC |
|---|---|---|---|
| 2 KiB | 7,168,871 | 110,656 | 0.962 |
| 8 KiB | 7,079,064 | 106,440 | 0.974 |

**容量翻 4 倍只换来 1.25%**，refill 几乎没降。⇒ 容量不是原因，已回退到 2 KiB（面积纪律）。

### 16.2 加上计量后的真正结论

在 `dcache_axi` 里加 `DC_DBG` 计数（`ifdef` 包裹，不影响综合）：

第一版计数用的是"`req_valid && req_ready` 为高的**周期数**"，当 `ready` 是电平且
`valid` 被保持多拍时会重复计数，所以改成**计边沿**（一次新的呈现算一次）：

```
DCDBG rd_new=1,093,268  hit=982,886  miss=110,382  reload=106,208  wr_new=331,519
```

三条读数：

1. **命中率 90.0%**（98.3 万命中 / 11.0 万缺失）——缓存本身工作正常；
2. **`reload/miss = 96.2%`**——几乎每次缺失都是"同一行紧接着又缺"，
   这是**同一笔请求被重复接受**的特征，不是真的替换；
3. **请求放大（边沿计数，真实）**：1,093,268 次读请求对 24.5 万次 load = **4.5 倍**；
   331,519 次写请求对 1.15 万次 store = **29 倍**。

`EX_SPLIT id_stall=1.86M` 与 `EX_OCCUPANCY lsu_nonidle=0.92M` 正好对应"每笔访存被
反复走一遍发射/接受"的代价，这就是 1.7M 周期停顿的来源。

### 16.3 下一步（已锁定，不再猜）

在 **LSU↔D-Cache 的请求通道**上加一对计数器：核心侧 `op_valid && op_ready` 的次数 vs
缓存侧 `req_valid && req_ready` 的次数，一次运行就能看出放大发生在哪一侧。
重点检查三处（都是"保持型"握手）：

- `lsu_axi.eng_req_valid` 在 `fast_issue` 下是否随 `i_req_ready` 撤销；
- `dcache_axi.req_ready` 在 `ST_BYP_RESP`/`ST_WR_DRAIN` 下对**同一笔**请求是否会二次拉高；
- 核心 `issue_mem` 的 `mem_issued_q` 在这些一次性响应（`accept_hit`）之后是否被清零，
  导致同一笔 op 再次发起。

修好放大之后，按 4.5× 折回估算，`id_stall` 至少能砍一半（~0.9M 周期，12%）。

> 注：`DC_DBG` 探针保留在 `rtl/core/dcache_axi.v`（`ifdef` 包裹，综合时不存在），
> 下一轮直接 `+define+DC_DBG` 就能接着量。

## 17. §16 的结论作废：请求放大不存在，真正的账目是这一张表

**纠正**：§16 说"缓存请求放大 4.5×/29×"，那是用错了分母——193k 是 EX 阶段的**周期数**，
不是访存指令数。加了核侧计数器后真相是：

```
MEMDBG presented=1,810,297  accepted=1,810,297  retired_mem=1,810,297
```

`presented == accepted == retired_mem` ⇒ **核对外发起的次数等于退休的访存指令数，
一次不多**。旧核在同一镜像上是 `rd_new=1,034,777 / wr_new=318,351`，同一个量级。
所以 LSU 和 D-Cache 的握手没有问题，§16 的三个嫌疑点全部排除。

**7,168,871 周期的真实分解**（`STALLDBG`，一个桶/原因，互斥，合计对上总周期）：

| 项目 | 周期 | 占比 | 含义 |
|---|---|---|---|
| `accept` | 4,858,312 | 67.8% | 正常接受一个包（4.72M 包） |
| **`load_use`** | **1,630,819** | **22.7%** | EX 里被 M1 的 load 挡住（含 miss 等待） |
| `starve` | 454,193 | 6.3% | 取指端没有指令 |
| `mem_wait` | 223,076 | 3.1% | M1 等访存（无依赖消费者） |
| `div` | 2,433 | 0.03% | 除法器 |

`EX_SPLIT` 佐证：`ex_busy=2,007,087` 里 `load=274,336 / store=10,197 / other=1,722,316`，
`other` 就是"被一条更老的 load 挡住"的周期。`lsu_nonidle=918,752` 说明真正在等
LSU 的只有 92 万拍，所以 **1.63M 里大部分是"紧跟 load 的那一条依赖指令"的固定代价**。

**实测容量验证（用可靠计数重做）**：`SETS` 32→128（2 KiB→8 KiB）
`miss` 110,382→106,458、周期 7,168,871→7,079,064（**1.25%**）。容量确实不是杠杆，
已回退到 2 KiB。

**踩过的坑（已回退，详见 `mistakes-log` §25）**：想用 `load_value` 直接旁路到 EX
省掉这一拍，收益只有 1.7%，却让 `crclist/crcstate` 算错——**ISA 21 例没抓住**。
判据：动 load-use 等于动流水线老化关系，必须连带重审 `kill_young`/`br_miss`，
而且必须用 CoreMark 的 crc 验收，不能只看 ISA。

**⇒ 5.2 的路还差什么（诚实结论）**
两点定标（20 迭代 7,168,871 / 40 迭代 12,451,519）：边际 **264,132 周期/迭代、
288,292 指令/迭代 → 边际 IPC 1.09**。5.2 要 192,307 周期/迭代 ⇒ **边际 IPC 1.50**，
即还要 +37% 吞吐。这不是"再调一个参数"能到的量级，需要：
1. 配对率 46%→65%+（`l0_alone` 450k + `pkt_lduse` 722k 两块结构性损失要动）；
2. load-use 的固定代价（要按 §25 的判据成套改，不能只加 mux）；
3. miss 延迟（110k 次 × ~13 拍，做 critical-word-first 可省一半）。

**优先级决定**：先把 **126 MHz 时序**做出来（P5）。理由很直接——现在跑分 4.02 CM/MHz，
把频率从 27 MHz 提到 126 MHz 就是 4.7 倍；而时序没过，再高的 IPC 也上不了板。
P5 做完再回来做上面三项。

### 18.2 时序：失败，且差得很远

周期 7.94 ns 而最差 slack −8.0 ns ⇒ **关键路径约 16 ns，等价上限约 63 MHz**。
路由器一直不收敛（每轮只修 700~900 条网）就是因为它在追一个物理上达不到的目标；
继续跑只会烧机时，已终止。

### 18.3 为什么：这次重写没有真正切短关键路径

原计划（`§3`）要求 8 级流水 + 乘法寄存器 + epoch 重定向，实际落地的是
**6 级 + 双发射**，而且为了配对把旁路网做深了（每个操作数 6 选 1 × 4 个口 × 32 位），
关键路径仍然落在
`寄存器堆/旁路 mux → ALU → 分支比较 → 重定向 → 冲刷使能` 这条链上。
这和老核那条 32.6 ns / 39 级的形态**同源**，只是短了一半。

**结论（不粉饰）**：
- 功能与面积已经达标：ISA 21/21（单发射门禁）、默认门禁 20/21、CoreMark crc 0x4983、
  4.02 CM/MHz、面积比基线还小；
- **120/126 MHz 未达标**，当前网表约 63 MHz。要真的上到 126 MHz，
  必须做原计划的**流水线加深**，而不是继续在 6 级上找余量。

### 18.4 下一轮的唯一正确动作（按收益排序）

1. **把 EX 拆成两级（EX1 地址/比较、EX2 数据/结果）**：直接砍掉 ALU→分支比较→重定向
   这条最长链的一半。代价：`br_miss` 晚一拍 → 预测失败代价 7→8 拍
   （53k 次 × 1 拍 = 5.3 万周期，可接受）。
2. **重定向改 epoch**：`kill_all/kill_young` 现在是长扇出组合链的一部分，
   换成"每级带 epoch 标签、标签不符即无效"，把冲刷从关键路径上摘掉。
3. **旁路 mux 减一级**：WB 级已由 `regs` 的写穿透覆盖（省了 1 级），
   再把 M2 级与 lane1 的合并比较改成"预先算好命中向量"，减少 32 位宽 mux 的串联。
4. 之后再回到 IPC：`l0_alone=450k` / `pkt_lduse=722k` 两块配对损失。
