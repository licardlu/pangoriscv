# Plan v12 — 5.2 分 + 120 MHz 的分段推进（基于逐跳实测）

日期：2026-10-22（P17）
前置：`plan-v11-120mhz-newcore.md`（重写路线的初版）；本文件取代它的路线判断。

---

## 0. 一句话

**120 MHz 不是调参问题，也不是布线收敛问题，而是"28 跳 / 24.6 ns"这条组合路径必须被
切成 3 段"的问题。切开必然花 CPI，所以本轮的第一件事是把 CPI 预算从 1.15% 做成 4% 以上，
第二件事才是切流水线。每一步都有可执行判据，不合格就回退。**

---

## 1. 硬数据：关键路径的逐跳构成（p15nx45 布线后 `.rtr`，45 MHz 约束）

| 段 | 内容 | 起止 (ns) | 耗时 | 占总比 |
|---|---|---|---|---|
| A | 译码/控制 → ALU B 操作数 mux → **ALU** → ALU 输出 mux | 2.648 → 11.320 | **8.67** | 35% |
| B | **AGU 进位链**（地址加法） | 12.241 → 13.675 | 1.43 | 6% |
| C | D-cache 请求（`ar_addr_q` → `early_req`/`op_ready`） | 14.199 → 16.808 | 2.61 | 11% |
| D | `br_miss` → `redirect_pc` | 17.157 → 18.598 | 1.44 | 6% |
| E | **I$ tag 读出 + way 选择 + hit** | 18.598 → 22.601 | **4.00** | 16% |
| F | IFU 队列写使能 | 23.616 → 24.835 | 1.20 | 5% |
| — | 总计 | | **24.60** | |

**单元延迟合计 3.84 ns，网络延迟合计 20.2 ns（84%）。** 平均 0.72 ns/跳，其中出现
单扇出网络 1.319 ns、`fanout=5` 网络 2.338 ns——这是**摆放把这条路径摊开了**，不是逻辑深。

### 1.1 由此得到的三条结论

1. **"优化逻辑"救不了这条路径**：即使把逻辑全部消掉，28 跳的布线本身就是 20 ns。
   要 8.333 ns，必须把跳数降到 **≤ 11 跳**。
2. **切 1 刀不够**：24.6 / 2 = 12.3 ns（81 MHz）。要 120 MHz 至少切 **2 刀**，
   且切口必须落在 A（ALU）与 E（I$）这两段上，因为它们各自已经超过 8.333 ns 的一半。
3. **区域约束仍然无效**（三次实验已证），所以不能靠"摆得近一点"来解决，
   只能靠"每级逻辑变少"。

## 2. 代价侧：每切一刀要花多少 CPI

| 量 | 实测值 | 来源 |
|---|---|---|
| cycles / iteration | 190,129 | `Total ticks 3,802,578 / 20` |
| retires / iteration | 351,284 | retire 计数 |
| IPC | **1.848** | 双发射 |
| 完美双发射下界 | 175,642 | retires / 2 |
| **全部停顿+误预测** | **14,487 / iter** | 差值 |
| 误预测次数 | 2,593 / iter | 51,854 / 20 |
| **每次误预测代价** | **≈ 2.75 拍** | BTB 32→64 的 ticks 差反解 |
| 5.2 分允许的 cycles / iter | 192,307 | 1e6 / 5.2 |
| **当前余量** | **2,178 / iter（1.15%）** | |

⇒ **一刀 +1 拍 = +2,593 / iter = 超出预算 415。** 所以：
- 切第一刀之前，必须先把误预测减少 ~20%（或省下等量停顿），否则分数会掉到 5.19。
- 切第二刀（+2 拍 = +5,186）需要把误预测砍掉一半，或把其他停顿砍掉 3,000/iter。

### 2.1 CPI 预算的三个来源（按性价比排序）

| # | 手段 | 预期收益 | 面积代价 | 风险 |
|---|---|---|---|---|
| C1 | **返回地址栈 RAS（8 项）** | `ret` 全部命中，按误预测占比可达 800~1,500/iter | 极小（~200 LUT） | 低 |
| C2 | BTB 64 → 128/256（直接映射） | 每次翻倍约 −20% 误预测 | 每项 ~41 LUT ⇒ 256 项 +8k LUT | 中（布线拥塞） |
| C3 | 配对规则放宽（回补 `!(lane0_mem && lane1_mem)`） | 未知，需剖析数据 | 需双端口 D$ | 高 |

**先做 C1。** 理由：直接映射 BTB 对同一 `ret` PC 只有一个目标槽，而函数被多个调用点
调用是 CoreMark 的常态，所以 `ret` 的误预测率接近 100%；RAS 是教科书解，代价几乎为零。

## 3. 分段路线（每段都有闸门，不过就回退）

### 阶段 A —— 频率台阶：45 MHz 交付（进行中，构建 `p16r45c`）

- RTL：S2（`br_miss` 去 `mem_wait`）+ 配对限制（`br_miss_h` 去 `mem_wait`）+ BTB 64
- 判据 1：摆放 WNS ≥ 0 且 TNS = 0
- 判据 2：布线 Unrouted → 0
- 判据 3：布线后 WNS ≥ 0（45 MHz / 22.22 ns）
- 判据 4：上板 UART 的 `Total ticks` 与 CRC 与仿真一致
- 落点：**5.260 CoreMark/MHz @ 45 MHz**（相对交付基线 5.213 @ 36 MHz：频率 +25%）

### 阶段 B —— 把 CPI 余量做成 4%（本阶段只改预测器，不动流水线）

1. **B1 加 RAS**（8 项，环形；`jal`/`jalr` 且 rd==ra 时 push，`jalr` 且 rs1==ra 且 imm==0 时 pop）
2. **B2 BTB 索引从 PC[6:2] 改为 PC[8:2]**（256 项），观察误预测与 LUT
3. 闸门：`Total ticks` ≤ **3,750,000**（对应 5.333，余量 3.1%）；ISA 21 条不退化

> 只有 B 段达标才允许进 C 段。否则 C 段切完必然掉到 5.2 以下。

### 阶段 C —— 第一刀：把 redirect 与 I$ 读出解耦（目标 ~66 MHz）

- 改动：`redirect_pc` 先写入一个 IF 级的 PC 寄存器，I$ tag/数据在**下一拍**读
- 从 EX 级路径中移除 E + F 两段 = 5.2 ns ⇒ 19.4 ns → **~14.2 ns**
- CPI 代价：每次重定向 +1 拍（+2,593/iter）
- 闸门：`Total ticks` ≤ 3,845,000（5.200）；布线后 WNS ≥ 0 @ 15 ns
- 若通过 ⇒ 交付 66 MHz 台阶（相对 36 MHz：**+83%**）

### 阶段 D —— 第二刀：ALU 与 AGU 分级（目标 ~90 MHz）

- 改动：ALU 结果打一拍，AGU 与 D$ 地址在 M1 级
- 从 EX 级路径中移除 B 段；A 段 8.67 ns 成为唯一瓶颈
- CPI 代价：load-use +1 拍（需实测）
- 闸门：`Total ticks` ≤ 3,845,000 且布线后 WNS ≥ 0 @ 11.1 ns

### 阶段 E —— 第三刀：ALU 内部再切（目标 120 MHz）

- 改动：ALU 拆成"低 16 位 + 高 16 位 carry-select"，或把 ALU 拆成两级
- A 段 8.67 ns → 目标 ≤ 7.5 ns（含时钟不确定性）
- 闸门：布线后 WNS ≥ 0 @ 8.333 ns + 上板实测

## 5. 与 plan v11（重写单发射核）的关系

`rtl/core/rv32i6/` 是**单发射**核，IPC 上界 1.0 ⇒ 分数上界 **2.85**，**不可能达到 5.2**。
它在 G1 阶段的作用只剩"验证流水线控制写法"，**不再作为交付路线**。
本文件 §3 的 A~E 段全部在**现有双发射核**上做，因为 5.2 分只可能从这里来。

保留 `rv32i6` 的两个成果：
- 取指队列（4 项）结构，阶段 C 正好要用；
- 三个流水线 bug 的教训（取指/PC 配对、重定向屏蔽、停顿语义）已进 mistakes-log。

## 6. 实测周期账（2026-10-23 00:0x，`RV32_PROF` 互斥计数器）

方法：跑 1 迭代与 20 迭代同一镜像，**相减**得 19 个纯迭代。这样启动期的
UART 轮询 / cache 预热被完全剥离——不剥离会得出完全错误的结论（见 §6.2）。

### 6.1 每迭代的真实账（190,395 拍，与 `Total ticks/20 = 190,129` 吻合）

| 桶 | 拍/迭代 | 占比 | 说明 |
|---|---|---|---|
| `pair` | 124,262 | 65.3% | 双发射，理想 |
| **`single`** | **42,149** | **22.1%** | 丢掉一个发射槽 |
| `memwait` | 10,390 | 5.5% | D-cache 不收请求 |
| `starve` | 8,641 | 4.5% | 前端空 |
| `redir` | 4,945 | 2.6% | 重定向当拍 |
| `divwait` | 8 | 0.0% | |

`single` 的构成（互斥，合计 42,150）：

| 原因 | 拍/迭代 | 占 single |
|---|---|---|
| **`nopair`** 前端没给出成对 | 12,436 | 29.5% |
| **`l1mem`** lane0 访存 + lane1 访存 | **12,256** | **29.1%** |
| **`l1ctrl`** lane0 访存 + lane1 控制 | **10,257** | **24.3%** |
| `mduse` lane0 乘除喂 lane1 | 3,576 | 8.5% |
| `l1notok` lane1 不是可配对类型 | 1,706 | 4.0% |
| `alone` lane0 必须单独发射 | 1,240 | 2.9% |
| `lduse` lane0 load 喂 lane1 | 679 | 1.6% |

### 6.2 关键校正：`memwait` 不是 21%，是 5.5%

20 迭代总量里 `memwait` 是 1,198,432 拍（21%），**看起来**是最大瓶颈。
但减去 1 迭代基线后只剩 197,413 拍 / 19 = 10,390 拍/迭代。
那 100 万拍属于**启动期**：程序对 `0x3xxx_xxxx`（UART）做了 122,245 次轮询读，
每次 miss 约 9.5 拍。它发生在计时区间之外，对分数**零影响**。
⇒ **任何"优化"如果不先把启动期剥离，就会去优化 UART 轮询。**

### 6.3 误预测：每次约 4 拍，不是 2.75

`redir` 4,945 + 由它引起的 `nopair`（≈12,400，与 4,945×2.5 几乎相等）≈ 17,345 拍，
加上重定向本身的气泡，**每次误预测约 3.5~4 拍**。误预测总数 100,549/20 = 5,027/iter，
其中 **lane0 62,016 / lane1 38,533（38% 在 lane1）**。
`ret` 数量 37,228、`jalr` 43,746、`call` 6,687 ⇒ RAS 最多只能挽回几千次，
实测 `jalr0` 误预测仅 7,556，**RAS 不值得做**（原假设被数据否掉）。

### 6.4 由此确定的优先级

1. **`l1mem` + `l1ctrl` = 22,513 拍/迭代（11.8% 的周期）**：两者都是
   "lane0 访存 + lane1 也要发射"，根源是 **D-cache 每拍只收一个访问**。
   这是最大的可回收项，也是唯一能撑起流水线加深的储备。
2. **误预测（≈20,000 拍/迭代，10.5%）**：BTB 扩容是最便宜的手段（见 §7）。
3. `starve` 8,641：I$ 缺失，与频率强相关（120 MHz 下会更差），暂不动。
4. `memwait` 只值 10,390，且一半是 D$ 缺失延迟，优先级低于 1、2。

## 7. 实测记录（P17，2026-10-23）

### 7.1 分数阶梯（同镜像 `sim20_O2`，20 迭代，CRC 全对）

| 配置 | ticks(20it) | 分数 | 备注 |
|---|---|---|---|
| 交付基线（BTB32，P15 前） | 3,833,976 | **5.213** | 上板实测 5.213 |
| + P16（S2 + 配对限制 + BTB64） | 3,802,578 | 5.260 | 但 18,957 LUT **不收敛** |
| + P17（恢复 l1ctrl 配对），BTB64 | ≈3,775,264 | 5.298 | 由 cycles 差推算 |
| **+ P17，BTB32** | **3,833,976** | **5.2165** | 实测；与基线同为 18,157 LUT 量级 |
| + BTB128 | — | ~5.27 | 只省 6,991 拍/20it |
| + BTB256 | — | ~5.28 | 只省 15,421 拍/20it |

**BTB 已饱和**：64→256 只买到 812 拍/迭代，却要 +8,000 LUT。这条路封死。

### 7.2 45 MHz 时序已达标（摆放层面）

`p16r45c`（BTB64 配置）在 45 MHz / 22.22 ns 下：
```
Worst slack is 1548, TNS after placement is 0
```
**WNS +1.548 ns，TNS = 0** —— 比 p15nx45 的 +1.162 ns 好 0.39 ns，是历史最好。
这证明 P16 把 D-cache 从两条重定向锥里摘掉确实有效。

### 7.3 布线的真实门槛是 LUT 总量，不是 seed

| 构建 | LUT | 详细布线 |
|---|---|---|
| p15nx45 | 18,157 | **收敛，0 @ 575 轮** |
| p16r45c | 18,957 | 第 11 轮 17,251，斜率 ~800/轮，按同期对比需 800+ 轮（10 小时以上） |

+800 LUT（+4.4%）把设计推过了本器件的拥塞拐点。**这是"面积就是频率"的直接证据**：
在 66,600 LUT 的 PG2L100H 上，多 4% 面积换 4% 分数，代价是 15 倍布线时间。
⇒ 交付口径用 BTB32；要更大的 BTB，必须先在其他地方省出等量面积。

### 7.4 P17 的配对改动

去掉 `!(lane0_mem && lane1_ctrl)`，改成
`br_miss_h = ... && !((rr_load||rr_store) && mem_wait) && ctrl_miss_h`。
- 收益：3,610 拍/迭代（实测，不是剖析器估的 10,257，见 mistakes-log §52）；
- **代价实测只有 0.086 ns**：45 MHz 摆放 WNS 从 p16r45c 的 +1.548 ns 变到 p17r45 的
  +1.462 ns。原先估的 1~1.5 ns 高估了一个数量级——因为 S2 已经把 D-cache 请求路径
  从 lane-0 重定向锥里摘掉了，lane-1 这条本来就不再是最差路径。
  ⇒ **P16 的配对禁止几乎是纯损失**（3,610 拍/迭代换 0.086 ns）。
- 正确性：CoreMark CRC 五项全对；ISA e2e **20/21**（case 21 与基线同样红）。
