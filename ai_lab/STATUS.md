**利用率只有 27% 的原因**：每像素 9 拍算 MAC，但输出按字节串行写 8 拍（COUT=8 时），
加上状态切换，实际约 64 拍/像素。这是明确的优化点，但在整机闭环前不改。

### 整层测试暴露的三个 bug（单层核测试看不到）

1. **权重与激活的 K 维顺序不一致** —— 激活按 `tap*CIN+c`，权重按 numpy 默认 `c*9+tap`。
   RTL 与这个错参考完全一致，于是“8/8 通过”是假通过。
   实测旧配对与真实卷积余弦仅 **0.2275**，修正后 0.9846。现已在 `gen_vectors.py` 加余弦门槛拦截。
2. **行缓冲滑错一行** —— `S_LOAD` 里 `fy` 尚未自增，新底行应为 `fy+2` 而非 `fy+1`。
   症状：第 0 行全对，第 1 行起全错。
3. **移位丢最后一个字节** —— 写操作放在 `else` 分支里，`gi_ == 2*RSZ-1` 时不移位。

另有两个仿真陷阱：两个 `always @(*)` 共用循环变量导致零延时死循环；`int x = expr;`
在 always 块里是静态变量，只初始化一次。

按用户指示，**暂停 AI/YOLO 线**，主线转为把自研核推到 110 MHz。

### 已完成：基线冻结

`preserved/v40_baseline/`（rtl + platform + sbit + FROZEN.md）。
成绩 5.2599 @ 50 MHz、LUT 17,020、WNS +1.139 ns、CRC 全对。任何改动失败即回滚到此。

### 关键发现：E 盘仓库里的 CPU 源码不是 v40

`project/firmware/code/rtl/core/pangoriscv.v` 只有 208 行、**单发射**，与跑出 5.2599 的
双发射版不是同一份。v40 真实源码在 C 盘工作区（`pangoriscv.v` 630 行，含 `rr_inst`/`lane1`），
已复制到 **`project/firmware/code_hf/`** 作为独立工作目录，不动队友那份。

### 构建流程（已摸清）

`platform/pango_native/build.tcl`，需要三个环境变量：
- `PANGO_NATIVE_REPO` / `PANGO_NATIVE_BOARD_DIR`
- `PANGO_NATIVE_RUN_DIR`：必须是**新建**目录，且 pds 的当前工作目录等于它（Tcl 里 cd 无效）
- `NATIVE_IMAGE_DIR`：指向 `build/native_software/coremark/performance/<变体>/`

**坑**：build.tcl 里写死了 `board_clk_hz = 126000000`，镜像 manifest 的 `cpu_hz` 不匹配就直接 error。
所以换频点必须用 `tools/build_native_software.py` 重编固件（UART 波特率与时间换算都依赖它），
不能只改 fdc。现成 fdc 变体：`pango_native_100mhz/120mhz/126mhz.fdc`。

### 技术路线（沿用 `docs/plan-v28-ex-split.md`，不在本次重写）

| 阶段 | 内容 | 验收门 |
|---|---|---|
| S1 | RR→E1(旁路)→E2(ALU/乘法/AGU)→M1，两拍 | WNS ≥ 0 @ 10.0 ns；板上 5 项 CRC 与 v40 相同 |
| S2 | 再拆 E3（D\$ tag 比较 + 分支判定），三拍 | WNS ≥ 0 @ 8.33 ns；CRC 相同 |
| S3 | IPC 补课（BTB 64→256 起） | CoreMark/MHz ≥ 5.0 且 ≥110 MHz |

**已知硬约束**：拆分本身会让 CoreMark/MHz 掉到 4.5~4.7（重定向 +2 拍 = +7.2%，
load-use +1 拍 = +5~9%），所以 **S3 是必需的，不是可选**。乘法器 4 个 APM 级联 6.14 ns
必须独占一拍，否则 110 MHz 保不住。

### 难度评估（不开玩笑）

不是"改几行"：拆分要重做**旁路网络、retire/young_path 逻辑、LSU 握手位置**三处联动，
且必须保持 5 项 CRC 逐位相同。按我们的历史记录，50→52 MHz 九次满流程还差 0.195 ns，
说明这个核的时序极其敏感。**这是一个需要多轮 PDS（每轮约 10 分钟）+ 每轮板上回归的工程，
不是单轮能交付的。**

### 资源结论（决定架构）

1.77 M 参数按 int8 约 1.69 MiB，而整片 DRM 只有 155×4.5 KiB ≈ 680 KiB。
**全模型权重不可能常驻片上，必须从 DDR 流式读取**；`acc_shell` 现在"整层权重先搬进 w_ram"
的结构只能用于小层验证，整网要改成按 tile 流式。

## T20 选型定案：在 PG2L100H 上跑哪个垃圾分类 YOLO（2026-10-29）

### 0. 目标复述（不再改动）

盘古100Pro+ 上，**我们自己的 RISC-V CPU 做调度**，CNN 加速器作为 CPU 的一个外设；
摄像头 → DDR → 加速器 → CPU 后处理 → HDMI 显示"这是什么垃圾、投哪个桶"。
只做识别与分类，不做机械分拣。PC 仅用于训练/量化/仿真对照。

### 1. 开源工程检索结论（逐个仓库核实，非凭印象）

### 2. "现成"能拿到的是模型这一半

|---|---|---|---|---|---|

| `Jy0thsna/AutomaticGarbageSegregation` | 5：glass/wood/plastic/metal/paper | — / **8.27 MB** | **1344.2 M** | 自报 mAP 61.47%（其自身数据集） | 公开权重 |
| `alexNova/YOLO-TrashDet-Pruned` | 缺有害垃圾 | — | — | — | **AGPL-3.0**，传染性，不适合比赛交付 |

### 3. 定案

**用 `yolov5n-garbage`，输入 320×320，INT8，加速器自己写。** 依据（全部由脚本算出，见下）：

- **算力**：518.7 MMAC vs 1344.2 MMAC。同一引擎下 v3-tiny 慢 **2.6×**；
  按 64 MAC/cycle @100 MHz 估，81 ms vs 210 ms（未计存储效率）。
- **权重**：1.76 MB vs 8.27 MB → DDR 读取量与上电加载时间 **4.7×**。
- **可比性**：v5n 有我们自己测的 FP32 基线 0.3432 和已溯源的类别顺序；
  v3-tiny 的 61.47% 是作者在自建数据集上的自报值，与我们的标注集不可比。
- **算子覆盖**：v5n 需要 conv(k=1/3/6, s=1/2) + SiLU + concat + nearest upsample +
  maxpool(k=5,s=1) + residual add，**一个引擎可全覆盖**；v3-tiny 的算子集是它的真子集。
  先支持 v5n，v3-tiny 自动可跑，不需要第二套设计。

计算脚本内联在本次会话中（yolov3-tiny 层表逐层累加，含 5/6 类两种 head）：
320/5 类 1344.15 MMAC、320/6 类 1344.38 MMAC、416/5 类 2271.62 MMAC；
权重 8672.69 K（8.27 MB）；最大单层激活 416 输入时 2704 KiB → **整张量片上放不下**，
必须 DDR 分块 + 行滑窗，这一点与 T19 第 7 节的结论一致。

### 4. 对 T19 第 8 节的更正（重要）

T19 记录的 "INT8 mAP 0.0523" 是**评测脚本的坐标错误**，不是量化损失：
`eval_yolov5n_labeled.py` 的 INT8 分支把 `quant_yolov5n.decode()` 返回的
**letterbox 320 坐标系**里的框，直接和**原图像素坐标系**的 GT 算 IoU，
两套尺度不同，IoU 必然接近 0；FP32 分支走 `eval_yolov5n.detect()` 里有
`(b-pad)/r` 反变换所以正常。已在该分支补上同样的反变换。
**该数字在重测前作废，不再引用**；本表其余数据不受影响。

### 5. 下一步（按此顺序，不再并行发散）

1. 乘器密度标定：确认 64/128/256 个 int8 乘法的真实 APM/LUT 代价 → 定 lane 数

## T21 按评审纠正后的进展（2026-10-29 晚）

### 1. 撤回一条结论：「乘法器共享导致算力 1/8」证据不足

评审说得对：APM 数量不能证明每周期吞吐。查综合报告 `pds/core8_run3/synthesize/apm_drm_lutram_utilization.log`：

```
-----Multipliers :
                8 x 8   Multipliers := 64
                32 x 32 Multipliers := 8
```

RTL 里是 64 个 8x8 乘法器；映射到 APM 的实例总数 **8**，其中只有 **4** 个是
`8(signed) x 8(signed)`（N85/N92/N98/N104），另外 4 个是 32x32 requant 的部分积
（N573_m1/m2、N867_m1/m2）。总量 LUT 726 装不下 60 个 LUT 乘法器。

**事实只有这些：64 个 RTL 乘法器，8 个 APM，726 LUT。到底几个物理乘法器、
连续输入时每周期完成几个有效 MAC，必须看网表/后仿，不能用资源数推断。**
该结论已从记录中撤回，待后仿核实后再写。`mac_array` 的 64 APM 只证明它自己被
完整展开，不构成对旧实现的判决。

### 2. DRM 推断验证（评审要求，先小实例确认）

`rtl/dram_probe.v`，两个 1024x8 阵列同一构建，结果来自
`pds/dramprobe_run/synthesize/apm_drm_lutram_utilization.log`：

| 写法 | 映射 |
|---|---|
| `rdata <= mem[raddr]`（地址/数据各寄一拍） | `GTP_DRM18K_E1`，SIMPLE_DUAL_PORT → **块 RAM** |
| `assign rdata = mem[raddr]`（组合读） | **128 × GTP_RAM64X1DP** → 分布式 RAM |

上一版整层加速器 39,936 LUTRAM 的直接原因就是这个。**引擎所有存储只能用第一种写法。**

### 3. 分块规划 `scripts/tile_plan.py`（本轮交付，第一步）

读真实层表，阵列固定 P=8 像素 × C=8 通道 = 64 MAC/cycle（**未扩大阵列**），
搜索每层行块 TR，约束片上容量。带宽需求：激活 16 B/cycle（stride 2 需 16 字节
窗口取 8 个 stride-2 字节）、权重 8 B/cycle，两项都在两三个 DRM 宽口内。
首层 k=6 单独处理（窗口 6 行，不是"三行滑窗"）。

| 预算 | 通过层数 | 片上峰值 | DDR 每帧 | 周期(串行) | 阵列利用率 |
|---|---|---|---|---|---|
| 70 DRM（名义 315 KiB，扣 12%） | 60/60 | 254.8 KiB | 9.01 MB | 9.286 M（84.4 ms） | 87.3 % |
| 64 KiB（保守） | 60/60 | 63.7 KiB | 10.25 MB | 9.449 M（85.9 ms） | 85.8 % |

64 KiB 方案只多 0.3 MB 流量，**建议按 64 KiB 实施**，把 DRM 留给 CPU/视频。
（评审指出 502 KB 与"未扣 CPU/视频"矛盾，此处以 70 DRM 名义容量为准，64 KiB 为执行值。）

DDR 敏感性（64 KiB 方案）：100 MB/s → 109.0 ms；200 → 83.5；400 → 77.7；800 → 77.1。
**DDR 低于约 200 MB/s 时才成为瓶颈，这个真值必须实测。**

这些都是**模型估算**：串行口径假设装载与计算不重叠、未计入边界/等待/其他算子，
不能当板上帧率承诺。

| plastic | 0.2237 | 0.2253 | +0.0016 |

### 本轮修掉的 8 个真 bug（都是仿真查出来的，编译查不出）

1. `S_FILLW` 吃完一个字不回 `S_FILL`，填充只走一步就停。
2. `S_WLDW` 同类问题，权重装载停在第一个字。
3. 权重装载把 `wld_o` 和 `wld_w` 一起自增，只写了每个 bank 的"对角线"，其余保持 X。
   表现为写回数据全 X —— 比数值错更隐蔽。
4. 尾处理舍入是 **round-half-up**，不是文档写的 round-half-away-from-zero：
   `pr=-3, SHIFT=2`（−0.75）应得 −1，原实现得 −2。改为先取绝对值再舍入、最后补符号。
5. 地址流水多了一级寄存器：数据比计数器晚两拍，累加只等一拍，
   **第一个 K 切片从未累加、最后一个被累加两次**。k=1 时因只有一个切片侥幸通过，
   k=3 才暴露。改为"地址组合、数据寄存"，并把使能对齐到"第 c 拍发地址→第 c+1 拍累加"。
6. `pad` 不能写死 `K/2`：首层是 6x6 stride 2，autopad 给 **pad=2**（不是 3），
   否则输出 161 而非 160。已改为参数，从层表读。
7. 写端口改为 64 位并等 ack（原来 32 位不等 ack，AXI 上会丢写）。
8. 测试台三个坑：`$fscanf` 要 `%x` 不是 `%h`（ModelSim 不支持 %h）；
   `$fopen` 返回 `0x8000_0000|ch`，**非零即成功**，用 `==0` 判错；
   全零向量会造成"假 PASS"，现在载入失败直接 `$fatal`。

#### T28 补充：时序未收敛（实测）

`conv_rt_top` 实现到 plcement 阶段的最差 slack **约 −6.8 ns**（固定形状版是 +1.58 ns）。

### T29 地址全部改成增量推进：**三个算例仍逐字节通过**

上一轮（T28）把"运行时尺寸"直译成地址乘法，时序 −6.8 ns。这一轮把内层循环里

| 原来（有乘法） | 现在（只有加法） |

| 写地址 `((band_i*r_tr+row)*out_w+col)*nt+ti` | `wrow_base + wcol_off + ti`，列加 `nt`、行加 `d_wrow`、band 加 `d_band` |

| `S_Q` 的 `2*qw` 比较、`q_i==2*qw+31` | 预算成 `qw2` |
| `S_NEXT` 的 `band_i*r_tr >= out_h` | `rows_done` 累加寄存器 |

#### 还没做但已经想清楚的事（下一轮直接照做，不必再试错）

1. **DDR 写放大是架构问题，不是参数问题。**
   引擎的输出端口一次写一个 64 位字 = 8 个通道。通道后置布局下，同一通道组相邻像素
   相隔 `cout/8` 个字，`cout=512` 时相隔 64 个字 —— 每 32 字节 DDR 行只用 8 字节，
   写放大最高 8 倍（一个 256 位 DDR 突发 32 字节只装 8 字节有效）。
   **修法**：在引擎里加一个"输出 band 缓冲"（`tr*out_w*ceil(cout/8)` 个字，
   规划表里最大 2560 字 = 20 KiB ≈ 5 DRM），计算时写缓冲、band 结束时按缓冲顺序
   顺序刷出。缓冲下标恰好等于 DDR 偏移，所以刷出是纯顺序的，写放大归 1。
   代价：每 band 多约 2560 拍，首层 40 个 band 共 +102k 拍（相对 2.78M 是 +3.7%）。
2. **输入读放大的上限是 `cin/8`**，比写小一个数量级，可以不动。
3. **DDR3 IP 的地址约定**（从 IP 自带示例设计反推，别再从视频工程猜）：
   `axi_awlen=15` 配 `axi_awaddr += 128`，即**每拍推进 8 字节**；
   示例里 `random_rw_addr` 低 3 位恒 0。数据总线 `8*MEM_DQ_WIDTH`，本板
   `MEM_DQ_WIDTH=32` ⇒ **AXI 数据 256 位、wstrb 32 位、无 B 通道**
   （写完成靠 `axi_wusero_last`）。要把 64 位引擎接到这条总线上，
   必须做 64→256 的宽度桥，且读要按 32 字节对齐取整拍。

### T31 CPU 接口从"约定"变成"能跑"：`conv_engine_axil` **三算例过 AXI**

`sw/acc_regs.h` 之前是按已删除的描述符序列器写的，和 `conv_band_rt` 的端口对不上，
而且 `conv_engine_axi.v` 封装的是**固定形状**引擎 —— 也就是说"CPU 能控制加速器"
一直只是纸面约定。这一轮补上了真正的那一块：

- 新增 `rtl/conv_engine_axil.v`：AXI4-Lite 寄存器堆（17 个写寄存器 + 4 个读寄存器，
  与 `sw/acc_regs.h` 一一对应）+ 已验过的 AXI4 单拍主口 + `conv_band_rt`。
- 新增 `tb/tb_engine_axil.v`：测试激励走的是**CPU 的真实序列**——写 17 个寄存器、
  写 CTRL.start、轮询 STATUS——输出从 DDR 模型里读回逐字节比对。
- 新增 `sim/run_axil.sh`：三算例一键回归。

| 算例 | 结果 |
|---|---|
| k=1 8x8 8→8 | **AXI-AXIL-PASS 64 words, 64 writes** |
| k=3 32→32 40x40 | **AXI-AXIL-PASS 6400 words, 6400 writes** |
| k=6 s=2 3→8 320→160 | **AXI-AXIL-PASS 51200 words, 51200 writes** |

写回次数与输出字数**完全相等**，说明没有重复写也没有漏写。

#### 这一轮修掉的两个接口 bug

1. **AW 和 W 同一拍被接收时，写地址晚了一拍。**
   原来 `aw_idx <= s_awaddr[7:2]` 在 W 分支里用，取到的是**上一个**寄存器地址，
   于是 17 次写全部落到前一个寄存器上，引擎拿到 `cin=0`。
   现象：`done` 立刻置起、输出全 0、总耗时只有 6.3 µs（正常要 9.5 µs）。
   修法：`wr_idx = (awvalid && awready) ? awaddr[7:2] : aw_idx`。
2. **`b_bad` 有两个驱动**（写通道和状态机各写一次）。旧文件里就有这个问题，
   只是在"没有错误注入"的测试里看不出来。已改成单驱动 + 单拍 `clr_bad` 脉冲。

> 教训：**"接口文件写好了"不等于"CPU 能控制加速器"**。这条在评审意见里被点过一次，
> 这次是用一个能跑的 tb 把它关掉的，不是用文档。

### T32 布线没收敛：**是拥塞，不是时序**

T30 的布局结果已经把 slack 收到 −0.104 ns（1 个端点），但详细布线跑了 24 轮仍有
**26,707 根未布通**（从 40,817 起步，每轮只降约 1,000）。固定形状版 LUT 只有 4,657、
利用率约 1.5%，几分钟就布完；运行时可配版 LUT 20,744、**布局利用率 59%**。

结论要分开写，别混：

| 项目 | 结论 |
|---|---|
| 逻辑深度（时序） | **基本达标**：布局后 −0.104 ns，只剩 1 个端点 |
| 可布性（拥塞） | **不达标**：59% 利用率下 24 轮未收敛 |

所以下一步**不是**继续调时序，而是**减面积**。按收益排序：

1. **把 `bias_r` / `mval`（各 512×32）显式推成 BRAM。**
   现在它们是"数据相关下标写入 + 数据相关下标读出"的数组，综合器给出的
   LUT 里很大一块是这两张表的读写译码树。用 `GTP_DRM18K_E1` 原语或
   `(* ram_style = "block" *)` 固定下来，LUT 应该能降一个量级。
2. `atab`（256×8）同理，本来就该是 LUTRAM。
3. 若还不够，把 AXI-Lite 寄存器堆里的 16 位字段合并成 32 位寄存器
   （`cin|cout<<16` 这类），减少比较器数量。

**在面积降下来之前，不要再去追 100 MHz**：现在追的是一个布不通的网表。

#### 复现入口

| 做什么 | 命令 |
|---|---|
| 引擎功能（裸接口） | `sim/run_rt.sh`（默认三个算例） |
| 引擎功能（CPU 视角，走 AXI） | `sim/run_axil.sh` |
| 综合→布局→布线→时序 | `pds/rt_run` 下 `pds_shell -project run_rt.pds`，日志 `shell_rt.log` |

后处理四算子（maxpool/upsample/concat/add）的回归入口是 `gen_postop.py` + `tb/tb_postop.v`，
不受这一轮改动影响。

### T33 减面积：**LUT 27,446 → 14,392，触发器 36,504 → 4,061**

T32 判定的拥塞根因得到证实。诊断依据很直接：`bias_r` 和 `mval` 是两张 512×32 的表，
按 2×512×32 = **32,768** 个触发器算，而综合报的 FF 总数是 36,504 —— 几乎全是它们。
它们又是"数据相关下标读"，所以每个都带一棵 512:1 的 32 位读 mux。

改法：**一个 tile 只需要 8 个 bias 和 8 个 M**，没必要把整层都留在片上。
删掉两张全表，新增 `S_TQ`/`S_TQW` 两个状态，在每个 tile 开始前从 DDR 取 4 个 bias 字
+ 4 个 M 字（8 个 64 位字）写进 8 项的 `b_tile`/`m_tile`。q 缓冲区现在只剩 256 字节的
激活表在开机时读一次。

| | 改前 | 改后 |
|---|---|---|
| LUT | 27,446（42%） | **14,392（22%）** |
| FF | 36,504（28%） | **4,061（4%）** |
| DRM | 48 | 48 |
| APM | 116 | 106 |
| 分布式 RAM | 0 | 0 |

代价是每个 tile 多 8 次 DDR 读：

| 算例 | 周期（改前 → 改后） | 增量 | 占比 |
|---|---|---|---|
| k=1 8x8 | 945 → **969** | +24 | +2.5% |
| k=3 40x40 | 322,832 → **323,216** | +384 | +0.12% |
| k=6 s2 320→160 | 2,782,269 → **2,784,141** | +1,872 | +0.067% |

层越深占比越小，因为 tile 数与像素数之比随 cout 下降。

**功能未变**：`sim/run_rt.sh` 与 `sim/run_axil.sh` 各三算例仍全部逐字节通过
（含 AXI 路径的 64 / 6400 / 51200 字，写回次数仍与输出字数相等）。

> 顺带说明为什么不能只加一句 `(* ram_style = "block" *)`：这两张表的读是**组合**的
> （`bias_r[ti*8+wld_o]` 当拍就要用），推成 BRAM 会让读晚一拍、行为改变。
> 要么改流水，要么像这次一样换成逐 tile 取数——后者顺带把存储量也砍掉了。

### T34 DDR3 AXI 地址约定：从两份**能工作**的代码里对上，不靠猜

`ddr3_test` 的 AXI 端口没有任何语义注释，控制器源码是 IEEE-1735 加密的（`.vp`），
所以只能从"已经跑通的代码"反推。两处独立证据一致：

1. IP 自带示例 `test_wr_ctrl_v1_0.v`：`axi_awlen <= 4'd15` 配 `axi_awaddr += 8'd128`
   → **16 拍 → 128 → 每拍 8 字节**。
2. 视频工程 `wr_cmd_trans.v`（本板 720p60 实测可用）：
   ```verilog
   wr_addr <= wr_addr + {wr_len,3'd0} + 4'b1000;   // (wr_len+1)*8
   ```
   同样是 **每拍 8 字节**。

两个互不相关的实现给出同一个数，所以桥接器的地址推进按 **8 字节/拍** 写，不再猜。
`axi_wdata` 是 256 位（`8*MEM_DQ_WIDTH`，本板 DQ=32），也就是说**一拍的数据宽度
和地址推进量不是一回事**——这一点在接宽度桥时最容易踩。

> 待实证的一点：数据 32 字节/拍 与地址 8 字节/拍 之间的比例关系，
> IP 文档没有说明，控制器源码加密。用 IP 自带的 DDR3 行为模型
> （`example_design/bench/mem/ddr3.v`）跑一次"写 16 拍、读回 512 字节"就能定死。
> 桥接器里已经把这个量做成 `ADDR_UNIT_BYTES` 参数，真值是 8 还是 32 只改一个常量。

### T35 减面积之后：**布局时序转正（+403 ps、TNS 0）**，布线仍受拥塞拖累

减掉两张 q 表后重跑同一套流程（10.000 ns 约束）：

| 阶段 | 减面积前 | 减面积后 |
|---|---|---|
| 布局利用率 | 59% | **22%** |
| 全局布局后 slack | −8656 ps | −3054 ps |
| 详细布局后 slack | −104 ps（1 端点） | **+403 ps，TNS 0** |
| 布线 | 24 轮后 26,707 未布通，停住 | 50 轮后 4,333 未布通，仍在缓慢收敛 |

**结论要分两句写**：

1. **逻辑与时序已经过了。** 布局给出 wslk **+403 ps、TNS = 0**，也就是 100 MHz 下
   这条网表的每一条路径都满足约束。这是从 T28 的 −6.8 ns 一路走过来的终点。
2. **布线仍不收敛，而且和时序无关。** 利用率只有 22%，却布不通，说明是**局部拥塞**，
   不是面积不够。

#### 拥塞的最可能来源（下一轮先试这个）

`bband` 是 **12288 × 64 位 = 96 KiB** 的单一数组，综合成 **22 个 DRM 连成一片**；
加上 8 个权重 bank，DRM 用到 48/155（31%）。一整块 22 DRM 的宏在版图上是
一个巨大的绕行障碍，周围走线通道被挤死——这和"22% 利用率却布不通"是吻合的。

可执行的改法，按代价排序：

1. **把 `bband` 拆成 4 个 3072 字的独立 bank，按低两位地址交织。**
   物理上变成 4 个 5~6 DRM 的块，planner 能把它们分开放，绕行障碍立刻小一圈。
   逻辑上只是把 `bband[i]` 换成 `bank[i[1:0]][i[11:2]]`，功能不变。
2. 若还不行，把规划表里 `tr` 调小一档（band 缓冲减半，DRM 降到 ~30）。
3. 再不行才考虑降频点（15 ns / 66 MHz）——但按第 1 条看，大概率不需要。

> 提醒：`report_timing` 在 `pnr` 之后才跑，所以这一轮**没有**布线后的 WNS 数字。
> 上面 +403 ps 是**布局后**的实测值，不要当成布线后的成绩引用。
> 布线任务仍在后台跑，日志 `pds/rt_run/shell_rt2.log`。

### T38 订正 T34：**DDR 的 AXI 地址是"32 位字地址"，不是字节地址**

T34 里我按"字节地址"去读那两份代码，得出"每拍推进 8 字节"，和 256 位数据总线
对不上（32 字节 vs 8 字节），当时留了个待实证的尾巴。重算一遍就通了：

视频工程 `wr_buf.v` 里
```verilog
localparam RD_LINE_NUM      = WR_LINE_NUM*RAM_WIDTH/DDR_DATA_WIDTH;  // 一行的拍数
localparam DDR_ADDR_OFFSET  = RD_LINE_NUM*DDR_DATA_WIDTH/DQ_WIDTH;   // 一行推进多少地址
```
`DDR_DATA_WIDTH = 8*DQ_WIDTH`，所以 `DDR_DATA_WIDTH/DQ_WIDTH = 8`，即**每拍推进 8 个地址单位**。

一拍的数据是 256 位 = **32 字节**，8 个单位 → **1 个单位 = 4 字节 = 一个 32 位字**。

于是三处全部自洽：

| 出处 | 每拍推进 | 换算 |
|---|---|---|
| IP 示例 `test_wr_ctrl`：16 拍 `addr += 128` | 8 单位 | 16×8×4 = 512 字节 = 16 拍×32 字节 ✓ |
| 视频工程 `wr_cmd_trans`：`addr += (wr_len+1)*8` | 8 单位 | 同上 ✓ |
| 视频工程 `wr_buf`：`DDR_ADDR_OFFSET = 拍数*8` | 8 单位 | 同上 ✓ |

**结论（接宽度桥直接按这个写）**：

```
字节地址 W  ->  突发地址 = (W >> 5) * 8          // 32 字节对齐的拍
                拍内偏移 = (W >> 3) & 3          // 第几个 64 位字
                WSTRB    = 8'hFF << (8*偏移)
```
读同理：按 `(W>>5)*8` 发一拍 32 字节，取 `rdata[偏移*64 +: 64]`。

> T34 里"每拍 8 字节"的说法作废，`ADDR_UNIT_BYTES` 的真值是 **4**（字节/地址单位），
> 不是 8。区别在于把地址当字节地址还是当 32 位字地址——这一点搞错，
> 整块 DDR 的数据会整体错位 4~8 倍，而且现象会像"某些层对、某些层错"，很难查。

### T39 DDR 宽度桥：`ddr_axi_bridge` **通过单元测试**

`rtl/ddr_axi_bridge.v`：64 位单拍 AXI4（加速器侧）↔ 256 位单拍 AXI3（DDR3 IP 侧）。

按 T38 推出来的换算实现：

```
字节地址 W -> 突发地址 (W>>5)*8      (32 字节一拍，一拍 8 个 4 字节单位)
             拍内 lane  (W>>3)&3
             WSTRB      8'hFF << (lane*8)
```

读侧按 32 字节行缓存：连续四个 64 位读只发一个 DDR 拍。

`tb/tb_ddr_bridge.v` 用一个按字节施加 WSTRB 的 32 字节行为模型（不是简单存字），
所以**lane 错位会直接表现为数据错位，而不会"看起来对"**。结果：

```
DDR-BRIDGE-PASS  5 writes, 4 reads, 2 read beats, 5 write beats
```

#### 这个测试台立刻抓到两个 Verilog 位宽 bug（都属于"会静默错"的那一类）

1. `wire [7:0] wr_stb = s_wstrb << (wr_lane<<3);` —— 结果只有 8 位，左移 8/16/24 位后
   **全部截断成 0**，于是除第一个 64 位字外，所有写都没写进去。
2. 上一处修好后仍不对：`wr_lane << 3` 的**移位量表达式只有 2 位**，`2'd1 << 3` 截断成 0，
   又是一个"全落在 lane 0"。改成独立的 5 位表达式 `{wr_lane, 3'b000}` 才正确。

两条都是"编译器不报错、综合也不报错、上板数据错位"的类型。
如果直接上板，现象会是"整块张量错位 4 倍/8 倍，看起来像某些层对某些层错"。

> 这个桥**只做了单元测试**，还没和真实 DDR3 IP 联仿（那需要跑 IP 自带 DDR3 模型的
> 初始化序列）。接进 SoC 前必须补这一步，或者至少用 ILA 在板上确认前几个 burst。

### T40 规划与引擎对齐 + 缓冲按真实需求缩到 56 KiB

两边对不上，等于规划对引擎不成立。

修了两头：

1. `tile_plan.py` 的 tr 候选从 `(1,2,4,8,16,32,out_h)` 砍到 `(1,2,4,8)`，
   注释写死原因（引擎 TRM=8，更大的 tr 不合法）。
2. 按引擎实际占用公式（`brow*wpadx*csl` 字，宽高/通道都按 pad 补齐）核对，
   60 层全部放得下：**最大需求是首层 model.0.conv 的 6,480 字 = 50 KiB**。
3. `BANDW` 从 12,288 缩到 **7,168 字 = 56 KiB**（留 10% 余量），

### T42 主机端工具链补齐：模型 → DDR 镜像 + 逐层寄存器表 + CPU 驱动

这是"模型"和"引擎"之间一直缺的一环，这轮补上了，并且**结构上验证过**。

**`scripts/pack_model.py`**（用 Python311 那个带 torch 的解释器跑）：

1. 按执行顺序取全部 60 个 Conv2d，前向若干张标定图，记录每个 conv 的
   输入/输出 abs-max；
2. 尺度**链式**确定：`sx[0]` 来自标定，`sx[i+1] = sy[i]`——每层输出按自己的
   scale 存，下一层必须按同一个 scale 读，所以标定只决定 sx[0] 和每个 sy[i]；
3. 权重量化 per-channel，`wp` 按 `[cout][k][k][cin_pad]` 展平成字节——这**正是**
   引擎遍历的顺序（tile→bank→tap→通道片），`sim/run_rt.sh` 的逐字节回归就是这条
   顺序正确的证据；
4. `bias_q = round_away(b/(sx*sw))`，`M = round_away(sx*sw/sy*2^15)`，
   并检查 |M| < 2^31（超了直接报错，而不是在板上静默错）；
5. SiLU 层生成 256 字节激活表。

1. **`ACC_CIN` 必须写"补齐后"的通道数**。引擎 `csl = cin>>3`，每字 8 通道，

### T44 模型加载窗口：绕过"CPU 碰不到 DDR"这个结构性缺口

之前列的阻塞是"模型 9.43 MiB 进不了 DDR"。根因不是串口引脚，而是**结构性的**：
CPU 的两个 AXI 主口只连片上 RAM 和外设，**它根本没有到 DDR 的通路**。

解法：加速器本来就有 DDR 主口，而跑层的时候它闲着。所以给它加三个寄存器：

| 偏移 | 名字 | 作用 |
|---|---|---|
| 0x54 | `ACC_LOAD_ADDR` | 下一个 64 位字的 DDR 字节地址 |
| 0x58 | `ACC_LOAD_LO` | 低 32 位 |
| 0x5C | `ACC_LOAD_HI` | 高 32 位；写这个动作即提交，地址自动 +8 |

于是加载一个 9.43 MiB 镜像就是 **120 万次 32 位寄存器写**，不需要 DMA、不需要突发、
不需要 CPU 有 DDR 主口。慢，但每次上电只做一次。

`tb/tb_engine_axil.v` 里加了对应断言：经这三个寄存器写两个字到 DDR 模型，
读回与期望逐位一致，同时原有的 64 字整层结果仍然 PASS。

#### 这一轮抓到的 bug（又是一个"静默"的）

`ld_kick` 在同一个 always 块里先被置 1、随后又被一条"默认清零"覆盖——
NBA 后写者胜，所以**每一次提交都被自己取消了**，DDR 里什么也没写进去，
但状态机不报错。现象是镜像看起来"加载完了"却全是旧数据。
修法：把默认清零挪到块首（和 `go`、`clr_bad` 一样）。

### T46 整图算子序列导出：**85 个算子，与 layers.csv 交叉验证一致**

之前所有估算都缺一个数：**网络不是 60 个卷积**。C3/SPPF 把卷积和 concat/add/maxpool
搅在一起，而这些额外算子是直接写在各 block 的 `forward()` 里的（`torch.cat((y, cv2(x)), 1)`），

`scripts/export_graph.py`：从模块树结构推导，然后**用 layers.csv 交叉验证**——
那份表是靠 hook 真实前向录出来的，两者逐条不一致就直接报错退出，

**结果：85 个算子**

| 类型 | 数量 | 说明 |
|---|---|---|
| CONV | 60 | 与 layers.csv 逐条一致（含 3 个检测头） |

| ADD | 7 | Bottleneck 的残差 |

#### 推导过程中发现的三个"看代码看不出来"的事实

1. **C3 是双分支的**：`cv1` 喂 bottleneck，`cv2` 直接进 concat，两者拼完再进 `cv3`。
   layers.csv 里 `cv2` 排在 bottleneck **之后**，正好是 `torch.cat` 参数从左到右求值
   的副产物——这个顺序是唯一能把结构钉死的证据。我第一版只写了 cv1，少了 8 个卷积。
2. **SPPF 固定跑 3 次 maxpool**，concat 有 4 路输入；这个变体**没有 `n` 属性**，
   按 `n` 循环会直接崩。
3. **形状不能自己算**。我一开始用 `pad=k//2` 推导，首层是 k=6 autopad pad=2，
   于是 320 出来变成 161，后面每层都错一行。**只能用 layers.csv 的真实几何。**

这三条都属于"照常识写会静默错一层"的类型，而错一层的结果就是整网精度崩掉但不报错。
