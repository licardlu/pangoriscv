## 1. 这一轮做了什么

上一轮（P17）交付的位流只含 **R03**（LRU 修复）。之后独立复核提出的另外三处
RTL 缺陷（R01/R02/R04）在 `f8c2b43` 中修好，但当时按"不重新跑分"的要求没有重建位流，
造成**源码 ≠ 位流**。本轮把三者对齐并重新出分：

| 修复 | 内容 |
|---|---|
| **R01** | 数据 RAM 之外的 store 不再提前应答（`DATA_RAM_LIMIT=0x1000_4000`），DECERR 能上报为 store fault |
| **R02** | MMIO 的 byte/halfword 读带真实 `ARSIZE`，不再触发 SLVERR |
| **R04** | 2-bit 预测器真正饱和（`11` 不再被打回 `10`） |

## 7. 下一轮（P19）实施方案：把数据 RAM 的 store 变成"受理即完成 + 单条后台缓冲"

> 这是目前**最大且已量化**的杠杆：store 等 B 响应占全部周期 **5.1%**。
> 收益预估 **+5%**（2.6948 → 约 2.83），改动集中在 `dcache_axi.v`，不碰 LSU。

### 7.1 为什么现在会等

时间线（`early_q=1` 的数据 RAM store）：

```
受理(1 拍) → ST_WR_REQ 等 LSU 给 W(1~2 拍) → 回答 CPU(early_now，b_valid)
           → 引擎发 AW/W、等 B(约 5 拍，期间 state=ST_WR_DRAIN)
           → 这 5 拍里 req_ready 是低的 → 下一笔 store 的请求被挡住
```

实测：LSU 在 REQUEST 状态累计等待 **14.77M 拍**，其中 **99.1% 是 store**
（`LSU_REQ_SPLIT request_store=14,636,166` / `request_load=130,381`），
平均每笔 store 等 **1.35 拍** × 1088 万笔 = 5.1% 的总周期。

根因是 P14 让 store 在 **W 握手**就完成并退休，CPU 往前跑了，
但 D-Cache 仍独占写引擎直到 B 返回。

### 7.2 方案（不动 LSU）

对 `req_write && early_q`（**数据 RAM 范围内、不可能失败**的 store）：

1. `ST_IDLE` 受理 → 进新状态 `ST_WR_POST`（替代 `ST_WR_REQ`）。
2. `ST_WR_POST`：等 `w_valid`，把 `{addr,data,strb,size,id,cached,hit,way,set,word}`
   锁进**单条后台缓冲** `pend_*`；同拍推进写通合并（cached hit）；
   **当拍置 `b_valid`/`b_resp=OKAY`** 回答 CPU；`state_q <= ST_IDLE`。
3. 独立的小 FSM 在引擎空闲时把 `pend_*` 发出去（把引擎的 `req_valid`/`w_data`
   从 LSU 源切换为缓冲源），拿到 B 后清 `pend_valid`；B 出错则作废对应缓存行。
4. `pend_valid` 为 1 且又有新的数据 RAM store 到来且引擎未空闲 → 保持
   `req_ready` 为低（背压）。实测 store 间隔约 26 拍、AXI 写约 6 拍，**极少触发**。
5. **顺序保护**：`pend_valid` 期间，任何**非缓存命中**的读（缺失填充 / MMIO）必须
   等 `pend_valid` 清零后再发 AR（保守全序）。缓存命中的读不受影响
   （合并已在第 2 步完成）。
6. MMIO 写（`early_q=0`）**保持原同步路径**，不参与排队，避免外设时序被改。

### 7.3 验收标准（不达标就回退）

- 20 迭代 A/B：**五项 CRC 逐项相同**，ticks 明显下降（目标 −4% 以上）
- `run_unit_tests` / `run_dcache_tests` / `run_isa_e2e` 15/15 / `run_ram_tests` 40/40 /
  `run_halt_reset_tests` 5/5 全绿
- 768 迭代跑分 + PDS + **上板实测**与仿真一致
- 若 `-O3` 那样被容量或其他硬约束挡住，或 CRC 不收敛 → **回退并记录原因**

### 7.4 更远的路（3.5 的必要条件）

`CM/MHz = IPC × 1e6 / 289,296`，单发射上限 **3.457**。若确实要 ≥3.5：

- 必须 **IPC > 1** → 双发射（取指双发 + 双 ALU/双端口寄存器堆），属于微架构重写；
- 或把**每迭代指令数**降到 285,714 以下（−1.2%），但 `-O3` 已被 16 KiB 程序 RAM 否决，
  需先扩程序 RAM（BRAM 成本会拖累 ③）；
- 现实目标：**3.1~3.3**（IPC 0.90~0.95），需要 store 缓冲 + if_wait + 分支预测三项都吃掉。

## 8. 3.5 / 4.0 的唯一路径：双发射（评估，未实施）

### 8.1 为什么单发射一定到不了

```
CM/MHz = IPC × 1e6 / 每迭代指令数        (每迭代指令数 = 222,179,042 / 768 = 289,296)
```

| 目标 CM/MHz | 需要 IPC | 单发射能否达到 |
|---|---|---|
| 2.6948（当前） | 0.7747 | ✅ |
| 3.0 | 0.868 | ✅ 需要把剩余停顿吃掉约 40% |
| **3.457** | **1.000** | ⚠️ 理论上限，需要**零停顿**，不可达 |
| **3.5** | **1.0125** | ❌ **需要 IPC>1** |
| **4.0** | **1.383** | ❌ **需要 IPC>1.38** |

即使把 store 等 B（5.1%）、if_wait（8.6%）、分支预测（3.7%）、load 占用（1.4%）
**全部**吃掉，也只能到约 **3.31**（IPC≈0.957）。所以 3.5 与 4.0 都得换微架构。

### 8.2 三条结构性尝试已实测失败，结论已入经验库

| 轮次 | 想法 | 结果 | 经验 |
|---|---|---|---|
| P19 | store 受理即完成 + 后台缓冲 | ISA 13/15、halt-reset 4/5 → 回退 | §4.5 延后写破坏 store→load 与停机排空 |
| P20 | I-Cache 32 B 行 → 64 B 行 | 牵连 `axi_ram` 猝发检查与拍计数 → 回退 | §4.6 行宽是跨模块迁移 |
| P21 | I-Cache 32 组 → 64 组 | 单元 T7/累计计数耦合 → 回退 | §4.7 瓶颈在测试耦合，需先重构测试台 |

### 8.3 双发射的最小可行方案（若要做）

**目标**：IPC 1.2~1.35 → CM 3.9~4.4。**代价**：面积大幅上升，③ 会明显下降。

| 部件 | 现状 | 双发射需要 | 面积影响（估） |
|---|---|---|---|
| 取指 | 每周期 1 条（I-Cache 1 读口） | **2 读口 I-Cache** 或 2 字/拍取指缓冲 | data_mem 端口翻倍 → +DRAM 或 LUTRAM |
| 译码/发射 | 单条 | 双发射槽 + 相关性检查（同拍两条之间的 RAW） | +300~600 LUT |
| 寄存器堆 | 1 写口 / 2 读口 | **2 写口** + 4 读口（或写回仲裁） | 寄存器堆面积 ×1.5~2 |
| ALU | 1 个 | 2 个（第二条只能是 ALU/branch，不能是访存） | +400~800 LUT |
| 访存 | 1 条/周期（单 LSU） | 保持单 LSU，**第二条发射必须是 ALU 类** | LSU 不变 |
| 分支 | EX 解决，2 拍惩罚 | 建议同步改为 ID 解决（1 拍） | ID 组合路径变长 |
| 退休 | 顺序单条 | 顺序双条 + 双端口退休记账 | +100 LUT |

**关键约束**：CoreMark 的指令流里只有约 **45~55%** 能与前一条配对（ALU+ALU、ALU+load）。
所以双发射的实际 IPC 上限约 **1.3~1.5**，对应 CM **3.7~4.3** —— 勉强够 4.0，但没余量。

**风险**：
1. 面积上去后 ③（CoreMark/kLUT）会掉，而 ③ 是并列评分项；
2. 27 MHz 时序余量目前只有 setup +15.2 / hold **+0.024 ns**，寄存器堆双写口与双 ALU 会压 setup；
3. 这是一次**前端 + 发射 + 寄存器堆 + 退休**的成组重写，必须像 §4.6/§4.7 教训那样
   先重构测试台，再动 RTL，否则又会陷入"追测试尾巴"。

### 8.4 建议的阶段顺序（每步都可独立交付、独立上板）

1. **测试台重构**（前置，无性能收益但解除三次失败的共同瓶颈）：
   每个用例独占地址区间、进用例前清零 `bursts/beats_out/inject_at` 等观测量。
2. **几何迁移**：I-Cache 64 组（4 KB）→ 预期 ① +3~4%，③ −6%（需权衡并如实并列报告）。
3. **store 缓冲（成组版）**：补 store→load 转发 + halt 排空点 → 预期 ① +5%。
4. **ID 级分支解决**：惩罚 2→1 拍 → 预期 ① +1.8%。
5. **双发射**：前三步做完后，IPC 约 0.85~0.90（CM 2.95~3.11），
   再叠加双发射到 IPC 1.25 → **CM 4.3**。

> 结论：**3.0~3.1 是单发射的现实终点；3.5/4.0 必须走第 5 步。**
> 我不会声称单发射能到 3.5——那与 IPC≤1 矛盾。

## 9. P25 方案（未实施，下一轮首选）：把 store 数据搬到"请求拍"

### 9.1 为什么这条和 P19 不一样

P19 错在**把 AXI 写事务延后**（受理即回答、写排队后台发），
结果破坏了 `store→load` 与非命中读的顺序（ISA case 5 挂）以及停机排空（halt-reset 挂）。

本方案**不延后任何写事务**：AXI 写仍在受理拍就发起，只是
**让 LSU 在请求拍就把 store 数据递出来**，D-Cache 在受理拍直接抓。
访存全序完全不变，只是少了一次"递数据"的往返。

### 9.2 现状与收益

```
REQUEST 拍（等 req_ready）→ WRITE_DATA 拍（w_valid/w_data）→ D-Cache 在 ST_WR_REQ 抓
```
`wdata_store` = **10.9M 拍 / 288M = 3.8%** 全部是"为了递一个数据多等一拍"。

预期：`wdata_store` 归零，`request_store`（5.1%）也会部分缩短 → **① +3~4%**（2.6948 → 约 2.80）。
面积：**不增反减**（可去掉 W 通道的一级 mux 与 `value_q` 握手的部分逻辑），对 hold 友好。

### 9.3 改动清单（两个模块，必须一起改）

**① `rtl/core/lsu_axi.v`（约 4 行）**
- 在 `REQUEST` 状态就把数据递出去：
  ```verilog
  assign eng_w_valid = rst_n && (state==WRITE_DATA || (state==REQUEST && is_store && op_valid));
  assign eng_w_data  = (state==REQUEST) ? (store_value << (8*address[1:0]))
                                        : (value_q << (8*address_q[1:0]));
  assign eng_w_strb  = (state==REQUEST) ? strb_of(size) : strb_of(size_q);
  ```
- `REQUEST` 受理后直接 `state <= READ_WAIT`（存）——**删掉 WRITE_DATA 这一跳**。

**② `rtl/core/dcache_axi.v`（约 10 行）**
- `ST_IDLE` 受理 store 时，若 `w_valid` 已为高，则**当拍锁存** `wdata_q/wstrb_q`
  （不再等 `i_w_ready`）。
- 引擎的 W 拍改由内部寄存器驱动：`.w_valid(<写事务在途>) .w_data(wdata_q) .w_strb(wstrb_q)`，
  因为 LSU 现在不会在下一拍再递一次。
- 写通合并与 `b_valid` 的回答时机保持"受理拍即回答"（数据已到齐，且写事务照常发起）。

### 9.4 必须过的判据（与 P19 同一套，缺一不可）

- `ISA 15/15`（**特别是 case 5 `store→load`**）与 `halt-reset 5/5`
- `RAM 20/20`、单元 5/5、`icache 1/1`
- 20 迭代 A/B：**五项 CRC 逐项相同**，且 `wdata_store` 应显著下降、`request_store` 不恶化
- 768 迭代 + PDS（**先 `set_switches.py status` 确认 ON，并用面积断言核对**，见 §4.10）+ 上板

### 9.5 剩余"不加面积"候选（按收益排序，供排队）

| 编号 | 内容 | 预期 ① | 面积 | 风险 |
|---|---|---|---|---|
| **A（本节）** | store 数据搬到请求拍 | +3~4% | 略降 | 中（两模块 + 回答时序） |
| B | 分支在 ID 解决（惩罚 2→1 拍） | +1.8% | 基本持平 | 中高（IFU 重定向 + flush） |
| C | I-Cache 在受理拍就发 AR（省 1 拍/缺失） | +0.24% | 持平 | 低 |
| D | 双发射 | IPC>1，唯一能过 3.457 | **大幅上升** | 极高 + ② 必破 |

**加面积的候选已全部关闭**（§4.8/§4.10：hold 余量只有 0.024 ns，
4 KB I-Cache 五个种子 hold 全不闭合）。所以在不放开 guardband 的前提下，
A→B→C 全部做完大约 **2.80~2.85**，这是单发射 + 零面积增量能到的现实区间。

## 11. P25 落地结果（2026-10-19 04:40）：① 提升 1.6%，② 尚差一个能闭合的种子

### 11.1 做了什么

把 store 数据提前到**请求拍**递给 D-Cache，LSU 从此不再进入 `WRITE_DATA`。
与已回退的 P19 的本质区别：**不延后任何 AXI 写事务**，访存全序不变。

- `lsu_axi.v`：`eng_w_valid/eng_w_data/eng_w_strb` 在 REQUEST 拍即有效；受理后直接进
  `WRITE_WAIT`；`eng_b_ready` 在受理拍即为高。
- `dcache_axi.v`：受理 store 当拍锁存数据、当拍做写通合并、数据 RAM 段当拍回 OKAY；
  引擎 W 拍改由内部寄存器驱动（`wpend_q`）。
- `tb_lsu_axi.sv`：激励（受理拍采样 W、受理拍给 B）+ 计分器（W 计数改为受理拍）同步更新。

### 11.2 判据（全绿）
