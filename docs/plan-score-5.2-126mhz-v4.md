# 5.2 CoreMark/MHz + 120 MHz 执行计划 v4（按模块，先量后改）

> 起点：`3da4bae` 之后的实测定标（见 v3 §1–§4，不再重复）。
> 本轮不推翻 v3 的定标，只把"到不了"换成"分几块、每块值多少 ns / 多少周期"，
> 然后按模块一块一块改、一块一块量。

## 1. 两个缺口，都换算成可分配的数

```
分数   253,664 周期/迭代 → 需要 192,307  ⇒  −61,357 周期/迭代 = −1.23 M 周期 / 20 迭代
频率   26.647 ns（布线后实测）→ 需要 7.94 ns  ⇒  −18.7 ns，即 −70%
```

上一个 20 迭代窗口里，`STALLDBG load_use = 1,714,576` 周期。**1.23 M 正好落在这一项里**，
所以分数这条线不需要"再想一个优化"，只需要把这一块里真正必须停的部分和不必停的部分分开。

## 2. 频率：26.647 ns 的真实分解（`p7_path40b/report_timing`，逐 cell 读出来的）

```
w_rd_h[4]  → 操作数选择网络（N190 / rd_valid_h / u_regs / N296）      4.4 ns
           → fwd2 → u_mul 4 级 DSP 级联（12.06 → 21.07）              9.0 ns   ← 最大一块
           → alu_a_h（lane1 操作数）→ 比较 → 目标加法 → 预测校验      ≈3.1 ns
           → perf_inst/cnt[*] 的 CE 级联                              4.6 ns
```

**为什么乘法会在 lane1 的输入上**：`fwd1_h/fwd2_h` 的第一优先级是包内旁路
`lane0_raw1 ? ex_value_w : ...`，而 `ex_value_w = rr_mul ? mul_y : ...`。
也就是说"lane0 是乘法、lane1 读它的结果"这一种包，把 4 级 DSP 级联整个塞进了
lane1 的 ALU 前面。**这种包在 CoreMark 里占比极小**（乘法本身少），
但代价是 9 ns —— 这是全设计最不划算的一笔交易。

⇒ 处理：**拒绝"lane1 读 lane0 的 mul/div 结果"这一种配包**（不是 v2 §26 那种
"拒绝一切包内 RAW"，那条会毁掉 ISA 用例），并且把该旁路输入改成只接 `alu_y`。
预计 −9 ns。这不是"少发一路"的吞吐损失：v2 §26 的教训恰恰是"拒绝的面要窄到
只剩做不到的那一种"。

## 3. 模块化清单（一次提交只动一个模块）

| 序 | 模块 | 改动 | 目标 | 预计收益 | 面积 |
|---|---|---|---|---|---|
| R1 | `rv32_top` | `m_value` 取 EX 组合结果；`load_use` 只对"需要 EX 入口寄存值"的消费者成立（load/store/csr） | 分数 | −1.0 ~ −1.3 M 周期 | FF 0（不加寄存器） |
| R2 | `rv32_top` | 拒绝 `lane1 ← lane0 mul/div` 的配包；包内旁路输入改 `alu_y` | 频率 | −9.0 ns | LUT ↓ |
| R3 | `rv32_top` | 分支结果（taken/target/predict-check）寄存一拍，重定向在 M2 生效 | 频率 | −4.6 ns | +FF ≈ 70 |
| R4 | `soc_config.vh` + SoC | 交付配置关 `PERF_ENABLE`（skill §9.7 硬要求） | 频率/面积 | −4.6 ns | −594 LUT |
| R5 | `dcache_axi` | refill 改 critical-word-first（先回请求字，再填其余） | 分数 | −0.2 M 周期 | 0 |

R2+R3+R4 相减：26.647 − 9.0 − 4.6 − 4.6 ≈ **8.4 ns**（≈119 MHz），
剩下的差额靠布局（40 MHz 那次布线本身带 −1.65 ns 的松弛，说明工具在这个约束下没尽力）。
**这不再是"砍 70%"，而是三块可独立验收的改动。**

## 4. 执行结果（一次一条，逐条实测）

### R2 拒绝「lane1 读 lane0 的乘/除结果」—— 保留

### 频率：40 MHz 满足式约束不再可信（教训 §37）

`p8_path40` 报 `All Constraints Met`、WNS **+1.053**，但同一份报告里
`Logic 4.038 ns (17%) / Route 19.447 ns (83%)` —— 约束太松，工具提前收敛、
走线占了八成。**这个数不是上限，是"工具停止努力的位置"**。
所以本轮改用 100 MHz（10 ns）这个"刚好违反"的档位来测真实边界。

## 5. 面积纪律

- `Δ(LUT+FF+LUTRAM) ≤ 0` 逐轮用 `check_area_budget.py --mode delta` 卡。
- R3 会加约 70 个 FF（taken/target/predict 的 32+32+5），由 R4 关掉 `perf_inst`
  （−594 LUT）与 R2 的 LUT 回收覆盖；**S 总量必须仍下降**。
- 每次提交信息写 `module: <名> ΔLUT/ΔFF/ΔLUTRAM`。

## 6. 验收顺序（每步都跑，不许跳）

1. `run_isa_e2e.py` 全 21 例（基线 20/21，case 21 是探针口径问题）。
2. `run_coremark_sim.py --image sim20_o2 --define RV32_DEBUG`，取 `Total ticks` 折算分数，
   并核对五项 CRC。
3. `run_pds_flow.py --freq 126 --mode synth`（综合 WNS + 面积），
   必要时 `--freq 40 --mode full` 测真实最长路径（126 约束跑不完布线）。
4. 结论写 `evidence/records/optimization/<阶段>/measurement.md`，一个实现一个目录。

## 7. 不做什么（明确排除，避免再走一遍）

- **不**拒绝"一切包内 RAW"（v2 §26，ISA 18/21）。
- **不**把乘法移出 ALU 拍换频率（v2 §27，−5% 分数）——但 R2 是"这一种包不配"，
  乘法的**执行**仍在 EX 拍，不影响 mul 的 CPI。
- **不**按 hit/miss 放行 load-use（v3 §33 的两次失败版本）。

## 9. 下一轮的唯一入口（把"到不了"变成"做什么"）

按 §36 的推导，分数与频率是**同一个改动**：

```
RD（读寄存器）: rf 读 + 旁路 mux + 地址加法  → 锁存 a/b 与 ex_addr
EX（执行）    : a/b + 上一拍生产者旁路 + ALU + cache 访问（用锁存地址）
```

- 分数：load 数据与 ALU 结果同拍落地 ⇒ `load_use` 整块（1.71 M）消失 ⇒
  (6.96 − 1.71 − 1.886)/20 = 168 k 周期/迭代 ⇒ **≈5.95 CM/MHz**，留出余量打 5.2。
- 频率：两段各约 6 ns，126 MHz 的 7.94 ns 预算有余量；乘法必须独占一级
  （2 拍延迟，代价 v2 §27 实测 −4.6%，在 5.95 的基础上仍 ≥5.6）。
- 风险点（必须一次到位）：分支结清随之后移一拍，`br_miss/kill_young/redirect`
  这套冲刷逻辑要整体搬到新边界；改完先用 ISA 21 例卡，再用五项 CRC 卡。
