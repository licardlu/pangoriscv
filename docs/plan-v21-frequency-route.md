## 1. 切②：为什么前两次失败、第三次怎么成

### 1.1 前两次失败的机制（lesson 88 只记了现象，这里补机制）

`serial_q` 的置位条件是 `id_accept && id_serial`，而 `id_serial` 是**已经在 ID 里**那条
指令的标志 ⇒ 紧随串行指令之后的那条会**在屏障升起前漏进 ID 一拍**。
于是相邻两条 CSR 指令只隔 1 拍，后一条正好在**前一条提交的同一拍**进 M2。

而 CSR 的写在 WB 的**边沿**才落地 ⇒ 任何"读提前到 M2"的做法都差半拍。
更硬的一条：`csr_new = w_csr_old | w_csr_src` 既是写回 CSR 的新值、也决定 `rd`，
**两者必须是同一个采样** —— 所以"读改早、写回另取来源"也不行。

探针实证（`--cases 6`，6 秒）：

```
CSRN commit=1 addr=340 wd=ffffffff mscr=00000000 nsc=ffffffff   <- csrrw 写 mscratch
CSRN commit=1 addr=340 wd=00000000 mscr=ffffffff nsc=00000000   <- csrrs 读到旧值 0，又写回去
```

`csrrs rd,csr,x0` 语义上不写，但 `commit` 只看 `w_commit && w_csr` ⇒ 把 0 写了回去。

### 1.2 第三版的三处改动（缺一不可）

1. `csr_native` 拆**三个**地址端口：`addr`（提交写）、`raddr`（取值，接 **M2**）、
   `iaddr`（合法性判断，接 ID）。读的 12 路 mux 从此只喂一个寄存器。
2. `wb_value = w_csr ? w_csr_old : w_value` 且 `w_csr_old <= csr_rdata`（M2 采）。
   `w_valid` 与 12 路 CSR mux 从 RF 写口前面彻底消失。
3. `serial_q` **早一拍置位**：`id_accept && (dec_serial || id_serial)`。
   相邻 CSR 指令正好隔开 1 拍，M2 取值落在前一条提交之后的周期。

第 3 条是承重的：只做 1+2 就是 v19 的第二次失败（ISA 19/21）。

### 1.3 判据

```
Total ticks : 3,810,700   （逐位不变）
五项 CRC    : 0x4983 / 0xe714 / 0x1fd7 / 0x8e3a
ISA e2e     : 20/21       （case 6 CSR read/write、case 7 mcycle 全过；只剩基线红的 case 21）
```

## 2. 切⑥：功能正确，但工具链吃不下

实现（`docs/patches/cut6-deferred-dcache-write.patch`）：store 命中的阵列写改成
`sw_we_q/sw_idx_q/sw_data_q/sw_strb_q` 寄存器输出、下一拍落地；读侧加
`sw_idx_q == rd_didx` 的 10 位比较 + 字节 mux 做 store→load 转发。
被删掉的是 `N4033[0]`（fanout=256，单根网线 **2.58 ns**，原路径尾部）。

验证：ticks 3,810,700 / CRC 0x4983 / ISA 20/21 —— **全对**。

**但它让 PDS 的 `tech-mapping phase 2` 从 2~3 分钟变成 40+ 分钟不结束**
（CPU 97%、内存 3.0→3.2 GB 持续涨、无任何报错）。去掉该改动后 2m52s 完成，
五次复现一致；给四个阵列加 `(* syn_ramstyle = "distributed" *)` 也无效（另一次 9 min 仍不结束）。

⇒ **不进交付树**，补丁封存。这是"功能正确 ≠ 能交付"的第三种形态
（前两种：分数不够 lesson 85、ISA 挂 lesson 88）。

## 3. 120 MHz：本轮用硬数据关死

| 约束 | 摆放后最差路径 | 摆放 slack | 说明 |
|---|---|---|---|
| 8.301 ns（120 MHz）| **14.07 ns** | **−5.77 ns** | 摆放器已经尽力（比 60 MHz 那次还紧 1.4 ns）|
| 16.667 ns（60 MHz）| 15.50 ns | +1.165 ns | 摆放器放松了努力 |
| 20.000 ns（50 MHz，交付）| 18.32 ns | +1.683 ns | 布线后 19.355 ns（+0.645）|

**结论**：切② 之后这条网表的"摆放地板"约 **14 ns**（≈70 MHz）。到 120 MHz 还差 5.8 ns，
需要**两级流水**（每级 ≥4,945 拍的重定向代价），而 5.2 分只剩 1,772 拍余量。
⇒ **5.2 分与 120 MHz 在"2 发射 + 现微架构"下不可同时成立**，本轮有摆放实测支撑。

### 3.1 剩下唯一还有价值的零拍候选（留给下一轮）

`alu_y → fwd1_h → lane1 地址加法器`（③+④ ≈ 5 ns）。它只因为**同包内 RAW 且 lane1 是访存**
才存在，而 ISA 17/18 正是覆盖它的用例 ⇒ 不能靠"禁止配对"消除。
可行方向：lane 0 的 ALU 若为 `add/addi/sub`，lane 1 的地址写成
`alu_a + alu_b + imm_h`（三输入 CSA + 一条进位链），**绕过 ALU→mux 两级**，
理论省 3~4 ns 且不花一拍。属结构性改动，需单独立项。

## 4. 交付目标：55 MHz（为什么不是 60）

布线在摆放之上还要 1.0~2.4 ns（交付那次 1.04 ns；51 MHz 那次 2.4 ns）。

- 60 MHz：摆放 +1.165 → 布线后 −0.6 ~ +0.2 ns，**五五开**。
- 55 MHz（18.18 ns）：按 0.85×周期 的摆设规律，摆放 slack 约 +2.0~2.7 ns
  → 布线后 +0.3 ~ +1.3 ns，**有真实余量**。

只跑得起一次满流程（合成 2 min + 摆放 3 min + 布线 **5~6 h**），所以取 55 MHz。
镜像 `hw_i2900_55`：2900 迭代 × 190,535 拍 ÷ 55 MHz = **10.05 s**（满足 ≥10 s）。

## 6. P56 追加：55 MHz 实跑结果把结论改写了两次（2026-10-24）

### 6.1 55 MHz 满流程：Fail，WNS −1.595

`build/p50r55`（切②、无 S1+S2、无切⑥）。摆放 **+1.256 ns**，布线后 **19.776 ns**
（布线在摆放之上又吃 **2.85 ns**），2,222 个失败端点、TNS −537.963。
证据：`evidence/records/optimization/p50r55-cut2-fail/`。

**最差路径不再是 CSR/AGU/D\$，而是 lane-1 乘法器**：

```
rr_inst[21] -> u_regs -> alu_b mux -> u_alu(4 级) -> fwd1_h -> u_mul_h 4×APM -> prod[60] -> ex_value_h
21.852 ns，DSP 级联约 8.8 ns
```

### 6.2 修复（P57）：把 `alu_y` 从乘法器操作数里摘掉

`packet_md_use` 只禁了"lane 0 是 mul → lane 1 读"，反方向一直没人管。
但**只加配对禁止无效**（综合读不到 `pair_ok`），必须给 lane-1 乘法器一套
不含 `lane0_raw` 的操作数（`fwd1_hn`/`fwd2_hn`）。

实测：**ticks 3,810,700 → 3,810,540（−160）**、CRC 0x4983、ISA 20/21、LUT 17,205。
见 lesson 92。

### 6.3 结论**又一次**被修正：D\$ 单拍是命门，"再切一级"这条路彻底关死

原本设想的"把 D\$ 访问挪到独立一级、换来 ~6.5 ns"被实测否掉：

```
load_in_ex  = 967,717
accepts     = 4,169,329
load_use_1  = 695,148   ⇒ 每迭代 ≈ 34,800 拍
```

（探针第一次量成 0，因为**稳态 ID 寄存器是空的**：`id_bypass` 一旦生效就自锁，
所有指令走组合译码直进 RR。必须用 `dec_*`。见 lesson 93。）

⇒ +1 拍 load 延迟要 **34.8k 拍/迭代**，5.2 的余量只有 1,772 拍。**不可行。**

### 6.4 120 MHz 的最终判定（三条独立证据）

1. **CPI 预算**：切一刀流水 = +4,945 拍起（重定向）；加宽到 3 发射才买得起，
   而 3 发射的 +面积会把 LUT 顶到 20k+，越过 18k 的布线门槛。
2. **访存不可分**：`load_use_1` = 34.8k 拍/迭代，任何加深访存流水的方案都要付 18% 拍数。
3. **摆放/布线实测**：120 MHz 约束下摆放后仍差 5.77 ns；
   55 MHz 满流程的 TNS 分布（2,222 端点、平均差 0.24 ns）说明 **fmax 由一整片
   18~19 ns 的近临界路径决定**，不是靠砍掉一条最差路径就能抬起来的。

⇒ **5.2 分 + 120 MHz 在本微架构 + PG2L100H 上不可同时成立。**
本轮的净收益是：**面积 −153 LUT、拍数 −160、两条真长链被结构性摘掉**，
交付档位从 50 MHz 往上试（P50r52 满流程进行中）。

### 6.5 还能做的（留给下一轮，需单独立项）

唯一没试过、且不花拍数的大杠杆：**把寄存器堆的组合读从 EX 路径上摘掉**
（`rr_d0` 预采样 + 把 `w_value` 提升为第三级旁路）。它在最差路径上值 ~1.5~2 ns，
而且**对一整片路径同时生效**——这正是 6.3 之后唯一可能抬 fmax 的形状。
风险：`lane0_raw` 的同包语义必须保住（ISA 17/18 判据），历史上有一次尝试因此失败。

## 7. P59：把"布线开销"量化到单根网线，找到两个从未用过的工具杠杆（2026-10-24）

### 7.1 最差路径的真实构成（`p50r52` 布线后，`report_timing.rtr`）

```
Logic:  3.685 ns (18.3%)
Route: 16.470 ns (81.7%)     共约 20 根网线  =>  平均 0.82 ns/根
Slack: -0.991 ns @ 19.231 ns
```

路径里几根典型的网线：

| 网线 | fanout | 延迟 |
|---|---|---|
| PLL `CLKOUT0` → 全局时钟缓冲 | 1 | **1.112 ns** |
| `rr_rs1[4]` → RF 读地址/旁路比较 | 39 | **1.051 ns** |
| 某个二级组合 | **2** | **0.958 ns** |
| `alu_a[11]` | 17 | 0.612 ns |
| `mem_from_h` | 126 | 0.861 ns |
| 时钟树插入（PLL→叶节点） | — | **2.597 ns** |

**三条结论（都比之前的推算更硬）**

1. **延迟的主因是物理距离，不是扇出也不是逻辑深度**：fanout=2 的一根线要 0.958 ns，而逻辑总量只有 3.685 ns。
   ⇒ 想提频，**唯一有效的动作是减少路径上的网线根数**（= 加流水级），减逻辑级数只值 ~1.5 ns。
2. **有效预算是 20.155 ns 的数据路径**（不能把时钟插入算进去）：报告里
   `Capture Clock Delay 2.254 / Launch Clock Delay 2.597 / Skew -0.154`，
   两者在 launch/capture 两侧**基本对消**，真正要压缩的是 `Logic+Route` 这 20.155 ns。
   于是"要几级流水"可以算出来：

   ```
   每级延迟 ≈ 3.7/S + 0.82 × (20/S) = 20.1/S          （S = 这一段被切成几级）
   120 MHz 需要 20.1/S ≤ 8.333  ⇒  S ≥ 2.4
   ```

   即**至少 3 级**才能进 120 MHz 的量级；考虑加级后每级的固定开销（tco、时钟偏斜、
   不可压缩的长线），实际需要 **4 级**。这不是调参能解决的。
3. **摆放器"够用就停"**：同一个网表，120 MHz 约束下摆放做到 14.07 ns，60 MHz 约束下只做到 15.58 ns，
   55 MHz 下 16.93 ns，50 MHz 下 18.35 ns。**slack 一转正，摆放器立刻收工**，它并没有做到极限。

### 7.2 由此得到的两个工具杠杆（此前 20 多轮从未用过）

`pnr` 的完整选项表（`puts [help pnr]`）里有四个直接针对上述第 3 点的开关：

```
-place_worst_slack <ps>              # 给摆放器一个"高于约束"的目标 slack，逼它做到极限
-gplace_times <n>                    # 摆放迭代次数
-enable_route_constraint_iterate     # 对最差路径做"布线-约束"迭代
-route_constraint_slack <ns>         # 迭代目标
-route_constraint_max_timing_path <n>
-route_constraint_iterate_times <n>
-optimize_routing_recovery TRUE      # 布线期做 recovery 分析
-slack_prior_in_global_router TRUE   # 全局布线按 slack 优先
-dc_duplication TRUE                 # 复制驱动单元，压 fanout
-refineplacement_cluster TRUE        # 按连接关系聚类
-plc_decongestion <n>                # 摆放拥塞模式
```

**这条路的价值**：它**不花一个拍数**。若能把摆放从 16.93 ns 压到 14.5 ns 且布线只加 1.5 ns，
55 MHz 就成立（需要 ≤18.18 ns）；而 5.2484 的分数完全不变。相比之下，任何"加流水级"的做法
都要付 ≥2,314 拍/迭代（前端）或 34,757 拍/迭代（访存），而 5.2 只剩 1,780 拍余量。

## 8. 5.2 分与 120 MHz 的**定量**不相容性（本轮结论，可逐项核对）

把 §7.1 的实测常数代入，可以得到一张"流水级数 → 频率 → 分数"的前沿表。
常数只有三个，全部来自实测：

| 常数 | 值 | 出处 |
|---|---|---|
| 现网表最差路径的数据延迟 | **20.155 ns** | `p50r52` 的 `report_timing.rtr`（Logic 3.685 + Route 16.470）|
| 每多切一级流水要付的重定向拍数 | **2,314 拍/迭代** | `mispred 46,285 / 20迭代`，即每个重定向 +1 拍 |
| 每多一拍 load 延迟要付的拍数 | **34,757 拍/迭代** | lesson 93 的探针（`load_use_1 = 695,148 / 20`）|
| 5.2 分的拍数上限 | **192,307 拍/迭代** | `20e6 / 5.2 / 20` |
| 当前的拍数 | **190,527 拍/迭代** | `3,810,540 / 20`，余量 **1,780** |

每级延迟模型：`20.1 / S`（S = 这一段被切成几级）。120 MHz 需要 `20.1/S ≤ 8.333 ⇒ S ≥ 2.4`，
实际 4 级。

| S | 预测 fmax | 附加拍/迭代 | 新拍数/迭代 | CoreMark/MHz | 5.2 |
|---|---|---|---|---|---|
| 1（当前）| 50~55 MHz | 0 | 190,527 | **5.2484** | ✓ |
| 1 + 前端一级（RF 读移出 EX）| ~56 MHz | +2,314 | 192,841 | 5.185 | ✗（差 0.3%）|
| 2（访存单独一级，load 延迟 2）| ~80 MHz | +34,757 | 225,284 | 4.439 | ✗ |
| 4（load 延迟 3）| ~120 MHz | +69,514 | 260,041 | 3.845 | ✗ |

**结论（用实测常数算出来的，不是估算）**

1. **只要把访存挪出 EX，分数就掉到 4.4 以下**，因为 5.2 只剩 1,780 拍余量，而一拍 load 延迟
   值 34,757 拍。
2. 唯一"几乎免费"的加级是前端那一级（+2,314 拍 = −0.063 分），但它只把 RF 读移出 EX 路径
   （≈2.1 ns），**买不到 120 MHz**，只买到 ~56 MHz，而且已经跌破 5.2（5.185）。
3. ⇒ **"5.2 分 + 120 MHz" 在本微架构 + PG2L100H + PDS 2022.2 上不可同时成立**，
   缺口是 **18% 的拍数**，与工具、seed、布线抽签都无关。
4. 因此本项目的可行目标是：**保住 5.2484 的前提下把频率推到能收敛的最高档**，
   并把这个"能收敛的最高档"用 §7.2 的工具杠杆推到极限。这就是本轮剩余工作。

## 9. 摆放余量不是频率的预测器：布线后的真实地板 ≈19.3 ns（P60，2026-10-24）

四次满流程的"摆放 → 布线"对照（同一族网表，`exp/split`，切②+P57）：

| 构建 | 约束 | 摆放后路径 | 布线后路径 | 布线增量 | WNS |
|---|---|---|---|---|---|
| `p48r50e`（交付）| 50 MHz | 18.32 ns | **19.355** | +1.04 | **+0.645** ✓ |
| `p55max2` | 55 MHz | 17.18 ns | **19.324** | +2.14 | −1.143 ✗ |
| `p50r55` | 55 MHz | 16.93 ns | **19.776** | +2.85 | −1.595 ✗ |
| `p50r52` | 52 MHz | 17.33 ns | **20.222** | +2.89 | −0.991 ✗ |

**摆放从 18.32 优化到 16.93（−1.39 ns），布线后的绝对值几乎不动（19.32~20.22，跨度 0.90 ns）。**

⇒ 两条结论：

1. **摆放器的时序估计是乐观模型**，而且越逼它越乐观：约束 50 MHz 时只差 +1.04 ns，
   约束 55 MHz 时差 +2.14~+2.85 ns。它优化的是估计线长，不是可布线的结果。
2. **修正（P62 之后）：不是一个"地板"，而是一个分布 19.32~21.53 ns（跨度 2.2 ns）。**
   `p50cut2`（cut2-only，LUT 17,021、摆放最好 +1.774）布线后是 **21.532 ns、WNS −1.532**，
   比交付的 19.355 差 2.18 ns——**摆放更好、面积更小，结果最差**。
   所以"摆放得更好"既买不到频率，也买不到可布性；**50 MHz 需要 ≤20.0 ns，
   正落在这个分布的中位附近 ⇒ 任何新网表能否过 50 MHz 都是五五开**，
   已交付的 19.355 ns 是比较好的一次抽样。

**因此 50 MHz 就是本网表形状的交付上限**（已交付 `pangoriscv_board50_i2800_5p248.sbit`）。
再往上只有两条路，都要付拍数：
- 加流水级（§8）：前端一级 +2,314 拍/迭代 → 5.185（已跌破 5.2）；访存一级 +34,757 → 4.44。
- 缩短路径上的网线根数（结构改写，同样要加级）。

### 9.1 一个仍然开着的技术手段（本轮已实现并验证接口）

**两步流程**：按 8.333 ns 只做摆放（实测地板 14.118 ns，两次逐位一致），
再按交付周期布线。工具接口已验证：
`--place-db <第一步>/place_route/pangoriscv_top_plc.adf` 会让 pnr **跳过摆放直接布线**
（传 `prr.db` 会报 `Flow-0013 ... should be of phase 'PLC'`）。
**实测结论：这条路也关掉。** `build/p60step2b` 从 14.118 ns 的摆放出发按 60 MHz 布线，
第 370 轮仍卡在 **760 根未布通**（最近 200 轮在 680~1280 之间震荡，不再下降）。
原因是**拥塞**：为了在 8.333 ns 下满足时序，摆放器把逻辑压得过密，路由器拆不开。
这正好复现了 `performance-analysis` 第 6 节早就记录的规律——**越过 50 MHz 后，
限制从"时序"变成"拥塞"**。

⇒ 所以"摆放得更好"既买不到时序（布线地板 19.3 ns），也买不到可布性（紧摆放更拥塞）。
两步流程的价值只剩下"验证了一个工具事实"：`-input_place_db_file` 必须传 PLC 阶段的 `.adf`。
