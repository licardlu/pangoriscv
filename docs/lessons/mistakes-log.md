# 可复用的错误经验（现象 → 查什么 → 怎么办）

> **收录标准：只有"下次遇到同样现象能直接用上"的才写这里。**
> 一次性事实（某一轮超时了、某个编号忘了改、某文件编码坏了）**不写这里**，
> 它们属于 `docs/verification.md` 的 §2 问题台账，或 §4/§5 交接记录。
>
> **遇到问题先翻这一页**，按现象找对应小节；找到了就照"怎么办"做，别从头再踩一遍。
> 新踩的坑先问自己"这条能被复用吗"，能，才加一条。

## 0. 【第一铁律】上板前先确认：位流里到底有没有"程序"

**任何"板上零输出 / 板子不跑"的排查，第一步不是看 RTL、不是看时序，而是先证明位流里有固件。**

判据只有两条，缺一不可：

1. 该位流的构建目录里**有** `program.hex` 与 `data.hex`（各 40,960 B）；
2. 该次综合日志里 **grep 到**这一行（正常）：
   ```
   I: [...] Loading memory data from file .../<build>/program.hex
   ```
   若出现下面这行，**位流是空的，板上必然零输出**：
   ```
   C: Verilog-3001: [...] Cannot open specified data file "program.hex"
   ```

**为什么要写成铁律**：2026-10-19 一整晚出现 6 次"上板零输出"，
全部被我判成 RTL 缺陷并逐一回退 —— 真实原因都是**为做种子扫描而新建的构建目录里
没放这两个 hex**，综合出的是**没有程序**的位流。代价：
- 白回退了 3 个本来可用的优化（store 数据提前一拍、pipe_slot 异步复位等）；
- 把错误结论写进了 §4.13 与 §4.17（"仿真全绿但板上不跑"）。**那三例的真因是缺镜像。**

**还有两个连带事实，必须一起记住**：

3. **镜像会改变时序结果**。同一份 RTL、同一个种子：带镜像 hold **−28 ps**，
   不带镜像曾报 `All Constraints Met (+18 ps)`（因为 BRAM 的实现/布局随镜像变化）。
   → **缺镜像的 PDS 结果，连时序都不可信**，不只是"上板不跑"。
4. **它只报 `C:` 级别**（comment），不是 `E:`，混在几千行综合日志里极易漏掉。
   → 所以不能"看日志找红字"，必须**主动 grep 那一行**。

### 0.1 正确流程（每次出位流都照做）

```powershell
# 1) 新构建目录里先放镜像
Copy-Item "$code\build\pango_native\program.hex" $newdir
Copy-Item "$code\build\pango_native\data.hex"    $newdir

# 2) 综合后必须确认这两行之一（有则继续，无则停下修）
Select-String -Path "$newdir\pds.log" -Pattern "Loading memory data|Cannot open specified data"
```

**只有看到 `Loading memory data from file` 才允许继续 PDS/上板。**

### 0.2 为什么"仿真过了、板子没分"一定是这里的问题

仿真用的是 `tb_*` 里的行为模型，**不读 `program.hex`**，所以仿真永远发现不了缺镜像。
而板上运行时 BRAM 里没有指令 → CPU 执行到空存储器 → **没有任何串口输出**。
因此出现"仿真分数正常 / 板上完全无输出"时，**先怀疑镜像，再怀疑 RTL**。

## 1. 数字类：分数 / 余量 / 资源被算大或算错

### 1.1 用被截断的字段反推分数 → 虚高 6.4%

- **现象**：算出的分数比另一处算法高好几个百分点，或"和预期对不上"。
- **查什么**：固件打印的 `Total time (secs)` 与 `Iterations/Sec` 是否**整数截断**
  （CoreMark portme 里 `HAS_FLOAT 0` 时必然截断）。
- **怎么办**：分数**只用 `Total ticks`**：`iterations / ticks × 1e6`。
  截断字段只可原样展示，不得参与换算。
  实例：P16 用 `Iterations/Sec=76` 算得 2.8444，真值 2.6740，**高 6.4%**。
- **为什么可复用**：任何"下位机打印整数、上位机想看小数"的场合都会重演。

### 1.2 引了"中间报告"当最终值

- **现象**：你写的 slack 与工具摘要、或别人重跑的结果差 0.1~1 ns，两边都"通过"。
- **查什么**：`place_route/*_timing_summary_after_hold_fix.txt` 是**中间快照**；
  收尾还会有一轮优化，通常是"用 setup 换 hold"（setup 降、hold 升）。
- **怎么办**：**slack 只从 `multiseed_summary.csv` 的 `single` 行取**，并把文件名写进文档。
  实例：27 MHz 中间 15.404/0.025、收尾 15.267/0.030。

### 1.3 LUT 报数不写阶段

- **现象**：同一份实现，你报的 LUT 和别人差 100~200，双方都说"取自资源报告"。
- **查什么**：三个阶段三个数 —— synthesis（Mapping Summary）、**device_map**、后布线。
- **怎么办**：**报 LUT 必须写阶段**，且分数换算用同一个数。默认用 device_map
  （可在 `multiseed_summary.csv` 的 `Used` 行核对）。

### 1.4 百分比标错对象

- **现象**："ticks −2.43%"，实际 ticks 只降 2.35%，2.43% 是另一个量的增幅。
- **怎么办**：写成 **"A 从 x 变成 y，±z%"**，把"哪个量"写死。
  `ticks` 降幅与 `CoreMark/MHz` 增幅**不是同一个数**（互为倒数）。

### 1.5 把自算的数写进标着"原始输出"的代码块

- **现象**：读者按代码块复现，发现和工具输出不一致。
- **怎么办**：标了"原始输出"的块，**每行都必须是工具/固件一次产出的原文**；
  推导值放正文并注明"由 X 计算"。这条比看起来重要：它决定别人信不信你的数据。

## 2. 证据类：事后无法自证

### 2.1 同一个构建目录跑两次实现 → 证据被覆盖

- **现象**：交付位流存在，但它对应的时序/资源/日志目录里是**另一次**实现的产物。
- **怎么办**：**一个实现 = 一个独立目录**，跑之前先建；先跑非交付频率、最后跑交付频率，
  让交付频率的产物留在目录里。目录内容：位流+SHA、`multiseed_summary.csv`、
  `report_timing.rtr`、各阶段 log、镜像 manifest。

### 2.2 `.gitignore` 把证据文件误伤

- **现象**：本地有这份证据，仓库里没有，别人 clone 下来无法自证。
- **查什么**：`*.rtr`、`*.sbit`、`*.log`、`build/` 这类通配规则会连带证据目录。
- **怎么办**：用**退出码**判断，别看输出：`git check-ignore -q <路径>`
  → **0 = 被忽略，1 = 会入库**。（`check-ignore -v` 对**否定**规则也会回显 `!模式`，
  别把"有输出"当成被忽略。）要找回就加否定规则，如 `!evidence/**/*.rtr`。

### 2.3 证据只留在 `build/` 里

- **现象**：清理构建目录后，某个数字再也找不到出处。
- **怎么办**：关键数字**先抄进证据文件，再清理**。顺序永远是"先归档、后删除"。

## 3. 测试类：绿灯可能是假的（最危险）

### 3.1 runner 用"黑名单"判据 → FAIL 永远匹配不到

- **现象**：测试台明明打印了 `FAIL`，runner 仍报 `PASS`。
- **查什么**：日志行是否带前缀（本项目是 `# `），而判据是 `line.startswith('FAIL')`
  —— 前缀一加就永远匹配不到。
- **怎么办**：判据改成**白名单**：必须看到显式成功标记（`TEST_PASS <名字>`）；
  失败行先去前缀再匹配。本项目已抽出 `sim/tb_verdict.py` 统一处理。
- **为什么可复用**：任何"抓日志判结论"的脚本都有这个陷阱，**黑名单判据天生不可靠**。

### 3.2 "全绿"必须先证明判据能变红

- **现象**：改完代码测试全过，其实是测试根本没在检查。
- **怎么办**：挑一处改动**临时改回旧版本**，确认测试**真的会失败**，再相信绿灯。
  本项目正是靠这一步发现"新用例在旧代码下也 PASS"，进而挖出判据 bug。

### 3.3 用例的"次数"会掩盖边界缺陷

- **现象**：2-bit 饱和计数器用例全过，实机却多出 10% 预测失败。
- **查什么**：用例训了几次？**偶数次**恰好停在饱和值，**奇数次**才暴露"饱和被降级"。
- **怎么办**：验证饱和/溢出/往返计数时，**奇偶两种次数都试**。

### 3.4 测试台不等 `ready` 就撤 `valid`

- **现象**：单元测试台偶发超时；换成真实总线却正常。
- **原因**：DUT 当时 `ready=0`，请求被静默丢弃，测试台以为已受理，于是死等响应。
- **怎么办**：驱动任何带反压的接口，都要 `while(!ready) @(posedge clk);` 之后再撤 `valid`。

## 4. RTL 类：快捷路径的四个坑

> 这一类最值钱：四个坑里三个都是"为了省一拍而引入的正确性问题"。

### 4.1 同拍应答忘了读写分流 → 死锁

- **现象**：基准跑到某个 PC 后完全停摆，退休数不再增长。
- **原因**：给"读命中当拍应答"开的快捷路径没排除写；一次**缓存写命中**被当成读应答，
  CPU 以为完成就退休，而缓存还在等它的写确认 → 双方互等。
- **怎么办**：任何"同拍/提前完成"的快捷路径，**第一步先确认它对读和写都成立**；
  把 writer 排除掉再谈优化。

### 4.2 绕过某个状态 → 该状态里的副作用全丢

- **现象**：功能正常、CRC 不变、测试全绿，但**质量指标变差**（如缺失率上升）。
- **原因**：把响应路径从"停在某状态"改成"直接回空闲"，而 LRU/计数器更新写在被跳过的状态里。
- **怎么办**：绕过某状态时，**逐个检查该状态里的所有副作用**（替换策略、计数器、
  握手标志、错误码记录）。这类回归只有查质量指标才看得见。

### 4.3 提前应答的地址范围按"总线窗口"定 → 吞掉错误响应

- **现象**：访问不存在的外设地址不报 fault，程序静默跑偏。
- **原因**：乐观完成的范围用了 256 MB 总线窗口上界，而非从站**真实可服务**的 16 KiB
  物理范围；空洞里的写拿到错误响应时已退休，无法再报异常。
- **怎么办**：**乐观完成/提前应答的范围按从站物理可服务范围定**，并写成显式参数
  （如 `DATA_RAM_LIMIT`），不要复用窗口常量。

### 4.4 一个信号服务两条语义不同的路径

- **现象**：整字访问正常，byte/halfword 访问偶尔变成总线错误。
- **原因**：`ARSIZE` 被硬写成"永远整字"—— 对缓存行填充成立、对 MMIO 单拍读不成立；
  且读路径没锁存 size，用的是**上一次**的值。
- **怎么办**：一个信号服务两条路径时先问"**两条路径的要求一样吗**"；不一样就用选择器
  分开，并确认每条路径都**锁存了自己需要的字段**。

### 4.5 "延后发出"的 store 会破坏顺序语义（P19 实测失败）

- **想做什么**：store 等 B 响应占全部周期 5.1%，于是想把数据 RAM 的 store 改成
  **受理即回答 CPU + 进一条后台缓冲延后发 AXI**，让 `req_ready` 不再等 B。
- **现象**：改完 `ISA 13/15`（case 5 `store→load`、case 15 定时器中断失败）、
  `halt-reset 4/5`（scenario 2 写触发失败）。
- **根因**：把写延后，等于让"已经退休的 store"在内存里**尚未生效**。这会破坏两类假设：
  1. **store→load**：后续 load 若未命中该行，会从 AXI 读到**旧值**
     （只有缓存行做了写通合并，非命中路径没有转发机制）；
  2. **停机/复位前排空**：测试（以及真实的 halt 流程）假设"store 退休后写事务已在路上"，
     延后之后排空窗口被推后，触发点可能错过。
- **正确做法**（若要重做）：必须同时提供
  ① **store buffer 转发**（load 命中缓冲或内存前先查缓冲）；
  ② **明确的排空点**（halt/reset 时强制 drain，且 `req_ready` 的反压要覆盖缓冲满）；
  ③ 非命中读在缓冲非空时全序等待（本次做了，但不足以弥补 ①② 的缺失）。
- **结论**：这不是"少一拍"级别的改动，而是**访存一致性语义**的改动。
  在单发射、顺序退休、写通的核上，store 必须**在对后续访存可见前真正落地**，
  否则一定会踩上面两类假设。收益 5% 但代价是一次完整的内存模型重做。
- **纪律**：按"改不动就退回"处理——本次已完整回退，ISA/halt-reset 恢复 15/15、5/5。

### 4.6 改 Cache 行宽是"跨三个模块 + 一个联调 TB"的连带改动（P20 实测失败）

- **想做什么**：`if_wait` 占 8.6% 的周期，主要是 I-Cache 缺失成本。把几何从
  **32 组 × 2 路 × 32 B** 改成 **16 组 × 2 路 × 64 B**（容量仍是 2 KB、tag 宽度不变），
  顺序代码的缺失数应近乎减半，而面积不变。
- **实测过程（三次都失败，逐步逼近）**：
  1. 只改 `icache_axi`：`unit icache` 直接红 —— 测试台把 `ARLEN=7 / 8 拍 / 行尾 0x1C /
     最后拍 7` 全写死了。把期望改成跟随 `dut.LINE_BEATS` 后，又暴露
     **`line_addr` 还在按 32 B 清低 5 位**（`{tag,set,5'b0}`）→ 取错行。
  2. 改对 `line_addr` 为 `6'b0` 后，单元测试过了；但 **halt-reset 0/5、ISA 无结果**。
     根因是 `axi_ram.v` 的 `burst_ok` 写死 `len<=8'd7`（"最多八拍填一条 32 B 行"），
     **16 拍猝发被当成非法突发**。
  3. 把 `burst_ok` 放开到 `len<=8'd15` 后：**ISA 15/15 通过**，但
     **halt-reset 仍 3/5**（读触发场景 1、2 失败）—— 还有 8 拍/时序假设没有覆盖。
- **结论**：Cache 行宽**不是一个常量**，它同时牵动
  ① 位段（set/word/tag）与 `set_q/word_q/beat_q` 宽度、
  ② **行地址掩码**（最容易漏，且错得很隐蔽：数据字看起来是对的，只是取错了行）、
  ③ 猝发长度（`m_arlen`）**以及从机的猝发合法性检查**、
  ④ 所有把拍数/行尾写死的单元与联调测试。
  单点改动一定失败；正确做法是把它当**一次几何迁移**来做，四处同时改，
  并用 `dut.LINE_BEATS` 之类的参数把测试与实现解耦。
- **纪律**：三次都按"改不动就退回"处理，已完整回退，回归恢复
  `icache 1/1 / ISA 15/15 / halt-reset 5/5 / RAM 20/20`。
  保留的净收益：`tb_icache_axi.sv` 里把 `ARLEN/拍数/行尾/最后拍` 全部改成
  跟随 `dut.LINE_BEATS`（这次没吃到的收益，是下次的基础设施）。

### 4.7 扩 Cache 组数（8 KB 级）同样要过"联调 TB 这一关"

- **想做什么**：把 I-Cache 从 **32 组 → 64 组（2 KB → 4 KB）**，
  **只改组数、不动行宽**（这是 P20 失败后刻意收窄的风险面：不碰 `axi_ram` 猝发、
  不碰拍计数、不碰行地址掩码的位数）。
- **结果**：单元测试 T1–T6 全过（几何解耦生效），但
  **T7「猝发进行中被打断」超时**——因为它用的地址 `0x3000` 已被 T4 缓存过，
  命中后没有猝发可打断，`while(!(m_arvalid && m_arready))` 永远等不到。
  把 T7 换到新行 `0x0C00` 后，又出现 `bursts=12` 这类**累计计数**不匹配
  （T7 的 fork 遗留了未清的观测状态）。改动在"测试期望"这一层继续发散。
- **结论（比 P20 更具体）**：这类几何实验的真正瓶颈往往不是 RTL，
  而是**单元/联调测试里大量隐式的"地址—组—行—拍"耦合**：
  同一个地址被多个用例共用、跨用例的累计计数器、fork 分支的时序假设。
  正确做法是先做一次 **测试台重构**（每个用例独占地址区间 + 每次用例前清零观测），
  再动 RTL；否则每次都在追测试的尾巴。
- **纪律**：已回退 RTL，只保留**测试台的几何解耦**（`T1/T3/T6` 跟随 `dut.LINE_BEATS`、
  `T4` 用对 32/64 组都同组的地址、`T7` 换到独占新行），
  32 组几何下回归全绿：`icache 1/1 / ISA 15/15 / halt-reset 5/5`。

### 4.8 面积一涨，27 MHz 的 hold 就先破（P22 实测：+2.6% 性能但不可交付）

- **做了什么**：把 I-Cache 从 **32 组 → 64 组**（2 KB → 4 KB），只改组数、不动行宽。
  这次把 P21 的漏点补上了——`rd_index_q` 必须从 9 位加宽到 10 位，
  否则读回索引被截断、返回**另一行**的数据字（P21 的"数据不对但地址对"就是这么来的）。
  补上后：单元 1/1、ISA 15/15、halt-reset 5/5、RAM 20/20 **全绿**。
- **跑分确实变快**：768 迭代 ticks **284,997,892 → 277,725,088（−2.55%）**，
  IPC 0.7747 → **0.7949**，CoreMark/MHz **2.6948 → 2.7653（+2.6%）**，CRC 全同。
- **但综合不过**：LUT 13,503 → **14,485**（+982）、FF 8,507 → **9,836**（+1,329）。
  三个种子全部 **hold 违例**：seed 11 路由不收敛（2,700+ 未布通）、
  seed 23 hold **−0.017 ns**、seed 41 加强 hold 修复后反而 **−0.028 ns**。
  基线本来就只有 **+0.024 ns** 的 hold 余量，**面积一涨就先破 hold**。
- **结论**：赛题 ② 要求 `report_timing` 无失败端点，hold 破就意味着位流不可靠 →
  **这条优化不可交付，已回退**。① 赚 2.6%、③ 掉约 5%，还把 ② 弄破，不划算。
- **可复用**：本项目 **hold 是第一个被面积撞破的约束**（setup 还剩 12~15 ns，hold 只剩 0.024）。
  以后任何"加面积换性能"的想法，**先估 FF 增量**（这颗设计每 +1,300 FF 就会把 hold 打穿），
  要么同步做时序优化（少一级组合、少一片 LUTRAM），要么换不来。

### 4.9 BTB 索引散列不是杠杆（P23 实测，零收益）

- **想法**：预测器 32 项、索引 `PC[6:2]`、全 tag 比较。怀疑分支冲突导致 10.6% 的
  预测失败率，于是把高位异或进索引（零面积，只改连线）。
- **实测**：
  - `index = PC[6:2] ^ PC[31:27]`：**mispred 137,945，与基线一模一样**。
    原因：程序只占 `0x0000~0x3FFF`，高 5 位恒为 0，异或等于恒等。
  - `index = PC[6:2] ^ PC[12:8]`：ticks −0.07%（噪声），但 **mispred 反而升到 139,252**。
- **结论**：**CoreMark 在这个 32 项 BTB 上几乎没有冲突缺失**，
  10.6% 的失败率来自"冷启动 + 分支本身无规律"，不是容量/别名问题。
  要再降只能换算法（锦标赛/局部历史），那是**加面积**的方向——而 §4.8 已证明
  加面积会先破 hold，所以这条在 27 MHz 下也基本关死。
- **可复用**：**先确认"高地址位是否真的在变"**再设计散列；小程序镜像的高位恒 0，
  任何只用高位的散列函数都会退化成恒等。改完必须比较 `mispred`，
  只看 ticks 会被 `i_miss` 的随机波动骗过去。

### 4.10 综合前必须核对"开关"和"面积"，否则会拿一个假位流当真（P24 实测踩中）

- **现象**：4 KB I-Cache 改完后按 P22 的教训换种子扫 PnR，seed 7 报
  `All Constraints Met`、setup **+16.928** / hold **+0.239**、
  **LUT 7,774 / FF 2,932 / 端点 29,888** —— 看着是完美结果。
- **为什么这是假的**：2 KB 版本是 LUT **13,503** / FF **8,507** / 端点 **54,333**。
  **缓存变大而面积和端点腰斩**，物理上不可能 —— 真实原因是上一轮收尾跑了
  `set_switches.py off`，**三个开关关着，缓存根本没被综合进去**。
  那版"通过"的位流不是赛题配置，一旦烧进板子就是另一个设计。
- **怎么防**：
  1. **每次 PDS 前后都跑 `set_switches.py status`**，并把三个开关状态写进日志；
  2. **拿面积当断言**：LUT/FF/端点数应当与上一版同量级（缓存+2 KB 应是
     LUT 与 FF **上升**约 1,000）；**面积突变就要停下来查配置**，不要庆祝 slack；
  3. 把端点总数（`endpoint` 列）当作配置指纹，它比 slack 更能暴露"综合了别的东西"。
- **附带结论**：开关打开后重扫 seed **7 / 13**，hold 分别是 **−1 ps / −25 ps**，
  加上之前的 seed 11（路由不收敛）、23（−17 ps）、41（−28 ps）——
  **4 KB I-Cache 在本项目声明的约束下诚实收不了**（`pango_native.fdc` 明确
  "不添加人工 hold 不确定度"，所以不能靠加 guardband 把它凑过）。
  → ① 的 +2.6% 已在仿真验证，但 ② 过不了，**不可交付，已回退**。

### 4.11 改"LSU ↔ D-Cache 的 store 协议"必须同步改单元测试的引擎模型（P25）

- **想做什么**：`wdata_store` 占 3.8% 的周期，全是"为了递一个 store 数据多等一拍"。
  方案：让 LSU **在请求拍就把数据递出来**（`eng_w_valid/eng_w_data/eng_w_strb` 在 REQUEST 拍有效），
  D-Cache 在受理拍锁存并当拍回答，LSU 从此不再进入 `WRITE_DATA`。
  **注意这与 P19 不同**：P19 是延后 AXI 写事务（破坏顺序），本方案写事务照常发起。
- **实现结果**：两侧都改完（`dcache_axi.v` 加 `wpend_q`、受理拍锁存 + 当拍回答、
  引擎 W 改由内部寄存器驱动；`lsu_axi.v` 请求拍递数据 + 受理拍接受 B）。
- **失败点**：`unit 5/5 → 卡在 lsu_axi`，报 `Fatal: store lanes/backpressure`
  （`tb_lsu_axi.sv:75`）。原因：测试台的**假引擎**按旧协议断言
  "受理后 `eng_w_valid` 要连续 5 拍保持、`eng_w_data/strb` 要对"，
  新协议下 W 只在**受理拍**有效，测试台模型随即不成立。
- **结论**：这不是 RTL bug，而是**接口契约变了**——凡是"谁在什么时候递数据"的改动，
  都必须同时改 **单元测试里的对端模型**，否则会被判成功能回归。
  正确顺序：先改 TB 的引擎模型（在受理拍采样 W）+ 保留一个"W 迟到一拍"的负向用例，
  再改 RTL。
- **纪律**：本轮按"改不动就退回"处理，已完整回退，`unit 5/5 / ISA 15/15` 恢复。
  完整 diff 与验收清单保留在 `evidence/records/optimization/P18/measurement.md` §9。

---

- **补充（第二次尝试，按"先改 TB 再改 RTL"的正确顺序）**：
  先按新契约重写 `tb_lsu_axi.store_case`（在**受理拍**采样 W、受理拍给 B），
  同时改两侧 RTL。结果仍然失败，但**推进了一层**：
  - 第一层 `Fatal: store lanes/backpressure` → 已解决（模型改对了）；
  - 第二层 `Fatal: LSU side effect counts` → **测试台的副作用计数器**
    （`requests/writes/completions`，按 `eng_w_valid && eng_w_ready` 计 W 拍）
    在新协议下不再成立，因为 D-Cache 不再用 `eng_w_ready` 握手，LSU 也不等它。
- **教训升级**：协议改动要连带改**三样**，缺一不可：
  ① 对端 RTL 模型；② 单元测试的**激励**（什么时候采样）；③ 单元测试的**计分/断言**
  （握手次数、副作用计数、覆盖点）。只改前两样，会在第三样上被判失败。
- **纪律**：两次尝试都完整回退，`unit 5/5 / ISA 15/15` 恢复。
  这条拆成了三个独立可验证的小步（模型 → 激励 → 计数），下次按此顺序逐个子步提交。

### 4.12 构建开关是"被跟踪的文件"，`git add -A` 会把开关状态一起提交

- **现象**：两次"只改文档"的提交（`0f21436`、`c43ae79`）里，
  `firmware/code/rtl/core/soc_config.vh` 被一起提交，三个宏被注释掉：
  ```diff
  -`define CACHE_ENABLE
  -`define PREDICT_ENABLE
  -`define PERF_ENABLE
  +// `define CACHE_ENABLE
  ```
  也就是说 **HEAD 一度处于"缓存关闭"状态**，而位流和成绩是"全开"配置下产生的。

- **可复用**：**任何"改文件来改配置"的工具，都是提交污染源。**
  交付前要核对的是"仓库里那份配置"，而不是"我这台机器当前那份"。

### 4.15 推测（待 ILA 验证）：P25 的 `wpend_q` 可能给旧事务多发一拍 W

- **背景**：P25 在仿真里跑通 768 迭代（CRC 全同），PDS 也 `All Constraints Met`，
  但**板上零输出**。仿真与板子的差异之一是**从机响应延迟**。
- **可疑时序（复核 P25 diff 后发现）**：
  ```verilog
  wire eng_w_valid = rst_n && wpend_q;          // 只看"欠一拍"
  if (wpend_q && i_w_ready) wpend_q <= 1'b0;    // 一拍就清
  ```
  `wpend_q` 在**受理拍**置 1。但受理那一拍，写引擎可能正被**上一笔写**占着
  （上一次的 `AW` 还没走完，引擎停在 `WR_PREP` 且 `i_w_ready` 为高）。
  于是下一拍 `eng_w_valid=1` 会被**上一笔的 AW** 当成它自己的 W 拍取走，
  等于给旧事务多发了一拍 W → 从机收到的 beat 数与 AW 的 len 不匹配 → 卡死或报错。
  - 仿真里 AXI RAM 响应快，几乎不会出现"受理时引擎还被占着"；
  - 板上真实 RAM 慢，这个窗口就打开了 —— 与"仿真过、板上挂"完全吻合。
- **正确修法**：把 W 拍的使能绑定到**本次事务已被引擎接收**，而不是"欠一拍"的计时器：
  ```verilog
  reg wsent_q;                                   // 本次 AW 已被引擎接收
  if (i_write_accept && i_req_ready) wsent_q <= 1'b1;
  if (eng_w_take)                    wsent_q <= 1'b0;
  wire eng_w_valid = rst_n && wsent_q;           // 只有本事务的 AW 在飞时才是 1
  ```
  同时补一条**定向用例**：让引擎在受理时正处于上一笔写的 `WR_PREP`，
  断言"不会出现第二拍 W"。
- **验证顺序（下一轮按此执行）**：
  1. 先在 `tb_unit_lsu_axi` / dcache 单元测试里构造"引擎被占"的场景（仿真可复现）；
  2. 修好后再跑 `ISA/halt-reset/RAM` + 768 跑分；
  3. **PDS 之后必须上板**（§4.13），板上看到 `284,997,892 → 280,487,382` 才算成立；
  4. 若仍无输出，再用 ILA 抓 `aw/w/b` 三通道对照（顺带补齐赛题 C02 的波形证据）。

### 4.16 批量改多个文件时，脚本中途退出会留下"改了一半"的树

- **现象**：用脚本按顺序改 3 个文件（`lsu_axi.v` → `dcache_axi.v` → `tb_lsu_axi.sv`），
  第 2 个文件的锚点不存在（因为上一次已回退，锚点随代码消失），脚本 `sys.exit` 退出。
  结果：**文件 1 已写入、文件 2/3 未动**。
  回归立刻给出 `ISA 0/15`、`halt-reset 4/5` —— 看起来像"改坏了 RTL"，
  其实是**半成品状态**。
- **为什么危险**：如果只看失败数字去调试，会去查一个根本不存在的"新 bug"；
  真正的错误是"只改了一半"。
- **怎么办（三条）**：
  1. **先把所有锚点在内存里全部校验通过，再统一写盘**（两阶段提交）。
     改脚本时最容易忽略这一点——边校验边写盘，前面几个文件就已经落盘了；
  2. 每个文件**独立提交**（一个文件一个 commit），失败时可精确回退；
  3. 脚本退出码非 0 时，**先 `git status` 看哪些文件被改了**，再决定继续还是还原。
- **可复用**：**回归突然大面积失败时，先确认"改动是不是完整落地"**，
  再怀疑逻辑。`git status` + `git diff --stat` 比读波形快得多。

---

- **第三次尝试（P28，按 §4.15 修竞态、按 §4.16 两阶段提交）**：
  `unit 5/5`、`ISA 15/15`、`halt-reset 5/5` **全过**，20 迭代 A/B 与 P25 完全一致
  （`7,300,826`，CRC 全同，`store req=0`）。
  但 `run_ram_tests` 里的 **`lsu-seed1`** 报 `Fatal: LSU_RAM timeout` ——
  那是**第三个**按旧契约建模的测试台（直接驱动 LSU + RAM 的集成 harness），
  它期望 W 在受理后单独握手。
- **教训再升级**：一次 store 协议改动会牵动**至少三个**测试台模型：
  ① `tb_lsu_axi`（单元，引擎模型 + 计分器）
  ② `tb_lsu_ram`（`run_ram_tests` 里的集成 harness）
  ③ 任何在 `run_*` 里直接给 `eng_w_valid/eng_w_ready` 建模的地方。
  **改协议前先 `grep eng_w_valid`/`eng_w_ready` 把全部落点列出来**，逐个评估，
  否则会连续三次撞在不同 harness 上。
- **可复用**：搜索协议信号名，比逐个跑测试发现失败更快；
  `grep -rn "eng_w_valid\|eng_w_ready" tb/` 应在动手前就做。

---

- **根因（已定位到具体连线）**：`tb/axi/tb_lsu_axi_ram.sv:33-53` 把 `lsu_axi` 的
  `eng_w_*` **直连到 `axi_data_engine`**，中间**没有 D-Cache**。
  新协议下 LSU 一进 `WRITE_WAIT` 就不再输出 W 拍（数据已经在请求拍递过了），
  而引擎在 `WR_PREP` 才需要 W → **永远等不到 → `LSU_RAM timeout`**。
  真实 SoC 里 D-Cache 用自己锁存的 `wdata_q/wstrb_q` 驱动引擎，所以 SoC 仿真能过；
  这个 harness 直连引擎，就暴露了缺口。
- **最干净的修法（下一轮直接做）**：让 LSU **把 W 拍保持到引擎取走为止**，而不是"递一拍就撤"：
  ```verilog
  reg wtake_q;                                   // 本笔 store 的 W 拍尚未被引擎取走
  always @(posedge clk) begin
    if (!rst_n)                                  wtake_q <= 1'b0;
    else begin
      if (eng_w_valid && eng_w_ready)            wtake_q <= 1'b1;   // 已被取走
      if (fast_issue || state==REQUEST)          wtake_q <= 1'b0;   // 新的一笔 store
    end
  end
  ```
  `eng_w_valid` 的表达式在 `REQUEST / WRITE_WAIT` 两态下都保持有效，直到 `wtake_q` 置位。
  这样：① `tb_lsu_axi_ram`（直连引擎）能过；② 真实 SoC 不受影响
  （D-Cache 忽略 LSU 的 W，用自己的寄存器）；③ 语义上"数据可用直到被取走"更规范。
- **顺序（重要）**：先改 LSU 的 W 保持（单独一个提交，跑 `run_ram_tests` 验证），
  再把 P28 的 D-Cache 部分叠上去。**两个改动分开提交**，否则又会分不清谁坏。

---

- **第二步（叠加 D-Cache 部分）时的两个必须同时改的点**（P29 之后新发现的耦合）：
  1. `wtake_q` 的**置位条件必须限定在 `WRITE_DATA`/`WRITE_WAIT`**，不能让它被
     `WRITE_DATA`→`REQUEST` 那种"引擎恰好正为**上一笔**写准备"的 `eng_w_ready` 误置位：
     ```verilog
     if ((state==WRITE_DATA || state==WRITE_WAIT) && eng_w_valid && eng_w_ready)
         wtake_q <= 1'b1;
     ```
     否则就是 §4.15 那个竞态的**镜像版本**（这次错在 LSU 侧，把别人的 W 握手当成自己的）。
  2. `eng_w_valid` 要新增 `(state==REQUEST && store_q)` 与 `(fast_issue && is_store)`
     两个条件（D-Cache 在受理拍就要采数据），**但同时保留 `WRITE_WAIT && !wtake_q`**，
     两者缺一：少了前者 D-Cache 采不到数据；少了后者直连引擎的 harness 仍会 timeout。
- **这条再次印证 §4.11 的结论**：一个"谁在什么时候递数据"的改动，
  会在**双方**（LSU 与 D-Cache）各产生一个对称的归属判定，
  任何一侧写错都会表现成"偶发卡死"，而仿真快时看不出来。**必须两侧同时审。**

---

- **第四次尝试（P30，两侧对称改完）**：`unit 5/5`、`ISA 15/15`、`halt-reset 5/5` 全过，
  但 `ram_tests` 的 `lsu-seed1` 仍然 `LSU_RAM timeout`。
  说明 `wtake_q` 的置位域收窄 + `eng_w_valid` 双条件**还不足以**让"直连引擎"的 harness 通过。
- **仍然成立的部分**：P29（`wtake_q` 让 LSU 把 W 拍保持到被取走）单独上线是**全绿且行为中立**的
  （`RAM 20/20`、A/B 与基线完全一致），已保留在 `70681c7`。
- **下一步必须先读 `tb/axi/tb_lsu_axi_ram.sv` 的完整时序期望**（它给 `axi_data_engine`
  的 `READ_DELAY(20)/WRITE_DELAY(30)` 和它自己的检查点），
  再决定是改 LSU 还是那条 harness 的期望——**不要再猜**。
  读的时候重点看：它是否假设"受理后先有一个 W 拍、然后才等到 B"，
  以及 `wr()`/`rd()` 任务里对 `eng_w_valid` 的采样周期。
- **纪律**：四次尝试全部完整回退，回归恢复 `unit 5/5 / ISA 15/15 / RAM 20/20 / halt-reset 5/5`。

---

- **读完 `tb/axi/tb_lsu_axi_ram.sv` 后的关键事实（这次才看清）**：
  - 它把 `lsu_axi` 的 `eng_*` **直连** `axi_data_engine`，引擎再接 `axi_ram(READ_DELAY=20, WRITE_DELAY=30)`；
  - 它的 `ws` 计的是 **AXI 总线上的** `wvalid&&wready`（第 74 行），**不是** `eng_w_valid`，
    所以 LSU 侧"W 在哪个状态给出"它并不直接检查；
  - `LSU_RAM timeout` 来自第 131 行的**全局看门狗** `initial begin #50000; $fatal(...) end`
    —— **整个用例限时 50 µs**，不是某条断言失败。
- **因此失败只有两种可能，必须先用波形/打印分清**：
  1. **store 真的不再完成**（`wait(done_valid)` 挂住）——是功能 bug；
  2. **只是变慢**，总时长超过 50 µs——那是测试时长问题，改看门狗即可。
- **怎么一次分清**：在 `operation()` 的 `wait(done_valid)` 前后各打一条
  `$display("OP start/end t=%0t", $time)`，跑一次就知道是卡住还是超时；
  或直接把 `#50000` 临时放大到 `#500000`——若变绿则是"只是变慢"。
- **教训（第四次重复同一模式）**：**先把失败信息的来源查清楚**（是断言？是看门狗？是超时？），
  再动 RTL。前四次都把它当成"协议不匹配"去改 LSU/D-Cache，方向从一开始就没验证过。

---

- **决定性证据（本轮）**：同一个 `lsu-seed1` 用例，**通过时只用到 3,130 ns**
  （看门狗 50,000 ns，仅占 6%）。所以 P30 的 `timeout` **不可能是"变慢"**，
  只能是 `wait(done_valid)` **永久挂住** —— "只是超时"的猜想被证伪。
  **判断"卡住 vs 变慢"最快的办法：看通过用例的 `$finish` 仿真时间离看门狗有多远。**
- **顺带定位到一个明确的 bug**：P30 里把引擎的 W 数据写成
  ```verilog
  assign eng_w_data = (state==REQUEST) ? (value_q << (8*address_q[1:0]))
                                       : (store_value << (8*address[1:0]));
  ```
  `WRITE_WAIT` 时 `state != REQUEST`，于是取的是**实时输入** `store_value/address`；
  而调用方在受理后立刻把它们改成垃圾（`tb_lsu_axi_ram.sv:93`
  `address=32'hdeadbeef; access_size=7; store_value=32'habcdabcd;`）。
  **正确写法：只要数据是"本笔 store 锁存的那份"，就必须一直用 `value_q/address_q/size_q`；
  只有受理的那一拍才用实时输入。**
  ```verilog
  assign eng_w_data = wdata_on_req || wdata_on_iss
                      ? (store_value << (8*address[1:0]))     // only on the accept edge
                      : (value_q     << (8*address_q[1:0]));  // every later cycle
  ```
- **可复用**：**"提前一拍递数据"的实现里，最容易错的就是"哪些拍用实时输入、哪些拍用锁存值"。**
  判据很简单：**数据必须一直代表"这一笔请求"**，所以除受理那一拍外，一律用锁存值。

## 4.17 store "受理即完成"这条路线的最终结论（P25~P32，六次尝试）

### 4.17.1 做了什么、结果如何

| 轮次 | 内容 | 结果 |
|---|---|---|
| P25 | store 数据随请求拍递出 | 仿真 +1.58%（`280,487,382` / **2.7381**）、PDS `All Constraints Met`、**板上零输出** |
| P28/P30 | 加 `wreq_q`/`wsent_q` 归属判定 | 仿真三门前全过，`lsu-seed1` **timeout** |
| P31 | 修"受理后用实时输入"的 bug | **全部判据首次通过**（含 `RAM 20/20`、`lsu-seed1`），768 仍是 `280,487,382`；PDS seed 41 `All Constraints Met`（+0.018）→ **板上仍然零输出** |
| P32 | 补读后写顺序门控（怀疑 UART 轮询被抢跑） | 仿真全过、A/B **零代价**，但 PDS 两种子 hold **−28 ps**（门控的组合逻辑把 hold 打穿） |

### 4.17.2 现在能确定的事实

1. **仿真完全无法区分这条改动的好坏**：`unit/ISA/RAM/halt-reset/icache/predictor` 全绿、
   768 迭代 CRC 全同、PDS `All Constraints Met`，**板上依然一个字节都不输出**。
2. 板上失败的表现是**配置成功（`done bit=1`）但串口无输出**，换回 P18 位流立刻正常
   —— 排除板子/串口/烧写流程。
3. **这不是时序问题**（P31 的 PDS 是 clean 的），是**功能/协议层面**的问题，
   而且只在真实 AXI 从机的延迟下才暴露。
4. 加顺序门控（P32）能修语义，但**在 27 MHz 下收不了 hold**（−28 ps，两种子同值）。

### 4.17.3 结论与建议

- **这条路线在当前 27 MHz + 0.024 ns hold 余量的约束下不可交付**：
  要么功能在板上不成立，要么为修功能而加的逻辑收不了时序。
- 若要继续，**必须先开放 hold 预算**（加 guardband 或做时序重构），
  否则"每加一条正确的门控就掉 30~50 ps"会把所有尝试都堵死。
- 交付位流保持 P18：`6C5D819C…CAF65`，板上实测 `284,997,892` / **2.6948**，
  已于本轮**再次上板复验通过**。

## 7. 上板类：工具、驱动、通道抢占

> 这一类是"代码全对、就是找不到板子"的地方。判断顺序永远是：
> **先分三件事** —— ① JTAG 用什么芯片 ② 板载串口用什么芯片 ③ 谁占了同一颗 USB 芯片的通道。
> 三者混在一起看，会一直在错误的方向上重试。

### 7.1 JTAG 工具"秒退、零输出、退出码空" = 缺 DLL，去查导入表

- **现象**：`cdt_js.exe` / `cdt_cfg.exe` 一启动就退出，stdout/stderr 都是 0 字节，
  `Process.ExitCode` 读出来是空。看起来像崩溃或驱动问题。
- **查什么**：用 `cmd /c` 包一层 `.bat` 拿到真实退出码（注意：`cmd /c "... & echo %ERRORLEVEL%"`
  里的 `%ERRORLEVEL%` 在解析时就展开了，**读到的是上一条命令的**，必须写成 `.bat` 文件才准）。
  实测 `-1073741515` = **`0xC0000135` = DLL 未找到**。
- **定位缺哪个**：解析 PE 导入表（可用 Python 读 DataDirectory[1]），并**递归检查被导入的 DLL 自己的导入**。
  本例：`cdt_js.exe → FTD2XX.dll → CH347DLLA64.DLL`（最后这个缺失）。
- **怎么办**：`CH347DLLA64.DLL` 就在 PDS 安装包自带的
  `PDS 安装包\驱动安装包\CH341PAR.ZIP` 里的 `CH341PAR/` 目录下，
  解出来放到 `PDS_2022.2-SP6.1\bin\` 即可。

### 7.2 打开串口会把 JTAG 踢掉（同一颗 USB 芯片的多通道）

- **现象**：单独扫链成功，一旦"先开串口再烧"就报
  `E: JtagServer-0306: No devices detected while scanning the JTAG chain`，
  且 `cfg_connect` 从 4 s 变成 40~60 s、`The cable List` 变成空。
- **原因**：下载线是一颗双通道 USB 器件（FTDI FT2232），
  **通道 A 走 D2XX 给 JTAG，通道 B 是虚拟串口**。把某个通道当串口打开会抢占整颗器件。
- **怎么办**：**烧写期间不要打开任何属于下载线的 COM 口**；确认办法是
  关掉全部串口后重烧一次，成功即证明。
  板子的**串口是另一颗独立芯片**（本例是 CP2102），打开它不会影响 JTAG。

### 7.3 板载串口芯片的驱动要单独装

- **现象**：`CP2102 USB to UART Bridge Controller` 在设备管理器里带黄色感叹号，
  `ProblemCode = 28`（未安装驱动），于是**一个 COM 口都没有**，
  板子明明在跑却读不到任何输出。
- **怎么办**：装厂商驱动（本例 `CP210x_Universal_Windows_Driver` 里的 `silabser.inf`）：
  ```
  pnputil /add-driver "<...>\silabser.inf" /install      # 需要管理员
  ```
  装好后会多出一个新 COM 口，那才是板子的串口。
- **判断顺序**：先看设备管理器有无感叹号，再数 COM 口数量，别直接怀疑固件。

### 7.4 工作目录带空格 → 工具参数被拆断

- **现象**：`E: Flow-0072: In command 'cdt_js', the argument 'Nebula\AppData\...' is not defined`。
- **原因**：`Start-Process -ArgumentList @('-work_dir',$path)` **不加引号**，
  路径里的空格把参数切成两段。用户名带空格的机器（如 `Twinkle Nebula`）必踩。
- **怎么办**：**把工具的工作目录放到无空格路径**（如 `D:\pangowork`），
  比自己改脚本拼引号更稳。

### 7.5 工具报 `Public-4023 ... run command clean` 时的正确理解

- **现象**：`cfg_assign_file` / `cfg_program` 前打印
  `W: Public-4023: Error has occurred, please run command clean before running again`，
  而脚本用 `catch` 吃掉错误后照样打印 "OK"，**看起来烧成功、实际 done bit 仍是 0**。
- **查什么**：`cfg_clean` / `clean` / `cfg_cmd clean` 这三个命令**都不存在**
  （`cfg_*` 命令全表可用 `cfg_help` 打印）。这条消息的真实含义是
  **"前一条命令失败过，状态已脏"**，要去修前一条命令，而不是找 clean。
- **怎么办**：判断烧写是否真的生效，**只看两样**：
  ① `configuration_tcl.log` 里有没有 `cfg_program succeed`；
  ② 重新扫链看 **`done bit`** 是否变成 1。不要相信脚本打印的 "OK"。
- 附带：`cfg_verify` 在这套工具/板组合上会报 `Configuration-0009: Operation error`，
  **属固有失败，不代表烧写失败**。

---

- **补充（2026-10-19，用户反馈"每次烧写都看到报错"）**：
  这个报错**每次都会出现**，因为烧写脚本里保留了 `cfg_verify`：
  ```
  E: Configuration-0004: Can not open file: .../pangoriscv.fdc
  E: Configuration-0009: Operation error : cfg_verify command can't be exec.
  W: Public-4023: Error has occurred, please run command clean before running again.
  ```
  `cfg_verify`（不带参数）在**SRAM 下载**模式下会去找与位流同名的伴随 `.fdc`，
  这里根本不存在 → 必然失败。而它发生在 **`cfg_program succeed` 之后**，
  所以从来不代表烧写失败，**纯粹把每一次成功的烧写都显示成失败**。
  → **处置：把 `cfg_verify` 从烧写脚本里删掉**（保留注释说明原因）。
  删掉后同一次烧写日志变为 `program OK: 1` + `PROGRAM_SRAM_DONE`，
  板上照常打印 `284,997,892`。
- **成功判据只认两条**：`configuration_tcl.log` 出现 `cfg_program succeed`，
  且 `cfg_scan_chain` 报 `done bit: 1`。**不要用 `cfg_verify` 的成败判断烧写。**

### 7.6 抓串口必须先开、后烧（"板上零输出"最常见的一次假警报）

- **现象**：位流 SHA 与上一次**能打出成绩的那一份完全相同**、`cfg_program succeed`、
  `done bit: 1`，串口却 **0 字节**；换一个"自由运行发送"的测试位流（每 20 ms 发一次）
  又能收到。于是得出一堆错误结论："`axi_uart` 没发"、"CPU 没跑到 UART"。
- **查什么**：**抓串口的时刻**与**固件开始打印的时刻**谁先谁后。
  本项目 CoreMark 的打印在 `core_main.c` 的 **`start_time()→iterate()→stop_time()` 之后**，
  整份报告（691 B）**只发一次**，之后 `start.S` 停在 `loop: j loop`，**永不重发**；
  832 迭代在 2.88 CoreMark/MHz 下是 **10.7 s**，所以板上只在前 **11 s** 左右有输出。
- **原因**：`run_flash.ps1` 里的 `cdt_cfg.exe` 在 file-only Tcl 结束后**不会退出**，
  脚本要等满 `-TimeoutSec`（默认 120 s）才杀掉它。**同步**调用它之后再启动
  `capture_uart.ps1`，串口打开时距配置完成已约 100 s —— 报告早在 11 s 就发完并丢了。
  实测：一次"烧写+抓取"总耗时恒为 **144 s = 120(阻塞) + 20(抓取) + 开销**，
  这就是铁证。
- **怎么办**：**抓串口放后台先开，再烧**。现成脚本
  `evidence/records/bottleneck_audit/board/flash_and_capture.ps1`：
  它先启动 `capture_uart.ps1`（`-Seconds` 取 ≥3 倍运行时间，如 90 s），
  `Start-Sleep` 几秒后调 `run_flash.ps1`，最后校验五项 CRC 和
  `ticks/27e6 ≥ 10 s` 并按 `iterations/ticks*1e6` 算分。
- **验证记录（2026-10-20 22:50）**：同一份交付位流 `1FAC6F43…B41F23`，
  改顺序后一次就抓到 `288,558,769 ticks / 832 迭代 / 五项 CRC 全对 / 2.8833`，
  与 10-19 完全一致；报告前面那 91 行 `P21UART` 是"抓取已在听、而 FPGA 里还是
  上一次的 `uart_free`"的痕迹，正好证明窗口盖住了启动与打印。
  证据：`evidence/records/optimization/P21/board_uart_score_recheck_2026-10-20.txt`
  （根因与复核清单同在 `P21/uart_zero_output_diagnosis.md`）
- **可复用**：**任何"跑完才打印一次"的固件（CoreMark、自检、崩溃日志）都必须
  在复位/配置前就打开串口**；只有"周期重发"的测试设计才允许事后抓。
  看到"0 字节"先问一句"我的接收窗口真的盖住了打印窗口吗"，
  不要先去改 RTL。**判据**：一次烧写+抓取的总耗时里，抓取之前是否还有 ≥运行时间的阻塞。

## 8. 提分天花板类：先算边界，再动手

### 8.1 单发射的 CoreMark/MHz 上限 = 1e6 / 每迭代指令数

- **怎么算**：`CM/MHz = IPC × 1e6 / 每迭代指令数`。
  本项目每迭代 289,296 条指令（222,179,042 / 768），
  所以 **IPC=1.0 时上限 = 1e6 / 289,296 = 3.457**。
- **含义**：想要 3.5 就必须 **IPC > 1**（双发射）或**把每迭代指令数降到 285,714 以下**。
  在单发射 + 现有编译器的前提下，**3.457 就是天花板**，任何"优化到 3.5"的说法都是假的。
- **以后**：接手先算这条边界，把目标定成"逼近上限"而不是"超过上限"，
  否则会一直做注定失败的尝试。

### 8.2 `-O3` 在小程序 RAM 上不可用

- **现象**：`region 'flash' overflowed by 5220 bytes`。
- **根因**：程序 RAM 只有 **16 KB**（`link.lds` 的 `flash` 区），
  `-O3` 的代码比 `-O2` 大约 5 KB，直接装不下。
- **怎么办**：**编译器口径这条路被硬件容量封死**，`-O2` 是唯一可用档位。
  想靠编译器提分，只能先扩程序 RAM（那是 BRAM 成本，会拖累 ③）。
- **可复用**：任何"换个编译档位就更快"的念头，先看 `.text` 是否还装得下；
  小容量裸机镜像上 `-O3` 经常是负收益。

## 9. 时序收敛类：guardband 不是"让工具更努力"的开关

### 9.1 加 `set_clock_uncertainty` 只把报告值下移，不会真的多插延迟

- **背景**：27 MHz 交付版 hold 只有 **+0.011~+0.018 ns**，导致所有提性能的改动
  （4 KB 缓存、store 提前一拍、顺序门控）都因为 hold 变成负值而被否。
  于是想用 guardband「让工具把余量做出来」。
- **实测（同一份 RTL、同一个种子 41、同一套 pnr 选项）**：

  | 约束 | hold(slow) | 差值 |
  |---|---|---|
  | 无 guardband | **−0.028 ns** | — |
  | `set_clock_uncertainty {0.100} [get_clocks {clk}] -setup -hold` | **−0.128 ns** | **正好 −100 ps** |

  PDS 原文仍是 `hold violation ... fixed unsuccessfully`。
- **结论**：**guardband 是"检查标准变严"，不是"优化力度变大"。**
  它从 slack 里减掉 100 ps，而路由器并没有因此额外插入 100 ps 延迟，
  所以只会让 ② 更容易判失败，**不会**腾出物理余量。
- **正确认识**：要给新逻辑腾出时序预算，只有三条真路——
  ① **减逻辑/减 FF**（换实现，不是加约束）；
  ② **换种子**（PnR 敏感，实测同一 RTL 跨种子 hold 从 −28 ps 到 +100 ps 都出现过）；
  ③ 真正改变约束的**时钟频率**（27 MHz 已固定）。
- **可复用**：看到"加 guardband 就能过"这类说法，先做一个**同 RTL 的 A/B**：
  报告值应当恰好下移 guardband 的数值。如果不是，才说明工具真的改了实现。

---

### 10.5 复测结论（2026-10-19 晚，8 KB I-Cache 配置下）：**反而是负收益，已否决**

用**正确方法**（构建目录带固件镜像）重测 §10 的"pipe_slot 改异步复位强制 FF"：

| 项 | 8 KB I-Cache 基线（P21） | 改异步复位后 |
|---|---|---|
| 仿真 A/B | ticks 6,935,568 | **完全一致**（行为中立） |
| ISA / halt-reset / RAM / 单元 | 全绿 | **全绿** |
| **hold** | **+0.061 / +0.047 ns** | **−0.153 / −0.129 ns** |

**从 +61 ps 掉到 −153 ps，恶化 214 ps。**

**原因**：异步复位会让整片宽流水寄存器改用异步复位网络；
在 2 KB 缓存配置下（§10 那次）净影响是 +3 ps，但在 8 KB 配置下网络更宽、
扇出更大，**hold 直接被压垮**。

**教训（可复用）**：
1. **同一 RTL 改动在不同面积/配置下的时序结论可能反号** ——
   §10 测出来"略好"，是因为当时面积小；面积一涨，同一个改动就变成"很差"。
   所以**任何时序结论都必须绑定当时的配置**，不能跨版本引用。
2. 判断"某个技巧好不好"必须**在当前配置下复测**，不能拿旧结论直接套。

## 11. 【严重】新建构建目录跑 PDS 会得到"没有程序"的位流（且日志只报 C 级提示）

### 11.1 事实

PDS 的 `build.tcl` 会把固件镜像以**相对文件名** `program.hex` / `data.hex` 交给综合器，
这些文件必须**位于 PDS 进程的当前工作目录**。我为了做种子扫描，给每次实验都新建了目录
（`p22_4k`、`p31s41`、`ff11`、`a2s3` …，共 40 个），**但都没把这两个 hex 放进去**，
于是每个位流都变成了**没有程序**的空设计，日志里只有一行：

```
C: Verilog-3001: [ .../axi_ram.sv(line 118)] Cannot open specified data file "program.hex"
C: Verilog-3001: [ .../axi_ram.sv(line 118)] Cannot open specified data file "data.hex"
```

`C:` 级别（不是 `E:`），混在几千行综合日志里，**我整晚都没看见**。
只有 `pango_native/`（早期由别的流程生成的目录）里有这两个文件，所以**只有从它出的位流能在板上跑**。

对比同一次综合的两种日志：

```
pango_native（能跑）: I: Loading memory data from file .../pango_native/program.hex
ff11        （不能跑）: C: Cannot open specified data file "program.hex"
```

### 11.2 这直接推翻了我之前三个"板上不跑"的结论

| 我之前的结论 | 真实情况 |
|---|---|
| P25「store 数据提前一拍」仿真全绿但**板上不跑** | **位流没装程序**，板子跑的是空设计 |
| P31「同上 + 归属修复」仿真全绿但**板上不跑** | 同上 |
| 「pipe_slot 异步复位」时序更好但**板上不跑** | 同上 |
| §4.13「仿真全绿+时序全过≠硬件可用」 | 这三例的**真因是构建缺镜像**，不是硬件玄学 |

**教训：一次"板上零输出"必须先确认"位流里到底有没有程序"，再谈 RTL。**
判据：综合日志里有 `Loading memory data from file .../program.hex`。

### 11.3 正确做法（以后每次都必须做）

1. 新目录跑 PDS 前，**先复制** `program.hex` 与 `data.hex` 进去：
   ```powershell
   Copy-Item "$code\build\pango_native\program.hex" $newdir
   Copy-Item "$code\build\pango_native\data.hex"    $newdir
   ```
2. 综合日志里 **grep 这两条**：
   `Loading memory data from file`（正常） / `Cannot open specified data file`（致命）
3. **镜像会改变时序结果**：同一份 RTL、同一个种子，带镜像时 hold **−28 ps**，
   不带镜像时曾报 `All Constraints Met (+18 ps)` —— 因为 BRAM 的实现/布局随镜像变化。
   所以**不带镜像的 PDS 结果连时序都不可信**。
4. 任何位流在烧板前，先确认它来自"有镜像"的构建目录。

## 12. 面积类：先立账，再动手（2026-10-21）

### 12.1 没有账本就谈"优化面积"，一定会砍错地方

- **现象**：想给 Cache 扩容量/加预测器，理由是"面积还够"；或者反过来，觉得"面积紧了"就去删功能。
  两种判断都没有依据——**没有分模块的面积账本**。
- **查什么**：先把综合网表按模块统计一遍（`GTP_LUT*` / `GTP_DFF*` / `RAM64X1D` / `DRM36K` / `APM`），
  再拿 `apm_drm_lutram_utilization.log` 看**每个存储阵列到底落在 LUTRAM 还是 BRAM**。
- **本项目实测（`build/code_ic4k`）**：真正的大头不是 Cache，而是
  ①`perf_regs`+其从机 约 3,100 站点（纯仪表，交付不需要）；
  ②16 KB **数据 RAM 被推断成 2,048 个 LUTRAM**（占全设计 LUTRAM 的 56%），
  而同构的 16 KB 程序 RAM 却是 4 个 DRM（BRAM）。
- **怎么办**：**先立账再动刀**，并按"功能必需 / 仪表 / 实现错误"三分类处理：
  仪表直接删；实现错误改推断方式；功能必需才谈优化。
- **可复用**：**"面积紧"永远要按模块说，不能按整颗说。** 一份 34 行的账本，比十次"感觉还够"有用。

### 12.2 同构的两个 RAM 跑到了两种物理资源（最隐蔽的面积浪费）

- **现象**：两个功能同构的 16 KB AXI 从机 RAM，一个进 BRAM、一个进 LUTRAM；
  面积账上"LUT 数没变"，但布线突然变差、hold 变紧。
- **查什么**：`apm_drm_lutram_utilization.log` 里两段表——`DPRAM Inst Name`（LUTRAM）与
  `Inst Name ... GTP_DRM36K`（BRAM）。**按实例名对，不要按模块名想当然。**
- **原因**：综合器按**端口/读写模式**推断，不按"这两个是同类东西"推断；
  带同拍读写或多口的阵列容易落到 LUTRAM。
- **怎么办**：显式写推断属性（如 `/* synthesis syn_ramstyle = "block_ram" */`，
  必要时 `no_rw_check`），然后用资源报告验证它真的换了表。
- **可复用**：**"LUT 数没变"不等于"面积没变"**——LUTRAM 占的是 LUT 站点与局部走线。
  看面积必须同时看 LUT / FF / LUTRAM / DRM 四项。

- **补充（2026-10-21，M2 三次尝试全部无效）**：给那个落在 LUTRAM 的数据 RAM 加
  `/* synthesis syn_ramstyle = "block_ram" */`，综合日志打印
  `Convert attribute name from syn_ramstyle to PAP_RAM_STYLE`，但**资源一个都没变**
  （LUTRAM 仍 3,628 / DRM 仍 4）。再试 `"block_ram,no_rw_check"`、以及把 `for` 字节写
  改成 4 条显式字节写，也全无效。这两个写法本身是对的——Pango 自带的存储器参考模型
  （`syn/lib/syncore/models/memories/ram/syncore_ram.v`）里就是这两行。
- **诊断套路（可复用）**：
  1. 先看日志有没有 `Convert attribute name from ... to PAP_...`——**有这行不代表生效**，
     必须回看资源表；本项目 `keep="true"` 也曾被翻译成 `PAP_KEEP` 后直接忽略；
  2. 再看推断日志的粒度：本项目是 `Found Ram mem, depth=4096, width=8.` **×4**（按字节通道拆开），
     说明映射器没把它当成一个 4096×32 的阵列；
  3. 对比同模块的**只读实例**（它进了 BRAM）——差异只可能在写端口/读端口形态，
     不要在属性名上耗时间；
  4. 结论：**属性管的是"偏好"，管不了"端口形态"**。要让阵列进 BRAM，读必须是
     "寄存器地址 + 寄存器输出"的同步形式；组合读（`data <= mem[addr]` 当拍取样）
     一律落 LUTRAM。
- **纪律**：三次无效就按停机规则回退，把否定结果与诊断写进证据（`area-M2/measurement.md`），
  不要为了"凑一个 BRAM"去改读路径的时序——那是访存语义改动，得单独走 A/B。

### 12.3 面积口径必须一次说清（否则预算一定算错）

- **现象**：给模块定面积预算时，把网表里数出来的 LUT 相加当总量，结果比 `device_map` 少 16%。
- **查什么**：网表只统计了 `GTP_LUT*`/`GTP_ALUT*`，**漏计 `GTP_MUX*`、`GTP_LUT7` 等组合原语**；
  而 `device_map` 是打包后的真值。
- **怎么办**：**验收只认 `device_map` 的 `Used` 行**；网表统计只用于模块间**相对排序**；
  FF 列可以相加（本项目合计 14,234 vs 真值 14,104，误差 0.9%）。
- **可复用**：任何"逐模块面积之和 ≠ 总量"的场合，先怀疑**原语类型没采全**，再怀疑工具。


## 13. 性能类：先证明"慢在哪一类周期"，再改 RTL（2026-10-21，P34）

### 13.1 单元测试台的手写写握手必须模仿 `lsu_axi`，否则 store 用例永远挂

- **现象**：`tb_dcache_axi` 的 D3（写命中）在 HEAD 上就超时，日志停在 `while(!w_ready)`；
  `plan-3.5-3.8.md` §4.10 把它记为"posted store 改了 b_valid 时序、TB 没跟上"。
- **查什么**：TB 把 `req_valid` 与 `w_valid` 分成两拍发（先请求、再喂 W），而真实主机
  `lsu_axi` 是 **fast-issue：请求与 W 同拍**（`wdata_on_iss`），并且**从不等待 `w_ready`**
  —— 缓存在 accept 拍就把 `w_data` 锁进 `wdata_q`，W 拍由缓存自己再交给内部写引擎。
  于是 TB 等的 `w_ready` 永远不会来。
- **怎么办**：单元 TB 的写任务按主机契约发：`req + w_data/w_strb + b_ready` 同一拍拉高，
  `#1` 等组合稳定后采 `req_ready`，`@(posedge)` 接受，再等 `b_valid` 采样。
  修完 D1~D9 全绿（这才是"测试台跟随契约"，不是放松判据）。
- **可复用**：任何"TB 里 `while(!xxx_ready)` 挂死"的写通路用例，先对照**真实主机模块**的
  时序（本项目是 `lsu_axi.v`），不要对照上一版 RTL 的波形。

### 13.2 把"接受条件"扩到新状态时，必须把**副作用**一并提到公共路径

- **现象**：posted store 队列加好后，CoreMark 的 `crcfinal` 变了、指令数 +49%、跑分反而更慢，
  但**写记分板 0 错**（CPU 写入 = AXI 写出，地址/数据/掩码全对）。
- **查什么**：把 `accept_post` 从"只在 `ST_WR_DRAIN`"放宽到"`ST_WR_DRAIN` 或 `ST_WR_POST`"，
  但**行合并那句 `data_mem[...] <= merged_accept` 只写在 `ST_WR_DRAIN` 分支里**。
  在 POST 态被接受的 store 因此"只入队、不合并"，随后对同一行的 load 命中旧值。
  证据链：retire trace 逐条比对 → 第一个分叉在 `core_list_init` 的 `sw`/`lw` 同址序列。
- **怎么办**：接受条件的每个"新状态"都要问一句"原来那个分支里还做了什么副作用"；
  把合并/计数这类**与状态无关的副作用集中到 case 之后的公共段**，只在公共段写一次。
- **可复用**：凡是"把 if 条件放宽"的改动，**逐条列出旧分支的全部赋值**，确认新路径都覆盖；
  用"写记分板 + retire trace 首分叉"两件工具，比猜 `crc` 快得多。

### 13.3 "队列加深"救不了**持续压力**，只有吞吐能救

- **现象**：store 停顿 594k 周期，拒绝原因 99.99% 是"drain 期 posted 缓冲满"，直觉是加深队列。
- **查什么**：先量两件事——① store 连续长度分布（97.2% 是孤立单笔）；
  ② **队列占用直方图**。占用在"满 4"上停了 805k 周期，说明不是短突发，是**持续压力**：
  `core_list_init` 每个节点 1 load + 5 store，需求率 ≈ 1 笔/8 拍，正好等于写出吞吐
  （379k 笔 / 2.88M drain 周期 = 7.6 拍/笔）。
- **怎么办**：队列只吸收**瞬态**；需求率超过写出吞吐时，加深队列收益≈0。
  要么提高吞吐（写引擎流水化），要么减少写（算法/合并），不要加深度。
- **可复用**：任何"缓冲满"的停顿，先算**需求率 vs 服务率**，再决定加深度还是加吞吐。

### 13.5 配对里的 WAW 检查是"看起来该省、其实省不出东西"的典型

- **现象**：`pair_ok` 里有一条 `(drd==0 || drdh==0 || drd!=drdh)`（两槽不得写同一 rd），
  探针把 210,181 个周期归到 "WAW 挡住了配对" ⇒ 直觉是删掉它就能白赚 3.6%。
- **查什么**：删掉后 A/B 的 `cycles` **逐位不变**，配对只多 3 对。原因是探针那条判据写成
  `drd!=0 && drd==drdh`，**漏了 `drdh!=0`**，于是"两槽都写 x0"也被算成 WAW ——
  而 x0 写本来就被 RTL 放行。真实可回收量≈0。
- **怎么办**：改动前先让探针**复刻 RTL 的判据原文**（包括每个 `!=0` 的守卫），
  再统计分桶；否则统计出的"机会"是假的。改完发现无收益就**立刻回退**，不要留。
- **可复用**：任何"删一条保守检查就能提速"的判断，先用**和 RTL 逐字对齐**的探针量；
  量不出来就回退，KEEP IT SIMPLE。

### 13.4 上板套件起不来 JTAG 服务器：脚本环境的键名大小写冲突

- **现象**：`flash_and_capture.ps1` 报 `FAILED to parse the port from jtagserver_run.log`，
  该日志是空的；但手敲 `cdt_js.exe -work_dir .` 能正常打印 `use port : 65420`。
- **查什么**：`Start-Process` 抛的是
  `已添加项。字典中的关键字:"HTTPS_PROXY"所添加的关键字:"https_proxy"` ——
  Windows PowerShell 5.1 构造子进程环境块时键名按大小写不敏感处理，
  环境里同时存在 `HTTPS_PROXY` 与 `https_proxy` 就抛异常，子进程**根本没起来**。
- **怎么办**：调用前先删掉小写那份（`Remove-Item Env:https_proxy` 等），再启动；
  若仍不行，改用单进程写法：**先 `Open()` 串口 → 再烧写 → 后循环 `ReadExisting()`**。
  CoreMark 报告在配置后约 10.7 s 只打印一次，串口已打开时驱动会缓存，事后再读也能拿到。
- **可复用**：任何"脚本起的子进程没有日志"的上板/工具链问题，先怀疑**启动方式**
  （环境块、重定向、大小写冲突），不要怀疑目标 exe 或电缆。

## 14. 性能类：把 ID 级译码信号用到 EX 级（2026-10-21，P37a）

### 14.1 现象与代价
给「配对内 RAW」加 EX→EX 前递，功能仿真在新增用例上直接挂死（`E2E_TIMEOUT`，x21 变 X）。
两轮调试才定位，三轮才修对：

| 轮次 | 写的条件 | 实际后果 |
|---|---|---|
| 1 | `erd==rs1h`（ID 阶段寄存器号） | `rs1h` 是**下一包**的 rs1，前递选不中 → 仍是旧值 |
| 2 | `alu0 / op1`（ID 阶段译码） | 前递给"下一包"的指令类型，X 依旧 |
| 3 | `ei`/`ei_h` 的 opcode 与 rs 字段（EX 级） | 正确 |

### 14.2 为什么容易错
`pangoriscv.v` 里有两套同名族信号：
- **ID 级**：`rs1/rs2/rs1h/rs2h`、`dinst/dinsth`、`alu0/mem0/alu1/ctrl1`、`du1h/du2h`、`op1`
  —— 描述**当前在 ID 的包**，用于 `pair_ok` 这类*发射决策*；
- **EX 级**：`ei/ei_h`、`er1/er2`、`er1_h/er2_h`、`erd/erd_h`、`ep/ep_h`
  —— 描述**这一拍在 EX 的指令**，用于执行与前递。

一拍的差距就是"下一包"与"本包"的差距，而两者在仿真里都非 X，错了不会报红，只会算错。

### 14.3 还有第二个坑：操作数有两个口
`ex_alu` 的寄存器操作数分两条路：
- `op1_i/op2_i`：ID 阶段**已经选好**寄存器或立即数的值（ADD/ADDI/XOR/分支比较都走这里）；
- `reg1_rdata_i/reg2_rdata_i`：只有**移位**结果直接用它（`rshift_low`）。

只改后者，`add` 依旧拿旧值。前递必须两条都改，且要判断该槽是否真的读寄存器：
`lui/auipc` 的 `uses_rs1=0`；`addi` 的 `uses_rs2` 仍为高但第二操作数是立即数 —— 所以
`op2` 只用 `opcode ∈ {0x33, 0x63}` 作判别，别信 `uses_rs2`。

### 14.4 可复用判据
1. 在 `pangoriscv.v` 里写**任何**与"这一拍正在执行的指令"有关的逻辑，先问：
   `ei/ei_h` 还是 `dinst/dinsth`？前递/异常/写回一律用 `ei*`。

## 16. 面积类：**存储阵列的复位方式决定它能不能变成 RAM**（2026-10-21，E1）

### 16.1 现象
I-Cache 的 tag 阵列 `tag_mem[0:127]`（21 bit × 128 = 2,688 位）在网表里是 **2,688 个触发器**，
而同样结构的 D-Cache tag 是 `ram64x1d`（分布式 RAM）。同一份代码、同一个工具，结论却不同。

### 16.2 根因
I-Cache 复位段里有这一句：

```verilog
for(i=0;i<SETS*2;i=i+1) begin
    valid_mem[i] <= 0;
    tag_mem[i]   <= 0;      // <-- 整块清零
end
```

分布式 RAM **没有按项复位**的能力（`ram64x1d` 只有写口，没有 reset）。工具看到"每个存储元都要被复位"，
就只能把整块存储实现成触发器；连带 128:1 的 tag 读 mux 也变成 LUT。
D-Cache 的复位段**只清 `valid_mem`/`lru_mem`，从不清 `tag_mem`**，所以它一直是 RAM。

### 16.3 改法与为什么安全
只删掉 `tag_mem` 的复位循环，`valid_mem`/`lru_mem` 照旧复位。安全性来自一条不变式：

> **只有 `valid_mem` 置位的行才参与 tag 比较**，而 `valid` 只在写 `tag` 的**同一拍**（fill 边沿）置位。

所以未初始化的 tag 永远不会被比较。仿真里 X 也不会传播：`0 && X == 0`。

### 16.4 实测收益（交付 profile，同一份 1152 镜像）
| 项 | 改前 | 改后 |
|---|---:|---:|
| `icache_axi` LUT | 2,547 | **1,330** |
| `icache_axi` FF | 3,070 | **383** |
| 全设计 LUT | 13,252 | **12,020（−9.30%）** |
| 全设计 FF | 9,966 | **7,278（−2,688）** |
| `ram64x1d` | 3,628 | 3,670（+42） |

分数**逐位不变**：A/B 窗口 5,212,477、retires 5,782,437、全部计数与 `crcfinal 0x4983` 完全相同。

### 16.5 可复用判据
1. 设计里凡是"大数组 + 复位时 `for` 逐项清零"，先问：**这块需要复位吗？**
   只要有一层 `valid` 门控（cache 的 valid、FIFO 的 valid、BTB 的 valid），
   **只复位 valid**，把数据阵列留给 RAM。
2. 判断"阵列是否真的变成 RAM"不要看 RTL，看**网表**：按模块统计 `ram64x1d` / `GTP_DFF` 的实例数。
   本轮就是靠这个方法一眼看出 tag 落在 FF 里。
3. 这类改动是**功能等价**的（不是优化），所以判据必须是"仿真逐位相同"：
   窗口/退休数/每个探针计数/全部 CRC 一字不差，才算真的没动行为。

### 16.6 结局：先回退，一天内用 E2 救回（**最终已交付**）

E1 单独上阵时四次尝试全部倒在 IO hold 上，按纪律回退；随后 E2 用三处改动把它救回来并**交付**：
板上 ticks 与上一版**一字节不差**（298,780,717），LUT −4.4%、FF −27.3%、站点 −10.9%、kLUT +4.6%。
下面的表格保留第一次失败的过程记录，作为"单点改动会扰动全局"的证据。
面积收益是真的（LUT −1,232 / FF −2,688 / 只多 42 个 RAM 块），但净表少掉 2,688 个 FF 之后，
时钟树与放置整体改变，`led[*]` 的**IO 端口 hold 路径**（`reset_sync→led`、`gpio_inst/reg_data→led`）
稳定落在 −0.021～−0.038 ns，`Convergence=Fail`。四次尝试：

## 17. 物理类：**先降扇出，再谈种子**（2026-10-21，E2）

- **现象**：`tag_di_q → tag_mem_*/DI` 这条 hold 路径连续多个构建都是最差项（−0.001 ~ −0.038 ns）。
  换种子、加大 hold 修复预算、加"只喂 RAM 的复制寄存器"，全都只是把 −0.038 拉到 −0.021 或 −0.001。
- **根因**：D-Cache 的 tag 用 `{way,set}` 单数组，两个同拍读口需要两份物理副本；于是**一次填充要同时
  写两份，一个触发器扇出 42 个分布式 RAM 数据脚**，这些脚在版图上分散，hold 由最远那个决定。
- **怎么解**：把数组按路拆成 `tag_mem`/`tag_mem_1`（各 32 项），每个数组天然 1 读 1 写，
  填充只驱动 **21** 脚 —— 根因消失后，配合 `set_di_q`（写地址同样复制）与一次种子，hold +0.025、端点 0。
- **可复用**：hold 违例先问三句：① 这个网络的**扇出**是多少？② 它驱动的是不是一个被复制的阵列
  （复制是综合为多读口自动做的，写口也跟着复制）？③ 能不能**从结构上把扇出砍半**，
  而不是让工具去插延迟？扇出砍半 > 三次换种子。

## 18. 面积类：**用 LUTRAM 扩容不等于不涨 LUT**（2026-10-21，E3）

- **直觉**：I-Cache 数据本来就在分布式 RAM 里，加倍容量只是多占 LUTRAM，LUT 应该不变。
- **实测**：8 KB（128 组）确实只多 1,062 个 LUTRAM 站点，但 **LUT 从 17,534 涨到 19,474（+1,940）** ——
  1024 深的分布式 RAM 要 4 个 `ram64x1d` 拼起来，读口需要一级 4:1 mux，每个读位一份。
- **后果**：`CoreMark/kLUT` 从 0.2199 掉到 0.2049（−6.9%），setup 也从 +7.816 掉到 +6.588（−1.2 ns）。
  换来的分数是 +3.4%。三项并列评分下净亏，因此不交付。
- **可复用**：任何"存储扩容"提案，先按 `深度/64 × 位宽 × 读口数` 估 LUTRAM，

  然后用 `CoreMark/kLUT` 而不是"LUTRAM 没满"来判定值不值。

## 19. 性能类：**"配对被拒的 l0 桶" != "可回收的不跳分支"**（2026-10-21，P38 实测）

- **直觉**：`PAIR_BLOCK` 里 `l0=444,391`（lane0 是分支、配对被拒），
  "放开 lane0 分支配对（branch + fall-through 配对，预测不跳）"看着是白赚的 -4~5%。
- **实测（20 迭代 A/B）**：窗口 5,212,477 -> 5,205,599（**-0.13%**，3.8557 -> 3.8608）；
  l0 桶 444,391 -> 402,860（-41,531）；退休配对只 +14,097；`crcfinal 0x4983` 逐位相同。
- **为什么几乎没用**：l0 桶的成立前提是"fall-through 进了 lane1"，即**分支被预测为不跳**。
  但 CoreMark 的循环分支**约 90% 实际跳转**，所以这 44.4 万里绝大多数是"预测不跳、实际跳转"
  的**误预测**分支。放开配对后，4.1 万个新配对里只有 1.4 万个真的不跳（双双退休），
  其余 2.7 万个分支跳转 -> fall-through 被冲刷 -> **白配对、零收益**。
- **可复用**：**任何"配对被拒分桶"的数字都不能直接当"可回收周期"**。要判断一个桶值不值，
  先问"这桶里的指令，配对成功后是双双退休、还是另一半被冲刷"。
  只有"双双退休"的那部分才是收益；对 l0 这种"控制转移 + 其后继"的桶，
  收益 = 桶大小 x **实际不跳比例**，而循环分支的不跳比例极低，所以收益~0。
  同理，"l1 桶（lane1 是访存）"要回收必须**真加第二个访存口**，不是"放开配对"就能白拿。
- **纪律**：改动已回退（`git checkout HEAD -- rtl/... isa_e2e.S run_isa_e2e.py`），
  交付仍是 E2 的 3.8557。真正的大桶是 redirect 气泡（48.9 万，9.4%）与 l1 访存（66.4 万）。

## 20. 工具类：**`.align` 会产生 `R_RISCV_ALIGN`，链接器把其后所有符号前移 4 字节**

- **现象**：给 `tests/isa_e2e/isa_e2e.S` 新增 case，`nm` 出的符号地址比 `.org` 写的**少 4**。
  实测 `.org 0x1300` 的 `test18`，链接后落在 **0x12fc**，而 entry stub（`jal x0, 0x1300`）
  仍按 `CASE_PC` 里的 0x1300 跳 -> 跳过第一条指令 -> 寄存器全是 X、挂起。
- **查什么**：`.o`（`gcc -c`，未链接）里符号是对的（0x1300），链接成 elf 后少 4。
  根因：`test17` 里的 `.align 3` 会发射一个 `R_RISCV_ALIGN` 重定位，链接器即使加了
  `-Wl,--no-relax` 也会把紧随其后的 `.org` 填充吃掉 4 字节，于是**其后的所有符号整体 -4**。
  `test16`/`test17` 在 `.align 3` 之前，所以地址正常；`test18` 是第一个在它之后的，首当其冲。
- **怎么办**：
  1. 新增 case 后，**必须 `nm <elf>` 核对实际地址**，把真实值写进 `CASE_PC`，不要信 `.org` 字面量；
  2. 若用例要"分支落在 8 字节边界"，**别用 `.align`**（会引入这个 -4 漂移），
     改用显式 `nop`/数指令个数手动对齐，或用 `.balign` 并复核；
  3. 入口 stub 与 `CASE_PC` 必须一致，否则跳过首指令、寄存器 X、`E2E_TIMEOUT`。
- **可复用**：**RISC-V 汇编里凡在 `.align` 之后的 `.org`/符号，链接地址都可能被前移**；
  任何"改了汇编后测试突然挂起/寄存器 X"先 `nm` 查符号真实地址，再怀疑 RTL。

## 21. 重写流水线时的三个"看起来对、实际丢指令"的坑（rv32 核 P1）

**现象**：新核 ISA 回归里整条指令"凭空消失"——退休轨迹里 0x208 之后直接跳到 0x214，
中间既没有 trap 也没有 redirect；或者寄存器里出现 `xxxxxxxx` / `0000000x`（低 4 位未知）。

**查什么（按顺序，每条都能独立定位）**

1. **同步读寄存器堆的 x0 判断与写穿透用的是哪个地址？**
   数据是"上一拍地址"读出来的（`q0 <= rfile[ra0]`），如果 `rd0` 的 `ra==0` 判断和
   写穿透比较用的是**当前**`ra`（也就是下一条指令的 rs1），读 x0 就会返回未初始化的
   `rfile[0]` → 操作数全 X。修法：把地址打一拍（`a0_d <= ra0`），x0 判断和 hit 比较都用 `a0_d`。
   症状特征：低 4 位或整字 X，且**第一条** `addi x1,x0,5` 就错。

2. **`jal`/`jalr` 有两个立即数，不是一个。**
   链接值恒为 `pc+4`，跳转位移是 `imm_j`/`imm_i`。若译码只留一个（早先给 ALU 算链接值时
   把 `imm` 写成 `4`），跳转目标会变成 `pc+4`——现象是程序"跳过一段代码直接落到下一个段"。
   修法：`b_sel` 增加一个"字面量 4"选择，`imm` 保留真正的位移。

3. **"冻结"必须是"本级保持 + 下一级进气泡"，不是"本级出气泡"。**
   写反了会把正在等待的指令**丢掉**：`mem_wait` 时 `m_valid <= 0` 且 `ex_valid <= 0`，
   这条 load 既没进 M2 也不再留在 M1，退休轨迹里就"少了一条指令"，而且后面的指令照常退休。
   正确写法：`freeze_m1` 时 `ex_*` 保持不变、`m_valid <= 0`；`freeze_rr` 时 `rr_*` 保持不变、
   `ex_valid <= 0`。判据：**任何时刻"丢掉一条指令"和"重复退休一条指令"都必须能追溯到
   某个 kill/redirect，否则一定是保持/气泡语义写错。**

**怎么办**：先看退休轨迹有没有"缺号"（pc 跳段），有缺号先查第 3 条；
再看数据是不是 X（低 4 位 X 优先怀疑操作数选择），X 优先查第 1 条；
控制流跳错段优先查第 2 条。

## 22. 重写流水线：五个"ISA 测试全过但 CoreMark 跑不对"的真 bug

P1 的 ISA 回归从 2/21 走到 21/21 之后，CoreMark 仍然跑不完（40 M 周期、crc 拿不到）。
逐层剥下来是五个独立的结构错误。**共性：ISA 用例的指令序列太短、依赖太规整，
覆盖不到"负载紧邻控制转移""背靠背 CSR""停顿时解析分支"这些组合。**

### 22.1 同步读寄存器堆把"操作数/指令配对"绑死在"ID 每拍前进"上

**现象**：`sub x19, x17, x11` 得到 `x17 - 0`（rs2 读成 x0 的强制零），`add x18` 得到 X。

**原因**：同步读的地址来自正在译码的指令，数据下一拍才出来，于是 `rr_op1 <= rf_d0`
只能在与指令**同拍**锁存时对齐。第一次 `load_use` 停顿，读指针就漂到后一条指令，
解冻那一拍锁进 `rr_op1` 的是别人的操作数。

**修法（结构，不是补丁）**：改成**异步读**分布式 RAM，地址直接来自 EX 级寄存器
`rr_rs1/rr_rs2`。流水线冻结时地址自然冻结，这一类对齐问题整体消失。
面积也更小：4 份 32×32 阵列 = 128 LUT（单发射只用 2 份 = 64 LUT），
原来 4 组 q/a 寄存器是 148 个触发器。

### 22.2 分支比较用了立即数而不是 rs2

`b_sel=imm` 让 ALU 拿 `rs1` 和**位移量**比。`bne` 恰好蒙对（1 ≠ 16），
`beq/blt/bge` 全错——所以"某个分支能用"不能证明分支译码正确。

### 22.3 CSR 旧值在 ID 采，而前一条 CSR 写要等 WB

背靠背 CSR：`csrrw x2,...` 读到的是自己写入的新值，紧跟的 `csrrs` 读到 0。
**修法**：旧值在 **WB（提交点）** 采。`read_data` 是边沿前的值，正好是本条的架构旧值，
且更老的 CSR 写已经落地，天然保序，还省掉 3 个 32 位流水寄存器。

### 22.4 csrrsi/csrrci 的 zimm 被当成寄存器读

`u1_r = (funct3 != 5)` 只覆盖了 csrrwi。funct3 = 5/6/7 都是立即数形式，
正确判据是 `funct3 < 5`（1/2/3 才是 rs1 形式）。

### 22.5 中断用 pipe_empty 做门控 → 自旋循环永不进中断

`lw; beq spin` 永不排空流水线，中断永远不触发（case 15 超时）。
**修法**：在**控制流指令退休**的边界注入——此刻下一条 pc 精确等于 `w_next`，
可以直接写 `mepc`，而 kill 年轻指令本来就是 redirect 做的事。

### 22.6 停顿时就解析分支 → 用陈旧操作数跳飞

**现象**：CoreMark 的 `get_seed_32` 跳表里 `lw a5,0(a0)` 紧跟 `jr a5`，
跳到 `0x10000658`（表的**数据**地址）→ 取指访问错误（cause 1）→ 固件死自旋。

**原因**：`br_miss` 没有检查 `hold_ex`。`hold_ex` 为高的那一拍，操作数还在路上
（load-use / 除法 / 访存等待），`ctrl_target` 是**陈旧值**，但 `ctrl_next != rr_pred`
照样成立 → 立即重定向并 kill 整条流水线。

**修法**：`br_miss = rr_valid && is_ctrl && !hold_ex && !ex_trap_w && (ctrl_next != rr_pred)`。
判据：**任何"用操作数算出来的控制决策"，其有效条件必须包含"操作数有效"**，
而"操作数有效"在分级使能的设计里就是 `!hold_ex`。

**定位方法（本轮定型，可直接复用）**：在核里加 `RV32_DEBUG` 条件编译的两条不变式打印——
① 任何 trap 打 `pc/cause/tval/mepc`；② 任何 `redirect_target` 落在数据窗口
（`[31:28]==4'h1`）打 `from/target/pred/jalr/rs1v/imm`。两条在正确核上都是静默的，
一旦出现就直接指向出问题的指令。

## 23. 双发射落地时的三个"只在配对生效后才暴露"的错

ISA 21/21 在单发射下全绿，把 `fetch_ready2` 打开、让 lane1 真正提交之后，
立刻出现"一半寄存器是 X / 低 4 位 X"。三个错都不在单发射路径上存在：

### 23.1 包内 RAW 的判断写反了对象

我写成"lane1 自己写的寄存器等于它读的"（`rr_rd_h == rr_rs1_h`），正确条件是
"**lane0 写的寄存器被 lane1 读**"（`rr_we && rr_rd == rr_rs1_h`）。
症状：紧跟 lane0 的消费指令全拿到 X（lane0 的结果要到 WB 才进阵列）。

### 23.2 每一级旁路都少了 lane1 这个来源

一个包写两个寄存器，所以 EX→WB 之间**每一级都有两个活的生产者**，且同级里 lane1 更年轻。
只补了"包内"那一级、忘了 M1/M2 的 lane1，就会出现"隔 1–2 条指令读不到"：
`add x3,x2,x1` 里 x2 由上一个包的 lane1 写入、当时还在 M1，lane0 读到 X。

**判据**：旁路链的级数 = 流水级数 × 每级通道数；写口有几个，每级就要比几个 `rd`。
距离 3（WB 那一包）不需要单独一级——`regs` 已经把两个写口做进读路径，
所以 `rf_d*` 本身就是写穿透结果，这一级可以省掉（正好抵消新增比较器的延迟）。

### 23.3 load-use 只检查了 lane0 的源寄存器

`load_use` 原本是 `ex_rd == rr_rs1 || ex_rd == rr_rs2`。M1 里的 load 结果在 M2 才可用，
所以**两个通道**读它的目的寄存器时都要停。漏掉 lane1 的后果不是崩溃而是"偶发错值"——
CoreMark 的 printf 变参正好靠 `lw` + ALU 相邻序列走栈，打印出来是 `0x%`。

**判据**：任何"跨通道共享的生产者/资源"（旁路、load-use、LSU 端口、CSR、写口），
单发射版本里的判据都必须重新过一遍"另一个通道会不会也用到"。

### 23.4 为什么 lane1 只放 ALU + 分支/jal

lane1 不承载访存（LSU 单端口）、不承载 CSR/系统（串行化）——这两条把
"lane1 触发 trap"整类问题删掉了。分支/jal 允许进 lane1 是因为
**目标恒为 `pc+imm`，只要配对时要求 `imm[1]==0` 就能保证 4 字节对齐**，
于是 lane1 依旧永不触发未对齐陷阱。`jalr` 排除（目标是运行期值）。

## 24. 性能问题先量"请求次数"，再谈容量

D-Cache 只有 2 KiB，而 CoreMark 工作集约 4 KiB——直觉上必然抖动，改容量似乎天经地义。
实测把容量翻 4 倍只涨 1.25%，refill 几乎不动。加上命中/缺失计数后才看清：

| 读数 | 值 | 含义 |
|---|---|---|
| 命中率 | 92.5% | 缓存是好的 |
| `same_line_reload / miss` | 99.8% | 同一行连续缺失 = 重复接受同一请求 |
| 缓存读请求 / 核心 load | 142 万 / 24.5 万 | **放大 5.8 倍** |
| 缓存写请求 / 核心 store | 39.4 万 / 1.15 万 | **放大 34 倍** |

**判据**：当"缺失率不随容量变化"时，先怀疑请求被重复发起，不要继续加容量。
两个计数就能定位：发送侧握手次数 vs 接收侧握手次数；再配一个
"这次的缺失地址是否等于上次缺失地址"的计数器——比值接近 1 就是重复，不是替换。

这一类 bug 的温床是**保持型握手**：`valid` 一直挂着、`ready` 反复拉高，
双方各按自己的状态机推进，就会出现"一笔操作被接受多次"。

## 25. "少停一拍"的旁路为什么反而算错：load-to-use 不能只加 mux

**目标**：`STALLDBG` 显示 `load_use` 占 163 万周期（23%），而每条 load 平均只花 1 拍多。
于是想：D-Cache 命中时数据在**同一拍**就回来了（`mem_rsp`），把 `load_value` 直接
加进 EX 的旁路链，并把 `load_use` 改成"数据没回来才停"，就能省掉这一拍。

**实现**（`ld0_now/ld1_now` + 4 条旁路入口 + `load_use` 与 `!ld0_now` 合取）后：
ISA 默认门禁仍是 20/21（功能测试**没抓住**），但 CoreMark 的
`crclist 0xe714 → 0x4c2d`、`crcstate 0x8e3a → 0x861b` 全错，`crcmatrix` 正确。

**用空测试定位（值得复用的手法）**：保留旁路 mux、只把 `load_use` 恢复成无条件停顿，
crc 立刻回到 `0x4983`、周期与改动前**逐位相同**。⇒ mux 是死代码（无害），
问题在"认为数据已就绪"这个放松条件上。

**结论**：这个改动只值 1.7%（7,168,871 → 7,046,498），却引入数据相关错误，
按"低收益不冒险"已回退。**判据**：
1. load-use 的停顿不只是"等操作数"，它同时**定义了流水线的老化关系**——
   停一拍让 load 走到 M2，消费者才发现自己在读一个比自己老的指令。
   拆掉它，必须同时重审 `kill_young`/`br_miss`/重定向这一整套控制，
   不是加一个 mux 就完事。
2. **ISA 用例抓不住这类错误**：21 例的指令序列太短、依赖太规整；
   CoreMark 的 `crclist`/`crcstate`（字节访问 + 指针追逐）才是这类 bug 的探针。
   任何"少停一拍/多发射一路"的改动，必须跑 CoreMark 看 crc，而不能只看 ISA。
3. 逐条退休轨迹（`RV32_TRACE`）对比**不能直接逐行 diff**：配对率一变，
   行数和分组就不同。要比较必须先按 `v1/pch` 把配对展开成指令序列，
   否则会把"配对时机不同"误判成"执行顺序不同"。

## 26. 为了让关键路径变短而拒绝"包内 RAW"，等于把双发射的核心能力关掉（2026-10-22，P6）

**动机**：关键路径是"寄存器读 → lane0 ALU → 包内旁路 → lane1 ALU → 分支比较 → 重定向"。
两条 32 位加法器串在一拍里显然不划算，于是加了一条配对规则
`lane0_raw_pair`：只要 lane1 读 lane0 这一拍要写的寄存器，就**拒绝配对**，让它下一拍再发。

**结果**：ISA 全量回归从 **20/21 掉到 18/21**，`case 19/20`（lane1 访存 fault 前缀）报
`fault did not occur in lane1`；日志里 `E2E_PIPELINE lane1_mem=0 lane1_fault=0`。
`PAIRGAP` 对比（同一构建、同一镜像、只差这一条规则）：

| 项 | 有 `lane0_raw_pair` | 无 |
|---|---:|---:|
| `pair` | 9 | 16 |
| `lane1_mem` | 0 | 3 |
| `lane1_fault` | 0 | 2 |

**根因**：`test19` 的 `sw x23, 0(x10)` 的**存储数据**就来自同包 lane0 的 `addi x23, x0, 33`。
也就是说"lane1 读 lane0 同拍结果"不是可以牺牲的优化，而是**这套 ISA 用例和 CoreMark 的数据通路本身**
（`test17` 名字就叫 "RAW in one issue pair"，专门验证它）。

更糟的是**错误表现有欺骗性**：19 例里 `addi x20 / lw x0` 那一对并没有 RAW，看起来不受影响，
真正被打断的是后面那一对 store。只看第一处会以为规则没问题。

**判据（写进规矩）**：
1. **任何"少发一路/少配一对"的规则，动之前先确认它买的是延迟还是吞吐**。
   包内 RAW 是"一拍出两个结果"的全部意义所在；拒绝它换来的 ns 一定小于它在吞吐上的损失。
2. 排查"某个 lane1 能力消失"这类问题，先看 `PAIRGAP` 的桶有没有新增，而不是猜旁路。
   `pair / l0_alone / pkt_lduse` 三个数一起看，缺的那个桶就是新加规则吃掉的地方。
3. **一次只加一条拒绝规则**。这次同时改了旁路基值（提前采样）、配对规则、重定向三件事，
   回归从 20/21 掉到 18/21 时无法归因，最后只能整组 `git stash` 回退重来，白跑四轮仿真。

## 27. 乘法移出 ALU 周期：拿得到 ns，拿不回分数（2026-10-22，P6）

**动机**：33×33 有符号乘是 4 级 DSP 级联，放在 ALU 拍里约 6 ns，看起来是最肥的一块。
做法是把操作数在 RR/M1 边界寄存，乘积在 M1 取，消费者按 load-use 同款规则停一拍。

**收益**：126 MHz 综合 `Synthesize Setup WNS` 从 −12.464 改善到 **−8.384 ns**（+4.08 ns），
其中乘法贡献约 3.3 ns，同期加的"重定向寄存一拍"只贡献 0.74 ns。

**代价**：同一镜像 `sim20_o2`，20 迭代周期 **7,168,871 → 7,500,066（+4.6%）**。
账目对得上：`pkt_lduse` 722,907 → 914,417（+191,510）、`load_use` 1,630,819 → 1,818,422（+187,603），
合计 378 kcycles，正好是 CoreMark 里"乘完立刻用"的密度（`crcstate`/`core_state` 的哈希）。

**结论**：已回退。理由不是"3.3 ns 不香"，而是**评分口径是 CoreMark/MHz，频率不进分子**。
在 120 MHz 本来就够不着的前提下，用 5% 分数换 3.3 ns 是纯亏。
判据：**先确定这一轮的优化目标函数**。目标函数是"分数"时，任何 CPI 损失都要按分数折算；
目标函数是"频率"时才看 ns。两个目标同时挂在一条链上时，先各自算出可达边界再决定投入。

## 28. 综合阶段的 WNS 和布线后的 WNS 不是同一个数，但差值很稳定（2026-10-22）

`report_timing` 在 `place_route` 之前调用会直接报 `Flow-0044`，所以只有综合时，
唯一能拿到的时序指标是 `multiseed_summary.csv` 里的 `Synthesize Setup WNS`。

实测同一套 RTL 的两个口径：

| 口径 | 目标周期 | 最差 slack | 反推路径 |
|---|---:|---:|---:|
| 综合（`Synthesize Setup WNS`） | 7.937 ns | −12.464 | 20.40 ns |
| 布线后（`Worst slack after placement`） | 7.937 ns | −8.005 | 15.94 ns |

**布线比综合好约 4.5 ns**（综合的器件映射偏保守）。所以：
- 想看"改一行 RTL 值多少 ns"→ 用综合 WNS 做 **A/B**，差值可信；
- 想判断"这个频率能不能收敛"→ 必须用 `综合WNS + 4.5 ns` 反推，不能直接拿 −12 说"差 12 ns"。
- 按这个映射，本轮 RTL 的路径约 **15.4 ns（≈65 MHz）**，离 126 MHz 的 7.94 ns 差一倍，
  换算下来需要把路径再砍掉 48%，不是"再调一个参数"的量级。

## 29. PDS 新构建目录的两个硬约束：镜像校验 + 不复用目录（2026-10-22）

本轮把 PDS 流程脚本化（`firmware/code/tools/run_pds_flow.py`），踩到四个坑，都已修进脚本：

1. **仓库里是 `.v`，流程要 `.sv`**；但 `defines.v` 必须保持原名，否则所有
   `\`include "defines.v"` 失败，日志只报一句 `Program Error Out`，看不出是哪个文件。
2. **`report_timing` 不能在 `place_route` 之前跑**（`Flow-0044`），且 `> file` / `-file` 都不支持。
   综合模式必须跳过它，改读 `multiseed_summary.csv`。
3. **出位流前必须证明镜像进去了**：脚本检查综合日志里出现
   `Loading memory data from file`，没有就以退出码 3 中止（第一铁律）。
4. **一个 tag 一个目录，不删旧目录也不复用**。用 `rm -rf build/xxx` 清理会触发工具的批量删除确认，
   正确做法是换一个新 tag 重建。

**判据**：脚本自己打印 `image: loading=True cannot_open=False` 和 `exit`。
只看到 `exit 0` 不能证明位流里有程序。

## 30. 面积门禁"逐维度只降不升"会咬打包噪声（2026-10-22）

`check_area_budget.py --mode delta` 的规则是 LUT/FF/LUTRAM/DRM **每一项都不许涨**。
本轮交付版 LUT −106、LUTRAM/DRM/APM 持平、S（LUT+FF+LUTRAM）−103，
但 FF 从 9,475 涨到 9,478，门禁 `exit=1`。

**为什么不是新状态**：本轮没有新增任何寄存器（唯一加过的是 `br_go_q/br_pc_q`，已撤回；
`id_u1_h/id_u2_h`、`ex_mul`、`ex_pred/m_pred/w_pred` 都已删除）。这 3 个触发器只能来自
"给 `ex_*_h` 补异步复位后，触发器原语从无复位版换成带复位版，打包结果变了"。

**判据**：
1. 先用 `--mode baseline` 看百分比；S 总量在降、单项 ≤0.05% 的波动应视为噪声，
   不要为了让它变绿去删功能逻辑（那才是真的降质量）。
2. 想真正压 FF，优先找**只写不读的整条链**（本轮 `ex_pred/m_pred/w_pred` 就是这样找到的，
   但综合器其实已经自动删了，所以数字没动——这也说明"RTL 里删掉"和"综合器删掉"是两件事，
   都能做，但不要指望删了 RTL 面积就一定降）。
3. 观察类计数（`retire_cnt_q` 64 位）收窄成 32 位是合法瘦身，但如果它整条都是悬空的，
   综合器早就删了，别把它算进你的收益账。

## 31. "交付成绩"和"正在改的核"不是同一个核 —— 先查构建日志里的模块名（2026-10-22）

**现象**：拿仿真周期去和板测 3.8557 比，怎么算都是"差 24%~45%"，换了几种改法都解释不了；
同一份 RTL 的"关键路径"一次是 35.9 ns、一次是 21.4 ns，差 1.7 倍。

**查什么**：构建目录里到底综合了哪个核。

```bash
grep -a -c "rv32_top" build/<tag>/compile/*.log    # 0 => 旧核；>0 => 新核
grep -a -o "u_if_id\|u_id_ex" build/<tag>/compile/*.log | head   # 旧核 pangoriscv 的子模块
```

- `build/perf_p37b`（板测 3.8557 / 1152 迭代 / 298,780,717 ticks）：`rv32_top` 出现 **0** 次，
  层次名是 `cpu/u_if_id`、`cpu/u_id_ex`、`cpu/u_ex` ⇒ 跑的是**旧核 `pangoriscv`**。
- `build/p5_126` 及其后所有构建：`rv32_top` 出现 14 次 ⇒ 跑的是**新核 `rv32_top`**。

**原因**：`soc_config.vh` 默认定义 `CORE_RV32`，`pangoriscv_axi_top.v` 据此实例化 `rv32_top`；
而 `pangoriscv.v` 仍然在源文件清单里（它只服务于 `RV32_OLD_CORE` 的 A/B），
所以"两个核都编译了"这件事在 compile 日志里看不出来，**只有实例化名能区分**。

**怎么办**：
1. 任何"相对交付基线"的比较，第一步先 `grep rv32_top build/<tag>/compile/*.log`
   确认是同一个核，否则这条比较作废。
2. 时序报告的层次名是最快的指纹：`u_if_id`/`u_id_ex`/`u_ex` ⇒ 旧核；`u_alu`/`rr_*`/`u_mul` ⇒ 新核。
3. 结论写进文档时**必须带"哪个核 + 哪个镜像 + 哪个构建 tag"三个限定词**，
   否则下一轮又会把两个核的数字拼在一起。

## 32. 20 迭代仿真的绝对周期里含 ~1.89 M 固定启动开销 —— A/B 能做，折算不能（2026-10-22）

**现象**：同一套 RTL，20 迭代仿真的 `cycles/iter`（348,031）比板上 1152 迭代的
`ticks/iter`（259,358）高 34%，于是得出"新核比旧核慢 30%"的错误结论；
用总周期算 IPC 得到 0.99，用边际算得到 1.09，差了 10%。

**查什么**：两点定标。同一镜像、同一 TB 跑 20 与 40 迭代，取斜率。

```
20 迭代 7,168,871 / 40 迭代 12,451,519
⇒ 边际 264,132 周期/迭代、288,292 指令/迭代、边际 IPC 1.09
⇒ 固定开销 = 7,168,871 − 20×264,132 = 1,886,231 周期
```

**原因**：仿真把 CRT 初始化、`.bss` 清零、UART/时钟初始化、CoreMark 第一次自检全部算进
`Total ticks`；板测跑 1152 迭代时这笔开销摊到 1,901 周期/迭代（可忽略），
20 迭代时它占 **26%**。所以"20 迭代总周期 ÷ 总指令"既不是 IPC，也不是分数。

**怎么办**：
1. **A/B 看总周期**（同一固定开销会抵消），**反推分数/IPC 一律用边际斜率**。
2. 写文档时把 `cycles` 和 `cycles/iter(边际)` 分开列，别只写一个。
3. 想用总周期口径做小改动 A/B 时，先确认改动没有动初始化路径（否则固定开销变了，
   你会把它误记成稳态收益）。

## 33. load-use 互锁不只是"等数据"，它还是响应落进 `m_value` 的唯一时窗（2026-10-22）

**动机**：`STALLDBG load_use = 1.63 M / 7.17 M 周期（22.7%）`是最大单项停顿，
而 `DC_DBG hit = 982,886 / miss = 110,382` 说明 90% 的访问是命中、
数据缓存是**在接受边沿**就回数据的（`dcache_axi.accept_hit`）。
于是判断："命中那一拍根本不需要停"，把互锁改成只在 miss 时生效。

**两次实测（ISA 21 例全量）**：

| 放行条件 | 结果 | 失败例 |
|---|---|---|
| `!mem_rsp`（任何响应） | **16/21** | 2, 5, 14, 18 |
| `!(mem_accept && done_valid)`（只放行 accept 边沿命中） | **17/21** | 2, 5, 18 |

**原因**：那条 load 的响应并不是在它自己的 `ex` 拍里就落地的。`m_value` 的捕获式是
`(ex_load && mem_rsp) ? load_value : ex_value`，只有在 load **仍在 `ex` 级**的那一拍
`mem_rsp` 才有效；而"load 在 `ex` 级多待一拍"正是 `load_use` 干的事
（`hold_ex` 冻结该级）。所以 `load_use` 是一个**自给自足的两拍结构**：
停一拍 → 响应到 → `m_value` 捕获 → 消费者下一拍走 `m_value` 旁路。
把停顿拿掉，响应就没有地方可落，消费者读到的是上一拍的 `m_value`。

**怎么办**：
1. 这类"停一拍换一次缓存访问"的互锁，**不要**按"命中/miss"去放行。
   要省这一拍，只有两条正路：把数据在 `ex` 拍内组合旁路进 ALU（路径会毁掉频率），
   或者把 load 拆成独立的 M 级（改流水结构）。
2. **动 load-use 必须用 CoreMark 五项 CRC 验收**，不能只看 ISA——本轮 ISA 掉 3~4 例
   是运气好，§17 记录过一次"ISA 21 例全过但 `crclist/crcstate` 算错"的先例。
3. 判据：改动前后都要打印 `STALLDBG`，如果 `load_use` 降了而 `mem_wait` 等量升了，
   说明你只是把停顿换了个名字。

## 34. PDS 整流程的命令是 `pnr`，不是 `place_route`（2026-10-22）

**现象**：`--mode full` 的脚本跑完 `dev_map` 后直接结束，退出码 0，
但目录里没有 `place_route/`、没有 `report_timing/`，只有一句

```
E: Failed to execute the script : invalid command name "place_route"
```

**查什么**：`build/*/platform/pango_native/build.tcl` 里交付流程用的是
`eval pnr -fix_hold_violation_threshold 0 ...` 然后 `report_timing`、`gen_bit_stream`。
`place_route` 是**报告目录名**，不是命令。

**原因**：脚本把目录名当命令写进 tcl；`pds_shell -continue` 遇到未知命令只记一条 `E:` 就往下走，
所以"综合成功 + 退出码 0"看起来像整流程成功。

**怎么办**：
1. 整流程一律用 `pnr`（带上交付版那五个 hold 修复参数）+ `report_timing`；不要用 `place_route`。
2. 判据不是退出码，而是 `ls build/<tag>/report_timing/*.rtr` 有没有文件。
   **没有 .rtr 就等于没有布线与时序结论**，只能报综合 WNS。

## 35. 关键路径上"最大的一块"可能只是一个 MUX 输入，而那个输入几乎从不被选中（2026-10-22）

**现象**：`p7_path40b` 的最差路径 26.647 ns / 39 级，逐 cell 读出来是：

```
w_rd_h → 操作数选择 4.4 ns → fwd2 → u_mul 4 级 DSP 级联 9.0 ns
       → alu_a_h（lane1 的操作数）→ 比较 → 目标加法 → 预测校验 → perf CE 4.6 ns
```

乘法的输出**为什么会在 lane1 的输入上**？因为 `fwd1_h/fwd2_h` 的第一优先级是包内旁路
`lane0_raw1 ? ex_value_w : ...`，而 `ex_value_w = rr_mul ? mul_y : ...`。
也就是说：**"lane0 是乘法、lane1 同拍读它的结果"这一种包**，把 4 级 DSP 级联整个塞进了
lane1 的 ALU 前面。

**查什么**：不要只看"这条路径经过哪些模块"，要问**这条边在什么条件下才被选中**。
工具给的是结构上最长的边，不是统计上最热的边。

**怎么办**：拒绝那一种包（`packet_md_use`：lane0 是 mul/div 且 lane1 读它的 rd），
并把包内旁路的输入改成 `alu_y`（单拍加法器结果）。实测 CoreMark 周期
**6,960,622 → 6,960,617（−5 周期，噪声级）**，ISA 仍 20/21。

**关键区别（这一条比上面更重要）**：同样是"拒绝包内 RAW"，
- 拒绝**一切**包内 RAW → ISA 18/21，lane1 完全不扛访存（§26）；
- 只拒绝**生产者不是单拍加法器**的那一种 → 0 代价。
判据：**要拒绝的粒度是"做不到的那一种生产者"，不是"这一类依赖"。**

## 36. load-use 停拍不是互锁写法的问题，是"ALU 放在了读寄存器那一拍"（2026-10-22）

**现象**：`STALLDBG load_use = 1,714,576` 周期（占 24.6%），而 5.2 分只差 1.23 M 周期。
三轮里试过三种写法（无条件停、`!mem_rsp` 放行、只放行 accept-hit），
分别得到 20/21、16/21、17/21。看起来是"写不对"，其实是**结构上就消不掉**。

**查什么**：把 load 与它的消费者在两个相邻流水级上的时间摊开：

```
T    : load 在 EX，cache 在 accept 边沿回数据 → m_value 在本拍末尾写入
T+1  : 消费者在 EX —— 但它用到的操作数是在"上一拍"（RR）算好的
```

这个核的 `ex_value / ex_addr / ex_sdata / ex_csr_src` 全部是
**"在 RR 那一拍用当时的 fwd 算好、再在 RR→EX 边沿寄存"**。
所以消费者的执行发生在 RR 拍，而 load 的数据在 RR 拍末尾才写进 `m_value`——**永远差一拍**。

**结论（可复用的判据）**：只要"执行"和"读寄存器"在同一拍，load-use 就必然是一拍，
改互锁条件只会改变出错的方式，不会消掉那一拍。三种写法的失败例
（2/5/14/18、2/5/18）都是同一个原因：消费者拿到了上一拍的 `m_value`。

**唯一能消掉它的结构**（下一步要做的，不是本轮）：
把 ALU 从 RR 挪到 EX，同时把地址加法器留在 RR：

```
RD（读）: rf 读 + 旁路 mux + 地址加法  → 锁存 a/b 与地址        ≈6 ns
EX（执行）: a/b + 上一拍生产者的旁路 + ALU + cache 访问（用锁存地址）≈6 ns
```

这时 **load 的数据和 ALU 结果在同一拍末尾落地**，消费者的 EX 在下一拍，
通过一级旁路就能拿到 —— load-use 停顿整块消失（−1.42 M），
而且两段各约 6 ns，126 MHz 的 7.94 ns 预算也有余量。
代价：分支结清晚一拍（误预测 +1 拍 ≈ 40 k 周期，0.6%），乘法必须独占一级（2 拍延迟）。

## 37. 满足式约束一旦"满足"，工具就不再尽力，测出来的不再是上限（2026-10-22）

**现象**：40 MHz（25 ns）约束下 `report_timing` 报 **WNS +1.053 / 布线后全过**，
看起来"路径 23.9 ns"；但同一份报告里 `Logic 4.038 ns (17%) / Route 19.447 ns (83%)`。
上一轮同一套方法测出的是 26.647 ns（WNS −1.647）。同一份 RTL 两次差 2.7 ns。

**原因**：约束宽松到"随便布都能过"之后，布局布线器提前收敛，不再为时序做优化，
走线长度占比飙到 80% 以上。**"满足"这个结果本身把测量方法废掉了。**

**判据**：
1. 用满足式约束测上限时，必须同时看 `WNS` 与 `Logic/Route` 占比。
   Route > 70% 且 WNS > 0 ⇒ 这个数不是上限，是"工具停止努力的位置"。
2. 要测上限，约束取"刚好违反"（WNS 略负）那次；要证明"能跑多快"，
   必须让 `Design Summary` 是 `All Constraints Met` **并且** WNS 接近 0。
3. 126 MHz 约束对 20+ ns 的路径跑不完布线（30 分钟后仍有 10,638 条未布线），
   所以中间档位（100 MHz）才是可用的测量点。

## 38. 把发射点前移一拍，就把"杀掉错路指令"的时窗压成了 0（2026-10-22，P9/R5）

**现象**：R5（访存请求从 M1 挪到 EX）之后 `load_use` 从 1,714,576 直接归零，
`Total ticks` 5,073,264 → 4,529,953（看起来 3.94 → 4.41，涨了），
但五项 CRC 里 `crclist` / `crcstate` / `crcfinal` 全错，另加十条

```
LSU_FAULT cycle=4760224 addr=00000031 store=1 size=0 pc=00002b10 rd=0
```

`pc=0x2b10` 是 xprintf `number()` 里的 `sb s1,0(a5)`，`addr` 是 `0x31/0x32/0x34/0x36/0x61/0x62`
——都在 0x1000_0000 数据窗口之外，落进 0x0..0x1000_0000 的空洞（DECERR）。

**查什么**：不要查地址是怎么算出来的，查**这条 `sb` 该不该存在**。
在 `rv32_top` 里加一个只在地址越界时触发的探针（`ifdef RV32_MEMDBG`），
把 accept 那一拍的 `op_pc / rr_inst / rs1 / fwd1 的胜出来源` 全打出来：

```
MEMBAD cyc=4654464 pc=00002b10 inst=e65ff06f st=1 sz=0 addr=00000061 l1=1 rs1=31 s1=4
```

一行就够了：`inst=e65ff06f` 是**车道 0 的 `j 2970`**，`l1=1` 说明这条 `sb` 是车道 1，
`pc` 却是 0x2b10 —— 也就是说这个包里车道 0 是**跳转**，车道 1 是它的**顺序后继**。
预测器把这个 `jal` 的目标猜成了 0x2b10，所以 `lane1_is_pred=1` 让它们配了对；
真值 `j 2970` 一算出来 `br_miss=1`，车道 1 是错路，必须在 RR/EX 边沿被杀。

**原因**：老结构里请求从 M1 发出，比 `br_miss` 晚**整整一拍**，所以"杀"总在"发"之前；
R5 把发挪到 EX 之后，`br_miss` 与 `issue_mem` 落在**同一拍**，
边沿上的 `ex_v1 <= ... && !br_miss` 只能拦住它进入 M1，拦不住它已经被 LSU 收下。
错路的 `a5` 是无意义寄存器值（探针里 `rs1=31` 的 `fwd1` 落到 `rf_d0=3`），
于是 `sb` 拿着这个垃圾地址真的写了内存。

**怎么办**（两条都做了）：
1. `ex_is_mem_h` 增加 `&& !ctrl_miss_now`（`ctrl_miss_now = rr_valid && is_ctrl && ctrl_next != rr_pred`），
   让"车道 0 要把 PC 改掉"这种包里的车道 1 访存**整条从 EX 里消失**——
   不是"等一拍再杀"，而是"根本不进 `mem_wait`"。
2. 只在 `issue_mem` 上加 `!br_miss` 是不够的，而且会**死锁**：`br_miss` 自己带 `!hold_ex`，
   而 `hold_ex` 来自 `mem_wait`；错路访存一旦开始"等"，`hold_ex` 就一直高，
   `br_miss` 永远不成立，重定向永远不发（实测 `STALL_DETECT`，20 万拍不退休，
   `MEMWAITDBG blocked` 全是 store）。**判据：任何"因为 X 所以不发"的守卫，
   必须同时让 X 不进入 `mem_wait`，否则在"停拍本身依赖验证结果"的核里就是死锁。**

**可复用判据**：只要把一个"会写外部状态"的动作（store、DMA、UART 写）前移一级，
就必须把**所有**能杀掉它的信号（`br_miss` / `kill_all` / `trap`）都提到同一拍去比，
并逐条检查这些信号里有没有"依赖停拍"的分量。

## 39. freeze 是"跳过整块"写的，于是它顺手吞掉了 kill（2026-10-22，P9/R5）

**现象**：R5 第一版 ISA 用例从 20/21 掉到 19/21，新红的是 case 19
（"车道 1 总线故障只提交更老的前缀，含 load x0"）。逐拍打印 `TR_RDR/TR_FET` 看到：
第一次 trap 之后 `pcq` 卡在 `0x3f00` 长达 24 拍，然后**第二次** trap
（`store fault pc=0x1424`）才发生——比 faulting load **更年轻**的那条 `sw` 没有被冲掉。

**查什么**：看冻结条件是怎么写的，别看被冻结的那几个寄存器：

```verilog
end else if (!hold_ex) begin          // ← 整块跳过
    rr_valid <= id_valid && !kill_all && !kill_young;
```

`hold_ex` 为 1 时整块不执行，**包括** `rr_valid <= 0` 这一句。
而 `kill_all`（`trap_go || mret_go`，在 WB 结清）可能恰好与 `hold_ex` 同拍。

**原因**：老结构下 trap 那一拍 `hold_ex` 很少恰好为 1；R5 之后，
比 trap 更年轻的指令经常是一条**还在等 AXI 写响应**的 store，
`mem_wait` 和 `trap_wait` 同拍为真，kill 被冻住。

**怎么办**：

```verilog
end else if (!hold_ex || kill_all) begin
    id_valid <= !hold_ex && id_accept && !kill_all && !kill_young;
```

即"冻结跳过整块"与"kill 必须生效"这两件事要分开写：进入块的条件加 `|| kill_all`，
块内每条 valid 赋值再自己 `&& !hold_ex`。RD 与 RR 两级都要改。

**可复用判据**：**valid 位永远不许被 freeze 挡住清零**。
自检方法：任何 `else if (条件) begin` 形式的冻结块，逐句问"这条在冻结期间不执行，
语义还成立吗"——只要块里有一句是"清零/杀死"，这个写法就是错的。

## 40. "拒收配对"不会删掉那条路径 —— 因为综合读不到 `pair_ok`（2026-10-22，P11/R9a）

**现象**：`lane1_ok` 排掉 `dec_mul_h` 之后，车道 1 的乘法仍然 100% 拒收
（`WIN_L1BAD mul=115,086 / 20 迭代`），而**最差路径还是那条**
（`p7_path40b`：`u_mul` 四级 APM → `alu_a_h[10]` → `u_alu_h` → `br_taken_h` → `ex_next_h`，
26.6 ns）。拒收规则写在 `pair_ok` 里，路径一点没短。

**查什么**：不要看"规则写没写"，看**综合结果的锥里有没有那条级联**。
把 `report_timing` 每一行的 `Logical Resource` 和 RTL 里的信号名对上：
`APM_.../P_0[1] → u_mul/prod[42] → alu_a_h_4[10]` 这一串说明乘法器直接挂在
lane1 的操作数 mux 上。

**原因**：`pair_ok` 是**功能**约束，不是**结构**约束。综合器只优化结构：
那条级联在网表里是**可达**的，哪怕 `pair_ok` 永远不会让那种包发射。
（`prod` 究竟是经哪一级进到 `alu_a_h` 的，从报告上只看到
`ex_value_w = rr_mul ? mul_y : ...` 这一层被并进了 lane1 操作数的锥里；
不必把机制推到底——**只要实测证明"拒收不删路径"就够了**。）
**你用拍子买了一个"路径不存在"的假象。**

**怎么办**：把单位**复制**成并联，而不是把用法禁掉：

```verilog
wire lane1_mul_ok = dec_mul_h;                      // 只放开乘法
wire [31:0] mul_y_h;
rv32_mul u_mul_h(.op(rr_md_op_h), .a(fwd1_h), .b(fwd2_h), .y(mul_y_h));
wire [31:0] ex_value_h_w = rr_mul_h ? mul_y_h : alu_y_h;
```

两条级联各喂各的 EX/M1 寄存器，没有串联。实测 `Total ticks` 4,179,679 → 4,070,391
（+0.128 CM/MHz），代价 4 APM。**除法仍然拒收**：它是迭代式的，
"第二个单元"是第二个状态机，不是第二个加法器，那是另一类改动。

**可复用判据**：看到 `pair_ok` / `hazard` / `stall` 里有一条"因为 A 太慢所以这种组合不发射"，
先问一句——**把那种组合禁掉，A 的路径会不会跟着消失？** 答案是"不会"，
因为综合器不知道 `pair_ok`。这类规则只省拍子，不省 ns。

## 41. 一次拒收的净代价是 0.48 拍，不是 1 拍（2026-10-22，P11/R9a）

**现象**：D6 探针给出 `refused_pair=779,461`，按"一次拒收 = 一拆二 = 1 拍"估算，
消掉 229,247 次拒收应该省 22.9 万拍；实测只省了 **109,288 拍**（47%）。

**查什么**：看 `WIN_ACCEPT` 里非目标桶的变化。这次 `mduse` 从 186,372 掉到 72,211，
掉了 11.4 万——**根本没改这条规则**。

**原因**：被拆开的那条指令在下一拍会变成"新包的车道 0"，重新和它后面那条凑对。
所以一次拒收的真实代价是"流错位 1 拍"，而错位之后有接近一半的机会立刻重新配上。
再叠上"被拆的那条自己也可能落进本就要拆的桶"，净代价就摊到 0.48 拍。

**怎么办**：估算收益时一律乘 0.48（当前 RTL、CoreMark sim20_o2 口径），
并且**不要**把"顺带重排"的收益预先算进预算——它是事后读数，不是可以计划的东西。

**可复用判据**：任何"消掉 N 次停顿"的估算，先拿本核跑一次已知的 A/B 校准
（`l1bad mul` 那次的 115,086 → 109,288 ticks 就是这次的校准点），
把比例记在计划文档里，别每次用理想值 1.0。

## 42. 最宽的加法器常常是没人读的计数器（2026-10-22，P11/R9b）

**现象**：`p7_path40b`（40 MHz 约束、0 根未布线、`report_timing` 跑完）里
三条最差路径有两条的终点是 `soc/perf_inst/cnt[2][56]`，30.20 ns；
第一条是 30.34 ns 的乘法器链。也就是说**性能计数器的进位链和数据通路一样长**。

**查什么**：`report_timing` 每段路径的**终点寄存器名**。
只要终点是 `cnt[*]` / `mcycle` / `minstret` / 任何 `[63:0]` 的累加器，
就先看它的加法器有多宽，再看数据通路。

**原因**：`cnt[i] <= cnt[i] + 64'd1` 会生成 64 深的进位链，
在 -6 速率的 CLMA 上约 0.136 ns/级 ≈ 8.7 ns；`mcycle` 是每拍都加，等于每拍都走一遍。
这两样东西都是"给软件看"的，和发射、旁路、访存毫无关系，却能独占关键路径。

**怎么办**：拆成 16 位四段，**段间进位取寄存器值**（不是取低位加法器的进位），
四段就并联了，最长链 16 级：

```verilog
function [63:0] inc64;
    input [63:0] v;
    reg c1,c2,c3;
    begin
        c1 = (v[15:0]  == 16'hFFFF);
        c2 = c1 && (v[31:16] == 16'hFFFF);
        c3 = c2 && (v[47:32] == 16'hFFFF);
        inc64 = { v[63:48] + {15'd0,c3}, v[47:32] + {15'd0,c2},
                  v[31:16] + {15'd0,c1}, v[15:0]  + 16'd1 };
    end
endfunction
```

值、周期、流水级全都不变，不花一个触发器。`perf_regs` 的 11 个 32 b 活动计数器同理（拆两段）。

**可复用判据**：做时序优化前先跑一次 `grep -rn "64'd1\|63:0\]"`。
如果有 `[63:0]` 的每拍自增寄存器，它一定是关键路径候选，先修它再谈数据通路。

## 43. 摆放估计比布线后乐观约 4 ns；而"满足式"约束下测到的不是上限（2026-10-22）

**现象**：两个都已布通的跑法，`Worst slack after detailed placement` 与
`report_timing` 的 `Estimated Period` 差得很稳定：

| 跑法 | 约束 | detailed placement 估计 | 布线后实测 |
|---|---|---:|---:|
| `p7_path40b` | 25.0 ns | +2344 ps（路径 22.66 ns） | 26.65 ns（37.53 MHz） |
| `p12timing50`（未完成布线） | 20.0 ns | +1027 ps（路径 18.97 ns） | — |

即**布线后比摆放估计再差 ~4 ns**。

**查什么**：只信 `report_timing` 的 `Performance Summary → Estimated Period`。
摆放阶段的 `Worst slack` 只能用来**同向比较**两次改动的相对好坏，不能折算 fmax。

**原因**：摆放阶段的 slack 用的是线长估计模型，没有真实布线拓扑、没有拥塞绕行。

**怎么办**：判 fmax 只有一条路——跑完整 `place_route` + `report_timing`，
读 `Estimated Period`，且约束必须加在**核时钟引脚**上：

```tcl
create_clock -name core_clk -period 8.333333 [get_pins {u_core_pll/CLKOUT0}]
```

不能像 `pango_native_100mhz.fdc` 那样把 10 ns 加在 `get_ports {clk}` 上再让 PLL ×56/12 ——
那等于要求核时钟 467 MHz，测出来的东西和"100 MHz"没有关系（`p5_126`/`p7_impl126b`
都是上万个未布线网线的直接后果）。

**可复用判据**：`.fdc` 里每一行 `create_clock`，先问"这个约束点上的实际频率是多少"。
加在板级端口上、后面还有 PLL 的，写的周期和核时钟没有关系。

## 44. 返回地址栈"加了就该变快"，但 `sp_max` 已经顶到深度上限（2026-10-22）

**现象**：给 `branch_predictor` 加 8 深返回地址栈（RAS），`jalr` 预测命中率
看起来有 60%，但 `Total ticks` 只从 4,070,391 变成 4,068,258（−2,133，0.05%），
`mispred` 只从 88,087 掉到 87,742（−345）。改动本身正确、仿真通过、CRC 正确，
**收益却约等于零**。

**查什么**：加探针看四个数，缺一个都不能下结论——

| 探针 | 读数 | 说明 |
|---|---:|---|
| `push` / `pop` | 32,292 / 32,331 | 栈在进出，不是死的 |
| `fetch_ret` | 23,480 | 用上了栈顶（只是 push 数的 73%） |
| `sp_max` | **8** | 等于 `RAS_DEPTH`，**顶满了** |
| `jalr` / `jalr_pred_ok` | 44,448 / 26,579 | 只有 60% 的 jalr 是"返回"型 |

**原因**：`sp_max == RAS_DEPTH` 说明栈顶满之后不再推进（或开始覆盖）。
一旦栈内容与真实调用栈**错位**，之后每一次"返回"都会取出一个**错误**的地址——
预测错比不预测更糟：本来不预测只是按 fall-through 猜，错位后是往一个毫不相干的
地址跳，重定向的代价反而更大。这两个效应正好抵消，所以净收益 ≈ 0。

另外 40% 的 `jalr` 是 `jr` 型（`jalr x0, 0(rs)` 之外的间接跳转、函数指针、
switch 跳转表），它们**本来就不该**用返回地址栈去猜，`jalr_pred_ok=26,579/44,448`
里缺的那 18k 就是它们。RAS 的覆盖率天生不到 60%。

**怎么办**：判"预测器值不值得做"必须同时看**覆盖率和正确率**，只看覆盖率会得出
错误结论。这里的正确做法是先把栈加深到能容纳真实调用深度、并在**溢出时停止压栈
（不覆盖）**，否则就干脆不做。

已回退：`git checkout 01ba45e -- firmware/code/rtl/core/branch_predictor.v firmware/code/rtl/core/rv32/rv32_top.v`
重跑确认 `Total ticks` 回到 4,070,391。

**可复用判据**：任何"有界栈 / 有界队列 / 有界表"的加速结构，先测
`max occupancy == capacity` 是否成立。成立就说明它在**溢出后行为错误**，
这时候调大容量只是推迟出错，不是修好；调小容量才可能"少错一点"。
先证明"从不溢出"，再谈命中率。

## 45. 加旁路把流水改快了，性能反而掉 5 倍，而 CRC 全对（2026-10-22）

**现象**：把 IF/ID 寄存器旁路掉（ID 空时让指令直接进 RR），
`Total ticks` 从 3,971,170 变成 **19,484,710**（慢 5 倍），
IPC 1.20 → 0.29，但 **五项 CRC 一个都没错**、`Iterations` 也是 20。

**查什么**：先看窗口分解，不要看总时间。

```
WIN_ISSUE pair=13,539 single=3,089 none=19,490,308 (starve=233,992 other=19,256,316)
WIN_DC idle=17,960,827
```

`none other`（前端有指令、但一条都没发射）占了 19.26 M，而且**不是** `mem_wait`
/ `div_wait` / `trap_wait` / `redirect` / `hold_ex` 里任何一个 —— 说明卡在
`fetch_ready` 的另一项上。`fetch_ready = !hold_ex && !serial_q && !halt_pending
&& !halted && !redirect_any`，逐项排除只剩 `serial_q`。

**原因**：`serial_q <= (id_accept && id_serial)`，而 `id_serial` 是**ID 寄存器里的
旧值**。原来每次 `id_accept` 都会把 ID 寄存器整体改写，所以 `id_serial` 永远
描述"最新接受的那条"。旁路之后**不写 ID 寄存器了**，`id_serial` 就永久停在
最后一条 CSR 指令留下的 1 上 —— 于是每一次 accept 都把 `serial_q` 置位，
前端被反复串行化。

同一类"用户不检查 `id_valid` 的 ID 字段"还有三处，一起中招：

| 字段 | 谁在用（不检查 id_valid） |
|---|---|
| `id_serial` | `serial_q <= id_accept && id_serial` |
| `id_csr`, `id_csr_op`, `id_rs1` | `rf_write_intent`、`dcwe = id_csr` |
| `id_csr_addr` | `csr_native .addr()` |

**怎么办**：

1. 任何"跳过某一级寄存器写入"的旁路，都要先列出**这一级字段的全部读者**，
   把"读者不检查 valid"的那些在旁路拍**显式清零**。
2. 判据顺序改成：**先看 CRC，再看窗口分解，最后看总分**。
   这次 CRC 全对是最大的干扰项 —— 它只证明"架构结果对"，不证明"控制通路没坏"。
   `none other` 暴涨 + `misPred` 从 80,259 掉到 211，是"前端被串行化"的指纹
   （预测器根本没机会训练）。
3. 另一个反方向的坑顺手记下：**保守条件可能等于没做**。第一版只在
   `!rr && !ex && !m && !w`（流水全空）时旁路，`Total ticks` 只省了 1,849。
   原因是分支在 RR 解析时 M1/M2/WB 里还有更老的指令，等它们排空，
   重定向目标早就按正常路径进了 ID —— 条件写对了，时机永远不重合。
   **旁路类改动的收益必须先量"条件成立的那一拍与需要它的那一拍是否重合"**，
   不重合就白写。

## 47. PDS 只收一个 .pcf；show_device 名字、网格名、floorplan 坐标是三套编号（2026-10-22，P13）

**现象**：区域约束写好了，`add_constraint floorplan.pcf` 之后 pnr 报

## 48. 详细布线卡在 2~3k 条"未布"上不收尾——先分离 hold-fix 空转与真拥塞（2026-10-22，P13）

**现象**：40 MHz 约束下摆放 WNS +1.5 ns（过得很好）、全局布线 15 轮 0 条未布，
但**详细布线**从 27k 条磨到 2.2~2.5k 条后就卡住：数字上下震荡
（2,292→2,533→2,377→2,469...），200+ 轮不再下降。120 MHz 同样卡在 3.8k。
pds_shell 还会在 ~270 轮/48 分钟处无解释退出（exit≠0、log 尾部是正常迭代行、无 .rtr）。

**查什么**（按顺序分离，每一步都有判据）：
1. **hold-fix 空转？** 把 `-fix_hold_violation_*` 全部去掉重跑（`--plain-pnr`）。
   实测：照样卡 2.2~2.5k ⇒ **hold 参数不是原因**（它们只是让收敛更慢一点）。
2. **真拥塞？** `-plc_decongestion 1`、`-share_router_control_signal TRUE`
   （压 CE/RS 扇出）、`-dc_duplication TRUE`（复制高扇出单元）三个开关逐个/组合试。
3. **摆放随机性？** 换 `-gplace_seed`/`-gplace_times`（多 seed 摆放选优）。
4. **结构？** 三个 LUTRAM 阵列（data_ram 2,048 + I$ + D$）共用走廊时，
   WADDR/CE 总线是巨型交叉线——**按 skill §9.9 分区**才是根治。

**原因**（截至本条，已证实的部分）：最后 2k+ 条是**震荡而非单调下降**——
每轮都有网被竞争者拆掉重布。这是拥塞的指纹，不是时序目标不可达的指纹
（摆放明明是过的）。40 MHz 的 p7_path40b（P8 之前 RTL）同流程能收尾，
说明回归出在 P9~P12 的 RTL/资源变化（lane1 乘法器 +4 APM、跨行成对 +106 LUTRAM）。

**怎么办**：把"布线不收敛"当成独立问题先解决（它是位流/上板的前置），
实验按上表 1→4 顺序做，**每个实验记下"卡在哪一档"**（本例：无 hold 参数卡 2.3k）。
判据是"Unrouted nets"序列：**单调下降=在收敛，震荡=拥塞**。
别把两种混为一谈就去动 RTL。

## 50. "更保守"的防御性 AND 项会让重定向丢失（2026-10-22，P15）

**现象**：把 `br_miss` 的 `!hold_ex` 换成 `!trap_wait && !div_wait && !lane1_mem_raw`
（多一个"配对不变量"的防御项），CoreMark 在 retire 2855（PC 0xc8 的 JAL）分歧：

实际却**反向**——它把这个该发的重定向挡住了。

**查什么**：
1. 先比 `retire_trace.txt` 的**第一个分歧退休号**，不要从头读波形；分歧点前后的
   `pc/inst` 两列一比就知道是哪条指令丢了重定向。
2. 再问："我加的这个项，在**该信号本来会拉高的那群输入**上是不是恒 0？"
   不是"会不会更安全"，而是"会不会误挡"。

**原因**：流水线冻结（`hold_ex`）时 `rr_*` 全部保持，lane1 的旧译码（`rr_load_h`）仍在，

正是 `br_miss` 的触发条件。所以那个防御项**既多余又有害**。

**怎么办**：做"去掉某个门控"的手术时，先在 RTL 里找出**同源的已有保证**
（本例：`ctrl_miss_now`），用它证明"该门控在触发集上恒真"，然后只保留真正需要的分项。
不要靠"再加一个条件让它更安全"——那是给冻结期的陈旧信号开了一个反向的口子。
回归判据只有一条：`Total ticks` 与基线**逐位一致** + CRC 五项全对。

## 52. 互斥分桶的 `else if` 顺序会把"重叠原因"错标成"单一原因"（2026-10-23，P17）

**现象**：周期账显示 `l1ctrl`（lane0 访存 + lane1 控制）占 10,257 拍/迭代，
按此恢复配对后实测只赚到 **3,610** 拍/迭代。差 2.8 倍。

**原因**：剖析器用 `else if` 链，
```
else if (lane0_mem && lane1_mem)      sb_l1mem
else if (lane0_mem && pair_l1_ctrl)   sb_l1ctrl
else if (packet_load_use)             sb_lduse
```
当 lane0 是 **load** 且 lane1 读它的结果时，`lane0_mem && pair_l1_ctrl` 和
`packet_load_use` **同时为真**，但链条先命中 `l1ctrl`，于是这批"load-use"被记成
了"访存+控制"。恢复配对后它们仍然是 single（因为真正的阻塞是 load-use），
`l1ctrl` 只降了 68,591/20 而不是全部。

**查什么**：每个桶必须能独立回答"如果我只消除这一个原因，能赚多少"。
`else if` 只能给出"按这个优先级分，谁先命中"，两者不等价。

**怎么办**：分桶用**两个层次**——
1. 互斥桶用于**加总等于总数**的校验（`CYC_SUM`、`SINGLE_SUM` 都做了，很好）；
2. 每个原因另配一个**独立**（非互斥）计数器，用来估收益。
   估收益时看独立计数器，不要看互斥桶。

## 53. TB 的周期性 `$display` 会冲掉 UART 报告里的 `Total ticks`（2026-10-23，P17）

**现象**：`Total ticks  : PROGRESS cycles=4000000 retires=...` —— 数字被进度行覆盖，
多次 A/B 里 `Total ticks` 变成 "corrupt"，而它**就是分数**。

**原因**：TB 每 50 万拍 `$display("PROGRESS ...")`，固件在结尾通过 UART 打印报告，
两个通道在 transcript 里交错。

**怎么办**：把 `PROGRESS` / `LIVE` 包进 `` `ifdef TB_PROGRESS ``（默认关）。
A/B 不再需要进度行；要看进度就显式 `+define+TB_PROGRESS`，并接受这次运行的
`Total ticks` 可能不可用。**另外**：`$display` 的 `` `ifdef `` 必须包住整个
`if(...) begin ... end`，包在 `begin` 里面会让未定义时的 `if/end` 结构被编译掉。

## 54. "摆放时序通过"被当成"频率达标"（2026-10-23，P18）

**现象**：报告里写"45 MHz 时序已达标（摆放层面）WNS +1.548 ns、TNS=0"，
于是结论变成"唯一障碍是布线收敛"。而同一份网表布线后是
`WNS −2.376 ns、4,077 个端点失败、Estimated 40.65 MHz`。

**查什么**：`pnr` 日志里 `Worst slack after placement is ...` / `Worst slack is ...`
是**摆放估计**（用估算线延迟）。真正的判据只在
`report_timing/*.rtr` 的 `Performance Summary` 里：
`Requested vs Estimated Frequency`、`Setup(Slow) WNS`、`Failing Endpoints`。
`report_timing` 读的是布线后的数据库，没有布线就没有 `.rtr`（`-place_only` 构建
根本没有这个文件）。

**原因**：这套网表在当前摆放质量下，**布线比摆放估计多 ~3.8 ns（18%）**。
两者不是同一口径，差一个量级都正常。

**怎么办**：
1. 任何"频率达标"结论必须引 `.rtr` 的 `Estimated Frequency` 与
   `Setup(Slow) WNS ≥ 0` + `Failing Endpoints = 0`，并注明**布线后**。
2. 摆放值只能用于**同一轮内的相对比较**（A/B 排序），不能当结论，也不能写进交接表。
3. `-place_only` 构建的产物只有 `run.log` 里的 `Worst slack`，标注成"摆放探针"。

## 55. `pnr` 选项"写了"不等于"生效了"，要先用逐位相同排除掉（2026-10-23，P18）

**现象**：`-dc_duplication TRUE`、`-refineplacement_cluster TRUE`、
`-logic_optimize_enable TRUE` 三组加上去，摆放结果与基线**逐位相同**
（都是 `Worst slack is 1462`、LUT 18,181、LUTRAM 3,790），
日志里也没有任何 `W:`/`E:` 提示说选项被忽略。

**查什么**：做 A/B 时，先看两组的**中间量是否完全相同**（`Worst slack after
detailed placement`、`before Replication Place`、TNS）。完全相同 ⇒ 选项没生效，
后面 1.5 h 的布线没必要跑。

**原因**：PDS 2022.2-SP6.1 对这几个选项在本流程/本器件上是静默 no-op。
`help pnr` 里能列出来的选项，**不代表**这条流程会用。

**怎么办**：
1. 选项类实验先用 `-place_only`（8 min）做，且**必须**先确认中间量不同，再跑满流程。
2. 已确认 no-op（截至 P18）：`-dc_duplication`、`-refineplacement_cluster`、
   `-logic_optimize_enable`。仍有效：`-plc_decongestion`、
   `-share_router_control_signal`、`-seed`、`-place_only`。
3. 未验证但值得单独试：`-slack_prior_in_global_router`、`-place_worst_slack`、
   `-route_constraint_iterate*`、`-max_ctrl_chain_length`。

## 56. 利用率 33% 时，区域约束**没有压缩空间**——这才是三次 floorplan 全负的原因（2026-10-23，P18）

**现象**：横带 / 竖带 / 紧凑方块三种 floorplan 全部负优化（−0.6 ~ −2.7 ns），
每次都能"合法加载、绑定成功"，所以一直以为是形状没选对。

**查什么**：先算账，别先画形状。
```
设计 18,181 LUT + 3,790 LUTRAM = 21,971 LUT 当量
def_region 网格 123 × 204 = 25,092 格，1 格 ≈ 2.65 LUT
⇒ 设计占 8,290 格 = 33% 的合法网格
```
想把关键路径的物理跨度减半，就要把 8,290 格塞进 12,500 格 → **66% 局部利用率**。
66% 的局部利用率在这个器件上必然拥塞；48% 的"紧凑方块"实测已经 −2.7 ns。

**原因**：**这个设计不稀疏**。27% 的 LUT 利用率听起来很低，但换成区域网格是 33%，
而走线延迟 0.66 ns/跳 的根源是"相关逻辑分属不同模块、被摆在模块级的不同位置"，
不是"设计摊得太开"。区域约束能改"放哪儿"，改不了"必须连哪些"。

**怎么办**：
1. **不要再试第四种 floorplan 形状**。除非设计面积先降 30% 以上（例如
   `data_ram` 进 BRAM 省掉 2,048 LUTRAM），否则没有可压缩的余地。
2. 降走线延迟只能靠**打断组合路径**（加流水寄存器）——寄存器给了摆放器
   "把两级分别放在各自扇出附近"的自由，这是 floorplan 做不到的。
3. 判据：加寄存器后，**每一级**的 `Route` 占比应显著下降（目标 <70%）；
   若仍 >80%，说明该级逻辑还是太宽，需要再切。

## 57. 120 MHz 的 PLL 分频比是**可达**的（2026-10-23，P18）

**现象**：`pangoriscv_top.v` 与 `pango_native_120mhz.fdc` 都写着
"120 MHz 不可达（F/M=40/9 → VCO 1080 或 2160，均非法）"，
导致 120 MHz 被当成"只能做时序规格、出不了位流"。

**查什么**：`ipm2l_pll/ui.tcl` —— 输出分频器 `STATIC_RATIO0` 是**独立**的，
且支持 0.125 粒度（`dutyFracShownUnit_basicPage` 里有 `abs_odiv/0.125`）。
约束只有两条：VCO ∈ [1330, 2133] MHz、PFD ≥ 19 MHz。

**原因**：原推导把"输出频率 = VCO / 120"当成了 O 必须是整数且等于 F/…，
漏掉了 O 可以取任意整数（甚至 0.125 步长的小数）。

**怎么办**：
```
120.4615 MHz = 27 × 58 / 13     VCO = 1566 ✓   PFD = 27 ✓   （整数参数，可直接用）
120.000  MHz = 27 × 60 / 13.5   VCO = 1620 ✓（需小数分频寄存器）
```
出 120 MHz 位流时用 58/13，并把时序约束写成 **8.3014 ns**（不是 8.333），
否则"约束通过"比"实际运行"松 0.4%。

## 58. `run_coremark_sim.py` 的 `cycles` 不是分数口径（2026-10-23，P18）

**现象**：改了一处 RTL，runner 打印 `cycles/iter=285,827`，而记忆里的分数口径是
`190,129 拍/迭代`，于是判定"回归 50%"并回退了改动。

**查什么**：打开 `.sim_runs/coremark_sim/<tag>/transcript.txt`，看固件自己打印的
```
# Total ticks      : 3833976
# Iterations       : 20
```
分数只认这一行：`分数 = Iterations × 1e6 / Total ticks`。

**原因**：runner 的 `cycles` 是**仿真周期总数 / 迭代数**，包含约 190 万拍的
启动期（`.bss` 清零 + UART 轮询，其中 122k 次轮询读 miss 各约 9.5 拍）。
`Total ticks` 只覆盖固件的计时区间。两者差 1.9 M 拍，**在 20 迭代规模下差 50%**，
恰好落进"看起来像严重回归"的区间。

**怎么办**：
1. 跨 build 比分数，**只用 `transcript.txt` 的 `Total ticks`**；
   runner 的 `cycles` 只能用于同一图片、同一起点的横向比较，且不能换算成分数。
2. 更可靠的判据：`Total ticks` 与基线**逐位相同**（本项目多次出现"改动完全免费"，
   逐位相同是正常结果，不是量测失败）。
3. 反过来说：**如果 `Total ticks` 逐位相同但 `cycles` 不同，说明改动没被仿真覆盖**，
   要查 TB 是否真的重编译（看 `compile ok` 那一行）。

## 59. 一次满实现的真实耗时是 4 小时以上，不是 1.5 小时（2026-10-23，P18）

**现象**：文档里一直按"每次布线尝试 1.5 h"排计划，于是"换 seed 多抽几次"看着可行。
实测：详细布线 **27~60 秒/轮**，而收敛需要 400~600 轮（`p15nx45` 是 575 轮），
即 **3~8 小时/次**。一个晚上最多做 2 次尝试，不是 6 次。

**查什么**：`build/<tag>/place_route/run.log` 里的
```
route iteration 73, CPU time elapsed 27.343750 sec     <- 这是单轮耗时
Unrouted nets 5837 at the end of iteration 73.
```
`multiseed_summary.csv` 的 `Total Routing Cpu Time` 不要拿来除以轮数——它不含
rip-up-and-reroute 的全部轮次，会低估 6~13 倍（`p15nx45` 那一栏是 1183 s，
按 575 轮算出 2 s/轮，与本轮同参数实测的 27 s/轮差一个数量级）。

**怎么办**：
1. 排计划按 **4 h/次** 算，一次只能做一个假设，不要设计"跑 4 个 seed 比一比"的实验。
2. 能用 `-place_only`（约 8 min，含综合 3 min）回答的问题，绝不跑满流程。
3. 判据先看**斜率**：`Unrouted nets` 每 8 轮的增量从 940 掉到 150 时，说明进平台期，
   继续等下去没有意义，直接换配置或回退，不要"再等等看"。
4. 因此**可布线性必须作为一等约束**：任何 RTL 改动先在 `-place_only` 上看摆放，
   再用"是否能收敛"验收，最后才看分数与时序。分数再好、不能布线的改动等于零。
