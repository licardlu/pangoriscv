# 效率专项（E 系列）：分数不变的前提下提升时钟与资源效率

日期：2026-10-21 07:40　起点：**3.8557 CoreMark/MHz 已交付**（`bitstream/pangoriscv_i1152_p37.sbit`）
硬约束：**分数不得变化**（20 迭代评分窗口逐位相同、五项 CRC 逐项相同）；每步单独提交、单独复核。

## 1. 实测依据（来自交付位流的 `report_timing`）

前 3 条路径**同一起点同一种形态**，且第 1 条 slack = **+4.484 ns**（周期 37.04 ns）：

```
Startpoint : u_id_ex/slot/data_q[394]           <- 指令位（mul 的操作数选择）
             -> u_ex/signed_mul -> APM_239_978/PO[0] -> APM_239_1008/P_1[2]   (~6 ns, 3 个 DSP)
             -> u_ex/reg_wdata_o_25[4] -> alu_result[4]
             -> N537[4] -> ex1_o2[4]            <- P37a 的前递 mux
             -> u_ex_h/N4.eq_* -> jump_flag_o -> actual_next_pc_h -> last_next
             -> pred_miss -> redirect_valid -> u_if_id/.../CE
```

**结论**：`fwd0_alu` 的条件里 `ex0_alu_cls` 已经**排除** `0x33/funct7=1`（M 扩展），
所以乘法器结果**永远不可能**被前递；但物理上 `alu_result` 是"含 mul 的完整 mux 输出"，
于是静态时序把 DSP 链算进了 lane1 的操作数路径。这是一条**功能上不存在的数据通路**。

## 2. 步骤 E1（时钟效率）：前递改用"乘法前"的 ALU 结果

1. `ex.v` 增加一个输出 `reg_wdata_fast_o` = 内部 `ex_alu` 的原始结果（M 扩展 mux **之前**）。
2. `pangoriscv.v` 的 `ex1_r1/ex1_r2/ex1_o1/ex1_o2` 改用它；`wdata`（写回）**保持用完整结果**。
3. 正确性论证：`fwd0_alu ⇒ ex0_alu_cls ⇒ 不是 M 扩展`，两条路径在该条件下**逐位相同**；
   写回、CSR、load、div 的取值路径一字未动。
4. 面积：0（多一根 32 位输出线，综合后会与 `wdata` 的 mux 共享前置级）。
5. 门禁：窗口/CRC **逐位相同**（这是本步唯一可接受的"性能结果"）；setup 必须改善；
   hold 不得变差；ISA 17/17、dcache、engine 64/64 全绿。

## 3. 步骤 E2（资源效率）：待 E1 落地后按网表实测选点

候选（必须先有数据再动）：
- D-Cache `data_mem` 三份 512×32（M19 卡片：疑似副本）。2 路×32 组×8 字 = 512 字，理论只需一份。
  但三条同拍读路径（`accept_hit`/`rsp_data`/`merged_accept`）要改时分割，风险高，
  且 LUTRAM 不在 `CoreMark/kLUT` 分母里 → **优先级最低**。
- 预测器 32 项 BTB：P4 记录 64 项多 ~1,900 LUT 换 −27% 误预测，反向操作可省 LUT 但会掉分 → **不做**。
- 真正候选：跑一次逐模块 LUT 统计，找**不影响关键路径、也不在性能路径上**的大块（优先看 SoC 外设与互连）。

## 6. E1 的结论：**不做**（这是一条功能上不存在的路径，改它要用分数换不记分的指标）

把交付位流的第 1 条路径拆开看（`report_timing_p37.rtr` 第 121–215 行），延迟构成是：

| 段 | 延迟 | 说明 |
|---|---:|---|
| `data_q[394]` → `u_ex/signed_mul` → 3 个 APM | ≈**6.5 ns** | M 扩展乘法器（DSP 级联） |
| `alu_result[4]` → `N537` → `ex1_o2[4]` | ≈1.6 ns | P37a 的前递 mux |
| `u_ex_h` 比较链 → `jump_flag_o` → `actual_next_pc_h` | ≈2.6 ns | lane1 分支判定 |
| `last_next` → `pred_miss` → `redirect_valid`（扇出 159）→ IF/ID CE | ≈5.3 ns | 重定向到取指使能 |

**关键事实**：`fwd0_alu` 的前置条件 `ex0_alu_cls` 排除了 `0x33/funct7=1`，
所以乘法器的结果**永远不会**出现在 `ex1_o2` 的有效数据里 —— 这 6.5 ns 是静态时序的"假依赖"。

**为什么仍然不改**：唯一能在 RTL 里消除它的办法，是让 `ex.v` 再输出一份"乘法前"的
`reg_wdata_fast`，即把整个 `reg_wdata` 的 case mux **再复制一遍**（实测规模约 +100~150 LUT）。
代价是 `CoreMark/kLUT` 从 0.2103 掉到约 0.209（−0.5%），收益是 setup 从 +4.484 → 约 +10 ns。
**27 MHz 评分下，时钟余量不记分，kLUT 记分** —— 这个交易是亏的，因此**不做**，只记录在这里：
若将来要把 Fmax 抬到 40 MHz 以上，这就是第一优先级的改法（或改流程加 `set_false_path`）。

## 7. E2：资源效率的实测基线（逐模块，交付网表 `perf_p37b`）

统计口径：`synthesize/pangoriscv_top_syn.vm` 里每个 module 内的 `GTP_LUT*/GTP_ALUT*/GTP_MUX*` 与 `GTP_DFF*`。

| 模块 | LUT | FF | 评价 |
|---|---:|---:|---|
| `pangoriscv`（顶层胶合，含内联的 `ctrl`） | 2,894 | 1 | 重定向比较、写回 mux、配对规则；**在关键路径上，不动** |
| `icache_axi` | 2,547 | 3,070 | 最大块；tag/valid 全在 FF（3,070）。换 LUTRAM 只省 FF，不改 LUT → 对 kLUT 无益 |
| `ifu_axi` | 1,629 | 1,524 | 取指队列 + 预取链；队列深度直接决定性能 |
| `axi_ram_1`（data RAM） | 1,216 | 212 | 地址译码/字节选通；不在性能路径 |
| `branch_predictor` | 721 | 800 | 32 项 BTB；P4 实测"加大 BTB 掉面积提分"，反向操作会掉分 |
| `dcache_axi` | 654 | 320 | 含 4×75 的 store 队列（P37b） |
| `ex` / `ex_alu` | 607 / 504 | 0 | 纯组合 |
| `regs` | 479 | 992 | 双写口 + 4 读口 |

**结论**：没有"纯冗余"可删。所有大块要么在关键路径上（`pangoriscv`/`ifu_axi`/`dcache_axi`），
要么动它就要牺牲分数（`branch_predictor`/`ifu_axi` 队列深度），要么只换存储介质不改 LUT
（`icache_axi` 的 tag）。因此本阶段的资源效率**已经通过 P37 达成**：
`CoreMark/kLUT` 0.2008 → **0.2103（+4.7%）**，站点只 +0.55%。

## 10. E1 实测：I-Cache tag 阵列 → LUTRAM（**测量成功，交付失败，已回退**）

### 10.1 改动（一行）
`icache_axi.v` 复位段原本 `for(i...) tag_mem[i]<=0`，逐项清零 128×21 位。
分布式 RAM 不能按项复位，于是整块 tag 退化成 2,688 个触发器（读 mux 也变成 LUT）。
删掉 tag_mem 的清零（保留 `valid_mem`/`lru_mem`）即可。正确性由"valid 只在写 tag 的同一拍置位"保证。

### 10.2 面积收益（交付 profile，1152 镜像，`dev_map`）
| 项 | P37 交付 | E1 | Δ |
|---|---:|---:|---:|
| 全设计 LUT | 18,333 | **17,605** | −728（−4.0%） |
| 全设计 FF | 9,836 | **7,153** | **−2,683（−27.3%）** |
| LUTRAM（站点） | 3,664 | 3,706 | +42 |
| `icache_axi` 自身 | 2,547 / 3,070FF | **1,330 / 383FF** | — |

CoreMark/kLUT：0.2103 → **0.2190（+4.1%）**。

### 10.3 功能等价证据（三重）
A/B 20 迭代**逐位相同**（窗口 5,212,477 / retires 5,782,437 / 全部探针计数 / `crcfinal 0x4983`）；
icache 单测 PASS；ISA 17/17；dcache、engine 64/64、ram 40/40 全绿。

### 10.4 为什么没交付
净表少掉 2,688 个 FF 后，时钟树与放置整体变化，`led[*]` 的 **IO 端口 hold 路径**稳定违例
（FDC 只有 `create_clock`，没有 IO 约束，这几条在 P36/P37 只是恰好通过）：

| 尝试 | Setup | Hold | 失败端点 |
|---|---:|---:|---:|
| 默认 | +7.980 | −0.038 | 3 |
| + `set_di_q`（tag RAM 写地址重定时，+5 FF） | +2.541 | −0.021 | 1 |
| + 加大 hold 修复预算（4000 路径 / 300 轮） | +2.541 | −0.021 | 1 |
| + `-groute_seed 9` | +3.407 | −0.022 | 4 |

按"`All Constraints Met` 才交付"的纪律，**回退 RTL 到 `41382f7`**，交付位流仍是 3.8557。

### 10.5 复活条件（下一轮的第一步）
1. 让 `led[7:0]` 由 **IO 单元内的寄存器**驱动（或在 FDC 里给出合法的 `set_output_delay`，
   不再是"无约束的半拍 hold"）；
2. 重放本节的**一行改动**（删 `tag_mem` 清零），跑同一套门禁：A/B 逐位相同 → PDS `single,OK,OK` → 上板同 ticks。

这一步是"零分数风险、纯面积收益"的典型，值得优先排期。

## 11. E2：先修 IO hold，再重放 E1（计划 → 执行）

### 11.1 目标与判据
- **目标**：拿回 E1 的面积（LUT −4.0% / FF −27.3% / kLUT +4.1%）**且分数逐位不变**。
- **判据**（顺序固定）：A/B 逐位相同 → ISA 17/17 + icache/dcache/engine 全绿 →
  PDS `single,OK,OK`（hold>0、失败端点 0）→ 上板 ticks 仍为 **298,780,717**。

### 11.2 为什么先修 IO hold
E1 的四次尝试全部倒在 `led[*]` 的 IO 端口 hold 上（−0.021~−0.038 ns）。
那几条路径的起点有两个：`reset_sync[0]`（复位同步器）和 `gpio_inst/reg_data[*]`。
其中 `reset_sync` 这一项来自顶层的冗余门：

```verilog
assign led[i] = soc_rst_n && gpio_ctrl[2*i+:2]==2'b01 && gpio_data[i];
```

`axi_gpio` 把 `reg_ctrl/reg_data` 复位成 0，所以复位期间 `led` 本来就是 0，
`soc_rst_n` 这一项**功能冗余**，却把复位同步器拉进了 IO 路径（E1 里 3 个违例端点有 2 个从它出发）。

### 11.3 改动（两处）
1. `pangoriscv_top.v`：`assign led[i] = gpio_ctrl[2*i+:2]==2'b01 && gpio_data[i];`（去掉冗余项）。
2. `icache_axi.v`：重放 E1 —— 只删 `tag_mem` 的复位循环（保留 `valid_mem`/`lru_mem`）。

### 11.4 风险与回退
- 若 hold 仍不过 → 两处一起回退到 `fce2c5c`（= 交付状态），效率专项收尾于文档。
- 若过了 → 出位流、上板核对 ticks，然后更新模块卡（M04）、`area-budget.csv`、`bitstream/README.md`。

## 13. E3：I-Cache 4 KB → 8 KB（128 组）—— 用"省下来的余量"再换分

### 13.1 判断依据（为什么现在能做）
`icache_axi` 的头注释写明：4 KB 是**25k-LUT 时代**为了布通被迫缩的（"the 25k-LUT design could not
be routed on this PDS flow"），并注明"score trade-off must be measured"。
P20/P21 已在**同一镜像**上量过：`2.8115 (4 KB) → 2.8833 (8 KB) = +2.55%`。

E2 之后器件余量完全够：LUT 17,534/66,600（27%）、FF 7,153/133,200（6%）、
**分布式 RAM 3,684/19,900（19%）**。而 I-Cache 扩容只吃分布式 RAM、不吃 LUT —— 对 kLUT 无伤。

### 13.2 做法
- `SETS` 64 → **128**（8 KB）；`WORDS=8`、行宽 32 B 不变。
- **几何全部参数化**：新增 `SETW=$clog2(SETS)`、`TAGW=32-SETW-5`，
  `set_q/req_set/rd_set/hit_*_index/rd_*_index/tag 片选` 全部由它们推导，
  彻底避免"改组数忘改某个 [10:5]"这类位宽漂移（这个文件历史上就留下过 9 KB 时代的注释）。

### 13.3 结果（20 迭代 A/B）
| 项 | E2 交付 | **E3** | Δ |
|---|---:|---:|---:|
| 评分窗口 | 5,212,477 | **5,042,390** | **−3.26%** |
| I-Cache 填充周期 | 160,164 | **6,588** | −96% |
| retires / 五项 CRC | 5,782,437 / 0x4983 | 同 | 架构等价 |
| IPC（仿真实测） | 1.052 | **1.147** | — |

预测板上：`298,780,717 × 5,042,390/5,212,477 ≈ 289.0M ticks → 3.99 CoreMark/MHz`。

### 13.4 判定：**不交付，保留 E2**（三项并列口径下的净亏）

PDS 实测（`build/e3_deliver`，默认种子）：

| 项 | E2（当前交付） | E3（8 KB） | 判定 |
|---|---:|---:|---|
| ① CoreMark/MHz | 3.8557 | ~3.99（窗口 −3.26%） | **E3 赢 +3.4%** |
| ② setup（→ Fmax） | **+7.816 ns**（≈34.2 MHz） | +6.588 ns（≈32.9 MHz） | **E2 赢**（−1.2 ns，Fmax −4%） |
| ③ CoreMark/kLUT | **0.2199** | 0.2049（LUT 17,534→19,474） | **E2 赢**（−6.9%） |
| hold | +0.025 / 0 端点 | −0.007 / 3 端点 | **E2 赢**（E3 还不过门禁） |

结论：8 KB I-Cache 用 3.4% 的分数换掉了 4% 的频率和 6.9% 的资源效率，**三项并列口径下是净亏**，
且 hold 仍需再修。按"3.8 已达成、效率不得回退"的要求，**保留 E2**，E3 的位流不发布。
若比赛策略改为"只冲性能奖"，把 `SETS` 改回 128 即可复现（`git show 3a1a27b` 那次提交有完整实现）。

> 附带结论：**扩容不是免费的**。8 KB 的数组本身只吃 LUTRAM（+1,062 站点），
> 但 1024 深的分布式 RAM 需要 4 个 `ram64x1d` 拼 + 一级 4:1 mux，LUT 因此 +1,940。
> "用 LUTRAM 就不涨 LUT"是错误的直觉，下次评估缓存扩容必须把地址译码 mux 算进去。
