## 2. 两个候选模型（只保留两个）

### 候选 A：官方 YOLOv3-tiny（软件正确性参照，不裁剪）

来源：Darknet `cfg/yolov3-tiny.cfg`（原文已核对）。416×416、w1.0、80 类：
13 conv（16/32/64/128/256/512/1024 → 256/512/255…）+ 6 maxpool + 1 upsample + 1 route，
两个 yolo 头（mask 3,4,5 与 0,1,2），LeakyReLU。
参数量约 **8.88 M**。**只用来验证软件前向与量化误差，不用于硬件实现。**

### 候选 B：Lite-A（改动逐条列出）

| 改动 | 原版 | Lite-A | 理由 |
|---|---|---|---|
| 类别 | 80 | **4**（可回收/厨余/有害/其他） | 赛题场景 |
| 检测头通道 | 255 | **27** = 3×(5+4) | 随类别变，不随宽度缩 |
| 宽度 | 1.0 | **0.5**（→ 8/16/32/64/128/256/512） | 适配 66.6k LUT / 230 APM |
| LeakyReLU 斜率 | 0.1 | **0.125**（右移 3 位） | 零乘法；需重训恢复精度 |
| 输入 | 416 | **160 / 128 / 96（M1a 决定）** | 待识别效果实测 |
| 结构 | — | **双头 + upsample + route 全部保留** | 保证与原文同拓扑 |

## 3. 算力 → 阵列 → 时间（312 MMAC，纯理想值）

| 阵列 | APM | MAC/s @50 MHz | 理想时间 | 理想帧率 |
|---|---|---|---|---|
| **64 路（先做这个）** | 64 | 3.2 G | **97.6 ms** | 10.2 fps |
| 96 路 | 96 | 4.8 G | 65.0 ms | 15.4 fps |
| 144 路 | 144 | 7.2 G | 43.4 ms | 23.0 fps |
| 256 路 | 256 | 12.8 G | 24.4 ms | 41.0 fps |

这些都是**不含取数等待、换层、边界处理**的理想值，实测只会更慢。
10 fps 对"把垃圾放上去看分类结果"这个演示场景大概率够用，**所以没有理由先做 144 路**。
若 w0.25 版（约 78 MMAC）精度可接受，64 路可到约 24 ms。

## 4. M1a / M1b / M1c 的判据

### M1a 模型与输入尺寸
- 数据：`ai53_19/garbage_datasets`（先实地核查类别映射、标注质量、长尾分布、许可证原文）
- 对比：输入 96 / 128 / 160，官方 A 与 Lite-A
- 记录：mAP50、四类各自 AP 与小目标（电池/烟头/牙签）召回
- **通过条件**：真实演示距离与背景下四类可分辨；小目标不出现"完全检不出"
- 先 5~10 epoch 测单 epoch 耗时再外推，不承诺总时长

### M1b 存储与搬运
- 场景：**视频持续显示的同时**跑 AI 侧的真实读写流量
- 必须写清四件事：① 每类数据放哪个地址；② 谁能读写（CPU / 加速器 / DMA）；
  ③ 一帧完成的标志是什么；④ 如何避免读到正在更新的帧（双缓冲 + 写指针翻转 + 帧号校验）
- 记录：有效带宽、平均与最差等待、**图像是否出现撕裂或花屏**
- 权重可能被重复读取，不能假设"每帧只读一次"

### M1c CPU 后处理
- **不必等加速器**：用 PC 端真实模型输出（int8 反量化的 logits）作输入
- 在现有 CPU 上实测：阈值筛选 → Top-K → 框解码 → 分类别 NMS 的周期数
- 同时统计**漏检**：阈值 0.3 / 0.5 与 K=16/32/64 各档的召回变化
- **通过条件**：给出"周期数 vs 漏检率"的曲线，而不是一个最快值
